# changes/ — 給使用者看的更新說明

使用者重新載入新版後，會在畫面下方看到一張「這次更新」小卡片，設定裡的「更新紀錄」也列出全部。
內容就來自這個資料夾：**一個改變一個檔案**，所以多個 PR 同時新增不會互相衝突。

## 怎麼寫

檔名：`日期-短描述.md`，例如 `2026-10-29-add-view-from-menu.md`（日期用 `YYYY-MM-DD`，短描述用小寫英文與連字號）。
檔名決定排序與「這個帳號看到哪一筆」，所以日期要和檔案裡的 `date` 一致，也不要事後改名。

```
---
date: 2026-10-29
zh-TW: 新增檢視改到筆記右上角的 ⋯ 選單，一次列出所有可新增的檢視。
en: Adding a view moved to the ⋯ menu on a note, which now lists every view you can add.
---
```

- `date`、`zh-TW` 必填；`en` 選填（沒寫時，英文介面顯示繁中）。
- 每個欄位一行，一到兩句，寫給一般使用者看：他們現在能做什麼、哪裡變了。
- 不寫版本號、PR 編號、commit、檔名、函式名稱、資料表或其他技術字（介面不露技術細節）。
  UI 上看得到的字（按鈕、選單名稱）可以寫，用「」框起來。

## 什麼該寫

使用者看得到或用得到的改變：新功能、改了位置或名稱、修好了會碰到的問題（寫成「現在可以…」）。

## 什麼不寫

只改測試、內部重構、文件、部署紀錄、效能數字、開發工具；使用者看不出差別的修正。

## 漏寫檢查

`npm run changes:check` 比對 `origin/main...HEAD`：動到 `packages/frontend/src` 或 `packages/site/src` 的非測試檔，
卻沒有新增 `changes/*.md` 就會失敗。確實不需要時，在 PR 說明寫「不需要更新說明」，
並用 `CHANGES_SKIP=1 npm run changes:check`（或 `-- --skip`）略過。
