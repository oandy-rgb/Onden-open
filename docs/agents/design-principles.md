# 設計準則：複雜度、深模組、分層、契約與命名

> 狀態：現行（最後確認 2026-11-01）
> 涵蓋：無（設計原則，不描述任何一段程式）

何時讀：設計新公共介面、切分模組、拆函式、寫契約註解或命名時。硬規則的精簡版在 [AGENTS.md](../../AGENTS.md)。
原文自 2026-10-22 之前的 AGENTS.md 逐字搬入，只調整相對連結與標題層級。

## 控制複雜度與設計投資

- 評估設計時檢查三件事：一個小需求需要改多少地方、修改者必須同時理解多少知識、能否找出所有受影響的入口。
  說明改善前後的實際差異；程式碼變短或測試通過，不能單獨證明設計變簡單。
- 在本次涉及的邊界修正造成重複特例的根因，避免每個入口再補一個分支。
  以可完成的使用案例持續改善；不把所有技術債都納入當前任務。
- 對新公共介面或重要的責任切分，先比較至少兩種不同的設計草圖，再實作選定方案。
  比較呼叫範例、隱藏的知識與相容成本即可，不要求實作兩套；簡單修正不必套用此流程。
- 先確定本次最重要的使用情境與不變條件。在 Onden，常見例子是文字不遺失、保存狀態可信、
  權限結果正確，以及手機閱讀舒適；實際優先順序依任務決定。
- 將影響使用決策的保證放進介面和名稱，例如保存確認、覆蓋範圍與撤權結果。
  隱藏的是不影響使用方式的內部選擇，不能為了縮短 API 而藏掉呼叫者必須知道的行為。

依據：作者的 [Complexity and Dependencies](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=complexity)
與 [Modular Design](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=modularDesign) 講義；以上是 Onden 的操作準則。

## 深模組：按使用意圖封裝

- 功能層的公開介面表達使用者要完成的事，例如改名、完成任務、保存文章或復原筆記。
  模組內部負責其領域規則，以及與儲存、權限、事件、同步的協作。
- 介面是否簡單，要看呼叫者必須知道多少概念。搬檔案、縮短函式、增加轉呼叫層，本身不算完成重構。
- 元件、路由和 agent 工具應重用領域操作，避免各自組合權限、事件、交易、離線佇列與回復流程。
- 共用層處理跨領域機制；事件的業務意義、任務排程、復原衝突等規則仍由各領域擁有。
  不把所有領域塞進一個需要大量旗標與 callback 的萬用服務。
- 優先沿用現有模組與 registry。新增抽象須指出目前消除的重複責任或錯誤來源，並在本批遷移中實際使用。
  不為假想擴充預先建立政策語言、動態插件框架或新的事件平台。
- 按需要封裝的知識切分模組。例如離線格式與重播政策由其擁有者處理，避免因流程上有「準備、執行、完成」
  三個階段，就讓三個模組都必須理解同一份內部格式。
- 同一個儲存決策改變時，如果必須同步修改多個領域，先檢查資訊是否外洩。
  公開型別與文件應說明使用契約，避免迫使呼叫者理解內部資料表、處理順序或演算法。
- 底層介面採用能自然涵蓋目前需求的通用操作，將畫面或領域特化留在上層。
  例如任務頁、表格和筆記欄位可共用同一個屬性保存能力，底層不需要各自的畫面模式旗標。
- 平台或儲存媒介的差異可封裝在底層 adapter，讓共用核心維持一致契約。
  「特化往上移」不是所有程式的固定方向；依知識的擁有者決定邊界。

通用性與重要資訊的取捨亦參考作者公開的第二版節選第 6、21 章，來源與閱讀範圍見文末。

## 分層、拆分與常見操作

- 每層應提供不同的理解方式：畫面表達操作意圖，領域處理規則，共用寫入層處理保存契約，儲存層處理資料表示。
  若一層只把相同參數原封不動轉交下一層，檢查是否真的需要它；相容轉接或協定轉換須有明確用途。
- 相關操作若總要來回閱讀、共享同一項內部決策，考慮放在同一個責任範圍內。
  規則獨立或變更原因不同的功能可分開；不要只因程式碼長得相似就強行共用。
- 以閱讀與修改成本決定函式大小，不設「超過幾行就拆」的規則。
  拆分後應能憑子函式契約理解呼叫處；若仍要交叉追蹤所有區域變數和步驟，重新檢查切分。
- 常見操作使用少量必要參數與有語意的預設值；較少用的選項不應成為每個呼叫者的必修知識。
  基礎層能確定的排程、初始化或保存細節由基礎層承擔；產品選擇和授權決策則保持明確。

及 [與 Robert Martin 的設計討論](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md)。

## 契約、註解、命名與一致性

- 設計新的重要介面時，先寫簡短契約及呼叫範例，再填入實作；若契約無法清楚描述，先改善介面。
  無須為每個瑣碎函式增加制式註解。
- 介面文件說明呼叫者需要知道的輸入、結果與可觀察副作用；必要時補上單位、空值語意、邊界、
  所有權、併發限制及失敗行為。例如 `queued` 必須說清楚是否已持久化，以及是否代表伺服器接受。
- 實作註解保留不明顯的原因、不變條件與設計取捨，放在相關程式附近；不逐行翻譯程式碼。
  跨模組契約集中記錄並從使用處連結，變更程式時同步維護，避免複製多份說明。
- 註解寫程式現在是什麼、為什麼；不寫審查歷史（PR 編號、第幾輪、review of…），那些放 commit、PR 留言與 [mistakes.md](mistakes.md)。
  migration 檔頭例外（套用後不改，記下為什麼有這個 migration 是合理的）。歷史會過時，而且註解裡提到的函式名曾被未用程式檢查當成用到（業主 2026-11-28）。
  守門：`packages/markdown/src/test/guards/reviewHistoryComments.guard.test.ts`，每個檔案的筆數只准減少；既有的不專門清，改到那個檔案時順手拿掉。
- 名稱精確表達概念，同一概念維持一致用語。像節點 ID、事件 ID、同步游標、權限版本與時間單位，
  應能從名稱或型別辨識；不要讓含糊的 `data`、`info`、`manager` 掩蓋不清楚的責任。
- 保持可追蹤的控制流與副作用。同類操作使用一致的回傳型別與錯誤語意；既有慣例有問題時，
  在明確範圍內修正並遷移呼叫者，避免只為新入口建立另一套近似慣例。
