# 犯過的錯與對應的機制

> 狀態：現行（最後確認 2026-11-16）
> 涵蓋：無（只增不改的紀錄；每一筆的證據是當天的）

何時讀：審查 PR、回報結果給擁有者、修一個「好像見過」的問題之前。何時寫：發現自己或同伴犯了錯的**同一批工作裡**——
對擁有者說了錯的事、審查放過了缺口、擁有者比測試先發現問題、同一類問題第二次出現。

擁有者 2026-11-16：「犯了錯要記下來」「修補漏洞不要有暫時性修補，盡可能以一個機制回應同類問題」。

## 怎麼寫一筆

每筆七行，不寫經過的流水帳，不寫人名以外的責備：

- **發生了什麼**：事實。
- **證據**：PR、commit、測試、留言或指令輸出的連結。沒有證據的根因分析不進這份紀錄。
- **發現者**：`測試`、`審查`、`擁有者使用`、`實機`、`上線後` 之一。這一欄用來算攔截率：有多少問題是上線之後才被發現的。
- **為什麼沒擋到**：當時有哪個檢查本來該擋、為什麼沒擋。
- **類別**：這是哪一類問題（用下方已有的類別；沒有才新增）。
- **機制**：擋住這一類的東西，附位置，並標出層級（見下表）。「以後小心」不是機制。
- **還沒擋住的**：沒有就寫「無」。寫「尚無機制」是允許的——那一行就是待辦。

同一類再出現時，在原本那一筆下面加一行日期與證據，不另開一筆：一類出現幾次，就是那個機制有沒有用的答案。
機制生效之後又出現，代表機制擋錯地方，要換，不是再加一條。

### 機制的層級（由強到弱）

| 層級 | 是什麼 | 誰來執行 |
| --- | --- | --- |
| 1 測試／守門 | 會失敗的測試、只准減少的基準、CI 檢查 | 機器，每個 PR |
| 2 格式檢查 | lint、PR 或報告的必填欄位檢查 | 機器，每個 PR |
| 3 流程 | 由另一個工作階段驗證（例如審查者對照 diff） | 另一個人或 agent |
| 4 文字規則 | 寫在 AGENTS.md 或記憶裡的句子 | 寫的人自己 |

第 3、4 層最弱：第 4 層是「自己證明自己」。一筆紀錄的機制如果只有第 4 層，「還沒擋住的」要寫出往上一層的做法。
教訓變成第 1、2 層的機制之後，從 agent 的記憶檔刪掉：記憶只留下無法做成機制的東西。

## 類別

| 類別 | 意思 |
| --- | --- |
| 過渡修補 | 明知不完整或會被取代的規則被合併或上線 |
| 未查證就回報 | 對擁有者或同伴說了沒有親自確認的事 |
| 測試的模型錯了 | 測試自己算的「正確答案」是錯的，或測試沒走到真正的路徑 |
| 邊界沒走到 | 規則在一般情況成立，問題在最短、最空、最晚、最大的那一格 |
| 零件對、組裝錯 | 每個部分各自通過，接起來的那一層沒有測試 |
| 文件過時 | 文件說的檔案、數字、狀態已經不是現況 |
| 衍生資料沒跟上 | 寫入走了另一條路，沒有經過一般寫入之後會做的事 |
| 驗證的不是要上線的那一版 | 檢查跑在別的版本上：紅燈修完沒有重跑就合併、作者還在推送時就啟動檢查、合併後 main 又前進 |
| 派出去的工作沒有確認真的在做 | 交給雲端或同伴的工作停了、失敗了或沒有啟動，派的人不知道，還照著「正在做」回報 |
| 交代分散 | 一輪要做的事散在好幾則留言或訊息裡，接手的一方只處理最新的一則 |
| 沒查現況就定規則 | 定一個值或行為的新定義時，沒有先查今天哪些測試與程式刻意依賴舊的 |
| 已關閉的資源悄悄重建自己 | 資源關掉之後，下一次使用不報錯、而是在背後開一個新的（空的）來用；晚到的寫入落進沒人關、沒人看的那一份 |
| 背景工作比測試活得久 | 提交後才跑的背景工作（派發佇列、重試等待、立即清送）在測試關掉資料庫連線池之後還在用它，失敗被報成之後某個檔案的匿名未處理拒絕 |
| 跨時區比較日曆日 | 把兩個沒有（或不同）時區的日期字串互相比較，來決定「誰先誰後」；差一天的那幾個小時就判錯 |
| 散布的東西沒帶授權 | 隨軟體或 repo 散布的第三方檔案沒有授權聲明，或用了沒人看過條款的授權 |

### 2026-11-18　PGlite 連線池 `end()` 之後的查詢悄悄開了第二個資料庫（已關閉的資源悄悄重建自己）
- **發生了什麼**：#1860 的審查（note-cf）讀程式發現：`PglitePool.end()` 之後，`query()`／`connect()` 經 `database()` 重新 `openPglite()`，不像真 Postgres 丟 `Cannot use a pool after calling end on the pool`。本次實際執行確認：`memory://` 開出一個**空的**新資料庫；資料夾模式則在同一個資料夾開第二個沒人關的實例（資料夾裡多出一個檔案）。所以桌面版與瀏覽器版（都是 PGlite）上，比連線池活得久的背景工作會寫進沒人關的資料庫，沒有任何錯誤。
- **證據**：`packages/backend/src/test/dbPglite.test.ts` 的 `PglitePool after end()` 四個測試在舊程式上紅；`packages/desktop/test/shutdown.test.mjs` 用真正的 `serverEntry.mjs` 在舊程式上紅（結束後的寫入成功：`expected: false, actual: true`），新程式上綠。
- **發現者**：審查（讀程式）；本次補上執行的證據。
- **為什麼沒擋到**：`PglitePool` 只仿 `pg.Pool` 的方法，沒仿「結束後不可用」這條；既有測試只在最後 `end()` 一次，沒有測「之後再用」。#1860 的註解寫「一個程序只關一次」，但那是約定，不是會失敗的檢查。
- **類別**：已關閉的資源悄悄重建自己。
- **機制**：〔第 1 層〕`PglitePool.end()` 記下是誰結束的，之後 `query`／`connect`／`database()`（含已取得的 client 的 `query`）一律拒絕，訊息說連線池已結束並指出被呼叫的方法，堆疊是晚到的呼叫端，`cause` 是結束它的地方；Node、桌面、瀏覽器 worker 共用同一個類別，所以行為一致。要重新開始就必須是新的 `PglitePool`（產品裡沒有這條路：見 `dbClose.ts`）。測試見上。
- **還沒擋住的**：無（`on()`／`emit()` 只登記監聽器、不碰資料庫，不在此限）。

- **證據**：公開庫 run 44195089811（navBackStack:9、reviewLoop:21、reviewScope:13、reviewGradeRecovery:23、rssReader:183、tagModuleCenter:158、todayLens:14、zzDeepCol09:14、zzDeepRev02:30、zzDeepRev05:58、inkCanvas:75 紅）。本批在舊程式上加一則「明天」的說明重現：14 個紅（其中 9 個的錯誤訊息直接點名卡片，3 個——inkCanvas:273、tagBoardLens:16、uxP0:49——不點名但拿掉卡片就過），新程式同條件 23 綠；單元測試 `whatsNew.test.tsx` 在舊程式上 6 個紅。
- **發現者**：測試（合併之後的完整端對端）。
- **為什麼沒擋到**：完整端對端在 #1868 合併前沒跑完；單元測試只用固定日期，沒有一個案例是「帳號建立日與說明日期差在時區邊界」。
- **類別**：跨時區比較日曆日；驗證的不是要上線的那一版。
- **機制**：〔第 1 層〕規則改成比兩個時間點：帳號建立時間對這次建置的時間（`lib/buildTime.ts`、`whatsNewText.createdWithThisBuild`，建置時寫入 `__ONDEN_BUILT_AT__`），說明檔的 `date:` 不再決定誰看到卡片。〔第 3 層〕`changes.guard.test.ts` 擋日期晚於 UTC 今天的說明檔（日期同時是「看到哪一筆」的排序編號，寫成未來的日子會讓看過它的帳號漏掉之後較早日期的說明）。〔第 4 層〕`changes/README.md` 寫明日期用 UTC、一則說明何時生效。
- **還沒擋住的**：完整端對端沒跑完就合併仍然只靠人（部署的門另有紀錄，見 2026-11-17 那筆）；兩台機器的時鐘差在 10 分鐘內被當作同一時刻，超過的話新帳號仍可能看到一張卡片。
