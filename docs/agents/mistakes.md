# 犯過的錯與對應的機制

> 狀態：現行（最後確認 2026-11-16）

何時讀：審查 PR、回報結果給擁有者、修一個「好像見過」的問題之前。何時寫：發現自己或同伴犯了錯的**同一批工作裡**——
對擁有者說了錯的事、審查放過了缺口、擁有者比測試先發現問題、同一類問題第二次出現。

擁有者 2026-11-16：「犯了錯要記下來」「修補漏洞不要有暫時性修補，盡可能以一個機制回應同類問題」。

## 怎麼寫一筆

每筆七行，不寫經過的流水帳，不寫人名以外的責備：

- **發生了什麼**：事實。
- **證據**：PR、commit、測試、留言或指令輸出的連結。沒有證據的根因分析不進這份紀錄。
- **發現者**：`測試`、`審查`、`擁有者使用`、`實機`、`上線後` 之一。這一欄用來算攔截率：有多少問題是上線之後才被發現的。
- **為什麼沒擋到**：當時有哪個檢查本來該擋、為什麼沒擋。
- **類別**：這是哪一類問題（用下方已有的類別；沒有才新增）。
- **機制**：擋住這一類的東西，附位置，並標出層級（見下表）。「以後小心」不是機制。
- **還沒擋住的**：沒有就寫「無」。寫「尚無機制」是允許的——那一行就是待辦。

同一類再出現時，在原本那一筆下面加一行日期與證據，不另開一筆：一類出現幾次，就是那個機制有沒有用的答案。
機制生效之後又出現，代表機制擋錯地方，要換，不是再加一條。

### 機制的層級（由強到弱）

| 層級 | 是什麼 | 誰來執行 |
| --- | --- | --- |
| 1 測試／守門 | 會失敗的測試、只准減少的基準、CI 檢查 | 機器，每個 PR |
| 2 格式檢查 | lint、PR 或報告的必填欄位檢查 | 機器，每個 PR |
| 3 流程 | 由另一個工作階段驗證（例如審查者對照 diff） | 另一個人或 agent |
| 4 文字規則 | 寫在 AGENTS.md 或記憶裡的句子 | 寫的人自己 |

第 3、4 層最弱：第 4 層是「自己證明自己」。一筆紀錄的機制如果只有第 4 層，「還沒擋住的」要寫出往上一層的做法。
教訓變成第 1、2 層的機制之後，從 agent 的記憶檔刪掉：記憶只留下無法做成機制的東西。

## 類別

| 類別 | 意思 |
| --- | --- |
| 過渡修補 | 明知不完整或會被取代的規則被合併或上線 |
| 未查證就回報 | 對擁有者或同伴說了沒有親自確認的事 |
| 測試的模型錯了 | 測試自己算的「正確答案」是錯的，或測試沒走到真正的路徑 |
| 邊界沒走到 | 規則在一般情況成立，問題在最短、最空、最晚、最大的那一格 |
| 零件對、組裝錯 | 每個部分各自通過，接起來的那一層沒有測試 |
| 文件過時 | 文件說的檔案、數字、狀態已經不是現況 |
| 衍生資料沒跟上 | 寫入走了另一條路，沒有經過一般寫入之後會做的事 |
| 驗證的不是要上線的那一版 | 檢查跑在別的版本上：紅燈修完沒有重跑就合併、作者還在推送時就啟動檢查、合併後 main 又前進 |

### 2026-11-16　審查放行了明知有缺口的修正（過渡修補）
- **發生了什麼**：一個人打字卻出現「已合併」。#1753 只用 `updated_at` 擋筆記列；審查（note-96）已指出兩個缺口（時間不是可靠的依據；屬性、連結、標籤、任務等十多種資料仍會被晚到的回應蓋掉），仍寫「可以當成立即修正」並建議先部署；note-cf 明知缺口而合併。
- **證據**：#1753 的審查留言；#1754 的逐種類表格（當時十多種仍失敗）；`packages/frontend/src/lib/rowAge.ts`。
- **發現者**：擁有者使用（平板）；缺口本身由審查發現，但審查沒有據此擋下。
- **為什麼沒擋到**：審查的標準是「比現在好就合併」，報告裡沒有「已知缺口」這個必填的段落，結論可以跟缺口互相矛盾。
- **類別**：過渡修補。
- **機制**：〔第 4 層，文字規則〕PR 寫著「已知缺口」或「之後取代」的，退回去做完整機制；先用逐種類的測試釘住整類（#1750、#1754），一個修正讓它們全綠，並在同一個 PR 刪掉舊規則。
- **還沒擋住的**：往上到第 2 層——審查報告必須有「已知缺口」一節；這一節不是空的，結論就不能寫「可合併」或「可部署」，除非報告引用了擁有者本人的明確放行。用格式檢查強制（尚未實作）。另：`lib/rowAge.ts` 的時間規則已上線（擁有者例外放行，95dea5ce），位置規則（`fix/late-answer-by-position`）完成並刪掉它之前，這一筆不算結束。

### 2026-11-16　擁有者比測試先發現同步與搜尋的錯（零件對、組裝錯；邊界沒走到）
- **發生了什麼**：一個人打字卻出現「已合併」；「搜尋一個字找到的比兩個字少」。
- **證據**：擁有者的平板截圖（2026-11-16）；`packages/frontend/src/lib/data/noteSearch.ts` 的 `query.trim().length < 2`；`packages/backend/src/routes/nodes.ts` 的 `raw.length < 2`；#1750 的釘住案例。
- **發現者**：擁有者使用（平板）。
- **為什麼沒擋到**：桌面版 Chromium 的 e2e 裡，伺服器的回應幾乎總是依序到達，平板的時序不同，所以「回應比確認晚到」從來沒有在測試裡發生過。同步的測試各自驗「送出」與「套用」，沒有一條說「回應不論先後、重複、延遲到達，結果相同」。搜尋的測試分別測每個引擎，沒有測「依查詢長度選哪一邊回答」的那一層，也沒有走到一個字。
- **類別**：零件對、組裝錯；邊界沒走到。
- **機制**：〔第 1 層〕蛻變測試（`metamorphic` 輔助函式，#1761）：關係一路走到邊界（一個字素）、把組裝本身當成一個受測對象、跳過要分原因統計；新關係要先抓到一個已知的錯。
- **還沒擋住的**：(1) 同步那一條關係隨位置規則的 PR 進來。(2) e2e 的故障注入組（`packages/frontend/e2e/fullstack/faults/`）加入「回應延遲與亂序」，讓真實瀏覽器也覆蓋這一類。(3) 復原、檢視查詢、權限、時間的關係尚未寫。

### 2026-11-16　記憶索引超過上限，尾端的教訓沒有被讀到（文件過時）
- **發生了什麼**：agent 的記憶索引只載入前 200 行／25 KB。索引長到 207 行、25.8 KB，尾端被截掉，各工作階段不知道；修回 194 行後位元組仍超過，還是被截。
- **證據**：工作階段開頭的截斷警告（「Only part of it was loaded」）；`wc -lc MEMORY.md` → 194 行、25,809 位元組。
- **發現者**：擁有者（指出位元組上限）；行數是 agent 看到警告後才處理。
- **為什麼沒擋到**：上限沒有檢查，警告只是一行文字，容易被略過；索引只增不減。
- **類別**：文件過時。
- **機制**：〔第 2 層〕hook `~/.claude/hooks/memory-index-limit.sh`：索引超過 150 行或 20,000 位元組，寫入後立刻報錯，工作階段開始時也檢查。產品決定移到不自動載入的第二份索引；主索引只留規則與進行中的工作。
- **還沒擋住的**：記憶檔的內容多半是 agent 自己寫的，沒有經過人的篩選；已變成機制的教訓還沒有逐筆刪除（需要擁有者過目的清單）。
