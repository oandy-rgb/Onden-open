## 一句話

筆記平常就是一般 Markdown。想讓其中一段「升級」成節點，就在那個區塊最後寫上 `{標籤}`（或用介面貼）：系統替它補上隱藏的 `^id`，它就變成原筆記底下的**子節點**。子節點只有自己 `{…}` 裡的標籤（不從上層段落或筆記繼承，和筆記一樣）、可以掛模組能力（複習、任務、技能），**文字仍然只存在原筆記裡**。

## 為什麼

- 大綱筆記（Roam、Logseq、Tana、RemNote）每一行都是節點，資料細但寫起來被迫用大綱，匯出成 Markdown 不好看。
- 檔案筆記（Obsidian）整篇才是單位，段落不能單獨帶標籤、單獨被查詢。Obsidian 論壇反覆有人要「只替某一段貼標籤」，官方沒有做，有人自己寫了外掛（`^intro [status: draft]`）。
- 任務外掛的「一行還是一則筆記」之爭（Tasks 對 TaskNotes）、閃卡外掛靠 `^id` 記住卡片，都是同一個缺口。
- 選擇性升級是中間路線：寫的時候自由，需要的段落才付出成本。目前沒有主流工具同時做到「選擇性升級、文字留原處、能掛功能、純 Markdown」。

## 寫法

### 1. `{標籤}` 放在區塊最後，`^id` 由系統補

使用者只寫標籤：

```markdown
- 二分搜尋 {重要, 考點}
```

存檔時系統看到區塊最後的 `{…}`，在它後面補上 `^id`：

```markdown
- 二分搜尋 {重要, 考點} ^k3f9
```

編輯器裡 `{重要, 考點}` 顯示成小標籤，`^k3f9` 完全隱藏，使用者看到的是「二分搜尋 `重要` `考點`」。用介面貼標籤時，系統照同樣的格式寫進正文。

**為什麼放最後**：

- 主流慣例都是內容在前、標籤在後：Org-mode 的標題標籤規定放行尾（`* 寫報告 :work:`）、Pandoc 的屬性接在標題後（`# 標題 {#id}`）、Logseq 社群慣例把標籤放在那一行最後、Obsidian Tasks 的中繼資料接在任務文字後。
- 讀的時候先看到內容，標籤不擋在前面。
- 和 `^id` 相鄰，中繼資料集中在一處。Obsidian 規定 `^id` 必須在區塊最後，所以 `{標籤}` 放在 `^id` **前面**：寫成 `^k3f9 {重要}` 的話 Obsidian 會認不得這個 id，從 Obsidian 連過來的 `[[筆記#^k3f9]]` 會斷。
- 多行段落要找最後一行的問題由介面處理：游標在區塊任何地方按「貼標籤」，系統寫到正確的位置。

**為什麼用 `{ }`**：方括號在 Markdown／Obsidian 已有連結 `[文字](網址)`、wikilink `[[ ]]`、註腳 `[^1]`、行內註腳 `^[內容]` 等用途；大括號在標準 Markdown 和 Obsidian 都沒有特別意思，只顯示成普通文字，不會撞到現有語法。方向和 Pandoc 的 `{…}` 屬性一致。

### 2. 認定規則

- 只有**區塊最後**的 `{…}`（緊接在 `^id` 前，或在行尾）才算；句子中間的大括號就是普通文字。
- 程式碼（`` `{x}` ``、程式碼區塊）和數學（`$\{a\}$`）裡的大括號不算。
- 內容以逗號分隔標籤名稱，而且**每一項都必須是標籤名稱**（或名稱的路徑 `a/b`、`鍵: 值`）：有一項不是，整個 `{…}` 就是普通文字，不是標籤（2026-11-17；`@onden/markdown` `text.ts` 的 `isTagList`，名稱規則是 `sharedContract.ts` 的 `isTagNameShape`：不能有 `; ( ) [ ] = < > * | $` 與引號這類程式符號）。把 `^[ \t]+ { indent(); ECHO; }` 這種程式碼當一般段落寫，行尾的大括號因此不會變成標籤。以後段落要帶屬性也放這裡（例如 `{重要, 狀態: 草稿}`），參考 Obsidian 社群外掛 `^id [屬性]` 的方向。
- 名稱比對標籤時不分大小寫（和 #118 一致）；找不到的名稱自動建立新標籤。規則和 frontmatter `tags:`、快速捕捉的 `#a/b` 是同一套（D63，`tagHierarchy.tagIdForWrittenName`）：路徑從根層一層層找，所以單一名稱指的是**根層**那個標籤（`{book}` 不會接到 `課程/book`）；每一層先找名稱完全相同的，沒有才找不分大小寫相同的，而且只有剛好一個時才算（`Book`、`BOOK` 都在時寫 `{book}` 會另建 `book`）。
- **相容 Obsidian 的寫法**：匯入或手打的 `#標籤 ^id`（同一區塊同時有行內 `#標籤` 和 `^id`）視為同一件事；存檔時保留原樣，不改寫成 `{標籤}`。

### 3. 範圍：沒有結尾符號，由 Markdown 結構決定

`{標籤}` 只決定「哪個區塊」；範圍到哪裡結束由那個區塊的種類決定：

| 區塊 | `{標籤}` 放哪 | 範圍到哪裡結束 |
|---|---|---|
| 段落 | 段落最後一行的行尾 | 遇到空行 |
| 清單項目 | 這個項目那一行的行尾 | 下一個同層或更上層的項目之前，**包含底下縮排的子項目** |
| 標題 | 標題那一行 | 下一個同級或更高級的標題之前 |
| 引用、提示框 | 第一行（例如 `> [!quote] …` 那行） | 引用區塊結束 |

程式碼區塊、表格不升級。第一版不做句子內的局部標記。

**為什麼不要結尾符號**：不會忘了關閉或複製到一半；和 Markdown／Obsidian 的結構一致，在別的工具打開也一樣；範圍永遠是一棵樹（只會包含或不相交，不會交錯），遞迴和繼承都單純；看排版就知道範圍。

**代價與緩解**：

- 不能標結構框不住的任意範圍（例如段落中間兩句、或第 2–4 段）。想框住好幾段時用標題或提示框：
  ```markdown
  > [!quote] 作者的主要論點 {摘錄}
  > 第一段……
  >
  > 第二段……
  ```
- 改排版會改範圍（刪掉空行讓兩段合併、改標題層級、縮排清單項目）。這通常就是使用者的意思，但要**看得到**：游標在升級的區塊上時，編輯器在旁邊用細線標出範圍。
- 若之後發現常需要「框住幾段又不想加標題」，再加 Pandoc 式的容器（一個完整的開合區塊，仍是一棵樹）：
  ```markdown
  ::: {摘錄}
  第一段……

  第二段……
  :::
  ```

## 規則

### 4. 遞迴：上層由結構決定

一個區塊的範圍落在另一個子節點的範圍內，它的上層就是那個子節點；往上找不到，上層就是筆記。中間沒有標籤的層會被跳過。上層只決定結構，標籤不會往下傳（§5）。

```markdown
## 搜尋 {考點} ^s1
- 二分搜尋 {重要} ^a1
  - 邊界要用 lo <= hi {易錯} ^a2
```

| 子節點 | 上層 | 標籤（筆記貼了 `#課程`） |
|---|---|---|
| `^s1` | 筆記 | 考點 |
| `^a1` | `^s1` | 重要 |
| `^a2` | `^a1` | 易錯 |

### 5. 不繼承標籤（業主 2026-11-09）

子節點的標籤就是它自己 `{…}` 裡寫的，不從上層段落或所在筆記拿。筆記也不從上層筆記拿標籤（2026-10-18：「繼承」只指標籤樹本身，例如 #書/小說），所以全系統只有這一條規則。筆記貼了 `#課程`，算的是整則筆記，不必每一段再算一次。

原本（2026-10-14 起）子節點會繼承上層和筆記上「會繼承的」標籤，只有查詢區塊寫了 `blocks: include` 才用得到；複習卡、標籤頁、預設查詢一直只看自己的標籤。2026-11-09 拿掉：`blocks:` 這行現在會被略過，API 的 `include_blocks` 收下但不作用（還開著的舊頁面會送）；標籤上的 `tag_is_inheritable` 欄位由 migration 185 刪除（業主同意）。

### 6. 文字只存一份

子節點不存文字，只存「我是原筆記的哪一段」。顯示時用 `^id` 到原筆記正文裡切出那段。在子節點的畫面編輯，實際上是改原筆記正文的那一段。

為了搜尋和視圖的速度，可以另存一份文字快取，每次存檔重新產生；它只是索引，來源永遠是原筆記。

### 7. 身分和顯示分開

- **身分**：`^id`，系統自動產生、**編輯器裡隱藏**。匯出的 Markdown 保留 `^id`，Obsidian 認得。
- **顯示的標題**：有標題的區塊用標題，其他用第一行的前幾個字（不含 `{…}`）；文字改了標題跟著變，身分不變，進度不會丟。
- **連結**：`[[筆記#標題]]` 在存檔時對到該區塊的 `^id`；標題之後改了，連結的文字自動更新。這是 Obsidian 多年來做不到的（它改標題會斷連結），Onden 在存檔時解析所以做得到。比對標題時忽略 `{…}`。

為什麼不拿標題當身分：一改字就斷、一般段落沒有標題、標題可能重複。

### 8. 存檔時發生什麼

走正文副作用的單一路徑（`bodySideEffects.applyBodyChange`），所以同步、復原都自動成立：

1. 解析正文（沿用渲染用的語法樹），找出最後帶 `{…}`（或 Obsidian 式 `#標籤 ^id`）的區塊與範圍；缺 `^id` 的補上。
2. 用範圍包含關係算上層。
3. 和資料庫比對：新的 `^id` 建立、消失的刪除、上層或標籤改變的更新。每項變動都是事件。

同一則筆記內 `^id` 必須唯一（現有規則）；重複的自動改名並提示。補 `^id` 會改寫正文，所以要和使用者正在打的字協調（在存檔時補，不在打字當下插入；同步時照正文的合併規則）。

### 9. 查詢

| 查詢 | 結果 |
|---|---|
| `tags: 課程` | 只列出貼了 `#課程` 的筆記（**預設只看明確貼上的標籤**） |
| `tags: 易錯` | 列出所有標了「易錯」的段落，跨筆記 |

段落不繼承標籤（§5），所以不會像 Logseq 那樣一查就冒出一大堆段落。系統筆記一律不出現（#144 的規則）。

### 10. 模組能力

升級後的段落就是節點，可以掛：

- **複習**：`{複習}` 的段落是一張卡，顯示那段文字，進度記在子節點上。
- **任務**：`- [ ] 寫作業三 {task}` 就是有任務能力的區塊。現有的任務行改走這套機制（見「任務行」）。
- **技能**：可以只對某個段落套用技能（harness 加 `block` 範圍，或沿用 `nodes` 範圍傳子節點 id）。
- **屬性**：`{重要, 狀態: 草稿}`。

## 介面

功能能不能被發現，取決於入口：

- 選取段落（或游標停在區塊裡）→ 選單出現「做成複習卡」「設為任務」「貼標籤…」，系統寫入 `{…}` 和 `^id`。
- 升級的區塊在編輯器裡顯示標籤小圖示；游標停在上面時，旁邊的細線標出範圍。
- 子節點出現在原筆記的側欄（例如「本篇的段落：3 張複習卡、1 個任務」）。

## 已知行為（例子）

1. 中間層沒標籤：跳過，上層是再往上那個子節點。
2. 標題層級：範圍到下一個同級或更高級標題之前。
3. 引用區塊：引用本身有 `{…}` 時才是上層。
4. 拿掉 `{…}`、保留 `^id`：子節點移除，資料保留並隱藏，重新貼回就恢復。
5. 刪掉 `^id`：下次存檔會重新補一個新的，視為新節點；有進度時先提示，可復原。
6. 同筆記 `^id` 重複：自動改名並提示。
7. 只改段落文字：身分不變，進度保留，顯示的標題跟著變。
8. 搬到另一則筆記：第一版當成「刪除＋新建」，進度不跟著走（之後再做搬家）。
9. 模組標籤：`{複習}` 讓段落直接得到該能力。
10. 任務行：同一套機制。
11. 查詢：見上表。
12. 兩台裝置同時改：照正文的同步規則合併，子節點從合併後的正文重算，不會自己衝突。
13. 刪掉兩段之間的空行：後一段併進被標記的段落，範圍跟著變大（編輯器的範圍線看得到）。
14. 在有 `{標籤}` 的段落按 Enter（業主 2026-11-08，細節與邊角見[錨點提案 §5.3](proposals/block-anchors-2026-11-01.md)）：任何位置都切成兩段，身分（錨點、這一列、複習進度、任務、標籤、連結）跟著有 `{標籤}` 的那一半；另一半是沒有身分的新段落，在它上面再打 `{標籤}` 是新項目，不複製進度。Shift+Enter 是段內換行；手機 Enter 一律切段；輸入法組字中的 Enter 不處理；游標在 `{…}` 裡面時在 `}` 之後切。

## 已決定

使用者 2026-10-14 決定（「都照建議」）：

1. **拿掉 `{…}`、保留 `^id` 時**：子節點移除，但它上面的資料（例如複習進度）保留並隱藏；之後在同一則筆記重新貼回標籤就恢復。
2. **搬到另一則筆記時**：第一版不帶進度（當成刪除＋新建），之後再做「搬家」。
3. **查詢預設**：只看明確貼上的標籤；要連繼承的段落一起看時加「包含段落」選項。（2026-11-09 起段落不繼承標籤，選項拿掉，見 §5。）
4. **`{…}` 裡寫了不存在的標籤名**：自動建立（和行內 `#新標籤` 的行為一致）。
5. **Obsidian 式 `#標籤 ^id`**：存檔時保留原樣，不改寫成 `{標籤}`。
6. **不往下繼承的標籤**（借自 Org-mode 的 `org-tags-exclude-from-inheritance`）：這不在前五項裡，是 note-0f 在討論 Org-mode 時另外提的建議；使用者在建議提出之後回覆「都照建議」，所以視為同意，使用者若有不同想法再改。標籤設定加一個「不往下繼承」選項。**模組標籤預設不繼承**（父段落是複習卡，不代表子段落也是；父項目是任務，子項目不一定是），一般分類標籤（課程、考點）預設繼承。生效標籤的計算跳過不繼承的上層標籤。和現有的 `node_attributes.is_inheritable`（屬性是否往下繼承，預設 false）是同一個概念：實作時對齊它的命名與語意，不另造一套。旗標是 class_tag 列上的 `content_nodes.tag_is_inheritable`（migration 104），不放在 `tag_schema`：`tag_schema IS NOT NULL` 代表「這是集合」（見下方「儲存方式」）。（2026-11-09 起段落不繼承標籤，這個選項拿掉了，欄位由 migration 185 刪除，見 §5。）

以及先前的決定：`{標籤}` 放在區塊最後、`^id` 前；`^id` 由系統補且隱藏；沒有結尾符號，範圍由結構決定；匯出沿用 `^id`（Obsidian 相容）。

開工前要先驗證：Obsidian 對標題行上的 `^id`、提示框（callout）的 `^id` 怎麼處理（提示框的 `^id` 要放在區塊後的獨立一行；標題行可能不支援），據此決定系統替標題與提示框寫 `^id` 的位置。

### 驗證結果（2026-10-14，B1）

依 Obsidian 說明與論壇（[Internal links › Link to a block](https://obsidian.md/help/links)、[Adding block id for Callout](https://forum.obsidian.md/t/adding-block-id-for-callout/97060)）：

| 區塊 | Obsidian 的規則 | 系統寫 `^id` 的位置 |
|---|---|---|
| 段落 | 行尾空一格接 `^id` | 段落最後一行的行尾，在 `{…}` 之後 |
| 清單項目 | `^id` 可直接放在項目那一行 | 項目那一行的行尾，在 `{…}` 之後 |
| 引用、提示框 | 結構區塊的 `^id` 放在區塊後的獨立一行，前後空行（放在提示框最後一行 `> ^id` 也認得，但需外掛才普遍相容） | 區塊結束後空一行，獨立一行寫 `^id`；`{…}` 仍在第一行。解析時兩種寫法都認 |
| 標題 | 標題行尾的 `^id` 認得，但只指到**標題那一行**，不含底下內容（要連整節得用 `[[筆記#標題]]`） | 標題行尾，在 `{…}` 之後。範圍由 Onden 依結構自己算；從 Obsidian 連進來能跳到該標題，嵌入只會顯示標題那一行（Obsidian 的限制） |

Obsidian 不支援連到引用、提示框、表格的**局部**，所以引用、提示框只能整塊升級（和本設計一致）。

## 儲存方式（B1 決定，2026-10-14）

比較兩種做法後選 **B**：

- **A. 子節點是 `content_nodes` 的一列**（`node_type = 'block'`）：標籤、屬性、同步、權限可以直接沿用。但 216 個查詢讀 `content_nodes`，多數不分 `node_type`；子節點會跑進樹狀列表、搜尋、git 備份（每個節點一個檔）、嵌入向量、發布集合、計數，每一處都要檢查，容易外洩或重複文字。
- **B. 自己的資料表** `block_nodes`（所屬筆記、`^id`、上層、種類、顯示標題、文字快取、`hidden_at`）＋ `block_node_tags`（子節點自己的標籤，指向 class_tag）：預設任何地方都看不到子節點，要看見的地方（查詢的「包含段落」、同步、復原）明確加上。權限＝所屬筆記的權限。

「不往下繼承」放在 `content_nodes.tag_is_inheritable`（class_tag 才有意義；NULL＝依種類：保留／模組標籤不繼承，其他繼承），和 `node_attributes.is_inheritable` 同名同義。2026-11-09 刪除（migration 185，§5）。不放在 `tag_schema`：`tag_schema IS NOT NULL` 目前代表「這是集合」，放進去會讓一般標籤變成集合。

**一列裡哪些是複製、哪些是衍生**（2026-11-22，同步 4a 批）：列本身、它的 id、`note`、錨點（`anchor_id`）、`block_ref`、`task_id`、`detached_*` 與 `block_node_tags` 是**複製**的（每個都是單位，`spine/stampedMerge/dbUnits.ts`），由寫入那台的 `syncBlockNodes` 寫、跟著修改包走；`parent_block_id`、`kind`、`label`、`text_cache`、`hidden_at` 是**衍生**的：正文、筆記的錨點與這些列的純函式，由 `blockNodes.deriveBlockRows` 寫（經 `services/bodyDerivation.ts` `deriveFromBody`），本機存檔與收包的那一台跑同一個函式，所以兩台相同。每一段顯示哪一列，與 `syncBlockNodes` 給它的錨點相同：段落開頭第一個有效錨點；那個錨點若是別則筆記的列在用的（搬成子筆記後留下的），存檔替這段鑄了新的，於是顯示這段開頭、這則筆記有列的錨點裡最新的那個（PR #1941 審查第 1 輪第 5 點；`blockNodes.integration`「a block whose anchor another note's row answers to」）。收包絕不跑 `syncBlockNodes`（它會再鑄錨點、再建任務）。`_block_autotag`（區塊存檔建的標籤）在收包那台由 `markReceivedAutoTags` 依「標籤與那一列的建立標記相同」補上。
**文字快取只是索引**：`block_nodes.text_cache` 的來源永遠是筆記正文。標籤查詢與標籤頁只回 `label`，不讀它；它**不進** git 備份、嵌入向量、發布集合、搜尋索引（正文本來就被備份、索引一次），目前只有錨點找回比對讀它（`services/blockAnchors/store.ts`）。之後要讓任何一處讀到子節點的文字，都要在那裡明確加入並寫進這份文件。

**選 B 的後果**（2026-10-14 當時留待之後決定的兩件事，已各自決定；當時的原文見[歷史檔](block-nodes-history.md)）：任務行是子節點**包住**既有的任務節點（見「任務行」）；段落上的複習進度是複習模組自己的表、以目標（筆記或段落）為鍵，不另做一份 `node_attributes`（見「段落上的複習卡」）。

## 解析的線性時間

`{…}` 與 `^id` 的解析在每次存檔、寫入交易內執行，所以必須線性（`bodyParsersLinear` 計時守門，含大括號、長清單、`^` 連串等病態輸入）。解析器在 `@onden/markdown`（`parseBlocks`），前後端共用同一套規則。它用 remark 的語法樹，但**不含 GFM 的裸網址自動連結**：那個擴充在長段落上是平方級（64k 字的 `k: v` 行約 4 秒），裸網址也不影響區塊結構；表格、任務項目、註腳照常解析。（渲染器本身的同一個問題另案處理，note-54。）

## 存檔的實作（B1b，2026-10-14）

- **一律開啟**（2026-10-19，使用者：「就是我產品本來的設定，不用有開關」）：原本的 `ONDEN_BLOCK_NODES` 開關已移除。開關存在時預設關閉，原因是 micromark 在某些長段落上不是線性的；現在由下面的長度上限守住。打開不回填：既有筆記不會被批次改寫，沒有 `{…}`（或 Obsidian 的 `#tag ^id`）的筆記存檔時正文一字不改；有的筆記在下次存檔時才補 `^id`、建子節點。
- **長度上限**：正文超過 `BLOCK_PARSE_MAX`（32,000 字元）時不解析，**子節點維持原樣**（不隱藏、不改），存檔時記一筆 log（`blocks: note too long for block nodes`）。B2 的編輯器要在這種筆記上顯示「這篇太長，暫時不能用段落標籤」，不能讓使用者以為標籤生效了。上限是永久的界線，不只是暫時措施。上限處最壞情況約 0.9 秒（一長串沒關的 `![a](`），其他形狀 < 0.2 秒。
- **補 `^id`：誰寫**（#164 審查後修正）：
  - **游標所在的區塊先不補**（#164 第二輪審查）：編輯器把寫回的正文當成「只有差異的那一段」套用，CodeMirror 會把剛好停在插入點的游標留在插入內容**前面**，於是接著打的字跑到 ` ^id` 前面，`{…}` 不再在區塊結尾（以真的 `@codemirror/state` 重現）。所以游標所在的區塊、以及輸入法組字中的任何區塊都先不補；游標離開那個區塊（或編輯器失焦、換筆記）時再存一次把它補上（`lib/data/blockIdWriteback.ts`、`draftActions.reportEditorCaret`）。
  - **編輯器存檔由用戶端寫**：自動存檔送出前（`draftActions.flushPendingSave`，閒置 1.5 秒觸發時），用 `@onden/markdown` 的 `assignBlockIds` 把缺的 `^id` 寫進**草稿與送出的正文**。這樣用戶端留給下次三方合併的基準、送出的正文、伺服器的副本三者一致。若由伺服器在存檔時改寫正文，用戶端的基準少了 `^id`，下一次合併會「乾淨地」把 `^ab12` 搬到使用者新打的那一行，區塊失去身分（審查重現）。草稿裡某區塊的 `^id` 不見了，會從基準拿回同一個（種類、顯示標題、標籤相同）。`editNoteText` 同樣處理。
  - **伺服器只替沒有編輯基準的寫入者寫**：送了 `base_markdown` 的存檔（編輯器）**不改寫**；沒送的（API、MCP、agent）與建立筆記（`createNote`）由伺服器 `withBlockIds` 寫，是這次事件記錄的正文的一部分。
  - **不寫**：匯入（保留檔案原文，否則沒改過的檔案再匯入會被當成已修改）、復原（還原當時的正文）、卡片編輯器（`saveNoteBody`：卡片自己留基準，B2 再接上）。這些正文裡沒有 `^id` 的 `{…}` 區塊，等主編輯器存檔時才變成子節點。
  - 同一筆記重複的 `^id` 改名。
- **標籤名稱**：`{…}` 裡的名稱每一段都不分大小寫比對（`{Course/Week1}` 與 `{course/WEEK1}` 是同一個標籤）；找不到就建立，並在那個標籤上記 `_block_autotag`（模組擁有的屬性）。**打字途中的殘留**：某次存檔讓區塊不再用某個標籤時，如果那個標籤是區塊存檔建立的、而且已經沒有任何筆記、區塊、子標籤、schema 或頁面文字在用，就移到垃圾桶（例如先存到 `{重}`、再存成 `{重要}`，`重` 會被清掉）。判斷前先鎖住那些標籤列（`FOR UPDATE`）：同時替它加成員的寫入會透過外鍵持有 key-share 鎖，所以不會在判斷後才冒出一個成員。別處用到的標籤不動；沒有刪除權限時也不動。
- **比對與事件**：每次正文改變（編輯、建立、複製、匯入、復原）都在交易內讓子節點跟著正文。事件 `BLOCK_NODE_CREATED`／`BLOCK_NODE_UPDATED`（上層、種類、標籤改變）／`BLOCK_NODE_REMOVED`（`{…}` 或 `^id` 不見：隱藏、保留資料）／`BLOCK_NODE_RESTORED`（再出現：同一列回來）。只改文字不產生子節點事件（那是筆記本身的編輯事件）。事件的對象是**筆記**（`target_type = node`），所以只有讀得到筆記的人看得到（子節點的顯示標題就是筆記的文字）；它們由筆記的事件觸發。
- **復原**：子節點事件本身不能單獨復原；復原筆記的編輯時，正文回到當時的樣子，子節點跟著重算（隱藏的列會回來，資料還在）。
- **舊用戶端相容**：bootstrap 仍固定帶 `features: { block_nodes: true }`，給開關移除前快取的舊介面（service worker 保留到重新載入）用；舊介面沒拿到它就不顯示段落節點、也不替編輯器存檔補 `^id`。新用戶端不讀它。開關移除那一版部署後的下一版即可拿掉。
- **同步**：bootstrap、同步增量、`POST /sync/nodes` 都附上筆記的子節點（`blocks`：id、所屬筆記、`^id`、上層、種類、顯示標題、自己的標籤 id）；增量用 `replace_for` 取代用戶端手上那篇的整組。**不送文字**：用戶端從手上的筆記正文切出來。

## 段落上的複習卡（B3，2026-10-19）

使用者 2026-10-19：「複習應該也要」「你直接做」。

- **成為卡片**：段落**自己**有複習的函式引用（`function_refs`，`function_id` 為 `review`）才是卡片；段落不繼承標籤（§5），所以父段落是卡片不代表子段落也是。寫 `{review}` 或 `{複習}`（複習模組的保留字，`reviewSeam.cardWords`；不是標籤，存檔不會建出同名標籤）就替那段加上自己的引用；拿掉字則收回引用，但每個人的排程保留，字寫回來就接著排（`unmarkCardsWord`）。其他方式做成的卡（遷移 195 搬來的）不跟著文字走。複習模組關著時存檔不加引用。筆記與它的段落可以各自是卡片。
- **正反面**（`@onden/markdown` 的 `blockCardSides`，從筆記正文切出，不複製）：
  - 有下一層的清單項目：項目那一行是問題，縮排的下一層是答案（RemNote／Logseq 的寫法）；
  - `==挖空==`：正面換成「［⋯］」，背面以粗體顯示；
  - 標題：標題是問題，它的章節是答案；
  - 其他：第一行是問題，其餘是答案（可能沒有，複習畫面顯示「這張卡底下還沒寫答案」）。
  - `{…}` 和 `^id` 兩面都不顯示。
- **進度**：每人一份，在 `review_states` 的 `block_id` 列（migration 120 建了另一張表 `block_review_states`，183 併回同一張：一列是一則筆記或一個段落的卡片）：模組自己的表、以目標（筆記／段落）為鍵，不另做一份 `node_attributes`（上方「選 B 的後果」第 2 點的決定）。拿掉 `{…}` 時子節點隱藏、進度保留，貼回就接著排程。成員移除時一併刪除（`personalTables`）。
- **API**：佇列（`GET /api/review/queue`）的卡片多一個 `block`（`{ id, ref }`；筆記卡為 null），`node_id` 是所屬筆記；評分、狀態、復原走 `/api/review/blocks/:blockId/…`。卡片的牌組是所屬筆記。
- **入口**：段落選單與選取文字時的浮動工具列有「把這段做成複習卡」（複習模組的 `paragraphAction`，模組開著時），寫進複習模組的保留字；也可以直接打 `{複習}`（B2b 的 `{` 補全）。

## 任務行（B4，2026-10-19）

使用者 2026-10-19：「你直接做」。

- **寫法**：`- [ ] 寫下三個想培養的習慣 {task}`：清單項目有勾選框，而且**自己的** `{…}` 帶任務模組的保留字（`task`；工作區裡任務模組標籤現在的名稱，例如改名後的 `{任務}`，見[任務模組](tasks-module.md)）。保留字不是標籤：存檔時不交給標籤解析，所以不會建出 `task` 標籤（`services/blockNodes.ts` 讀 `taskSeam` 的 `lineWords`）。任務模組關掉時，`{task}` 不再變成任務，既有的行與任務維持原樣（見[任務模組](tasks-module.md)）。沒有 `{task}` 的勾選框維持普通勾選框。
- **形狀**（上方「選 B 的後果」第 1 點的決定）：子節點**包住**一個普通的任務節點（#task＋`_task_status`，筆記底下的隱藏子節點），以 `block_nodes.task_id` 相連（migration 122）。任務頁、期限、重複、提醒、同步全部照舊；沒有行的任務（在任務頁建的、B4 之前的）不受影響。
- **行 → 任務**（`modules/tasks/blockTasks.ts`，筆記存檔時，經 `services/taskSeam.ts` 由 `blockNodes` 呼叫）：新的任務行建立任務（已打勾就是完成）；打勾＝完成（有重複規則時照舊產生下一次），取消打勾＝重開；那一行的文字（勾選框之後、`{…}` 之前，完整不截斷）就是任務標題；拿掉 `{task}` 或刪掉那行，任務移到垃圾桶，貼回來就還原，期限保留（已決定 1）。
- **任務 → 行**（`modules/tasks/lines.ts`，經 `services/taskLineHook.ts` 接到 `updateTask`）：在任務頁完成／重開，筆記那一行跟著打勾／取消（照一般筆記存檔：事件、版本、合併）；取消（cancelled）不動勾選框。任務頁不能改行任務的標題（409 `task_is_a_line`，到筆記改）。
- **搬到別的筆記**：照已決定 2，第一版是「刪除＋新建」，期限不跟著走。
- **編輯器**：段落節點開啟時，「把這個勾選框轉成任務」（選取工具列、Mod-Shift-Enter）改成在那一行寫上 `{task}`，不再另建任務節點並把框打勾。
- **刪除任務**（2026-11-18）：刪掉寫在筆記裡的任務，是「任務進垃圾桶」加「筆記存檔時少了那一行」，同一個事件交易（`modules/tasks/deletion.ts`，細節在[任務模組](tasks-module.md)「刪除任務」）；之前只刪任務節點，那一行還在，筆記下次存檔時任務被還原。「復原」把任務與那一行一起放回原位。
- **還沒做**：任務頁的「新增任務」仍是建任務節點（日記開時放在今天的筆記）；改成在筆記裡寫一行留待下一步。

## 打 `((` 引用段落、最近存的段落（2026-10-27）

靈感：Emacs 的 `org-store-link`＋`org-insert-link`（存過的排最前面）、`org-roam-node-insert`（一個搜尋框搜全部）、Logseq 的 `((`。

## 搬成子筆記／展開回內文（B5，2026-10-27）

取代整篇指令「依標題拆分」「合併子筆記」：改成對**一段**做，入口在段落選單（¶；桌面是選取泡泡）。

- **搬成子筆記**（游標所在的段落、清單項目或標題；標題就是整節，範圍規則同上表）：建一篇這篇的子筆記，標題＝標題文字或段落開頭，
  內文＝那段文字拿掉 `{…}` 與 `^id`；原位置換成 `![[子筆記]]`（前後補空行，讀起來不變；標題的整節連標題行一起搬，所以子筆記內文第一行就是標題）。
  引用、輔助行為與資料：

  | 東西 | 處理 |
  | --- | --- |
  | 工作區（同一個空間）裡的 `[[原筆記#^id]]`、`![[原筆記#^id]]`（含 `\|別名`） | 改成 `[[子筆記]]`、`![[子筆記]]`；標題整節則連 `[[原筆記#標題]]` 一起改。程式碼、數學裡的不動 |
  | 搬走的文字裡面的其他 `^id`（例如節內的清單項目） | 跟著文字走；指向它們的 `[[原筆記#^內層]]` 改成 `[[子筆記#^內層]]` |
  | 搬走的文字裡寫給原筆記其他位置的 `[[#^別處]]` | 補上原筆記名稱，否則到了子筆記會指向子筆記自己 |
  | `{標籤}` | 成為子筆記的標籤（走一般的套用標籤，需有套用權限，否則整個操作被拒） |
  | 複習進度（`review_states` 的 `block_id` 列） | 該段的進度**複製**成子筆記的 `review_states`；節內其他卡片複製到子筆記裡同 `^id` 的新列。原列留著（隱藏），復原時回來 |
  | 任務行（`block_nodes.task_id`） | **擋下**（409 `block_has_task_line`）：任務掛在原筆記，搬走會失去期限與重複規則（B4 的「搬到別的筆記」本來就不帶期限）。範圍內任何一行是任務行都擋 |
  | 引用、表格、程式碼、引用區塊裡的段落 | 擋下（422 `block_unsupported`） |
  | 沒存過的 `{標籤}`（沒有對應的段落節點列） | 擋下（409 `block_not_saved`），等存檔後再試 |

- **展開回內文**（游標在一行 `![[某子筆記]]` 上，且它是這篇的子筆記）：用子筆記內文取代那行，給回 `^id`、標籤寫回 `{…}`；
  指向子筆記的引用改回 `[[這篇#^id]]`（有 `#錨點` 的保留錨點）；子筆記移到垃圾桶。子筆記的複習進度複製回該段。
  擋下：子筆記底下還有筆記（`child_has_children`）、有屬性（`child_has_properties`）、文字開頭有 frontmatter、
  內文不是單一段落／單項清單／標題整節（`child_not_one_block`）、這篇找不到或有多行嵌入它。
- **沒權限改的引用**：只改寫使用者有寫入權限的筆記。搬成子筆記時預設**拒絕**並列出這些筆記（看不到的只回數量）；
  使用者確認後以 `unwritable: "leave"` 照做，那些連結維持原樣（指向已經沒有的段落，點開只會到原筆記）。
  展開回內文**永遠拒絕**，因為子筆記要進垃圾桶，不能留下壞連結。同一空間內寫入權限一致，實際會碰到的主要是代理權杖。
- **一個操作、一個可復原單位**：`services/blockChildNote.ts`。原筆記的存檔（`NODE_UPDATED`）是根事件，
  子筆記的建立、標籤、其他筆記的改寫、子筆記進垃圾桶都在它的交易與 cascade 內；
  `restoreEvent(根事件, { cascade: true })` 一次復原全部（網頁的「復原」鈕就是呼叫它）。複習進度在核心經 `reviewSeam` 交給複習模組複製。
- **不處理的**：不同空間的筆記裡的引用（`[[標題]]` 本來就只在自己的空間內解析）；任務行與搬到別篇；`{標籤}` 以外的段落屬性。
- 純文字規則在 `@onden/markdown` 的 `blockChild.ts`（`planBlockMove`、`planBlockExpand`、`rewriteLinks`…，性質測試：搬出再展開還原原文、
  搬出的內文＝區塊嵌入顯示的內文、改寫後不剩指向該段的連結），權限與資料在後端 `blockChildNote.integration.test.ts`。

## 段落連結的後援：原筆記找不到時到整個工作區找（2026-10-27）

`[[A#^id]]`（含 `![[A#^id]]` 嵌入）維持 Obsidian 格式。搬成子筆記會改寫引用，但漏改的情形仍會發生：沒權限寫的筆記、
手動把段落剪貼到別篇、從外面匯入。Org-mode 的 ID 連結不綁檔案；我們用「找不到時的後援」達到類似效果，**不自動改使用者的文字**。

**規則**（`@onden/markdown` 的 `blockRef.ts`，所有入口共用，不各寫一份）：

1. 先在指名的筆記 A 找（`noteHasBlock`，與 `extractBlock` 同一個解析）。找得到就用 A，**不做任何額外查詢**。
2. A 沒有才找「讀者看得到」的其他筆記裡同一個 `^id`。只有一篇就用它。
3. 有多篇（`^id` 只在一篇內唯一，不保證全域唯一）：先留 A 的子孫（搬成子筆記的段落就在這裡，任何深度），
   再留與 A 同空間的；縮到剛好一篇才用，否則當作找不到——寧可顯示「找不到」，也不猜一篇。
4. 連結與嵌入照常顯示；嵌入底下的「— 筆記」小字與點擊都指向實際所在的筆記。編輯嵌入也改到實際所在的筆記。

**索引**：`block_nodes` 只有升級（`{標籤}`）的段落，不能用。新增 `note_block_refs`（migration 143：筆記、`^id`），
涵蓋所有 `^id`，由 `noteBlockRefs.syncNoteBlockRefs` 在每次寫正文時（`applyBodyChange`、`finishNewNote`，經 `bodyDerivation.deriveFromBody`；
收下修改包的那一台也經它，`services/receivedDerivation.ts`；同一個交易）依 `blockAnchors` 更新；筆記刪除時隨 FK 清除。它只是索引：查到候選後讀這幾篇的正文，用真正的解析器確認，
所以舊資料的回填（migration 用正則，比解析器寬鬆，會多收程式碼區塊裡的 `^id`）多收的列只多花一次讀取，不會連錯。
候選超過 20 篇（貼到處都是的樣板 id）直接當作找不到，不讀。

**各入口**：

| 入口 | 做法 |
| --- | --- |
| 後端 `GET /api/nodes/:id/block-home/:ref` | `services/blockRefLookup.ts`：一次索引查詢＋讀候選正文；範圍在 SQL 內用 `readableScopeSql` 切 |
| App 嵌入（`lib/embedDom.ts`） | A 的內文切不出該段時才問後端（`lib/blockHome.ts`，2 秒內相同問題共用） |
| App 點連結（預覽與編輯器） | `useOverviewMode.openWikilink(…, blockId)`：A 的正文（開著的列、本機副本，必要時讀一次）有該段就照舊，否則問後端 |
| 發布網站（靜態與 App 內的網站畫面） | `servedBlockTarget`／`servedBlockPage`：只在**已發布**的頁面清單裡找，與網站解析 `[[ ]]` 同一份清單 |
| 「被連結」引用句 | `siteModel.embedQuote` 同上 |
| MCP／agent 工具 | 目前沒有任何工具解析 `#^id`（只有前端與網站切段落），所以沒有要改的入口 |

**權限與不外洩**：候選在 SQL 內被讀取範圍切掉，看不到的筆記既不會被選中，也不會讓別的候選變成「多篇」而改變答案——
讀者得到的結果與那篇筆記不存在時完全相同。指名的 A 本身讀不到時，回覆與「沒有」相同（不確認它存在）。
發布網站的頁面清單本來就只含已發布、已遮蔽的筆記，私人筆記不在其中，所以不可能成為目標或對手。

**效能與取捨**：沒有掃描任何正文。一般連結（A 還有該段）零額外成本；只有連結「斷了」時才多一次索引查詢。
手機上筆記多半是不含內文的精簡列，所以**不**在前端用已載入的資料找（找不全、也要掃），一律問後端；代價是離線時
斷掉的連結不會被救（與先前行為相同，仍顯示「找不到」，不會更糟）。索引多一張表（每個 `^id` 一列，約為「有 `^id` 的段落數」）。

**沒做**：「修正這個連結」（把文字改成新位置，非必要）；首頁設計器裡「筆記元件」以 noteId＋blockId 指定的段落（不是 wikilink，
沒有自己的後援）。
