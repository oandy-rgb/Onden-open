# 分散式同步（beta）：節點、操作集合、權限

> 狀態：現行（最後確認 2026-11-06）。**草案／beta**：第 1 步（設計＋模擬測試台＋最小引擎）與**第 2a 步（接上真資料：創世匯入、擷取、投影、權限對齊、兩個真後端的影子比對，§12）**
> 已實作並測試；**沒有介面、沒有真傳輸（2b）、沒有簽章、不處理附件**，預設關閉（`ONDEN_DISTRIBUTED_SYNC=1` 才開），正式站行為完全不變。
> 業主決定（2026-11-01）：「分散式我認為該做，但當 beta。因為如果分散式的測試都沒問題，那有主伺服器就更沒問題了。」
> 前提文件：[可攜後端](portable-backend.md)、[瀏覽器版](browser-app.md)。尚未合併的姊妹設計：`docs/design/intermittent-server.md`（PR #1132）、`docs/design/desktop-app.md`（PR #1133）。

## 1. 結論先看

1. **同步的單位是「操作」，不是狀態。** 一個操作＝「某個人在某個空間對某個東西做了什麼」，帶混合邏輯時鐘（HLC）、來源節點與流水號。
   節點之間只交換操作；**狀態是「有效操作集合」的純函式**（`materialize.ts`）：兩個節點拿到同一組有效操作，不論順序、不論重送幾次，狀態一定相同。收斂就靠這句話。
2. **主伺服器是特例，這句話變成測試。** 同一串操作，星狀（裝置只跟伺服器同步）與網狀（裝置互相同步）跑完，每個節點每個空間的狀態必須相同。結果在 §8。
3. **權限不會因為收斂成立就成立**，所以獨立處理（§5）：節點只送對方讀得到的；收到的操作由收方依**自己的**成員資料重新判斷，不合法就不套用、不轉送；
   「現在能不能做」以操作在全序中的位置判斷，所以遲到的撤權會讓它之後的操作在每個節點同時失效。陌生人（協作連結）只能 `suggest`。
4. **這不是把筆記換成 CRDT。** 內文仍是現有的 diff3 三方合併（`services/eventLog/bodyMerge.ts`），只是合併的順序由全序決定；
   `docs/design/intermittent-server.md` 擔心的「要換成 CRDT、權限守不住」，這裡的回答是：不換資料型別，用操作集合＋確定性折疊；權限用收方重驗。簽章與惡意節點仍未解（§9）。

## 2. 節點身分

| 名詞 | 意義 |
| --- | --- |
| 節點（`NodeId`） | 一份完整資料庫副本：一台裝置、桌面 App、瀏覽器試用版、或伺服器。第一次開啟時產生，寫進自己的 `ds_node`；資料庫換了就是另一個節點。 |
| 人（`ActorId`） | 權限談的對象。**節點替自己的人作保**：裝置只替登入者說話，伺服器替所有人說話（它今天本來就是）。 |
| 目錄（`NodeDirectory`） | 「哪個節點可以替哪些人說話」，配對時定下（`ds_peers`）。收到的操作若 `作者 ∉ 來源節點的人`，直接拒收並記進 `ds_rejections`。**目錄不是簽章**（§9）。 |

操作編號 `<節點>:<流水號>`，流水號從 1 起、不跳號、不重用（崩潰重啟從資料庫還原，測試涵蓋）。

## 3. 操作與排序

```
Op = { id, origin, seq, hlc{wall,counter}, author, space, body }
全序 = (hlc.wall, hlc.counter, origin, seq)
```

- **HLC**（`hlc.ts`）：本機事件取 `max(前一個讀數, 牆鐘)`，收到遠端讀數後不落後於它，所以「看過 A 才做的 B」一定排在 A 之後（尊重因果）；併發的操作由 `(origin, seq)` 決定先後，所有節點一致。
- **時鐘偏差**：HLC 保證因果，不保證「真實時間」。**併發衝突中誰贏、離線編輯落在撤權之前還是之後，取決於各裝置的時鐘。**
  防線只有一條：遠端讀數比本機牆鐘快超過 10 分鐘就拒收（`clock_too_far_ahead`），避免一台壞時鐘把全域順序拖進未來。這是設計取捨，不是已解決的問題。
- 操作一經寫入 `ds_ops` 就**只增不改**（資料庫觸發器拒絕 UPDATE／DELETE），歷史因此不會被改寫。

### 3.1 為什麼同步「操作」，而不是 `domain_events` 或狀態

| 選項 | 為什麼不選／選 |
| --- | --- |
| 同步 `domain_events` | 游標是各庫自己的 bigserial；酬載為了**復原**設計（反向補丁、`prev_field_values`），不保證能重播；沒有時鐘與來源節點；被拒絕的嘗試與成功事件的語意不同。把它當跨節點順序會把 A 庫的 id 12 與 B 庫的 id 12 混為一談。 |
| 同步狀態（整列覆蓋） | 最簡單，但同一則筆記兩人同時改就只剩一人（遺失更新），且無從重驗「誰有權做這件事」。 |
| **同步操作（選）** | 每個操作自帶作者與空間，收方能重驗權限；歷史完整；狀態可由操作重建；內文可以帶基準版做三方合併。 |

與現有事件紀錄的關係（**2a 已做**，§12）：本機寫入照舊走 `spine/mutate`，提交後由 `domain_events` **擷取**成操作（在擷取時蓋 HLC）；
遠端操作套用時**也寫 `domain_events`**（`tx_meta` 帶 `ds_op_id`，由 `db.ts` 的 `event()` 在「正在重播遠端操作」時自動加上），歷史、復原、既有同步消費者因此看得到；
擷取看到 `ds_op_id` 就跳過，所以不會回送成迴圈。

## 4. 狀態與合併規則

### 4.1 折疊

`materialize(ops)`：依全序排好，逐一對「前面操作建好的狀態」套用。每個操作得到判定（`ok` 或 `{reason}`）：有效的改狀態，無效的不改並說明原因。
同一組操作＝同一個結果；單元測試用 fast-check 對 400 組隨機歷史打亂順序、重複、反轉，狀態與判定都相同（有效與無效判定都實際出現，不是空轉）。

### 4.2 各欄位的規則

| 東西 | 規則 | 併發時 |
| --- | --- | --- |
| 內文 | 三方合併 `threeWayMergeBody(操作的 before, after, 目前狀態)`；`before` 是作者編輯時看到的內文 | 不同行都留；同一行衝突時留全序較後的文字，**另一邊記在 `conflicts`**（兩邊文字都在狀態裡，不只在歷史） |
| 標題 | 最後寫入者勝（依全序）；被蓋掉的操作留在 `history` | 全序較後者勝 |
| 標籤關聯 | 每組（筆記，標籤）最後寫入者勝；標籤必須同空間、標籤節點必須是標籤類 | 同上 |
| 樹的位置（移動） | 設定 parent；父層必須同空間、未刪除、是內容筆記 | 兩個移動合起來會成環：**全序較前者成立，較後者判為 `cycle`**，每個節點都一樣；較後者的意圖丟失（只留在作者本機的日誌，見 §10-2） |
| 刪除／復原 | 軟刪除旗標，最後寫入者勝；不連帶子孫（讀的時候看祖先） | 刪除與併發編輯：內文照樣合進去，復原後看得到 |
| 建立 | 編號已存在 → `note_exists`（編號是隨機 UUID，撞號視為異常） | 先到全序者成立 |
| 建議（`note.suggest`） | 只記在筆記的 `suggestions`，**永遠不改內文** | 全保留 |
| 成員（`member.set`） | 只有空間擁有者（管理者）能設；擁有者自己的存取也能設（2a：與伺服器一致，見 §5） | 最後寫入者勝 |

唯一性規則（slug、同父層同名標籤）在 2a 有確定性的讓步規則，見 §4.4。

### 4.4 唯一性與「有效刪除」：真資料表的限制怎麼不讓節點分歧（2a）

真資料表有些限制是引擎的狀態沒有的；投影（`bridge/project.ts`）必須在**每個節點得到相同結果**的前提下遵守它們。規則都是「世界狀態的純函式」，不是「誰先到誰贏」：

| 限制 | 規則 |
| --- | --- |
| 同父層同名標籤（`tagHierarchy.assertTagNameAvailable`，409 `tag_name_conflict`） | 兩個節點各自離線建了同名標籤時，**操作本身的標題不變**；顯示名稱由 `view.ts` 的 `tagDisplayTitles(world)` 決定：依合併後全序，最早建立的保留原名，之後的依序是「名稱 (2)」「名稱 (3)」…（也避開兄弟已有的字面名稱）。投影把資料表的標題對齊這個顯示名稱：必要時先把本機既有的那個改名讓位，再建遠端的（`fieldPass`，標籤標題優先）。 |
| slug 唯一（每個空間內，`content_nodes_space_slug_uq`） | slug 是**節點本地的衍生標籤，不屬於複製的狀態**：投影建立／改名仍走 `createNote`／`updateNode`，它們用現有的 `uniqueSlug`（`-2`、`-3`）讓步，**永遠不會因 slug 失敗**。代價（寫明）：同空間兩篇同標題的筆記，兩個節點可能把 `-2` 配給不同的那一篇；標題、內文、父層、標籤、刪除狀態都收斂，影子比對不比 slug。需要穩定連結請用筆記 id。 |
| 刪除連帶子孫（伺服器的垃圾桶是子樹；引擎的 `note.delete` 只標那一篇） | 比對與投影用**有效刪除**：自己或任一祖先已刪。併發時（A 刪父層、B 在父層下建子筆記）子筆記在引擎裡自己的旗標是未刪，但有效刪除為真，投影把它放進垃圾桶；父層復原後它又自動「有效未刪」，投影把它拿回來。被刪的筆記**內容不即時對齊**（垃圾桶裡不能編輯），復原時才補上。 |
| 筆記只能放在未刪的父層下 | 投影要把筆記建在／移到垃圾桶裡的父層下時，先暫時把該父層鏈最上面被刪的那篇復原（`makeRoom`），做完，最後一步再把引擎狀態認為已刪的放回垃圾桶。 |
| 復原一篇筆記時，伺服器會順手把還在垃圾桶的祖先復原、或把父層仍在垃圾桶的子筆記提到最上層 | 這些副作用沒有對應的操作：**擷取**在每批事件後把「被本機事件碰過的筆記」的資料列與引擎狀態比一次，差的補成操作（`reconcileTouched`）；**投影**最後再對齊一次（步驟 6）。 |

### 4.3 刪除了的東西、被合併掉的東西查得到嗎

- 有效但被後來操作蓋掉的（標題、標籤、移動、內文衝突）：在該筆記 `history`（模擬測試 (b) 逐節點檢查），內文衝突另外在 `conflicts`。
- 因衝突被判無效的（`cycle`、`parent_deleted`…）與被撤權後才到的：留在**作者節點**的日誌與判定（`world.verdicts`），**不轉送**；其他節點看不到它。這是已知的缺口（§10-2）。

## 5. 權限

今天的權限由伺服器裁決（`spine` 寫入閘門、`readableScopeSql`），分散式沒有裁決者。引擎把四件事分開：

| 問題 | 誰回答 | 怎麼回答 |
| --- | --- | --- |
| 這個節點該不該收到這筆操作？ | **送的人**（`opsFor`） | 只送：①在送的人自己的狀態裡判定有效、②對方的某個人在該空間可讀。另外送「關於對方的人」的成員變更，讓被撤權的裝置知道自己被撤權 |
| 這筆操作合不合法？ | **收的人**（`ingest`＋`materialize`） | 作者必須是來源節點的人；時鐘不超前；編號不被改內容（`equivocation`）；該空間在套用後對本節點某個人可讀，否則整批拒收（`space_not_readable_here`）；之後折疊時再依成員資料判斷 |
| 當時能不能做？ | **操作在全序中的位置** | 「作者在該空間的角色」取自全序中**排在它前面**的成員變更。遲到的撤權（全序較前）會讓它之後的操作在每個節點同時失效；撤權之前的操作成立 |
| 失效的操作去哪？ | 不套用、不轉送 | 結構不合法（假作者等）→ `ds_rejections`；權限不合法 → 留在收的節點的日誌、判定為無效，**不再送給任何人**（`opsFor` 只送有效的） |

角色（空間內）：`edit` ＞ `suggest` ＞ `view` ＞ `none`。擁有者（建立空間的人）永遠是 `edit`，只有擁有者能改成員。
**陌生人＝協作連結**：連結給的就是一個角色，陌生人節點得到 `suggest`——可讀、可提建議、不能改任何東西；簽章與連結的產生／撤銷留到後面（§9）。

**撤權的邊界（必須說清楚）：** 已經送出去的資料收不回來。被撤權的裝置保有撤權之前收到的內容，之後收不到新操作，它之後的修改在所有節點被判無效。
撤權也不會「擦掉」對方的本機副本，這是分散式本質上的限制，不是這個實作的缺陷。被撤權的裝置的視圖**凍結在它得知被撤權的那一刻**：之後別人的權限變動（例如另一個人也被撤權）它收不到，所以它對「之後的操作」的判定可能與全體不同——這是設計內的，不變量 (a) (d) 只要求仍可讀的節點與全體一致（模擬種子 44 曾因此誤報，已改測試而非引擎）。

與現行權限模型的關係（**2a 對齊**）：空間（`spaces`／`space_members`）本來就是權限單位。

- **讀 ＝ 是成員；寫 ＝ 權限為 `edit`；管理 ＝ 空間擁有者**（共用空間：工作區擁有者；個人空間：本人）。**擁有者只在成員身分上讀寫**（`createSharedSpace` 讓建立者成為成員；工作區擁有者可以管理一個自己不是成員的共用空間而不能讀它）。
  引擎因此改成同一條規則：`roleIn` 只看成員表；`space.create` 讓建立者成為 `edit` 成員（可用 `ownerRole` 表示別的），擁有者可以用 `member.set` 改任何人（含自己）。2a 之前「擁有者永遠是 edit」「擁有者自己不能被改」兩條取消。
- **`suggest` 怎麼存**（決定）：`space_members.permission` 的 CHECK 加第三個值 `'suggest'`（遷移 `174`）。它是**成員**（所以讀得到，`readableScopeSql` 不改），但不是 `'edit'`（所以 `spaceCanWrite` 為假）；`SPACE_PERMISSIONS`（成員 API 讓擁有者選的）仍是 `view`／`edit`，
  只有同步投影寫 `suggest`（`StoredSpacePermission`）。不新增表、不改 SQL 規則：`spaceAccessSql` 的 `can_write` 本來就只認 `'edit'`。
- **全域標籤**：真資料模型的標籤定義不屬於任何空間、任何人都讀得到、只有工作區擁有者能改。引擎把它們放在每個工作區一個偽空間 `tags:<workspaceId>`（`GLOBAL_TAG_SPACE_PREFIX`）：擁有者 `edit`，其他人一律 `view`；`note.tag` 允許標籤在該偽空間。
- **一致性測試**（`distributedSyncPermissions.integration.test.ts`）：同一組情境（編輯者、檢視者、`suggest`、只在個人空間的人、AI 代理、管理共用空間但不是成員的擁有者、已刪空間、垃圾桶筆記、標籤），
  `readableAmong`／`readableScopeSql` 判可讀的集合與引擎 `canRead` 逐人逐筆一致，`assertAuthority(write_node)` 與 `roleIn === "edit"` 一致。

**遠端操作怎麼通過本機閘門**：「現在能不能做」在複製的世界裡看操作在全序中的位置（§5 上表）；本機資料表只有「現在」。撤權若先到本機，撤權前的合法編輯再問一次本機成員表就會被拒，節點之間就不再一致。
所以重播**一個已被引擎判為有效的操作**時，`spine/replicatedOp.ts` 的 `withReplicatedOp({opId, authorId})` 讓**該操作的作者**通過 `assertAuthority` 與 `spaceAccessSql`（不含 token）；
事件鎖、事件與狀態同一交易、membership epoch、cascade 全都照舊。這個範圍只有投影一個呼叫者（`distributedSyncOff.test.ts` 守住），不是 `open`／`cascade` 的新繞道：引擎判定取代的是「當時成員表」這一個輸入。

## 6. 傳輸抽象

引擎只認兩樣東西：`SyncDb`（它自己的 SQL，不碰行程共用的 `pool`，所以一個行程能開多個節點）和**訊息**：

```
offer { from, to, have, reply }   我有這些（每個來源節點的流水號區間）；reply=true 表示請你也回一份你有的
ops   { from, to, ops[] }         你缺的、你讀得到的、我判定有效的操作（一次最多 100 筆）
```

`node.handle(msg)` ＝ 一個訊息進、零到多個訊息出；**重送、亂序、遺失都安全**（`ds_ops` 以操作編號去重，缺的下一輪再問）。引擎不管怎麼送：

| 傳輸 | 狀態 |
| --- | --- |
| 記憶體（`test/helpers/distSim/network.ts`：丟包、重複、任意順序、隔離分區） | 第 1 步，測試用 |
| HTTP 到伺服器（伺服器是一個永遠在線的節點） | 第 2 步 |
| 加密中繼信箱（兩台裝置在伺服器不在時交換，`intermittent-server.md` ⑤） | 之後 |
| WebRTC 點對點 | 之後 |

`have` 用區間表示（因為權限過濾會讓某個來源的流水號出現空洞）；操作量大之後要改成快照＋增量（§10-3）。

## 7. 與主伺服器模式的關係

主伺服器＝一個永遠在線、替所有人說話、大家只跟它同步的節點。**同一套引擎、同一組規則**：星狀拓樸只是「邊」只連到它。
所以「分散式的測試沒問題，主伺服器更沒問題」成為可驗證的敘述：星狀＝網狀（§8 (e)）。

不同的只有信任：今天的伺服器是權威（它拒絕的寫入就不存在）；分散式中**每個節點都是自己的守門員**，沒有節點有最後決定權。
第 2 步的做法是影子模式：伺服器節點與現有 `/api/sync` 並行，比對兩條路的結果，不切換任何使用者的行為。

`src/test/helpers/distSim/`（叢集、網路、工作負載、不變量、縮減）＋ `src/test/distributedSync*.test.ts`。

- **節點**：5 個，各有自己的 PGlite（只含同步表）：`S` 伺服器（替 alice／bob／carol／eve 說話）、`A` alice、`B` bob、`C` carol、`E` eve（陌生人，`suggest`）。

- **不變量**（靜止＝停止干擾、全部恢復連線、互相同步到一整輪沒有變化）：
  - (a) 某空間的每個「最終可讀者」節點，該空間狀態＝全體操作折疊的結果。

  - (e) 星狀＝網狀（同一串編輯，兩種拓樸，每個節點每個空間的狀態相同）。
- **測試台本身有被驗證**：刻意注入兩個錯誤（送出時不過濾可讀性；折疊改用到達順序），測試各自在 6 個種子內抓到。

## 9. 遷移、相容、beta 範圍

**既有工作區怎麼變成一個節點（2a 已做，`bridge/genesis.ts`）：** 節點編號新產生；工作區現有的每個空間、成員、筆記以「創世操作」匯入——作者是該筆記的建立者、編號由筆記 id 推導、時鐘取固定的最小值，
所以由同一個伺服器開出的兩份副本得到**相同**的創世操作（不會彼此當成新增）。創世之後的修改才是一般操作。正式站與現有 `/api/sync` 不受影響，直到影子模式驗證完畢。

2a 的細節：創世操作的來源是 `genesis` 這個假節點（`GENESIS_ORIGIN`），流水號是依相依順序的位置（偽標籤空間與各空間 → 標籤 → 筆記（父層先）→ 標籤關聯 → 刪除 → 成員），時鐘固定 `{0, 0}`。
**作者**：個人空間是本人，其他空間是工作區擁有者（不是各筆記的真建立者：資料表沒存，且建立者可能已被撤權，那會讓創世操作自己無效）；擁有者本人在該空間的真存取（含「不是成員」）放在最後一個 `member.set`。
**只在資料庫第一次成為節點時推導一次**：之後重啟、或帶著 `ds_*` 表一起複製的副本，沿用 `ds_ops` 裡的創世，不會用已變動的資料列重新推導（重新推導會得到不同的操作）。要開第二份副本，必須在**成為節點之前**複製（或連 `ds_*` 表一起複製）。
創世不含的資料：非內容／標籤的節點（白板等）、已刪空間裡的筆記；數量記進 `ds_unsupported`（`snapshot: …`）。

**第 1 步已做：**

- 遷移 `173_distributed_sync.sql`：四張獨立的表（`ds_node`、`ds_ops`、`ds_rejections`、`ds_peers`），沒有外鍵、不動既有表；功能關閉時是空表。
- 引擎 `packages/backend/src/distributedSync/`（`types`、`hlc`、`materialize`、`node`、`index`），門只有 `index.ts`（catalog 入口 `be-distributed-sync`）。
  放在 `src/` 底下自成一格（像 `spine/`、`browser/`），**不放 `services/` 或 `modules/`**：那兩處的 SQL 寫入由 `spineGate` 要求走 `mutate()` 或逐函式列理由例外；
  引擎只寫自己的 `ds_*` 表、經注入的 `SyncDb`、從不碰行程的 `pool`，既不適用也不該新增例外。
- **關閉不留痕跡**：`ONDEN_DISTRIBUTED_SYNC` 不是 `1` 時不能開節點（`DistributedSyncOff`，連資料庫都不碰）；它**還不是 `MODULES` 的一員**，所以沒有路由、工具、勾子、背景工作，也沒有模組庫卡片。
  原因：註冊成模組庫模組就必須有前端的對應卡片（`moduleDefinitionsAlign` 守門），那會是使用者看得到的介面——這一步明確不做。第 2 步加介面時再改成模組（`moduleOffNoTrace` 的規則屆時適用）。
  目前由 `distributedSyncOff.test.ts` 守住：關閉時不能開節點、沒有任何檔案在自己的資料夾外 import 它、不是已註冊模組、引擎不 import `db.ts`／`spine`／`routes`／`services`（除了合併用的 `eventLog`）。

**不做（beta 明確排除）：** 介面；真傳輸（HTTP、信箱、WebRTC）；簽章與金鑰（目錄只是配對時的約定）；附件與圖片；擁有者轉移；快照與壓縮；
屬性、白板、手寫、任務等其他資料型別（2a 起「擷取不了的事件」會被計數，見 §12）；AI 工作階段。

## 10. 已知問題與限制（誠實清單）

**測試台在開發中找到並已修的引擎問題（都是縮減後 1–2 步的最小重現）：**

- **被撤權的節點收不到「撤銷自己」那筆操作**：收方檢查把它當成「這個空間我讀不到」而拒收，該節點永遠以為自己當時的修改有效。修正：曾經可讀的節點一定收得到「關於自己的人」的成員變更（`ingest` 的 `aboutMe`）。
- **第一版的修正太寬**：只要節點持有該空間的任何一筆操作（包括自己被改過的用戶端寫的），就接受「關於自己」的成員變更，結果收下一筆沒有上下文（沒有空間建立操作）的成員操作。修正：必須「在這批之前，我的某個人已經是該空間的可讀者」。

**目前未解決的：**


1. **沒有簽章：** 目錄只檢查「作者屬於來源節點」，一個被配對的惡意節點仍可偽造它自己的人的任何操作（不能偽造別人的）。測試涵蓋的是「被改過的用戶端」與假作者，不是密碼學對手。
2. **因衝突被判無效的操作不轉送**，只留在作者節點：其他節點查不到「有人想把 A 移到 B 底下但因成環被丟掉」。第 2 步考慮把它作為純資訊轉送（不影響狀態）。
3. **折疊成本與 `have` 是 O(總操作數)**：每次載入都重算；沒有快照、壓縮或修剪。夠 beta（幾百到幾千筆），不夠真工作區。
4. **時鐘偏差決定併發結果**（§3）；10 分鐘的上限只擋離譜的情況。
5. ~~與現行權限政策沒有一致性測試~~ **2a 已補**（§5）。仍成立：在影子比對看夠久之前，不得切換任何使用者的行為。
6. 新成員會收到該空間的完整歷史（含其他成員的名單與已刪除的內容）；撤權收不回已送出的資料。
7. 每個內文操作帶 `before` 全文，大筆記的操作會變大；可改成帶雜湊＋補丁，需先量測。
8. 這一步只跑 PGlite（同步表）。真 Postgres 上的引擎有遷移後整合測試（`distributedSyncMigration.integration.test.ts`），尚無多節點的真 Postgres 實跑。

### 12.3 規模量測

`distributedSyncScale.integration.test.ts`（PGlite、單一行程、兩個節點、每篇 30 行、每次改一行；寫入與追上都經完整的真服務，所以絕對值偏慢，重點是趨勢）。
`DS_SCALE_NOTES=N DS_SCALE_EDITS=M` 指定規模；1,000×10 實跑完成（總共 405 秒，沒有超過 30 分鐘），不需要換算。

| 規模 | 創世匯入（規劃） | `ds_ops` 筆數 | 每次寫入（含擷取） | 第二個節點追上 | 折疊全部操作 | 冷開節點 |
| --- | --- | --- | --- | --- | --- | --- |
| 40 篇 × 3 次 | 4 ms（46 筆創世操作） | 166 | 22.5 ms | 0.97 秒（約 6 ms／操作） | 約 0 ms | 6 ms |
| 300 篇 × 10 次 | 7 ms（306） | 3,306 | 21.1 ms | 44 秒（約 13 ms／操作） | 2 ms | 75 ms |
| 1,000 篇 × 10 次 | 15 ms（1,006） | 11,006 | 22.8 ms | 168 秒（約 15 ms／操作） | 8 ms | 274 ms |

- **每次寫入多花的時間（擷取）**：同樣的「讀一次內文＋`updateNode`」不開同步，300×10 是 16.8 ms／次；開同步 21.1 ms，**多約 4–6 ms（約 25–35%）**，1,000×10 時 22.8 ms。
- **追上**：第二個節點每筆操作要走投影（取事件鎖、經 `updateNode`／`createNote`、寫事件），是最貴的一步，成本隨操作數**近似線性**（約 13–15 ms／操作；6 ms 是小規模的固定成本被攤平前）。
  每輪最多 100 筆，11,006 筆至少 111 輪（測試的輪數上限因此改成依操作量）；實際輪數未逐項記錄。
- **折疊**：8 ms（1.1 萬筆）。折疊本身在這個規模不是問題；§10-3 的 O(總操作數) 在數十萬筆之前不會是瓶頸，但沒有量到那麼大。
- **創世**只讀幾張表，1,000 篇 15 ms；`openTwoNodesWithGenesisMs` 約 3.6 秒主要是建兩個資料庫。
- **什麼時候變慢**：新節點第一次加入或離線很久，要投影的操作數 × 約 15 ms：1 萬筆約 2.5 分鐘，10 萬筆約 25 分鐘（外推，未實測）。
  每篇帶 `before` 全文（§10-7）使 `ds_ops` 隨「筆記大小 × 修改次數」成長；大筆記、高頻修改的工作區應先做快照／壓縮（§11-5）再放進真使用。這是 PGlite 數字，真 Postgres 預期較快，但未量。

### 12.4 已知限制（2a 新增）

- 只涵蓋 §12.1 的資料種類；其餘事件只計數，**不同步**。因此 2a 不得用來取代 `/api/sync`。
- slug 在節點間可能不同（§4.4）；內文衝突仍是 diff3 的結果。
- 被刪筆記的內容不即時對齊，復原時才補。
- 創世的作者是各空間擁有者（見下），所以創世匯入不能回答「誰建立了這篇筆記」。
- 沒有簽章（§10-1），沒有真傳輸，沒有真 Postgres 多節點實跑（§10-8）。

### 12.5 請審查：兩個設計取捨

**一、`spine/replicatedOp.ts`：被引擎判為有效的操作，其作者可通過 `assertAuthority` 與空間存取。**

- 為什麼：引擎以操作在全序中的位置判斷權限（撤權前的修改在所有節點都有效）；若重播時再問「今天的成員表」，先聽到撤權的節點會拒絕這筆操作，節點就不再一致。
- 範圍：只在 `withReplicatedOp()` 作用域內、只對「被指名的作者」、不接受帶 token 的 actor；事件鎖、同交易寫事件、`membership_epoch`、連帶操作都照舊。
- 風險：若有別的呼叫者取得這個作用域，就能繞過本機政策。擋法：(1) `distributedSyncOff.test.ts` 掃描全部原始碼，只有 `bridge/project.ts` 與定義檔能含 `withReplicatedOp`；(2) 關閉時 `Replica.open` 在任何查詢前就拋 `DistributedSyncOff`，而投影只被 `Replica` 呼叫，路徑不可達；
  (3) 新測試 `replicatedOpBoundary.integration.test.ts` 證明：檢視者沒有引擎判定時被拒；判定指名別人時被拒；帶 token 時被拒；只有被指名的作者在作用域內通過；作用域結束後立刻又被拒。
- 審查後修正：重播的作者只跳過空間與筆記的權限；**工作區設定的擁有者規則（設定筆記、設定標籤）照樣檢查**（`assertReplicatedConfig`），因為引擎不認得這條規則，否則別台節點的編輯者可借此改設定。
  **尚未做**：引擎自己也要照這條規則判定，否則它會把這類修改判成有效、投影時才失敗，只記在 `ds_projection_failures`，各節點狀態可能不一致。
- 剩餘風險：`project.ts` 本身若把錯誤的 `author` 傳進去（例如沒經引擎驗證的操作）就會放行——投影只處理 `materialize` 的有效判定，這靠審查與影子比對，不是型別保證。

**二、創世操作的作者是各空間的擁有者，不是各筆記的建立者。**

- 為什麼：創世必須是「資料列的純函式」，兩份同一伺服器的複本才會導出相同操作；現有資料表沒有可靠的「建立者」欄位（`domain_events` 可能已被修剪）。
- 風險：創世之前的作者歸屬在同步後的歷史顯示不準；並且若擁有者之後被撤權，創世操作仍在全序最前面，不受影響（創世的 HLC 是最小值）。創世之後的操作作者都是真實的人。

### 12.6 2b 需要的東西

1. **HTTP 傳輸**：實作 §6 的傳輸抽象（拉取／推送、信箱），沿用冪等鍵；擷取失敗與重送不得吞掉有效操作；認證用現有 token／session，節點身分配對。
2. **伺服器節點**：星狀拓樸的中心；伺服器端節點的 `Replica` 常駐、擷取與投影在背景工作（走既有 outbox／job 機制，不另開提交流程）；`/api/sync` 與節點並存期間的切換與關閉開關。
3. **桌面版配對**：配對流程（目錄＝配對時的約定，§10-1）、離線很久的新節點如何追上（§12.3 的外推顯示需要快照）、配對與撤銷的介面（使用者可見文字須符合 UI 規則）。
4. 之後：簽章（§11-4）、快照／壓縮（§11-5）、屬性／任務／白板／手寫／附件（2c–2g）。
