## 0. 業主已決定的前提（2026-11-15）

1. Onden **沒有代管服務**：專案只營運碰面點與下載頁，不碰別人的筆記。沒有伺服器的路（瀏覽器版、桌面版、手機）是主產品，自架伺服器只是使用者自己多擁有的一個完整節點。
2. 「掃 QR 加入第二台裝置」要盡早能測，分兩段：**第 1 段**＝新裝置一次拿到整個工作區；**第 2 段**＝兩台之後持續互換修改。
3. 選 A：第 1 段傳的是**保留每一列來源標記（來源、序號、邏輯時鐘）的快照**，不是一般備份。這樣兩台複製後各自寫的東西，第 2 段來時還合得起來。

備份刻意不帶標記，已查證：`packages/backend/src/test/syncStamps.integration.test.ts` 的「stamps and the structure log are in no note response, no sync content and no backup」逐字檢查備份 zip 內每個檔案不含 `sync_stamps`、`hlc_wall`、來源編號；
`services/backupArchive.ts` 的備份只有 `.onden/notes/<id>.json`、`spaces.json`、`extras.json`、`manifest.json`；`services/backupRestore.ts` 還原時一律走領域寫入入口（`createNote`、`setNodeAttribute`…），所以**每一列在新裝置上都蓋上新裝置自己的新標記**。備份是「重新建立一份內容」，不是「複製一份狀態」。

## 1. 使用者看到什麼

情境：使用者有一台已在用的裝置（電腦的瀏覽器版、桌面版，或自架伺服器的網頁），想讓另一台裝置（通常是手機）也有完整的工作區。

| 步驟 | 已在用的裝置 | 新裝置 | 還沒完成／中斷時 | 失敗時 |
|---|---|---|---|---|
| 1 | 設定 › 裝置 › 「加入另一台裝置」。說明一句：「會把你有權看的全部筆記複製過去。」按「開始」→ 顯示 QR | 打開 Onden，空白狀態按「這是新裝置，加入我已有的筆記」→ 相機 | QR 10 分鐘後失效：「這個 QR 過期了，重新產生一個。」 | 相機被拒：提供手動輸入代碼 |
| 2 | 「等待另一台裝置掃描…」 | 掃描後顯示「請對照另一台裝置上的六個數字」＋六位數 | 一直沒人掃：維持等待，可取消 | QR 已被別台用過：「這個 QR 已被另一台裝置使用。如果不是你，請取消並重新開始。」 |
| 3 | 顯示六位數與「你要把全部筆記交給剛掃描的那台裝置。兩邊數字一樣才按『一樣，開始複製』」 | 「等另一台裝置確認…」 | 2 分鐘沒按：自動取消，**沒有任何筆記傳出** | 數字不同：按「不一樣」→ 兩邊都顯示「已取消，沒有複製任何東西。可能有人想冒充，請換個地方重做。」 |
| 4 | 「複製中：已完成 40%。請保持這個畫面開著。」 | 同樣的百分比；筆記先到、附件後到。 | 見下一欄 | |
| 5 | 「完成。新裝置已經有你的全部筆記。」＋第 5 節的提醒 | 自動打開工作區：「已複製完成」；附件還沒到的顯示「附件還在複製」 | | |

- **中斷**（任一台關掉分頁、斷網、休眠）：
  - 已在用的裝置離線：新裝置顯示「另一台裝置暫時連不上，連上後會自動繼續。已複製的不會重來。」
  - 新裝置關掉再開：顯示「這台裝置只複製了一部分（40%）。請到另一台裝置按『繼續』。」**這台在複製完成前不能當一般工作區使用**（只有這個畫面與「取消」）。
  - 取消：新裝置把已收的內容**全部清掉**，回到空白；已在用的裝置不受影響。
- **失敗的白話**（`lib/serverErrors.ts` 以外不寫新字串）：空間不夠（沿用 507「空間不夠存放…，沒有儲存任何東西」）；
  資料損壞（「收到的資料有問題，沒有加入任何東西，請重試」）；兩台版本不同（「兩台裝置的 Onden 版本不同，請先把比較舊的更新」）；
  碰面點逾時（「傳送逾時了，已複製的會保留，請重新按『繼續』」）；新裝置不是空的（「這台裝置已經有筆記，不能加入。請用全新的瀏覽器或清空後再試」）。
- UI 不出現「快照」「標記」「節點」「裝置編號」。

## 2. 信任方向

「傳到我的手機」是**不可信的頁面 → 可信的手機，單向**：頁面是借來的電腦，只准給東西、拿不到任何東西。
這裡是反過來：**已可信的裝置把整個工作區交給一台新裝置，新裝置之後也完全可信**（它能寫、之後能收別台的修改）。後果與要守的事：

| 問題 | 答案 |
|---|---|
| 六位數保護什麼 | 擋「碰面點或旁人把雙方公鑰掉包」。沿用 [配對與加密](../send-to-phone-crypto.md) 的導出：兩邊由同一份交換紀錄各自算出，掉包就不同 |
| 誰要按確認 | **已在用的裝置**（資料給出去的一方）。這和傳到手機相反（那裡是手機按）。**在它按下之前，已在用的裝置一個資料物件都不上傳**（只有配對用的 hello）；這是新增的規則，要有測試：確認前碰面點上除了 hello 沒有任何物件 |
| 拿到 QR 照片的人能做什麼 | 能搶先掃（hello 先到先得）。搶到了，**真的新裝置會收到「已被使用」**，使用者會停下；已在用的裝置顯示的六位數對不上任何一台，按「不一樣」即可。搶到也**拿不到資料**，因為資料要等確認才上傳。能 10^6 分之一碰運氣猜碼：每個 QR 只有一次配對，猜不到第二次 |
| 拿到照片但沒搶到 | 什麼都做不到：QR 只含碰面點網址、工作階段編號、一次性公鑰，沒有秘密 |
| 使用者沒對照就按確認 | **擋不住**（人為）。畫面文字要講清楚「你正在把全部筆記交出去」；2 分鐘內沒按就取消。自架伺服器網頁版建議再要一次密碼（第 10 節 5） |
| 裝置標籤（「我的 Pixel」） | 由新裝置在配對完成後以加密訊息送來、在已在用的裝置顯示；視為不可信文字（只當純文字顯示，限制長度） |

**之後怎麼移除一台裝置**（兩種做法比較）：

| | 每台裝置各自一把金鑰（建議） | 全部裝置共用一把 |
|---|---|---|
| 加入 | 新裝置自己產生金鑰；已在用的裝置把資料金鑰用新裝置的公鑰包一份給它 | 把那把秘密交給新裝置 |
| 移除一台 | 換新一代資料金鑰，包給**其他**裝置；被移除的拿不到之後的新資料（對應 [分散式準備 4.1](distributed-ready-2026-11-12.md)「撤權只對之後有效」） | 換金鑰＝每一台都要手動重新交付，等於重新配對所有裝置 |
| 遺失／被偷 | 只移除那一台 | 全部重來 |
| 代價 | 要一份「裝置清單」資料 | 最簡單，但沒有移除這件事 |

這屬於 [節點同步 §6](node-sync-channels-2026-11-14.md) 已定的方向（資料金鑰＋各裝置金鑰包起來＋世代）。**現在就要定、之後很難改的**：
(1) 裝置清單的一筆資料長什麼樣（節點編號、公鑰欄位、金鑰世代、加入時間、由誰加入、顯示名稱）；
(2) 加入時的最終清單（final manifest）帶「金鑰世代」欄位，第 1 段填 0 並不使用；
(3) 新裝置在第 1 段就產生並保存自己的裝置金鑰，只是還不用來加密（為了第 2 段不必再掃一次）；
(4) 移除時要被拒收的是「節點編號」，與下一節的身分一起記。
第 1 段**不做移除**，畫面老實寫：「目前還不能從這裡移除裝置；已複製過去的內容收不回來。」晚到的撤權怎麼讓之後的寫入作廢，仍是 [分散式準備 §5](distributed-ready-2026-11-12.md) 的未解題。

## 3. 快照：三種做法

先看現況，再比較。

**現況**（都讀過程式）：
- 標記表 `sync_stamps`（每列或每欄位一筆）、`sync_clock`（每個工作區的下一個序號與時鐘）、`sync_node`（這個資料庫一個節點編號）、`structure_log`（只增不減的舊值→新值）。
- 標記**只有一個交易一個**的進入方式：`spine/stamps.ts` 的 `stampTransaction`（本機）與 `adoptForeignStamp`（別的節點的標記原樣收下，序號不動、時鐘往上推到至少收到的讀數）。後者一次只能設一個標記，註解寫明「之後才用」。
- `syncClasses.json`：15 張表是「要標記且已接線」（`content_nodes`、`node_attributes`、`node_tags`、`node_edges`、`note_pointers`、`node_positions`、`spaces`、`space_members`、`function_refs`、`actor_module_settings`、`rss_mutes`、`rss_subscriptions`、`external_calendars`、`workspaces`、`block_node_tags`）；
  **9 張是要標記但還沒接線**（`block_anchors`、`block_link_bindings`、`focus_sessions`、`review_states`、`actor_prefs`、`rss_seen`、`ai_edit_suggestions`、`ai_edit_suggestion_items`、已移除的 `read_later_done`）；**24 張還是「未決定」**（多半看起來是節點自己的：`push_subscriptions`、`agent_tokens`、`ds_*`…）。
- S5（#1684，**已合併並上線**；本文寫作時尚未合併）：每個現存單位補一筆創世標記（來源 `genesis`、序號 0、時鐘 0/0、無作者、無裝置），並記下基準結構；兩個節點各自補的結果逐位元相同。

| | (a) 備份＋標記附檔，走現有還原 | (b) 逐列帶標記的快照格式（同時是節點同步 §4 的「快照」） | (c) 「自某個進度以來的帶標記變更」單一讀取介面；快照＝從空進度讀起 |
|---|---|---|---|
| 已有 | 備份寫出與還原、合併式還原、整批可復原、版本歷史（格式 3） | 標記表與觸發器、`adoptForeignStamp`、`syncClasses.json` 分類、`readPolicy` 的讀取範圍 | 同 (b)，另加「進度」概念 |
| 新做 | 標記附檔的寫出；還原後把標記改寫成來源的；工作區 id 對齊 | 逐表匯出器、逐列匯入器、檔頭（進度、格式版本）、分頁 | (b) 全部，加上「自進度以來」的條件（`stamp.seq > 進度[來源]`） |
| id 保留 | 空工作區還原「id 空著就沿用」，其他情況換新 id（`backupRestore.ts` 檔頭）；衍生 id（migration 201，由工作區 id 算出）與逐裝置／逐人的列要靠額外對應；**新工作區的 id 與來源不同**（還原做的是新工作區），而標記以工作區 id 為鍵 | 列原樣複製，id 不變；工作區 id 與人的 id 必須在加入時對齊（第 4 節） | 同 (b) |
| 歷史與版本（§5） | 備份格式 3 已能帶每個儲存（種類、標題、內文、原始時間）；還原時重寫成「備份匯入」事件，**事件編號與來源不同** | 分層：版本另成一層分頁，同樣用來源事件編號當冪等鍵 | 同 (b)；版本的身分（雜湊＋來源標記）第 2 段共用 |
| 附件與手寫 | 備份帶 `attachments/`（zip）；手寫在筆記屬性（`ink_data`）與 blob 裡，已含 | 附件按內容雜湊／媒體 id 分層取；手寫是屬性值，隨列走 | 同 (b) |
| 線上大小 | 每則筆記存兩份（vault 的 `.md` 與 `.onden/notes/<id>.json`）；zip 壓縮；沒量 | 每列內容一份＋每個標記一小列（估每筆約百位元組，**沒量**）；分頁壓縮後再加密 | 同 (b) |
| 手機記憶體 | 瀏覽器版的備份是**整個 zip 在記憶體**（`browser-shims/archiver.mjs` 讀完串流再加；IndexedDB 路徑附件整檔進記憶體，見 [瀏覽器版](../browser-app.md)），還原再疊上資料庫本身 | 一次只處理一頁（≤ 4 MiB 解壓前）＋資料庫；可以邊收邊寫 | 同 (b) |
| 能不能續傳 | 備份是一整包，中斷＝重來（還原作業有 job，但來源檔要先收齊） | 每頁有編號，已套用的頁記在新裝置；從缺的頁繼續 | 同 (b) |
| 第 2 段能重用多少 | 幾乎不能：還原路徑不產生來源標記；第 2 段要另寫一套 | 讀取側的欄位與標記格式、匯入側的「收到的標記原樣寫入」可原樣用；但「快照」與「之後的修改包」是兩種形狀 | **最多**：第 2 段只是用非空的進度再讀一次，匯入側不變 |
| 主要風險 | 還原時 id 與標記都被重寫，之後兩邊同一列會被當成兩個東西；備份已知缺口（白板分區尚未還原、成員不重建、`_` 開頭多數屬性不帶）直接變成兩台資料不一致 | 兩種形狀要維護；快照分頁讀取不是原子的（來源邊傳邊被編輯） | 同 (b) 的非原子問題，但用「進度取在讀取開始時」解掉（下） |

**不選 (a) 的理由，一句話**：備份的設計目標就是「不帶來源資訊、重新建立」，要把它改成「複製狀態」等於把它改成另一個東西，而且第 2 段完全用不到。
**另一個被丟掉的方向**：整份資料庫檔直接複製（PGlite 的 `dumpDataDir`，約 60 MiB 未壓縮／6 MiB 壓縮，來自 [瀏覽器版](../browser-app.md) 第 4 節）。快，但連 `sync_node`（節點編號會相同）、`domain_events`（事件不外傳的原則）、登入、金鑰、冪等鍵一起複製，伺服器的 Postgres 與瀏覽器的 PGlite 也不通用。

**建議：(c)，以 (b) 的格式實作。** 即：一個讀取介面 `自進度 P 以來、這位操作者讀得到的、帶標記的列`，P 為空就是快照。理由：第 2 段整個接收端不用重寫；格式只有一種；第 1 段的所有測試（逐表逐列相等）第 2 段繼續用。

### 進度（cut）與為什麼讀取不需要鎖住來源

來源在複製期間會被繼續編輯。做法：**讀取開始時記下來源自己的序號頭 `H`**（`sync_clock.next_seq - 1`），整個傳送期間分頁讀取不要求一致的交易快照。
理由：複製期間發生的任何修改，標記序號都 `> H`；新裝置收到的進度是 `{來源: H}`，第 2 段問「序號大於 H 的」就會補到，頁面讀到較新版本也無妨（套用時只收「標記比現有的新」的）。
這是第 1 段必須**持久保存**的唯一新狀態（`join_record`：來源節點編號、進度向量、加入時間）；來源是已經收過別台修改的節點時，進度要涵蓋每個來源，這需要第 2 段才會有的「已收到哪裡」表，所以**第 1 段只支援來源從沒收過別台標記，或來源本身就是以 `join_record` 加入過的裝置**（後者進度＝它的 `join_record` 加上自己的頭）。

### 接收端怎麼寫入：一個受保護的入口（審查後改定）

~~原案「依標記分組、用現有觸發器重放」~~**不成立**（審查者讀 `190_sync_stamps.sql` 第 153–155 行與第 234 行的 `WHEN`）：觸發器只在欄位值**真的變了**（`IS DISTINCT FROM`）時才蓋該欄位的標記。快照只有最終值，所以「先用最舊標記建列、再 UPDATE 較新標記的欄位」時值已經是最終值，觸發器不會動，**被編輯過的欄位會悄悄留著舊標記**；
而且依標記由舊到新排列也排不出外鍵順序（父列的每個欄位都被晚改過時，它的「最舊標記」比子列新）。

**兩種草圖**（[設計原則](../../agents/design-principles.md)要求）：

| | 草圖 A：`spine/` 的受保護入口，函式直接寫列與標記 | 草圖 B：觸發器改成讀「暫存標記表」 |
|---|---|---|
| 做法 | 一個函式：同一交易內依外鍵順序寫列，再把 `sync_stamps` 列原樣寫入；該交易設一個只有這個函式能設的旗標，觸發器看到旗標就不動 | 先把收到的標記放進暫存表（列鍵→標記），再寫列；觸發器遇到暫存表有該列就用那組標記，不產生新標記 |
| 與 `mutate` 的關係 | 並列：不經 `mutate`、不寫事件、不查一般寫入的權限；**授權來自「已確認的加入中狀態」**，不是來自某個操作者的能力 | 同左，但多一條觸發器分支，每次一般寫入都要多查暫存表 |
| 誰能呼叫 | 只有加入流程（`join` 服務）；函式第一行檢查：工作區是空的且處於「加入中」，否則丟錯；不接受外部傳入的工作區狀態 | 同左，另外暫存表的寫入也要受限 |
| 守門怎麼擋別人用 | (1) ESLint／守門測試：整個 repo 只有 `join` 服務可以 import 它；(2) 旗標名稱與計數進 `stampedWrites.guard.test.ts`，次數只減不增；(3) 整合測試：一般 `mutate` 交易、非加入中的工作區、非空工作區呼叫都丟錯，且旗標不會在交易結束後殘留 | 要擋兩處（暫存表與觸發器），且「一般寫入路徑被暫存表影響」難以證明不發生 |
| 代價 | 新增一個明列的繞過寫入入口 | 改動每次寫入都會跑的觸發器，風險面更大 |
| 選擇 | **採用（符合審查要求）** | 不採用：把例外放進熱路徑 |

改為：`spine/` 內**唯一一個**受保護的入口（暫名 `applyJoinRows`，草圖 A），在同一個交易裡**依外鍵順序**（空間與標籤 → 筆記由父到子 → 其餘）寫列，並把 `sync_stamps` 的列**照收到的原樣**寫入，這個交易內觸發器讓開。性質：
- 是**看得見、有計數的例外**（比照 `allowUnstampedWrite`），次數進守門測試；只在「加入中」狀態、**空工作區**開放，別處呼叫就丟錯。這是對 AGENTS.md「寫入走 `spine/mutate.ts`」的一個明列例外，要由審查（第 8 節）確認它不能被一般寫入路徑呼叫。
- `adoptForeignStamp` **仍然只負責推進時鐘**：整批用該批最高的時鐘讀數呼叫**一次**（含第 4 節的上限檢查）；它不是逐列的機制。
- `structure_log` 不從快照重建（它不外傳）：加入時的基準照 S5 的方式在新裝置上取。
- 階段 0b 的實驗要量**這條路徑**（1,000 則筆記的時間與記憶體），不是分組重放。


契約與呼叫範例（只寫形狀）：

```ts
// spine/joinRows.ts：只有 join 服務 import；只在「加入中」的空工作區。整批的標記照收到的寫入。
applyJoinRows(join: JoinCtx, page: { rows: { table: string; key: string; values: Json | null; stamps: Stamp[] }[]; maxWall: number }): Promise<void>;
// 呼叫（在 join 服務的一個交易裡）：
await withEventTransaction(ws, async () => {
  await assertJoining(join);                 // 空工作區、加入中，否則丟錯
  assertWithinClockBound(page.maxWall);      // spine/stamps.ts：超前 > 10 分鐘整批拒收
  await applyJoinRows(join, page);           // 寫列＋標記，觸發器讓開，計數進守門
  await advanceClockOnce(ws, page.maxWall);  // 即 adoptForeignStamp 的時鐘推進，整批一次
});
```

衍生資料（內文連結索引、嵌入、區塊參照、自動連線、由內文算出的屬性）**不傳**，加入完成後由新裝置自己重算（[來源標記 §4.2](causal-stamps-2026-11-12.md)）。

## 4. 節點身分

- **新裝置自己的節點編號與序號**：`sync_node` 的節點編號是每個資料庫自己產生一次（`db.ts` 開機時 `INSERT … gen_random_uuid()`；`spine/stamps.ts` 對本機寫入用它與該工作區的 `next_seq`）。
  **主線現在就有的錯（審查者（note-cf）已讀程式確認，沒執行）**：瀏覽器版第一次開啟從建置時做好的 `snapshot.tar.gz` 起步，`browser/prepareSnapshot.ts` 先呼叫 `migrate()`，`db.ts:433` 在那裡建立 `sync_node`，所以**每個瀏覽器版副本都有相同的節點編號、工作區 id、本機人的 id，`sync_clock.next_seq` 也從同一個數字起跳**。
  兩個獨立副本已經會產生**同一個 `(來源, 序號)` 卻內容不同**的標記——標記絕對不能發生的事。這與加入裝置無關，業主的測試副本已經帶著它。
  **前置條件：PR #1706「瀏覽器版每份副本有自己的節點編號」**（業主與 note-cf 已談定；本提案不設計它，只依賴它的保證）：
  (1) 打包的快照不帶節點編號，每份副本**第一次開機**取得自己的編號；
  (2) 舊副本**下次開機換一次**，並在**同一個交易裡**把 `sync_stamps` 上舊的共用編號改成自己的新編號（序號與時鐘不動），所以**沒有「停用編號」清單**，不需要記哪些來源已退役；
  打包時就存在的列（`prepareSnapshot` 寫的工作區資料列）要改蓋**創世標記**，所有版本、所有副本都相同；舊副本上這些列會是它自己的編號（它分不出哪些是打包的）。這**不放在 #1706**，而是等 #1684（S5，定義創世標記的 `sync_genesis_pass()`）合併後另開一個**跟進 PR**：讓 `prepareSnapshot` 清掉建置時的標記並呼叫同一個函式，避免兩份定義。
  **所以 1a 的前置條件是三個：#1684、#1706、這個跟進 PR；三個都合併前 1a 不開工。**（狀態：#1684 與 #1706 已合併並上線；第三項「打包列蓋創世標記」**還沒做**，由 note-cf 接著做。）
  **匯出端允許的來源只有兩種**：這個節點自己的編號、創世標記；其他來源一律當成外來的並拒絕匯出（第 1 段）。
  **匯入端的一般規則**：內容相同就不算衝突，不管標記是否相同。
  **`structure_log` 永遠不離開裝置**：它只能新增，舊的幾行仍帶著共用編號；任何匯出、比對都不得使用它的來源欄位。
  各副本的工作區 id 相同對加入無害（空殼本來就改用來源的），但**不得依賴它**。
- **收下別人的標記不重新編號**：[同點並行插入的研究](../../research/eg-walker-bench/tiebreak-findings.md)的結論 4 要求來源標記的序號是**來源節點自己的真實流水號，不得在接收端依到達順序重編**。
  所以快照裡每個標記的 `(來源, 序號, 時鐘, 作者, 裝置)` 原樣寫入；新裝置自己的序號 `next_seq` 不動，時鐘用 `receive` 推到至少是收到的最大讀數，使它之後寫的東西排在所有已收到的之後。
  **時鐘上限（審查者（note-cf）的審查，必須做在 `spine/stamps.ts`，不是畫面）**：`hlc.ts` 的 `receive()` 沒有上限（`wall = max(本機, 收到, 現在)`），一個來自遙遠未來的標記會把這個節點的時鐘永遠推到那裡，它之後每一次寫入都「贏」。所以：
  (1) **整批最高的 wall 比本機 `Date.now()` 超前超過 10 分鐘，就整批拒收（一筆都不寫），在呼叫 `adoptForeignStamp` 之前**，放在 `spine/stamps.ts`。理由：兩台正常裝置的時鐘差是秒級，設錯時區之外的手動誤設多在分鐘級；10 分鐘比第 5 節的 5 分鐘警告寬（被警告後仍可用，不會被硬拒），又遠小於會讓一台時鐘「永久領先」的程度。落後的標記（舊標記）不拒。測試要涵蓋：剛好門檻（收）、超過一毫秒（拒收且時鐘與資料都沒動）、落後很多（收）、整批只有一筆超前也整批拒收。
  (2) 加入時的「兩台時鐘差超過 5 分鐘」警告只是上面一層的 UX，且**在已配對的通道裡**比對兩台的牆上時間；**它偵測不出「過去曾經錯過的時鐘」**，舊標記的讀數照舊。
- **S5 必須先做完**：沒有創世標記的列在來源上是「標記未知」，新裝置若自己補創世標記，雙方不對稱。S5（#1684）在兩台各自補的結果逐位元相同（來源 `genesis`、序號 0、時鐘 0/0），快照原樣帶過去即可。**S5 的 migration 在線上資料庫要等業主看過預覽數字同意才上**，這是第 1 段處理真實資料的前提。
  新裝置開機時 S5 的 migration 對空工作區沒東西可補；加入完成後不再補。
  凡是會再次執行 `sync_genesis_pass()` 的東西（`order_key` 接管 #1595 會）**不得在「加入中」狀態的裝置上執行**。來源端的匯出器要**檢查而不是假設**自己從沒收過別台的標記：`sync_stamps.origin` 出現本機節點編號與 `genesis` 以外的值就拒絕匯出（#1706 之後舊的共用編號已被改成各自的編號，所以只剩這兩種），並用一句白話說明（第 1 段的限制，見第 3 節進度）。
- **工作區 id 與人的 id 必須與來源相同**：標記以工作區 id 為鍵，衍生 id（migration 201）由工作區 id 算出，作者欄位是人的 id。新裝置的「空殼」要先把這兩種 id 換成來源的，並**刪掉殼裡原有的衍生列**（預設空間、個人空間、收件匣標籤…），否則兩台各有一份、id 又不同。這是第 1 段最不確定的一步（瀏覽器版能不能開成真正空的工作區：沒查）。
  **人的身分要改寫哪些列**：瀏覽器副本有自己的 `LOCAL_ACCOUNT`（登入程式的 `user`、`account` 列與一個對應的 `actors` 列）。加入時：新裝置的 `actors` 那一列的 id 改成來源的「這個人」的 id（連同所有指向它的欄位，例如各列作者、個人空間 id 的衍生來源）；**登入程式的表（`user`、`session`、`account`、`verification`）不從來源複製**，保持新裝置自己的、只把本機登入對應到改寫後的 actor。其他人（多人工作區）只帶顯示用的名字，不帶登入。這是第 1 段最容易出錯的改寫，要列出每個被改寫的表與欄位並逐一測試。

## 5. 第 1 段與第 2 段之間

兩台都能編輯，但還沒有東西互換。**精確地說**：

| 內容 | 之後合併會發生什麼 | 保證嗎 |
|---|---|---|
| 一台新增、另一台沒有的列（新筆記、新標籤套用…） | 直接加進另一台。自動建立的唯一項目（收件匣標籤、日記、各空間任務筆記、預設空間…）id 由工作區算出（migration 201）所以兩台各建一次仍是同一列 | 保證（以 id 為準） |

| 內文兩台都改 | 三方合併。**基底的身分＝（內文雜湊，加上該筆記內文欄位在切點（cut）時的標記）**，不用事件編號（兩邊的事件編號不同）。加入時新裝置把每則筆記的內文寫成一個版本，帶這個雜湊；來源端以同一個雜湊在自己的版本裡找得到，**兩邊都找得到同一個基底才自動合**，第 2 段用雜湊與標記去找，不靠事件編號。改到同一行就問人，其餘自動合（[內文合併](body-history-merge-2026-11-14.md)、`BODY_MERGE_RULE_VERSION`） | 保證有基底的情況；任一邊找不到基底（被修剪、缺漏）就**不自動合**，兩份都留（另存成「另一台裝置的版本」），不丟任何一邊的輸入 |
| 一邊刪、另一邊改 | [分散式準備 4.9](distributed-ready-2026-11-12.md) 已決定：刪除生效，改的字進垃圾桶並通知 | 規則已定，機制第 2 段才有 |
| 同層排序、同名標籤、網址代稱、同名檢視、兩台各開專注、搬動造成迴圈 | 4.2、4.3、4.4、4.7、4.8、4.10 各有決定 | **同層排序：不保證**，在 `order_key` 之前兩台各排過的順序會交錯；第 2 段在它之後才開 |
| `function_refs` 兩台各建同一個引用 | id 仍是隨機（[分散式準備 4.5「還沒做」](distributed-ready-2026-11-12.md)），自然鍵 `(持有者, 功能, 實例)` 唯一，**合併時會撞唯一限制** | 不保證；規則：以較早標記的那一列為準、另一列的 `config` 逐鍵合進來。要在第 2 段前決定 |
| 9 張還沒接線的表（複習進度、偏好、專注、錨點與連結綁定、已讀、待決定的 AI 建議） | 都**帶**（第 4 節），帶著等同創世的標記；沒有真標記就不知道誰較新，兩邊都改過時標記相等 | **不保證**。最不壞的規則：個人資料（複習、偏好、已讀）改用「列上最後修改時間」並明說這是裝置時鐘；錨點與連結綁定兩邊都留；AI 建議兩邊都留。要在第 2 段前把它們接線，不然合併結果就是這張表說的 |
| 事件（操作紀錄）與 `structure_log` | **不傳**（[節點同步 §5](node-sync-channels-2026-11-14.md)），所以新裝置的「復原」只能復原它自己做的事，「回到某一天」只回到加入那天（基準在加入時取，同 S5） | 這是設計，不是缺漏，但畫面要說 |

**這段期間畫面怎麼說**（設定 › 裝置、工作區頂端一個可關閉的提示，只講事實、不用「同步」二字）：
「這台裝置是從『我的電腦』複製來的。兩台現在各自保存，**修改不會自動傳給對方**。之後的版本會把兩邊合在一起；現在在兩台改同一則筆記，合併時可能要請你決定。」
第 1 段**不得**叫它「同步」或顯示「已同步」。

## 6. 通道

- **沿用不改**：[配對與加密](../send-to-phone-crypto.md) 的 X25519＋HKDF、六位數、分塊 AEAD、最終清單決定匯入什麼、碰面點 `packages/relay` 的介面與上限。**沒有自己寫密碼學**；加密與分塊仍然只經 `@onden/pairing`，快照只是被它當成「檔案」送的位元組。
  配對協定版本：主線的 `packages/pairing` 是 v1（邀請 `stp1:`）；**v4（加密回條 `r.receipt`、手機確認）只在 PR #1567**，還沒合併，且依第三次審查要有第四次獨立審查。這個提案**依賴 v4 的回條**（新裝置收完才讓來源說「完成」）。
- **分塊**在通道之上：每個頁面（≤ 約 4 MiB 解壓前、先壓縮再加密）是最終清單上的一個「檔案」項目，名稱如 `rows/0001`、`history/0001`、`blobs/<雜湊>`；**不新增項目種類、不動訊框**。
- **每個工作階段 200 MiB 的上限**（`packages/relay/src/limits.ts`：200 MiB、2,000 個物件、單物件 4 MiB＋1 KiB；同一來源位址每小時 10 個新工作階段；#1567 另加每位址 3 個未配對工作階段、合計 128 MiB）對真實工作區的意思：

| 方案 | 內容 | 評語 |
|---|---|---|
| 一次傳完 | 放進一個工作階段 | 筆記與版本多半放得下（**沒量**；備份的版本歷史預設在 200 MB 內才開），附件放不下 |
| 提高碰面點上限 | 改 `limits.ts` | 要重新審查與部署、增加營運成本與濫用面；**不建議** |
| 串接工作階段（建議） | 第一個工作階段的最終清單（已加密、已驗證）裡帶「下一個工作階段的邀請」（頁面的一次性公鑰＋新工作階段編號）；新裝置自動以 `acceptInvite` 接上，**不需再掃 QR 也不需再核對六位數**（邀請本身已在已驗證的加密通道裡） | 不改碰面點、不改協定；每個工作階段 ≤ 200 MiB；**這是配對的協定層行為（在已驗證的通道裡放新邀請），即使訊框不變也要列入第 8 節的獨立審查**；受每小時 10 個新工作階段限制（單一位址約 2 GiB／小時，夠用） |
| 附件之後再取 | 第一個工作階段只送筆記（含手寫屬性）與版本的第一層；附件、其餘歷史在加入完成後用串接的工作階段慢慢補，新裝置顯示「附件還在複製」 | 與上一列合用：**新裝置先能用，再補** |

建議：**串接工作階段＋附件與歷史放後面**，不改碰面點。順序固定：①筆記列（含基底版本）→ ②附件（按內容雜湊）→ ③其餘版本歷史；每層可獨立續傳。
- **同一個區域網路直接互傳**：之後的優化，不是這一版的條件。
- **瀏覽器版收資料時的存檔**：PGlite 在記憶體，副本是**整份**定期寫入（每次 `dumpDataDir`）。加入的匯入要像還原那樣在同一個工作內處理（`saveLoop.flushInJob`），**不要每頁都存**；改成每 16 MiB 或每 60 秒存一次，並把「已套用到第幾頁」放在資料庫裡，重開後從那裡繼續。（還原的各步驟不進日誌，所以不能靠日誌救。）

## 7. 兩端各在哪裡跑

頁面做配對、加密與上傳／下載；資料庫那一邊只提供「分頁讀取」與「分頁套用」兩個 API。所以**不論來源是哪種，同一個頁面程式**：

| 已在用的裝置（給） | 新裝置（收） | 第 1 段 | 理由 |
|---|---|---|---|
| 電腦的瀏覽器版 | 手機的瀏覽器版 | **第一個要測的組合** | 兩端都是同一套後端跑在頁面 Worker 裡（無伺服器主線）；不需要伺服器、不需要新後端路由 |
| 桌面版 | 手機的瀏覽器版 | 第二個 | 桌面版內含同一套後端；同上 |
| 自架伺服器的網頁 | 手機的瀏覽器版 | 第三個 | 要加一條伺服器路由供分頁讀取（同一個匯出器）；頁面經 VPN 取、經網際網路上傳 |
| 任一種 | 已安裝的 Android App | **不在第 1 段** | PR #1531（未合併）把 App 的畫面改成由「設定的伺服器」提供，原生端先探測 `/api/auth/providers`；沒有伺服器的使用者（瀏覽器版是靜態檔）這個外殼**現在連不上**，也沒有內建後端可當節點。要先決定 App 在無伺服器路線下是什麼（載入靜態的瀏覽器版？內嵌後端？）。我讀了 PR 說明，**沒有看原生程式碼，也沒有在裝置上試** |
| 任一種 | 桌面版／自架伺服器當新裝置 | 不在第 1 段 | 伺服器是已有登入與工作區的完整系統，「加入空殼」的前提不成立；桌面版可以是之後的一條 |

人與範圍：第 1 段只做「**本人加自己的第二台裝置**」。範圍＝這位操作者讀得到的（`readPolicy`；別人的個人筆記不含，垃圾桶只含他讀得到的）。多人工作區成員加自己的裝置同理；擁有者幫別人加裝置不在範圍。

## 8. 安全審查計畫

**兩個已存在、維持的閘門**：
1. 碰面點 Worker `onden-relay` **目前依業主同意關閉**；只有在「獨立審查通過」**且**業主明確說可以之後才能重新部署。
2. **真實筆記不得經過通道**，直到業主說可以。這一版先用合成的測試工作區。
測試**一律不碰已部署的 Worker**：用 `packages/relay` 的記憶體實作（`memory.ts`）與 Miniflare 本機的 workerd（`workers.runtime.test.ts`），或業主在自己機器上跑本機碰面點。前端的關閉開關（建置時 `VITE_RELAY_URL` 沒設＝功能整個不存在，#1567）維持：這個功能同樣藏在它後面。

**獨立審查者在真實筆記上路前必須嘗試的攻擊**（每條要有測試或審查紀錄）：

| # | 攻擊 | 要驗證的 |
|---|---|---|
| 1 | 拿 QR 照片搶先掃 | 搶到者拿不到資料；真新裝置得到明確的「已被使用」 |
| 2 | 碰面點換掉公鑰 | 六位數不同；每個 QR 只能試一次 |
| 3 | 略過確認：直接放資料物件、或重放舊確認 | 確認前碰面點上只有 hello；來源不依對方的任何訊息提前上傳 |
| 4 | 假裝是「已在用的裝置」：攻擊者顯示 QR，受害者的新手機去掃 | 新裝置只接受空殼；且內容經過下面 5、6、7 的驗證；畫面顯示「你要加入的是另一台裝置上的工作區」 |
| 5 | 惡意或損壞的快照內容：超大／壓縮炸彈、巢狀 JSON、重複項目、保留 id 與系統人的 id（系統角色、保留標籤與筆記）、`membership`／角色資料想取得權限、筆記內容裡的腳本 | 沿用 #1567 的大小與展開限制（壓縮比、解壓總量、項目數，在讀內容前就從表頭判斷）；匯入不接受任何授權資料；內容照一般筆記渲染的消毒 |
| 6 | 標記造假：序號極大、時鐘在遙遠的未來（把新裝置時鐘推到未來，之後它的每次寫入都「贏」）、同一個 `(來源, 序號)` 兩份不同內容、冒用本機節點編號 | 在 `spine/stamps.ts` 拒收最高時鐘超出容許偏差的整批（第 4 節），在 `adoptForeignStamp` 之前，有測試；`adoptForeignStamp` 已拒絕本機節點編號；同標記不同內容拒收 |
| 6b | 串接邀請：攻擊者在中途插入或替換「下一個工作階段的邀請」、重放舊邀請、把新裝置導去攻擊者的工作階段 | 邀請只存在已驗證的最終清單裡；綁定前一個工作階段編號與序號；每個邀請只能用一次；新工作階段仍要求相同的金鑰推導 |
| 7 | 掉頁、亂序、截斷、換成舊的完整快照（回滾）、把兩次加入的頁混在一起 | 最終清單列出全部頁與總摘要；頁以工作階段編號與序號綁定（AEAD 的附加資料）；沒有最終清單就不算完成；進度向量以最終清單內為準 |
| 8 | 快照含秘密或他人資料 | 比照 `syncStamps` 那條測試，逐檔逐頁檢查不含：AI 憑證、行事曆網址、登入、推播訂閱、`agent_tokens`、別人的個人空間、讀不到的垃圾桶 |
| 9 | 耗盡：位址占滿碰面點、手機記憶體或儲存 | 沿用上限；每頁大小上限；空間不足先檢查（沿用 507 路徑）；分頁處理 |
| 10 | 降級：用舊版協定、舊的結構版本、舊的合併規則版本 | 版本閘門：不同就拒絕並請更新，不靜靜繼續 |
| 11 | 取消或失敗後殘留 | 取消後新裝置沒有任何已複製的內容與裝置金鑰；失敗的加入不留可被打開的半個工作區 |
| 12 | 裝置標籤與錯誤訊息的注入 | 只當純文字，限長 |
| 13 | 碰面點看到什麼 | 看得到：大小、頁數、時間、來源位址；看不到內容。**要在畫面說明裡誠實寫出**（筆記數量的粗估能從頁數推出） |

審查還要確認：唯一的繞過寫入入口 `applyJoinRows`（第 3 節）只在加入中、空工作區才開、不能被一般寫入路徑或 HTTP 路由呼叫，且計數進守門測試；沒有自己寫的密碼學原語；沒有把 JSON、id、token 之類顯示在畫面上。

**1a 的檔案**：它是這位使用者所有可讀內容的**完整明文副本，不是備份**（沒有加密、沒有給備份還原用）。寫在哪裡：只寫在使用者自己選的位置（瀏覽器版是下載資料夾，桌面版是使用者選的資料夾），不放在應用程式資料或碰面點；畫面在存檔前明講「這個檔案沒有加密，任何拿到的人都能讀你的全部筆記，匯入後請刪除」；新裝置匯入成功或取消後提示刪除（無法替使用者刪除下載的檔案時就明說，不假裝已刪）；檔頭帶版本與摘要，匯入前先驗。只准匯入到空殼。測試用合成資料。

**分工**：1a 的後端核心（時鐘上限、帶標記的讀取、唯一的接收入口 `applyJoinRows`、空殼、兩個資料庫逐表逐列比對）由 note-cf 的分支 `feat/stamped-snapshot-core` 實作；本提案其餘部分（存檔／開檔的畫面、配對與碰面點的 1b、歷史層、附件層）由 note-ee 負責，**不另寫第二套匯出／套用**。

1a 先於 1b 的理由：快照對不對（id、標記、基底、隱私範圍）是資料問題，通道對不對是安全問題；拆開後前者今天就能測，後者可以等審查，而且業主「盡快能測」不必等部署。

**介面契約草稿**（只寫形狀；實作前再依 [design-principles](../../agents/design-principles.md) 補第二種草圖：把「讀取」做成每一表一個匯出函式 vs 一個統一的 `readStampedPages`，我選後者因為第 2 段只改一個參數）：

```ts
// 來源端：取操作者讀得到的、帶標記的列。since 為空＝快照；一次一頁；頁內每列帶它所有的標記（含墓碑）。
readStampedPages(actor: ActorCtx, workspaceId: Uuid, opts: { since: VersionVector | null; layer: "rows" | "history" | "blobs"; afterPage?: number }):
  AsyncIterable<{ page: number; cut: VersionVector; rows: { table: string; key: string; values: Json | null; stamps: Stamp[] }[] }>;
// 新裝置端：冪等，已套用的 (layer, page) 不重做；全部頁到齊且摘要吻合才把加入中改成完成。
applyJoinPages(join: JoinId, pages: AsyncIterable<StampedPage>): Promise<{ appliedPages: number[]; done: boolean }>;
```

呼叫範例（頁面程式，已在用的裝置端；`pairing` 部分是既有函式）：

```ts
const pairing = createInvite(relayUrl);                  // 既有：顯示 QR
const keys = await waitForHelloAndDerive(pairing);       // 既有：配對，得到六位數
await waitUntilUserConfirmed(keys.confirmationCode());   // 新：確認前不上傳任何資料
for await (const page of readStampedPages(actor, ws, { since: null, layer: "rows" }))
  await uploadItem(keys, `rows/${page.page}`, await compress(page));  // 既有：分塊加密上傳
await uploadFinalManifest(keys, { pages, cut, nextSession });        // 既有；內含串接邀請
```

## 伺服器端的三道門（2026-11-16）

`routes/stampedSnapshot.ts` 現在替「加入另一台裝置」的畫面把三件事放在伺服器，頁面不再各自判斷：

- **這台能不能加入、加入會刪掉什麼**：`GET /api/snapshot/readiness`（只有擁有者、不改任何東西）。答案與 `beginJoin` 共用同一個 `decideJoin`（`spine/stampedImport.ts`），所以兩邊不會不一致；`holds` 是這個資料庫裡「人自己的內容」的數量（筆記、垃圾桶、標籤、空間、檔案、偏好），只有數字。
- **檔案說自己是哪一版資料形狀**：第一行 hello 帶 `dataShape`（`spine/syncDataShape.ts`），接收端看到沒有或不同的版本就在第一行拒絕（`join_data_shape`）。
- **再輸入一次密碼由伺服器強制**：`GET /api/snapshot` 要帶 `X-Onden-Fresh-Proof` 票（`POST /api/fresh-proof` 換，2 分鐘、一次、綁人與用途；`services/freshProof.ts`）。瀏覽器版只有一個本機的人、密碼是公開的，伺服器能查的只有「兩分鐘內有第二次明確請求」，不是身分。

同一類、尚未套用這張票的路由（是否套用由擁有者決定；服務不用改）見 PR 說明。

**待決定，票擴大到備份之前必須有答案（2026-11-16 審查 note-96）**：只用 Google／GitHub 登入的擁有者沒有密碼，現在拿不到票（`fresh_proof_no_password`）。對「加入裝置」也許可以接受；但擁有者已決定同一張票之後要擋下載完整備份、匯出全部 Markdown、轉移擁有者，那時這類帳號會被鎖在自己的備份外面。對等的證明是「重新走一次登入提供者、要求重新驗證」之後發票。這要在票套用到那三個路由之前完成，並且走同一個 `issueFreshProof`（新增一種證據），不另開第二條路。

**密碼嘗試的鎖（同日補）**：錯密碼在資料庫裡計數（`fresh_proof_attempts`），計數在檢查之前，所以並行的猜測過不了；連續錯 5 次鎖 15 分鐘，鎖結束後每多錯一次加倍（最多一天），對的密碼清零；鎖住的那次留一筆 `FRESH_PROOF_LOCKED` 事件給擁有者看。確認（`acknowledgement`）只在瀏覽器版（`ONDEN_BROWSER_APP`）且是那個本機帳號時接受，伺服器上一律要密碼。
