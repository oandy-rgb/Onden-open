**業主提出但還沒定的**：AI 建議貼紙、貼紙特效。調度員的建議與我的看法在第 3.9 節。

名詞（只解釋一次）：**token**＝設計用的具名數值（例如 `--ac-ink` 代表正文顏色），元件只引用名字、不寫死數字；
**seed**＝只給兩個顏色（強調色、紙色），其餘顏色由公式算出來；**輸出**＝筆記離開 app 的方式（發布網站、Markdown 匯出、完整備份、簡報 PPTX、PDF／列印）。

## 0. 一頁摘要

1. 外觀（方向 A「安靜」已由業主選定）：Onden 已經有「顏色兩個 seed＋六組預設」「筆記字型、字級、寬度」。真正粗糙的地方不在設定少，而在**筆記頁的字體排印沒有走 token**：
   標題大小、行高、段距散落在好幾份 CSS，有的甚至和 token 檔裡定義的數值互相不用（第 1.3 節）。建議第一步先把它收進 token，**不新增任何設定**，既有筆記的樣子不變。
   業主指出：間距、圖示大小、框線粗細、控制項高度目前**沒有任何規則**；主題既然是「一組數值」，這四種要先有代號，主題才管得到（1.8、第 6 節）。
2. 「主題」＝一組既有 token 的具名數值，不是每個元件的 CSS；顏色沿用現有的兩個 seed，不建第二套顏色系統。自訂 CSS 先不做（第 1.4 節說明風險）。
3. 主題**不影響輸出**：發布網站和簡報本來就有自己的外觀。素材（貼紙）是內容，會帶著走（貼在哪個畫面就跟著那個畫面的輸出）。
4. 庫：主要是**社群庫**：一個公開 GitHub 庫放清單與項目檔（主題、貼紙包、範本），app 在使用者打開「社群」頁籤時才連網讀取，不架伺服器。
   **安裝＝驗證後複製進自己的資料**，所以作者刪掉也不影響已用的筆記與已發布的貼紙。社群主題**只能是數值**，不收樣式程式碼。
   庫**不是**現有「標籤包」那一套（那是安裝欄位定義的 JSON，且帶行為），但沿用它的「帶版本的 JSON 檔」慣例。app 自帶的起點用同一種格式。
5. 貼紙（業主 2026-11-17：貼在簡報、網站、手寫三個畫面，不寫進內文）：**一份共用的「放置」定義**（圖、位置、大小、旋轉），差別只在位置相對於什麼。圖檔是一般媒體，安裝與放下時都複製進自己的資料。
   手寫頁與簡報共用既有的 `page_images`（頁鍵 `page`／`pdf:<n>`／`slide:<頁鍵>`），簡報貼紙用簡報既有的頁鍵當錨，找不到頁的貼紙會保留並提示；網站貼紙建議貼在**網站設計的盒子**（頁首、首頁開頭、頁尾），不貼在段落旁。
6. 範本：app 已經有 4 個寫死在程式裡的範本，只能從指令面板找到。建議「筆記可以標成範本」（和「技能」同一個概念），並讓「從範本開始」出現在空白新筆記上，**不增加 ＋ 的選項**。
7. 素材來源：自己畫最乾淨；能用的開放素材我只**實際讀到授權文字**的有 Lucide（ISC）、Tabler Icons（MIT）、Twemoji 程式碼（MIT）與圖形（CC-BY 4.0）、Noto Emoji（README 說字型 OFL、圖像 Apache-2.0，但同一份 README 指向的根目錄 LICENSE 實際是 OFL，兩者矛盾，需再查）。OpenMoji、unDraw 等**沒有查證**（站台連不上）。

### 1.3 Obsidian 好看在哪裡，與 Onden 筆記頁今天比較粗糙的地方

Obsidian 的預設外觀好看，我認為（意見，不是文件事實）主要來自：**一套有節制的字體排印**（標題、段落、引用、程式碼、表格一致）、
**一致的間距**、**克制的顏色**（灰階底色 12 階，強調色只用在互動元素），以及**即時預覽的編輯器**（編輯與閱讀幾乎同樣的排版，只有游標所在行顯示語法符號）。
官方文件佐證的是前兩項的「結構」：字級與間距是一組命名變數、標題每級各有變數（上表）。

我只從 CSS／程式碼讀，沒有看過渲染結果。以下是**程式碼裡可驗證的粗糙處**：

1. **同一段文字兩套排版。** 編輯器的標題大小寫死在 `packages/frontend/src/lib/editorMarkdownLanguage.ts`（h1 1.65em、h2 1.3em、h3 1.15em，h4 只加粗）；
   `components/OverviewEditor.css` 又重複寫一次；閱讀檢視的 h4–h6 與 h1–h3 的邊距、行高在 `components/ObsidianImport.css` 另有一組（行高 1.2 對 1.4/1.3）；
   發布網站共用的 `components/MarkdownRenderer.css` 又是第三組。
2. **行高寫死、token 沒人用。** 正文行高 1.7 寫在 `OverviewEditor.css` 與 `ObsidianImport.css`；`styles/tokens.css` 定義了 `--ac-lh-prose`（1.9）與 `--ac-lh-quote`（1.8），
   但在 `tokens.css` 以外找不到使用者。`--ac-prose-max`（640px）只有任務專注模式在用；專注模式另寫死 `max-width: 680px`。
3. **間距混用 px 與 em，沒有用 `--ac-space-*`。** 段距有 1em 與 10px 兩種；程式碼區塊 14px/16px、清單 12px、分隔線 20px。
4. **程式碼與引用不一致。** 閱讀檢視的程式碼區用 `ui-monospace, monospace` 而不是 `--ac-font-mono`，大小跟介面字級而非筆記字級；
   編輯器的行內程式碼用 `fontFamily: "monospace"`；引用在閱讀檢視是左邊 3px 色條加底色，在編輯器只改文字色。
5. **表格與筆記字級脫鉤。** 編輯器畫的表格（`lib/editorTables.ts`）用 `--ac-fs-prose`，不跟筆記字級設定走；專注（zen）模式的 `.cm-content` 也用 `--ac-fs-prose`。
6. **寬度上限在容器、單位是 em，但筆記字級會隨視窗放大**（`styles/theme-tokens.css`），所以視窗越寬欄位的 px 寬度越大；「滿版」直接是 100vw。
7. **列印／PDF 寫死白底、`#111827`、Noto Serif TC 11pt**（`styles/print-export.css`），完全不讀 app 的外觀設定（這是刻意還是遺漏，我不知道；本提案先不動它，也不列為問題）。

結論：這些粗糙處的根因是「筆記排版沒有一組共同的 token」。這和 AGENTS.md「修掉造成重複特例的根因」同一方向。
所以**外觀強化的第一步是整頓，不是加選項**。

### 1.4 建議的機制：一個東西，叫「主題」

- **主題＝一組既有 token 的具名數值。** 兩部分，都已存在或只差一點：
  1. 顏色：就是現有的 `accent`＋`paper` 兩個 seed（`appTokens(accent, paper, mode)` 算出 29 個顏色 token）。現有六組預設（赭、綠、靛、琥珀、紫藤、石墨）**就是顏色主題**，不新增第二套顏色系統。
  2. 筆記字體排印：一小組 token，**取值只能是 A 規則文件的刻度（1.8）**，不新增層級：各級標題字級、標題行高、正文行高、段距、清單間距、引用樣式（色條／縮排）、程式碼區背景與圓角。目前這些散在上面 1.3 列的檔案；先把它們收成 token，**預設值取今天實際的值**，既有筆記看起來不變。
- **內建主題**：把「顏色預設＋一組字體排印預設」打包成名字（例如 安靜、紙本、書冊；這三個名字是網站樣式現有的，見 1.5，是否沿用待業主決定）。選主題＝一次套用兩部分；選完仍可單獨再改強調色、字型、寬度。
- **使用者自己的主題**：就是目前已有的「自訂強調色＋紙色」，加上字體排印那組的幾個值。**存在帳號偏好**（沿用 `createAccountPref`／`/api/me/prefs`，AGENTS.md 的唯一入口），不開新儲存。目前顏色是存在本機 `localStorage` 的 `theme.colors`（裝置專屬，開機前就要用），是否改成跟帳號走是個要先查的問題：我不知道這樣開機先畫會不會閃一下，要量過。
- **邊界**：主題的值只准是 token；不是任意 CSS。這樣一個主題不可能破壞版面，也不可能載入外部資源。**社群主題（第 2 節）也只能是這種數值**，由 app 驗證後再自己產生 CSS，不收作者寫的樣式。
- **自訂 CSS 片段，三個選項：**

| 選項 | 內容 | 風險 | 建議 |
| --- | --- | --- | --- |
| a 不做 | 只有主題與設定 | 沒有 | **建議** |
| b 只准覆寫 `--ac-*` 變數 | 使用者貼一段 `--ac-xxx: 值;`，由程式解析，其他一律丟掉；只存在這個帳號、這個裝置 | 壞值可能讓文字看不見（要有「還原預設」）；要自己寫解析器 | 之後若有人需要再做；等於是「進階版主題」 |
| c 任意 CSS | 像 Obsidian | 能弄壞介面；**能外洩資料**：CSS 的屬性選擇器加 `url()` 可以在筆記內容符合條件時對外發請求，共用空間裡別人的內容會被讀到（這是已知的 CSS 外洩手法，我沒有實測，也沒有查證來源）；與「設定用畫面說、不用技術說」（`decisions-ui.md` 2026-10-30）相衝突 | **不做** |

  若做 b：禁止 `url()`、`@import`、選擇器，只留自訂屬性宣告；片段只存本機帳號分區（`accountStorage.ts`），**不隨工作區同步、不進匯出**。

### 1.5 主題會不會影響輸出？

現況（`packages/site/src/style.ts`、`packages/frontend/src/modules/slides/theme.ts`、`styles/tokens.css` 開頭註解）：

- 發布網站有自己的外觀：四組樣式（安靜、紙本、書冊、手寫）＋強調色＋明暗，用 `--s-*` 變數；`tokens.css` 明寫「發布網站不跟這個檔」。app 的外觀設定**不會**改到網站。
- 簡報有主題 `site`（跟網站樣式）、`dark`、`paper`，每份簡報自己選；app 的亮／暗只在網站配色是「系統」時影響簡報（`theme.ts`）。
- 列印／PDF：固定樣式（1.3 第 7 點）。

**建議規則**：「**app 的主題只改畫面上的你看到的，不改任何輸出。** 輸出的外觀由輸出自己決定（網站樣式、簡報主題、列印樣式）；
素材（貼紙、圖片）是內容，一定帶著走。」理由：同一篇筆記今天在手機上看是暗色，發布出去不該變暗色；也避免「換個 app 主題，已發布的網站悄悄改版」。
**業主要決定**：網站的四組樣式要不要和 app 內建主題用同一組名字與數值（讓人覺得「這就是我的樣子」），還是各管各的（現況）。我建議各管各的，只在命名上別撞（Q1 的另一半；網站與 app 主題 A 撞名見 1.8）。

## 2. 內建庫與社群庫

業主 2026-11-17（PR 留言）改了方向：**主要是能在 app 裡搜尋社群做的主題、貼紙、範本**（像 Obsidian 的社群主題瀏覽器）；app 自帶的只是起點。

### 2.1 Onden 現在有什麼「可安裝的東西」

我查了程式與文件（`docs/architecture/module-library.md`、`docs/agents/decisions-modules.md`）：

| 機制 | 是什麼 | 裝東西的方式 | 和社群庫的關係 |
| --- | --- | --- | --- |
| 模組庫 | 內建功能（行事曆、白板、簡報…）的開關；程式碼本來就在 app 裡 | 設定 › 功能 打開／關閉 | **不同**：它開關程式，不放素材 |
| 標籤包 | `onden.tagpack/v1` JSON：標籤的欄位、行為、模組（`backend/src/services/tagPacks.ts`） | 設定裡「匯入標籤包」選 `.json` 檔；內建 4 包在 `frontend/src/data/packs/`，第一次使用只推薦「書」 | **不同**，但它是先例：已經有「一個帶版本的 JSON 檔＝一個可安裝的東西」的命名慣例（`onden.<東西>/v1`），社群庫沿用這個慣例。標籤包本身**不收進社群庫 v1**：它帶「行為」與「模組」，不是純資料 |

沒有現成的「素材庫」或「從網路找東西裝」的機制。**社群庫是新的，但不是第二套安裝包**：它只負責「找到一個純資料檔、檢查、複製進自己的資料」，
資料格式沿用上面的慣例，內建的起點也用同一種格式（2.7）。

### 2.3 Onden 社群庫的具體設計

**一個公開的 GitHub 庫（暫名「社群庫」）**，內容全是文字檔，沒有伺服器、沒有資料庫：

```
index.json                 清單（由腳本從項目檔產生，投稿者不手改）
items/<id>/item.json       一個項目＝一個檔
CONTRIBUTING／審核清單、驗證腳本（CI 跑）
```

**項目放哪裡——兩案：**

| | A 項目放在社群庫裡（投稿＝開一個加檔的 PR） | B 項目放在作者自己的庫，清單只記位置（Obsidian 做法） |
| --- | --- | --- |
| 審的是什麼 | 就是將被散布的那幾個位元組 | 清單記「固定的 commit＋sha256」才等於同樣保證；否則作者事後可改內容 |
| 作者刪庫 | 不影響 | 項目消失（已安裝的複本不受影響，見 2.6） |
| 一個主機 | 只連 `raw.githubusercontent.com` 一個 | 要連很多作者的庫 |
| 對業主的負擔 | 庫會長大（文字檔，很小） | 較小，但要驗證 commit 與雜湊 |
| **建議** | **A** | 之後若項目變大再考慮 |

**清單 `index.json`**（每筆 ≈ 250–350 位元組，**估計**，沒有量）：

| 欄位 | 內容 |
| --- | --- |
| `id` | 英文小寫連字號，唯一、不重用 |
| `kind` | `theme`、`stickers`、`template` 三種之一 |
| `name`、`author` | 顯示名稱（≤ 40 字）、GitHub 帳號 |
| `licence` | SPDX 代號，只准清單內的幾種（2.5、第 5 節） |
| `version` | 整數，每次改動加一 |
| `file`、`bytes`、`sha256` | 項目檔路徑、大小、雜湊 |
| `modes`（主題）／`count`（貼紙）／ `swatch`（主題的兩個顏色） | 讓清單**不必下載項目就能畫出預覽**；所以**沒有 `screenshot` 欄位**，不載入任何外部圖片 |
| `keywords`、`added` | ≤ 3 個搜尋詞、加入日期 |

**項目檔格式**（每種一個帶版本的名字；全部是「純資料」）：

- 主題 `onden.theme/v1`：`{ "accent": "#…", "paper": "#…", "type": { 標題比例、行高、段距… 各自取自封閉清單或有上下限的數字 } }`，只准 1.4 的 token 名單；沒有字串形式的 CSS。
- 貼紙包 `onden.stickers/v1`：`{ "stickers": [ { "name": "…", "svg": "<svg…>" } ] }`；SVG 文字，每個 ≤ 8 KB、每包 ≤ 60 個、整包 ≤ 200 KB（上限是我的提議，沒有依據，可調）。用 SVG 是因為它是文字，PR 上看得到差異，也能走現有的消毒（`backend/src/services/svgSanitize.ts`）。
- 範本 `onden.template/v1`：`{ "name", "title", "body", "tags", "attributes" }`，形狀同 `noteTemplates.ts` 的項目；內文 ≤ 20 KB；佔位符只准 `{date}`、`{datetime}`。

**app 怎麼讀：**

- 只在使用者**打開「社群」頁籤時**才連網（GitHub 會看到對方的 IP，所以不能在背景偷連）；程式碼放在 `lazyWithReload` 後面，**不在開機路徑**；清單不隨 app 打包。
- 取得方式：瀏覽器直接向 `raw.githubusercontent.com` 讀。我 2026-11-17 實測該主機對 `community-css-themes.json` 回 `access-control-allow-origin: *`、`cache-control: max-age=300`、有 ETag，所以純瀏覽器版也能讀。**我不知道**：app 自己的內容安全政策（CSP）是否允許連這個主機（我只找到發布網站與媒體路由有 CSP 設定，app 本體的沒找到）；GitHub 對 raw 檔案的流量上限與條款（沒有查證）。另一條路是讓伺服器代抓（`services/safeFetch.ts` 已是對外抓取的 SSRF 防護入口），但純瀏覽器版就沒有；**只留一條路比較簡單：瀏覽器直讀**，CSP 要放行時再說。
- 快取：清單存進本機（帶 ETag），打開頁籤時若超過 1 小時才重抓；離線時顯示上次的清單，並說「目前沒有網路」；**已安裝的東西完全不受影響**。
- 大小與載入：Obsidian 的 1037 筆是 178 KB（上面的實測）；Onden 每筆大一點，千筆約 300 KB 未壓縮（估計）。起初只有幾十筆（幾 KB）。超過約 2000 筆或 500 KB 時，改成每種類型一個清單檔。搜尋在本機對 `name`、`author`、`keywords` 做。
- 預覽：主題用 `swatch` 兩色＋打開項目後以實際值畫預覽卡；貼紙直接畫 SVG；範本顯示全文——**安裝前使用者看得到將複製的完整內容**。

### 2.4 誰審、流程、對業主的工作量

流程：作者開 PR 加一個 `item.json` → CI 跑驗證腳本（格式、大小上限、白名單、授權欄位、雜湊、SVG 消毒、主題對比度）→ 人看一眼 → 合併 → 腳本重產 `index.json`。

| 種類 | 自動檢查能擋什麼 | 人要看什麼 | 估計時間（我的假設，沒有資料） |
| --- | --- | --- | --- |
| 主題 | 幾乎全部：值都是白名單內的數值，對比度不夠就擋 | 不必（只剩「好不好看」，那是品味不是安全） | 0–2 分鐘 |
| 範本 | 大小、佔位符、連結與外部圖片 | 內文：有沒有廣告、追蹤、對 AI 的指示（範本內文日後可能被 AI 讀到） | 3–5 分鐘 |
| 貼紙 | SVG 消毒、大小 | 每一張圖：內容是否合適、是不是抄來的 | 5–10 分鐘（一包 20 張） |

業主的持續工作量＝每週投稿數 × 上表。**投稿量我不知道。** 例：每週 10 個、平均 5 分鐘＝約 50 分鐘（舉例，不是預測）。降低工作量的辦法：
(1) 主題完全自動；(2) 起初**只收業主自己與受邀作者的項目**，等流程順了再開放投稿；(3) 加共同維護者（GitHub 的 CODEOWNERS 檔）；(4) 項目一律送審一次，**之後不准改檔**（要改就是新版本、再審一次）。

**不審會怎樣：** 主題仍然安全（只是數值）；範本可能夾帶廣告、追蹤連結、或對 AI 的指示；**貼紙會被使用者放進他發布的網站，等於業主的社群庫替別人的公開作品背書**，可能含不當或侵權圖片。所以貼紙與範本我建議人工看，不建議全自動。
**下架：** 從清單拿掉即可；已安裝的複本留在使用者手上（2.6）；若是授權或侵權問題，要另外通知，這個流程我沒有設計。
**索引本身被竄改：** 有庫寫入權的人能改 `index.json`。對策：分支保護、雙重驗證；而且 app **不信任清單**——每個項目安裝前都在本機重新驗證（見 2.5），所以被竄改的清單最多讓使用者看到不想要的東西，不能繞過驗證。

### 2.5 安全：逐種類的威脅與對策

共同：項目檔只被當成**資料**解析、驗證、再由 app 自己的程式轉成畫面；**絕不把作者的字串直接當 CSS、HTML 或程式碼套用**。每個項目安裝前在本機驗證格式、大小、雜湊。

| 種類 | 威脅 | 對策 |
| --- | --- | --- |
| 主題 | ① 把介面弄壞或讓字看不見；② 用 `url()` 把資料送出去、載入外部資源；③ 超大字串拖慢 | 只收 1.4 白名單 token 的數值（顏色用固定格式、數字有上下限、字型只准四種）；CSS 由 app 從驗證過的數值**重新產生**，不存作者字串，所以沒有 `url()` 的立足點；安裝前用 `appTokens` 現有的對比目標檢查（正文 ≥ 13 等），不及格不能安裝；**不收樣式程式碼** |
| 貼紙 | ① SVG 內含腳本、`foreignObject`、外部連結、內嵌 CSS 的 `url()`；② 內容不當或抄襲；③ 授權責任跟著貼紙進入使用者發布的作品 | ① 現有消毒（我沒有逐項核對它擋了哪些，**實作前要核對**）＋ 項目檔大小上限；放進筆記時再經媒體上傳的消毒一次；② 人工審、授權限制（下一點）、可下架；③ 只收**不要求署名也不要求同授權**的授權：CC0-1.0、0BSD、MIT、ISC、Unlicense；不收 CC-BY、不收任何 share-alike（CC-BY-SA、GPL 類），因為使用者會把它發布到自己的網站 |
| 範本 | ① 追蹤用的遠端圖片或連結；② 內文含給 AI 的指示（日後被 AI 助理讀到）；③ 垃圾與廣告 | 驗證器擋外部圖片、限制連結數；安裝前顯示全文；人工審；範本裝進來就是一則普通筆記，使用者可以改 |

### 2.6 安裝＝複製進自己的資料

- **主題**：驗證過的數值存成「我的主題」（帳號偏好，1.4）。作者之後從庫裡刪掉，主題仍在。
- **貼紙包**：每張貼紙存成使用者自己的媒體圖片（旗標為貼紙，列在「我的」）；放到某個畫面上時再複製進該筆記的媒體（3.1 的 A）。所以作者刪掉、庫下架、使用者離線，**已貼的貼紙與已發布的貼紙都不受影響**（對應業主「貼紙跟著輸出」）。
- **範本**：存成一則標成範本的筆記（第 4 節）。
- **更新**：不自動更新（Obsidian 也不會）；清單版本比本機新時顯示「有新版」，使用者自己按；更新是另一份新的複本，不改已用過的筆記。
- 安裝紀錄只存 `id`、`version`、`sha256`，用來顯示「已安裝」與「有新版」，**不當成輸出依賴**：沒有任何筆記會引用社群庫的 `id`。

### 2.7 app 自帶的起點，與怎麼遇到它

- 自帶的是**同一種項目格式**：現有六組顏色預設（＋第 1 節的內建主題）、少量自己畫的貼紙、4–6 個範本；用同一個驗證器、同一個「安裝」動作，只是來源是 app 打包（用到才載入，不進開機路徑；開機預算 gzip 上限 310,204 B，最近量測 305,084 B）。社群庫＝「同樣的東西，來源換成網路」，沒有第二套程式。
- **一個瀏覽元件，從用得到的地方打開**，依種類過濾，桌面用彈出、手機用 `ui/Sheet`：外觀頁「主題」→ 主題；手寫與白板工具列「貼紙」→ 貼紙；空白新筆記「從範本開始」→ 範本。每個瀏覽畫面分「內建」「我的」「社群」三段，搜尋框共用。
- **不新增 ＋ 的選項**（`lib/createKinds.ts` 七種不動）；不放在 ⋯。
- 離線與純瀏覽器版：內建與我的完全可用；「社群」段需要網路，沒網路時顯示上次清單。
- 「內建圖示」的疑問（有沒有筆記／標籤圖示欄位）見第 1.6 的對照表與 Q10：目前**沒有**這種欄位。

### 2.8 Obsidian 現成的主題能不能用

不能直接用。依據：
- Obsidian 主題是 `theme.css`，用 `.theme-dark`／`.theme-light` 覆寫 Obsidian 的變數，並常加針對 Obsidian 畫面結構的選擇器（[About styling](https://raw.githubusercontent.com/obsidianmd/obsidian-developer-docs/main/en/Reference/CSS%20variables/About%20styling.md)，2026-11-17）。
- Obsidian 的色彩是 12 階灰階底色加強調色的 HSL 三個值（[Colors](https://raw.githubusercontent.com/obsidianmd/obsidian-developer-docs/main/en/Reference/CSS%20variables/Foundations/Colors.md)，2026-11-17）；Onden 是兩個 seed（強調色、紙色）推出 29 個顏色。
- 能搬的頂多是：**一個強調色、一個背景色（紙色）、也許一個字型方向**。**排版與版面（卡片、圖片牆、分頁列…）搬不過來**，那是選擇器的功勞。
- Minimal 依賴伴隨外掛與 Dataview 才有完整功能（其 README：色彩配置靠 Minimal Theme Settings 外掛；`cards` 作用在 Dataview 表格，2026-11-17）。
- 自動轉換需要解析不可信的 CSS，**不建議**。人工把兩個顏色抄成 Onden 主題可行，但原主題的授權（Minimal 是 MIT；AnuPpuccin 是 GPL-3.0 且要求保留版權聲明，其 README，2026-11-17）對「只抄顏色值」是否有影響，**我不知道，也不是法律意見**。

## 3. 貼紙

### 3.0 業主 2026-11-17 的決定：貼在三種畫面上，各貼各的

業主原話：「貼紙我覺得能分別貼在簡報 網站 手寫」（PR 留言）。這一版照此重寫：

- **貼紙不寫進筆記的文字裡。** 內文維持純 Markdown；貼紙是貼在三種「畫面」上的東西——**簡報、網站、手寫頁**——每個畫面有自己的一層，**互不相干**（貼在簡報上的不會出現在網站或手寫頁）。
  原本「放進內文」的選項（一般圖片語法、文字中的小貼紙）**移到「不做」**。好處：(1) Markdown 匯出、任何其他編輯器、複製貼上、AI 讀到的內文都不會多出一堆沒有意義的圖片連結；
  (2) 內文的三方合併與歷史不會被裝飾圖片弄髒；(3) 圖片語法沒有大小屬性（程式探索報告），本來就做不好「夾在字中的小貼紙」；(4) 筆記換一個畫面（例如不做簡報）貼紙不會變成殘留在文字裡的垃圾。代價：貼紙只在三個畫面看得到，Markdown 匯出看不到（這是設計，不是遺漏，第 3.6 節逐項說明）。
- **一個機制，三個畫面**：「一張圖＋位置＋大小＋旋轉」的資料形狀只定義一份（3.2），差別只在「位置相對於什麼」。
- 素材仍是「**安裝時複製進自己的資料**」（2.6）；放下去時再複製一份進使用者自己的媒體（3.1 的 A），所以作者刪掉或庫下架都不影響已貼的。
- 白板貼紙：業主沒有點名，**這一版不做**（文字裡的貼紙是業主明確排除）；白板沒有圖片層（`components/KnowledgeWorkspace.tsx` 的節點只有 card／section／treeMore），要做是另一個設計題，放在「之後」。

### 3.1 貼紙的圖是什麼：三個選項（沿用上一版的比較，位置改由 3.2 決定）

| | A 圖檔複製進筆記媒體，貼在畫面的一層 | B 引用庫裡的項目 id | C 手寫文件裡的向量形狀 |
| --- | --- | --- | --- |
| 資料 | 圖檔＝一般媒體 `/api/media/<id>`；位置等資料在畫面那一層 | 層裡存庫 id | 手寫頁 `ink_data` 的形狀或筆畫 |
| 庫日後移除一個項目 | 不受影響 | **舊畫面壞掉** | 不受影響 |
| 其他裝置、備份、離線 | 圖檔與層一起同步與備份 | 每個裝置要有同一版庫 | 隨手寫同步 |
| 彩色、暗色 | 任意；圖片是否被暗色模式反相沒有查證（墨水會） | 同左 | 受限於墨水調色盤，暗色時墨水被反相（`lib/ink/palette.ts`） |
| 簡報、網站能用嗎 | 能（都是圖片） | 要各自解析庫 id | 簡報與網站沒有墨水層 |
| 新增的合併結構 | 無（3.7） | 要 | 受墨水合併影響 |

**建議：A。** 理由同上一版：輸出本來就會帶圖片；B 讓舊內容依賴會消失的庫；C 只在手寫頁能用。

A 的待查（**不知道**）：
1. 媒體檔「第一則存了引用的筆記就認領」（`services/mediaOwners.ts` 的 `claimUploadedMedia`）。同一檔被兩則筆記引用時第二則的讀取權限可能出問題，所以**每則筆記各複製一份**；要用權限測試確認。
2. 一個貼紙被貼了十次，是十個放置共用同一個媒體檔（同一則筆記內）——不是十份檔。
3. 內建貼紙放下去要「上傳」；**離線時能不能放**（離線佇列的行為）沒有查證。

### 3.2 一個機制：共用的「放置」定義

一份定義放在 `@onden/markdown`（和 `pageImages.ts` 同一層，前後端共用，AGENTS.md 的唯一入口原則）：

```
貼紙放置 = { id, src: "/api/media/<id>", alt, w, h, rot?, fx?, updated_at } + 位置
```

- `src`：沿用媒體引用的文法與驗證（`mediaRefs.ts`），所以伺服器的所有權認領與讀取檢查照舊。
- `alt`：**空字串＝純裝飾**（讀螢幕的軟體略過）；有值＝有意義的圖。預設空字串（貼紙多半是裝飾）。
- `w`、`h`：大小；保持放入時的長寬比（和 `page_images` 現況相同）。
- `rot`：旋轉角度（度），選填。**現有 `page_images` 項目沒有旋轉欄位**（欄位是 `id,x,y,w,h,src,alt,updated_at`），所以這是新增的選填欄位；舊版 app 不認得，但合併規則要求「未知欄位原樣保留」，所以不會弄丟，只是舊版畫成沒旋轉。
- `fx`：特效，之後才定（3.8），沒有就是靜態。
- **位置相對於什麼，由畫面決定**：

| 畫面 | 位置是什麼 | 單位 |
| --- | --- | --- |
| 手寫頁 | 頁面上的 `x`、`y`（左上角） | 頁面單位（頁寬 1000，不隨縮放） |
| 簡報 | 某一頁投影片上的 `x`、`y` | 同樣的頁面單位，畫布 16:9（寬 1000、高 562.5），所以與畫面實際像素無關 |
| 網站 | **沒有座標**（網頁會隨寬度重排）：位置＝「哪一格」＋大小級距（3.5） | — |

驗證（大小上限、旋轉範圍、`src` 文法、`alt` 長度）只寫一份，三處共用；資料在哪個屬性見 3.7。

### 3.3 手寫頁

- **它和圖形、區域標記是同一類嗎？不是。** 圖形（`InkShape`：線、箭頭、矩形、橢圓…）是 `ink_data` 裡的幾何，只有 9 種、填色只有「無／實心」，顏色受調色盤限制；區域標記是文字裡 `![[筆記|ink=page@x,y,w,h]]` 的嵌入參數。
  貼紙是**圖片**，所以和 `page_images`（頁面圖片）同一類：現有的「貼上一張圖到手寫頁」就是它，貼紙＝多了旋轉欄位的頁面圖片。
- **放在哪個既有合併結構：`page_images`**，不是 `ink_data`。理由：`page_images` 自己的檔頭註解就寫明它刻意與筆畫分開（筆畫格式自己演進；圖片畫在筆畫之下）；合併是「依項目 id、每頁」。
- **和手寫合併改版的相依（#1783）**：我讀了 #1783（2026-11-17 開啟中、狀態 `dirty`＝與 main 有衝突、尚未合併）。它把 `ink_data` 的合併改成一次吃所有頭（`mergeInkHeads`），並說明 `page_text`／`page_images` 仍走 `mergeItemsById([stored, incoming])`：**兩邊都改時仍是後到的贏（行為不變），只有排序規則換成 `weaveOrder`**。
  所以貼紙依賴的是：(1) 依 id 的項目合併（#1783 不改）；(2) 項目的順序＝疊放順序（#1783 會改成編織排序）。**貼紙不依賴 `ink_data` 的合併**，可以不等 #1783；但 `rot` 欄位與 #1783 都動到 `page_images` 周邊，實作時要在 #1783 合併後對齊測試。
- **PDF 頁上能不能貼：能。** 頁鍵本來就有 `pdf:<n>`（`pageImages.ts` 檔頭），貼紙放在該頁的 `images` 裡。
- 圖片畫在筆畫**下面**（現況）：寫字不會被貼紙蓋住，貼紙不會擋住筆。

### 3.4 簡報

背景（`docs/agents/decisions-slides.md`）：投影片是**從筆記文字算出來的**（`---` 優先，否則 `##`），文字一改頁就重切；每頁有一個「頁鍵」（`pageKey`）：標題的 `^id` → 標題文字（小寫、去記號）→ 頁首 24 字 → 位置；同鍵第 2 張起加 `~2`、`~3`。版型選擇存在 `slides_data`（一個屬性、整份取代、≤ 8 KB、≤ 64 筆）。

- **貼紙認得「是哪一頁」：用同一個頁鍵當錨。** 貼紙放在 `page_images` 的 `slide:<頁鍵>` 之下（這個鍵本來就是為簡報保留的，`pageImages.ts`／`pageText.ts` 檔頭）。位置是 16:9 畫布上的頁面單位（3.2），所以投影片縮放、全螢幕、縮圖、PPTX 都是同一個比例。
- **不放進 `slides_data`**：它是整份取代、有 8 KB 與 64 筆上限；貼紙放進去會讓「兩台裝置各改不同頁、後同步的整份蓋掉先同步的」這個已知限制波及貼紙（而且 8 KB 很快滿）。`page_images` 是依 id 合併，沒有這個問題。
- **頁被刪掉、合併、或標題被改掉（頁鍵變了）時：不默默丟掉。**
  - 頁鍵對不到任何頁的貼紙**照樣保留在資料裡**（和 `slides_data`「沒有對應頁的選擇保留」同一個做法）。
  - 簡報視角顯示一個看得到的提示：「有 N 個貼紙找不到它原本的頁」，點開列出縮圖與原頁名稱（頁鍵的文字），每個可以「貼到這一頁」或「刪除」。
  - 沒有任何自動搬移或自動刪除。
  - 兩頁合併後只留一個鍵，另一頁的貼紙就成為「找不到頁」的那一類，同樣處理。
  - **已知限制（和版型選擇一樣）**：標題沒有 `^id` 時，改標題就換鍵。可選的補強：第一次貼貼紙時詢問「要在標題加一個隱形編號（`^id`）讓貼紙跟著它嗎？」——它會改筆記文字，所以**預設不做**，列為待業主決定的細節（不佔 10 題之一）。
- **畫面**：貼紙層畫在投影片之上；`SlideView` 是「一套渲染」（大圖、縮圖、播放共用，批 1 的決定），所以只改一處。**貼紙不能算進「放不下」的量測**（量測的是內容是否溢出），否則一個大貼紙會害整頁被縮一級。
- **匯出 PPTX**：貼紙就是一張圖：`deckSpec.ts` 現在已經把圖片用 `{type:"image", frame, data, altText}` 輸出，貼紙照同一條路加進去，位置由頁面單位換算。SVG 在 PPTX 是否穩，**沒有查證**，穩妥做法是輸出前轉成 PNG。旋轉要查 PPTX 寫入函式庫支不支援（沒有查證）。
- 「定下來」的第 2 層（自由排版快照）還沒做；貼紙層是獨立的，那時再決定要不要一起快照，現在不需要。
- 權限：要有編輯權才能貼／移，沒有編輯權的人能看、能播（與版型按鈕同規則）。

### 3.5 網站

發布的網頁會隨螢幕寬度重排，**沒有固定座標**。選項：

| | a 貼在某一段旁邊（跟著那一段） | b 貼在頁面的固定位置（頁首角落、頁尾） | c 貼在「網站設計」的層級（每一頁都有） |
| --- | --- | --- | --- |
| 資料放哪 | 筆記屬性，錨是段落的穩定 id（`^id`，既有的區塊錨點機制） | 筆記或網站設計 | 網站設計（工作區層級，不在任何筆記裡） |
| 重排 | 窄螢幕要決定移去哪（可沿用 `note.right` 的規則：寬螢幕在側欄、窄螢幕移到內文後面） | 角落在窄螢幕可能蓋住內文 | 放進現有的「盒子」（`header`、`home.hero`、`foot`…），盒子自己決定窄螢幕怎麼折疊 |
| 對內文的影響 | 最大：在段落旁邊 | 可能蓋住字 | 最小：不在內文區 |
| 與既有設計的關係 | 新增一種「附在段落上的東西」，網站設計是凍結的、盒子模型沒有這種位置 | 盒子模型沒有「固定位置」這個概念，要新增 | **完全沿用**：盒子模型就是「Onden 決定每個盒子的位置與手機折疊，使用者只決定這一格放什麼」（`docs/architecture/proposals/site-boxes-2026-11-01.md` §1、§2） |
| 無障礙 | 裝飾圖 `alt=""` | 同左 | 同左 |
| 手機寬度怎麼縮 | 要新規則 | 要新規則 | 盒子已有（窄螢幕用 `@container` 折疊；貼紙跟著大小級距縮） |

**建議：c，貼在網站設計的層級。** 理由：它完全落在既有的盒子模型內（不新增位置概念），手機怎麼縮已經有答案，不會蓋住內文，也不影響閱讀。
實作上就是新增一個「貼紙」**零件**（`packages/site/src/widgets.ts` 的 `WidgetDef`，類別放進 `header`、`home.hero`、`foot` 這幾個盒子），樣式選項是大小級距（小／中／大）與是否旋轉。
**有一個資料形狀問題（我讀了 `designV3.ts` 的 `cleanPick`）：目前一個「選擇」只有零件 id 與樣式 id，沒有參數**；貼紙需要「哪張圖」，所以選擇要能帶一個媒體參數——這是網站設計資料格式的擴充，要經過網站設計的驗證（`designV3.ts`）與發布快照（`site-render-model.md`：發布時凍結），我**沒有讀網站設計的儲存與合併**，所以這點是「不知道」。
**閱讀與無障礙**：貼紙預設 `alt=""`（裝飾，螢幕閱讀軟體略過）；不放在 `note.left`／`note.right` 的欄裡以免與目錄與側註搶位置；窄螢幕折疊規則由盒子決定。
**每頁的、貼在某一段旁邊的貼紙（a）**：不在 v1；若業主之後要，錨用段落 `^id`，位置沿用 `note.right` 的折疊規則，是另一批。
**網站上的貼紙不影響筆記文字、不進 Markdown 匯出**，因為它在網站設計裡。

### 3.6 輸出逐一說明

| 輸出 | 手寫頁貼紙 | 簡報貼紙 | 網站貼紙（網站設計層） |
| --- | --- | --- | --- |
| 發布網站 | 發布的手寫頁怎麼畫：程式探索報告說網站不畫 `page_images`（當圖片用的 SVG 不能再載入別的檔）；**所以手寫頁貼紙不會出現在發布網站**，與業主「各貼各的」一致，不是缺陷；但已發布的手寫頁若有貼紙，使用者應被告知「貼紙不會出現在網站上」（文案待定） | 簡報不隨網站發布（我沒有查到簡報進發布的路徑） | **會出現**（這是它的用途）；媒體隨發布複製進網站 |
| Markdown 匯出 | 手寫頁匯出成 SVG 圖（`exportInk.ts`）；`inkSvg.ts` 看起來有把頁面圖片畫進去，我沒驗證——若有，貼紙會在那張 SVG 裡 | 不在 Markdown（簡報本來就不在） | 不在（不是筆記內容） |
| 完整備份、還原 | `page_images` 在側車、媒體在 `attachments/`，還原保留檔名 | 同左（同一個屬性） | 網站設計隨工作區設定備份；其中的媒體是否在備份範圍，**不知道** |
| PPTX | 不適用 | 一張圖（3.4） | 不適用 |
| 列印／PDF | 手寫頁列印：同上待驗證 | 不適用 | 不適用 |

### 3.7 同步、合併、資料放哪

- **手寫與簡報共用一個屬性 `page_images`**（不同的頁鍵：`page`／`pdf:<n>`／`slide:<頁鍵>`），沿用它的「依項目 id、每頁」合併、備份側車、媒體認領；**不新增合併屬性**。新增的只有選填的 `rot` 欄位（與日後的 `fx`）。
- 上限：`page_images` 現況每頁最多 100 個；簡報頁鍵會因改標題而變多、孤兒貼紙會累積，**整個屬性大小有沒有上限我不知道**，實作前要查（若沒有要加）。
- 網站層：存在網站設計，不是筆記屬性（3.5）；合併方式不知道。
- 「貼在手寫頁的貼紙不會出現在簡報」是因為頁鍵不同；**一個屬性裝三個畫面以外的東西會混淆**，所以守門測試要證明：寫入手寫頁鍵不會讓簡報看到、反之亦然。
- 手寫合併改版（#1783）：見 3.3。

### 3.8 特效（之後）

- 規則不變：貼紙檔永遠有一張靜態圖；特效是放置的選填欄位 `fx`（沒有＝靜態），所以舊版、列印、PPTX 自然退回靜態。
- **手寫頁**：持續動畫會讓手寫時的畫面重繪、耗電（沒有量測，**不知道**實際成本）；建議只在「沒有在書寫」時才動，或只在回放／唯讀時動。輸出：SVG／列印是靜態第一格。
- **簡報**：播放時可以動（一次性的進場動作比持續閃爍好）；縮圖與編輯畫面靜態。**匯出 PPTX：靜態第一格**（PPTX 的動畫是另一回事，不做）。
- **網站**：發布的網站可以動，但要尊重「減少動態效果」（`prefers-reduced-motion`）；靜態網站沒有 JavaScript 排版，所以只能用 CSS 動畫或動態圖檔；**發布的網站上一律靜態，直到有人需要**，是最簡單的規則（我的建議）。
- 三個畫面各自一句總結：手寫—安靜時才動；簡報—播放時動、匯出靜態；網站—預設靜態。

### 3.9 AI 建議貼紙；特效——調度員的建議與我的看法

調度員：先做靜態貼紙；特效晚一點（平板效能、每種輸出都要定義特效變什麼）；AI 建議貼紙現在不做（收益小、花業主的 AI 額度、AI 只能「建議」所以省不了一步）；替頁面整理版面的 AI 對輸出更有幫助。
我的看法：**同意**。補充：貼紙現在是「三個畫面各自一層」，AI 要建議得先知道使用者想貼哪個畫面，更不划算；「整理版面」是另一個提案，我沒有評估它的可行性。

## 4. 筆記範本

### 4.1 現況（程式裡有的）

- `frontend/src/lib/noteTemplates.ts` 的 `NOTE_TEMPLATES`：日記、會議、讀書、角色表四個；每個有標題（可含 `{date}`、`{datetime}`）、內文、標籤、屬性；`createFromTemplate`（`hooks/useNodeCreation.ts`）建立；入口只有指令面板與編輯器補全。
- 共用變數：`@onden/markdown` 的 `applyTemplateVars`。
- 標籤給子筆記範本（`template_children`，`backend/src/services/templateExpander.ts`）：業主 2026-10-28 決定**不要**預設蓋子筆記（`decisions-ui.md` 該日小節）；若要做是「標籤頁上看得到、能開關」的功能。
- 「父筆記的 `child:` 屬性給新子筆記預設值」（`services/childAttributes.ts`）：一次性複製屬性值。這是「由標籤／父層給新筆記預設值」現成的機制，只管屬性，不管內文。
- Obsidian 的範本（參照）：一個資料夾放範本筆記，插入時代換 `{{title}}`、`{{date}}`、`{{time}}`（1.1）。

### 4.2 一個範本是什麼：選項

| | a 一則被標成範本的筆記 | b 庫裡的項目 | c 兩者都有 |
| --- | --- | --- | --- |
| 使用者自己的 | 自然：就是筆記，有歷史、同步、備份、匯出 | 要另做儲存 | 要兩套 |
| 內建的 | 要在第一次使用時「建立」成筆記，或另外出貨 | 隨 app 打包，現有 4 個就是這樣 | 同左 |
| 理解成本 | 低（和「技能」同一種概念：一則筆記加一個開關） | 中 | 高 |
| 刪不掉的問題 | 使用者刪掉內建範本筆記就不見 | 不會被刪 | — |

**建議：使用者的＝a；內建的維持在程式裡（現有作法，b 的一半）；選擇器把兩者並排顯示**。不為「兩者合一」另建儲存。
「存成範本」的入口：筆記的「文字樣式」之類看得到的位置，不在 ⋯（待 UI 設計；不是 10 題之一）。

### 4.3 複製什麼、不複製什麼

| 複製 | 不複製 |
| --- | --- |
| 內文、標籤、屬性（沿用現有 `createFromTemplate` 的範圍） | 歷史版本、複習排程、發布狀態、「這是範本」的旗標本身、被別人引用的反向連結 |
| 手寫頁、檢視分頁：**第一版先不做**（我不知道檢視與分頁在資料裡怎麼存，沒有讀；手寫頁的圖片又牽涉媒體所有權，3.1 待查 1） | — |

佔位符**只保留現有的兩個**（`{date}`、`{datetime}`，已在 `applyTemplateVars`）；不做 `{title}`、不做格式字串、不做腳本。
理由：範本多半是結構（標題與空欄位），日期是唯一每次都不一樣的東西；每多一個變數就多一個「輸出和匯入」要處理的語法（Obsidian 的格式字串用的是 Moment.js 規則，見 1.1，我們不想承擔）。

### 4.4 內建範本短名單（給資工學生）

1. 課堂筆記（日期、課名、重點、問題、待辦）
2. 閱讀摘要（沿用現有「讀書」範本，不重做）
3. 題目與解法紀錄（題目、卡住的地方、解法、之後要複習什麼）
4. 會議筆記（沿用現有）
5. 每週回顧（本週完成、沒完成、下週三件事）
「日記」沿用；「角色表」是遊戲用，是否留在預設清單由業主決定（Q9）。我沒有調查學生實際怎麼用，這份名單是推測，用意是讓業主挑，不是結論。

### 4.5 「從範本開始」放哪裡

- 空白新筆記上，內文為空時顯示一排範本（看得到，不是 ⋯），開始打字就消失。
- ＋ 不變。指令面板保留現有入口。
- 範本能不能「依空間」或「依標籤」？今天標籤只有（被拿掉預設的）子筆記範本與 `child:` 屬性。建議**不做**標籤綁範本；要做時沿用 `child:` 那種「父層給預設」的手法，並且要看得到、能關。這不是 10 題之一，建議先不做。

我的建議（意見）：**貼紙自己畫（簡單幾何，風格統一，沒有授權疑慮）；介面圖示沿用已有的 Lucide；不收 share-alike 或需署名的素材**。

自己畫的成本我沒有估計：這是人力，不是程式。

大小：自己畫的簡單 SVG 約 1–3 KB（估計，沒有量）；Lucide 已在 bundle 內；Tabler 6545 個全收不合理，只能挑用到的。
每種素材要帶授權聲明檔（`mistakes.md` 有一類「散布的東西沒帶授權」），通過後跑 `npm run notices` 更新 `THIRD_PARTY_NOTICES.md`。

## 8. 請業主回答（10 題，是／否）

1. **app 的主題不影響任何輸出（發布網站、簡報、列印各管各的）？** 建議：是。另一個選擇：讓網站樣式跟著 app 主題（已發布的網站會隨設定悄悄改版）。
2. **社群主題只能是數值（顏色與排版代號），不收樣式程式碼？** 建議：是。另一個選擇：收 CSS（要全部人工審、仍可能外洩資料或弄壞介面）。
3. **不做使用者自訂 CSS 片段？** 建議：是（先不做；日後若要，只做「覆寫 `--ac-*` 變數」的版本）。另一個選擇：做 Obsidian 式任意 CSS。
4. **素材來源與授權：貼紙以自己畫為主；社群貼紙與範本只收 CC0、0BSD、MIT、ISC、Unlicense，不收需署名或 share-alike 的？** 建議：是。另一個選擇：也收 CC-BY（署名要隨使用者發布的頁面帶走，我沒有設計）。
5. **社群庫：項目放在公開的社群庫本身（作者開 PR 加檔），不放作者各自的庫；誰審——主題只靠自動檢查、貼紙與範本人工看、起初只收業主與受邀作者、順了再開放投稿？** 建議：是。另一個選擇：Obsidian 式（作者自己的庫＋清單記固定 commit 與雜湊）；或全部人工審（工作量大）／全部自動（貼紙會替別人的公開作品背書）。
6. **使用者自己的貼紙與範本能加進自己的庫（「我的」）？** 建議：是（貼紙＝標成貼紙的圖片，範本＝標成範本的筆記，不另建儲存）。另一個選擇：只能用內建與社群的。
7. **貼紙貼在三個畫面（簡報、網站、手寫頁），各一層、互不相干，不寫進內文；圖檔複製進自己的媒體（做法 A）；手寫頁與簡報共用 `page_images`、簡報用既有頁鍵當錨、找不到頁的貼紙保留並提示？** 建議：是。另一個選擇：B（存庫項目 id，小，但庫一改舊內容就壞）；簡報頁鍵改成寫進標題的 `^id`（改了筆記文字）。
8. **網站上的貼紙貼在「網站設計的層級」（頁首／首頁開頭／頁尾的盒子，每頁都有），而不是跟著某一段、也不是頁面固定位置？** 建議：是（落在既有盒子模型內，手機怎麼縮已有答案，不蓋住內文）。另一個選擇：跟著段落（要新規則，窄螢幕要決定移去哪）或固定位置（會蓋住字、盒子模型沒有這個概念）。
9. **內建範本：課堂筆記、閱讀摘要、題目與解法紀錄、會議筆記、每週回顧，加既有的日記，「角色表」從預設清單拿掉？** 建議：是。另一個選擇：保留角色表（可分開回答）。
