## 0. 結論

### 0.1 業主 2026-11-01 的決定（照寫）

1. **統一成子節點**：「段落節點」（帶 `{…}` 的區塊）與「搬成子筆記」合併成一個概念。子節點有兩種狀態、同一個身分：**留在原處**（文字在父筆記裡，左邊淡線）與**獨立出去**（文字搬成自己一篇，父筆記原處顯示嵌入）；可以來回切換，身分不變，連結、任務期限、複習進度不斷不丟。介面用語盡量不出現「子節點」，說「這段」。身分靠錨點；範圍與父子照排版即時算，錨點只在區塊開頭當身分（§S1）。
2. **`{…}` 保留**，是段落主題與功能的唯一依據；打什麼就留什麼，系統不自動從正文拿掉。大括號裡可以是主題（`{考點}`）或功能名稱（`{複習}`、`{task}`）。功能名稱在編輯器顯示成功能小圖示，不是標籤；寫了功能名稱的段落出現在該功能自己的頁面；在功能頁按「取消」會把正文的功能名稱拿掉；刪掉正文的功能名稱，功能就關掉（永遠一致）（§S2）。
3. **功能像函式庫，標籤是使用者的主題／類型**，標籤可以引用功能（與 2026-10-30 筆記層級的模型一致）。**主題往下繼承，功能不往下繼承**（§S3）。
4. **段落選單的入口（「做成複習卡」「設為任務」「標記這段」）這版不做**，要先做可在手機上試的原型、業主試過再加。這版段落的主題與功能只有正文 `{…}` 一個入口（加上既有的「搬成子筆記／展開回內文」，改名見 §S1.3）。
5. **顯示**：留在原處的子節點不出現在左側筆記樹；資訊欄加「本篇的段落」，依功能與主題分組、巢狀顯示上下層、點了跳過去（§S4.3）。
6. **連結語法**：`[筆記 › 開頭](筆記#錨點id)`，位址裡的筆記名稱只是提示、認的是 id；嵌入＝同樣寫法加連結標題 `"嵌入"`（不用 `![]`）；標題也用錨點；整篇連結 `[[筆記]]` 不變（§6）。
7. **這版不需要**：`:::` 圍欄、範圍把手、空的 `{}`。只引用半句話列為之後，且只用在連結與嵌入（§13）。
8. **匯出**：`{…}` 留在文字裡本來就帶得走；另給選項：段落連結轉成附原文的腳註（思源先例）、Obsidian 相容（§10）。

### 0.2 這份文件的建議

1. **正文不放任何記號**。錨點存在新表 `block_anchors`（§2）：筆記、錨點 id、起訖、原文 quote、前後文、狀態（有效／可能在這裡／找不到）、別名。
2. **子節點 = 錨點 + `{…}`**（§S1、§S4）：錨點提供身分與位置；有 `{…}` 的錨點才在 `block_nodes`（沿用現有表）有一列，帶主題、功能、上下層與各功能資料。**建議沿用獨立表，不進 `content_nodes`**；獨立出去時，`block_nodes` 列指向那篇新筆記，**列的 id 不變**，所以任務、複習進度、連結都不動。
3. **功能資料以 `block_nodes.id` 為鍵**（§S5）：錨點找不到時資料不丟，列進「找不到的段落」讓使用者重新指定。
4. **編輯器精確搬（M3）＋伺服器補救（M2）**（§3、§4），永不默默指到別處。
5. **連結改標準 Markdown 連結，認 id 不認名稱**（§6）；找不到有三種畫面（§7）。
6. **一次切換**（§11），**分五批**（§12）：地基 → 子節點統一 → 區塊引用改版 → 遷移 → 收尾；合併前業主 Android（注音）真機驗收。

### 0.3 為什麼不再把記號放進正文（實驗摘要）

引自實驗報告（30 個檔案、483 條錨點鏈、5,422 步；合成 174 例；數字與限制以報告為準）：

- 真實歷史：M2、M3 都在 96–97% 的步驟指對、找不到不到 0.2%；行尾 ` ^id`（M1a）有三分之一的步驟找不到，下一行註解（M1b）約 5% 找不到、3.4% 指錯。
- 合成情境：M3 指對 168／指錯 6／找不到 0；M2 147／22／5；M1b 129／13／32；M1a 96／9／69。M3 的 6 個指錯全是「剪下後本篇還留著近似段落」，把找回門檻提到 0.95 後降為 0。
- 正文記號的結構性問題：改到該段就和記號同一行衝突；範圍要成對記號；拆段、接段只能指到整段；超過 `BLOCK_PARSE_MAX`（32,000 字）解析器直接回空。
- 注意：參考答案本身不完美（人工判讀 29 例，參考答案只對 16 例），「指錯」是偏高的上限。

1. **`{主題}` 與 `{{功能}}` 分開**（業主原話：「`{{}}`是功能 `{}`是標籤之類的」）。
   - `{主題}`：區塊最後的主題標籤，照舊。
   - `{{功能}}`：區塊最後的功能，只認得已知的功能名稱；其他 `{{…}}` 當普通文字。
   - 打什麼就留什麼，不會打完就從正文消失（「萬一想留下來呢」）。編輯器把 `{{功能}}` 顯示成功能小圖示，不進標籤樹；那一段出現在該功能自己的頁面；在功能頁按「取消」會拿掉正文的 `{{…}}`。
   - 打 `{{` 跳出功能清單，打 `{` 跳出主題清單。
   - 全形 `｛｝` 與半形都認，存檔時統一成半形。
   - 舊正文裡寫成 `{task}`、`{複習}` 的功能名稱，遷移時改寫成 `{{…}}`。
   - 因此 §15 第 1 題（同名時功能優先）不再需要：功能與主題寫法不同，不會撞名。
2. **標籤帶功能**：`{單字}` 而「單字」這個標籤引用了複習，這段就是複習卡（功能頁標「來自 單字」）；`{單字} {{複習}}` 只算一張。主題往下繼承，功能不往下繼承；透過標籤帶來的功能也只給直接寫了那個標籤的段落。
3. **子節點的標題**：預設自動產生——標題就是標題文字；段落或清單項是第一行開頭一段，不含 `{…}`、`{{…}}`，文字改了就跟著變。可以另外取名，存在節點上，不寫進正文。獨立出去時有名字就用名字當筆記標題；收回時名字留在節點上。
4. **連結語法定案**（取代 §0.1 第 6 點與 §6.1 的 `[筆記 › 開頭](筆記#錨點id)`）：
   - `[[筆記]]` 是整篇；`[[筆記/標題、名字或段落開頭]]` 是那篇裡的某一段，可以多層（`[[筆記/這節/這段]]`）；`[[/文字]]` 是同一篇；`![[…]]` 是嵌入。
   - `#` 只用在標籤：業主說 `[[吃飯紀錄#晚餐的結論]]` 會讓人以為「晚餐的結論」是標籤，所以改用 `/`（業主：「可以 就這樣試試」）。
   - 標題本身含 `/` 時，先找標題完全相同的筆記。`[[內容]]` 沒有 `/` 時，先找同名筆記，找不到才找開頭符合的段落；唯一就連，多個就讓使用者選。
   - 真正的綁定存在旁邊的表（錨點 id），文字只給人看；`/` 後面的文字只在使用者編輯引用那篇時順便更新（學 InDesign）。畫面顯示「筆記 › 開頭」。
   - `((` 與「複製段落連結」產生這種連結；拿掉行尾打 `^` 的入口；版本歷史的差異不露出 id。
   - 找不到時：「可能在這裡」一鍵確認；「已刪除的段落」顯示原文加刪除線；或退成連到整篇。
5. **匯出**：預設保留 `{…}`、`{{…}}`、`[[…/…]]`；選項有「標準連結」「段落連結轉成附原文的腳註」「Obsidian 相容」（寫成 `[[筆記#標題]]` 與行尾 `^id`）。
6. **這版不做**：段落選單的功能／標記入口（「先不做 之後加」「我怕手感不理想」）、`:::` 圍欄、範圍把手、只引用半句、Eg-walker、Loro。

## S1. 子節點：一個概念、兩種狀態

### S1.1 一句話

> 一段文字有了身分（錨點）又寫了 `{…}`，它就是子節點。子節點可以**留在原處**（文字在父筆記）或**獨立出去**（文字搬成自己一篇，父筆記原處顯示嵌入），兩種狀態是同一個子節點，來回切換不換身分。

現在有兩套東西做相近的事：段落節點（`block_nodes`，文字留原處，B1–B4）與搬成子筆記（`blockChildNote.ts`，文字搬走，原處留 `![[子筆記]]`，B5）。使用者要分辨「這是段落還是子筆記」「搬了以後我的任務期限還在不在」。統一後只有一個問題：**這段要放在這裡，還是自己一篇**。

### S1.2 身分與範圍：錨點只當身分，範圍即時算

- **身分**：開頭位置的錨點（§2）。正文不放 `^id`。
- **範圍與父子**：照排版即時算，沿用現行規則（段落＝自己、清單項＝含子項、標題＝到下一個同級或更高級標題；引用／提示框＝整塊），不記整個範圍。
- **為什麼錨點不記整個範圍**：若記起訖，在一節末尾新增一段，新段落落在記錄的終點外，要靠「邊界打字納不納入」規則猜；而使用者的直覺是「標題底下新增的段落就屬於這一節」。範圍由排版算，這個直覺自然成立，不需要邊界規則。代價：範圍會因排版改變（刪掉空行讓兩段併一段、改標題層級），這是現行就有的行為（`block-nodes.md`「已知行為」第 13 點），編輯器仍在游標所在的子節點旁用淡線標出範圍。
- 因此 §2 的 `range` 種類**這版不需要**（業主決定 7）；`block_anchors` 只存單點。起訖欄位的 `end` 退為「這段開頭那個區塊的結尾，用來核對 quote」，不當範圍使用。

### S1.3 兩種狀態與來回切換

| | 留在原處 | 獨立出去 |
|---|---|---|
| 文字在哪 | 父筆記正文，左邊淡線 | 自己一篇筆記（`content_nodes`），父筆記原處是嵌入 |
| `{…}` 寫在哪 | 區塊最後（正文） | 主題變成那篇的標籤、功能變成那篇的功能（§S2.5） |
| 身分 | `block_nodes.id`（不變） | 同一個 `block_nodes.id`（`detached_note_id` 指向那篇） |
| 錨點 | 父筆記裡，起點在區塊開頭 | 錨點改指那篇筆記的第一個區塊（標題或內文開頭），連結 `(筆記#id)` 不用改 |
| 切換 | 「獨立出去」 | 「收回原文」 |

- 介面用語：「**獨立出去**」「**收回原文**」，取代「搬成子筆記」「展開回內文」。畫面只說「這段」，不說「子節點」「錨點」。
- 兩個動作是同一個領域操作的兩個方向（沿用 `services/blockChildNote.ts` 的交易、cascade 與復原單位：根事件是原筆記的存檔，`restoreEvent(根事件, { cascade: true })` 一次復原）。差別是：**不再「複製」複習進度、不再擋任務行**——因為功能資料以 `block_nodes.id` 為鍵（§S5），切換時列不動，期限、重複、複習進度自然跟著。現行 B5 「任務行擋下 `block_has_task_line`」「複習進度複製成子筆記的 `review_states`」兩條規則因此消失，由「功能資料不動」取代。
- 連結改寫簡化：現行 B5 要把 `[[原筆記#^id]]` 改成 `[[子筆記]]`。新模型連結認錨點 id（§6），錨點跟著走，**引用端不用改寫**——這解掉「沒權限改的引用」整段規則（`unwritable: "leave"`、展開回內文永遠拒絕）的來源。
- 擋下的情形沿用：子筆記底下還有筆記、有屬性、內文不是單一區塊、引用／表格／程式碼區塊不能獨立出去。這些是「這段能不能自己成一篇」的條件，與統一無關。（屬性的對應見 §S4.5。）

### S1.4 與「搬到另一篇筆記」的關係

`block-nodes.md` 已決定「搬到另一則筆記第一版當成刪除＋新建，進度不帶」。新模型下，App 內建的搬移（§5.1）帶著錨點與 `block_nodes` 列一起搬，進度跟著；編輯器剪下貼上走 §5.2 的推論規則。這個行為改變列入 §15。

## S2. `{…}`：段落的主題與功能的唯一依據

### S2.1 規則

- 寫了 `{…}` 的區塊就是子節點。**打什麼就留什麼**：系統不自動把 `{…}` 從正文拿掉、不改寫。
- 大括號裡逗號分隔的每一項，可能是：
  - **主題**：`{考點}` → 顯示成標籤，進標籤樹，往下繼承（§S3）。
  - **功能名稱**：`{複習}`、`{task}` → 顯示成功能小圖示，**不是標籤**，不進標籤樹、不當主題，不往下繼承。
- 認定位置、程式碼與數學裡不算、句子中間不算：沿用 `block-nodes.md` §2 的規則。
- 現有筆記裡的 `{task}`、`{複習}` **原樣保留**，只是顯示改成功能圖示。這部分不需要遷移（正文一字不改）；`block_nodes` 與任務／複習資料的對應見 §S5。

### S2.2 打 `{` 時的選單：名稱與功能同名

名稱解析順序：該工作區的功能名稱（內建模組＋標籤引用來的功能名）先比，再比主題。**同名時選單列兩項讓使用者選**：「功能：複習」與「叫『複習』的主題」。選了才寫進去；選「主題」寫入的文字相同（`{複習}`），所以正文不能表達這個選擇——**以選單當下的選擇建立或沿用主題標籤，之後名稱同時匹配功能與主題時，功能優先、主題照常存在**。這點與「打什麼就留什麼」並存的方式：使用者想要主題時，把主題標籤改名避開功能名（標籤名撞功能名時，標籤頁提示）。列 §15。

### S2.3 功能頁與正文永遠一致

- 寫了功能名稱的段落出現在該功能自己的頁面（複習頁、任務頁、技能清單…）。
- 在功能頁按「取消」（取消複習、取消任務）= 領域操作，**把正文的功能名稱拿掉**（走一般內文寫入，有事件、可復原）。
- 刪掉正文的功能名稱 = 功能關掉：`block_nodes` 的功能欄位與它的啟用狀態從正文重算，不另存「是否啟用」。
- **資料保留**：拿掉功能名稱時，該功能對這段的資料（任務期限、重複規則、複習進度）**保留並隱藏**（沿用 `block-nodes.md` 已決定 1）；再寫回同一個功能名稱就恢復。
- 正文是唯一真相來源，功能頁、資訊欄都從它派生。這一條取代舊文件「功能頁/選單 → 寫入 `{…}`」的雙向入口：這版只有正文一個入口。

### S2.4 功能名稱在編輯器怎麼顯示

主題顯示成標籤（現行小標籤）；功能名稱顯示成功能小圖示（沿用該模組已登記的圖示，`modules/<id>/index` 的登記資料）。游標進入該區塊的 `{…}` 時展開成可編輯文字。不認得的名稱＝主題（找不到會建立，沿用 `tagIdForWrittenName`）。

### S2.5 獨立出去 / 收回時 `{…}` 怎麼走

- 獨立出去：`{…}` 裡的**主題**變成那篇筆記的標籤，**功能**變成那篇的功能（走該筆記取得功能的同一條路，§S3），原位置的 `{…}` 隨文字一起搬走。
- 收回原文：那篇筆記目前的標籤與功能寫回 `{…}`。
- 往返一次後 `{…}` 的內容與順序應相同（性質測試，沿用 `blockChild.ts` 的「搬出再展開還原原文」）。

## S3. 功能與標籤的關係

### S3.1 模型（與 2026-10-30 筆記層級一致）

- **功能像函式庫**：複習、任務、技能、欄位等能力的名稱與行為由模組定義。
- **標籤是使用者的主題／類型**：標籤可以**引用功能**（標籤頁「＋加功能」；例：`單字` 標籤帶來複習與欄位）。
- 段落得到功能兩條路：(a) `{功能名}` 直接開；(b) 貼了帶功能的主題（`{單字}`），功能頁上標「來自 單字」。

### S3.2 主題往下繼承，功能不往下繼承

> **2026-11-09 改了**：業主決定段落不繼承任何標籤，主題也不繼承，和筆記一樣（`block-nodes.md` §5）。下面「主題往下」那一列不再成立；「功能不往下」照舊。

| | 繼承 | 理由 |
|---|---|---|
| 主題（標籤） | 往下 | 「這節是考點」「這篇是課程 X」是範圍性的分類 |
| 功能 | 不往下 | 父項是任務不代表子項是任務；父段是複習卡不代表子段也是 |

先例（未重新驗證，憑記憶）：CSS 的 color、font 繼承，border、margin 不繼承；Java 註解預設不繼承、加 `@Inherited` 才繼承；org-mode 的 `org-tags-exclude-from-inheritance`；「包含」不等於「繼承」。

**與現行的差別**：現行 `effectiveBlockTags`（`block-nodes.md` §5、B1c）用 `tag_is_inheritable` 決定標籤繼不繼承，並以「提供模組能力的標籤預設不繼承」間接做到「功能不繼承」。新模型把兩件事分開：**主題繼承規則**維持（`tag_is_inheritable` 保留給使用者想讓某主題不繼承時用）；**功能完全不走繼承**（功能名稱不是標籤；帶功能的主題貼在段落上時，功能只屬於貼它的那一層，來源標「來自 單字」）。`effectiveBlockTags` 因此可以拿掉「提供模組能力就不繼承」這個推導條件，改成「功能不是標籤，不進這個函式」——搬到更直接的根因，不是在每個入口補分支。

### S3.3 還要決定的

標籤引用的功能是否在標籤被「往下繼承」時一併帶到子段落？**不帶**（功能不繼承是硬規則）。子段落若也要複習，自己寫 `{複習}` 或自己貼 `單字`。列 §15 確認。

## S4. 儲存與可見位置

核心問題：子節點要像筆記一樣能有標籤、功能、欄位、被查詢、被連結，又不能讓每個任務行跑進筆記樹、搜尋重複、備份重複、發布集合、嵌入向量。

### S4.1 兩種做法

| | A. 進 `content_nodes`（`node_type = 'block'`） | B. 沿用 `block_nodes` 獨立表（建議） |
|---|---|---|
| 標籤、屬性、權限、同步 | 直接沿用 | 標籤用 `block_node_tags`；屬性要另做（§S4.5）；權限＝所屬筆記 |
| 預設可見性 | **預設到處看得到**：現在 216 個查詢讀 `content_nodes`，多數不分 `node_type`；每個任務行、每張卡都跑進樹、搜尋、git 備份（每節點一檔）、嵌入向量、發布集合、計數，每處要排除，漏一處就外洩或重複 | **預設任何地方都看不到**，要看見的地方明確加入並寫進本文件 |
| 獨立出去 | 同一列改 `parent` 與型別？但「內文在父筆記」與「內文是自己」兩種狀態要一列表達兩種文字來源，所有讀 `markdown` 的地方都得分辨 | `detached_note_id` 指向新的 `content_nodes` 筆記；兩邊各司其職，切換只動這一欄 |
| 風險 | 重複與外洩（難察覺） | 屬性、查詢要自己接（明確、可測） |

**建議 B**，理由與 `block-nodes.md`「儲存方式」一節相同，新模型再加一條：**獨立出去的內容是真筆記（`content_nodes`），留在原處的是索引列（`block_nodes`）**，兩者不在同一張表裡混著放，才不會「同一個東西有時是筆記、有時不是」。

### S4.2 身分怎麼貫穿兩種狀態

```
block_anchors（位置）            block_nodes（子節點）
  anchor_id  ─────────────────→  anchor_id   （1:1，只有帶 {…} 的錨點才有列）
  note_id、起點、quote、狀態       id          ← 任務/複習/技能資料都以這個為鍵
                                 parent_block_id、kind、label
                                 detached_note_id   NULL＝留在原處；非 NULL＝獨立出去
                                 hidden_at、created_at…
```

- **身分＝`block_nodes.id`**（uuid，既有；功能資料已經以它為鍵：`block_review_states.block_id`、`block_nodes.task_id`），**連結認 `anchor_id`**（文字 id，在連結位址裡）。兩者 1:1，錨點不換、`block_nodes.id` 不換。
- 獨立出去：建 `content_nodes` 新筆記 → `block_nodes.detached_note_id` 設值 → 錨點改指新筆記第一個區塊（`block_anchors.note_id` 與起點同交易更新）→ 父筆記原處寫入嵌入連結（`[筆記 › 開頭](筆記#id) "嵌入"`，§6.4）。收回：反向，`detached_note_id` 清空，新筆記進垃圾桶（沿用現行規則）。
- 沒有 `{…}` 的錨點（只是被連結的段落）沒有 `block_nodes` 列；之後寫了 `{…}`，存檔時為它建列（`anchor_id` 對應既有錨點，沿用錨點 id）。拿掉所有 `{…}`：列隱藏、資料保留（`hidden_at`），錨點仍在。
- 兩個 id 不合併成一個的理由：`block_nodes.id` 已被 5 個以上的資料表引用，改成文字 id 需要遷移所有外鍵；`anchor_id` 要出現在連結與匯出，需要短、可讀（6 個十六進位字元）。

### S4.3 每個可見位置的規則

| 位置 | 留在原處 | 獨立出去 | 說明 |
|---|---|---|---|
| **左側筆記樹** | 不出現 | 出現（它是一篇筆記，在父筆記底下） | 業主決定 5；`block_nodes` 預設不進樹 |
| **資訊欄「本篇的段落」** | 出現，依功能與主題分組、巢狀顯示上下層、點了跳過去 | 同樣出現（標「已獨立」，點了開那篇） | 沿用資訊欄功能分頁的列樣式；上下層由排版算（留在原處）或由 `parent_block_id` 取（獨立出去） |
| **全文搜尋** | 搜尋命中**父筆記**，不另列（文字在父筆記裡本來就被索引一次） | 命中那篇筆記 | `block_nodes.text_cache` **不進**搜尋索引；`reads.notes.search` 不改 |
| **查詢區塊（`tags:`、「包含段落」）** | 預設只看自己有該主題的段落；「包含段落」再加繼承到的 | 當一般筆記查詢（它有自己的標籤） | 沿用 `POST /api/query` 的 `blocks`；獨立出去的不重複列（`detached_note_id` 不為空者從 `blocks` 排除，因為它已經是筆記） |
| **功能頁**（複習、任務、技能清單…） | 列出，點了回到父筆記該段 | 列出，點了開那篇 | 兩種狀態同一條查詢（以 `block_nodes.id` 為鍵），顯示來源（來自父筆記／獨立筆記） |
| **git 備份、備份檔** | 不另備（文字在父筆記；`block_nodes`、`block_anchors` 列隨工作區匯出） | 隨它的筆記備份一次 | 與 `block-nodes.md`「文字快取不外流」同一規則；不重複文字 |
| **發布集合** | 隨父筆記整篇發布或不發布；`block_nodes` 不另成頁面 | 獨立出去的筆記有自己的發布設定（它是真筆記） | 切換時要提示發布狀態變化：留在原處→獨立出去，**新筆記預設不發布**（否則一個段落意外變成公開頁）；收回時以父筆記的發布設定為準 |
| **嵌入向量** | 不另算（父筆記算一次） | 那篇筆記自己算 | `text_cache` 不進向量 |
| **AI／MCP** | 讀寫都經父筆記（`updateNode` 共用入口）；查詢工具可選回傳「本篇的段落」清單（id 用 `block_nodes.id`，不用錨點文字 id） | 當一般筆記 | 不新增直接寫 `block_nodes` 的工具；子節點的主題、功能由改 `{…}` 的內文寫入達成，與使用者同一條路 |
| **同步** | `blocks`（含錨點）隨筆記增量送，用戶端從手上的父筆記正文切文字 | 隨它的筆記 | 沿用現行 `replace_for`；`block_anchors` 加進（§9） |
| **垃圾桶／復原** | 隨父筆記進垃圾桶、復原 | 獨立筆記自己進垃圾桶；`block_nodes` 列因 `detached_note_id` 跟著隱藏 | 沿用 `retained_node` 規則 |

### S4.4 功能資料存哪、錨點找不到時不丟

功能資料全部以 `block_nodes.id` 為鍵（不是以錨點文字 id、也不是以位置）：

- 任務：`block_nodes.task_id` → 既有的任務節點（`#task`＋`_task_status`，期限、重複、提醒都在任務節點上，照舊）。
- 複習：`block_review_states`（每人一份）。
- 技能設定：沿用 `nodes` 範圍傳 `block_nodes.id`（`block-nodes.md` 技能一節「未做」，這版仍不做，但資料鍵先定）。

**錨點找不到（`lost`）時**：`block_nodes` 列與所有功能資料**原封不動**，功能頁的列顯示「找不到段落」（附 quote 與最佳猜測），資訊欄「本篇的段落」下新增「**找不到的段落**」一區。使用者可以：
- 「重新指定」→ 選一段文字，把這個子節點的錨點重建到那裡（走領域操作 `blockAnchorReassign`，同一交易寫錨點＋事件；`block_nodes.id` 不變，資料全部沿用）；
- 「刪除」→ 才真的丟資料（含確認，可復原）。
任務與複習進度不會自己掛到別的段落，也不會自己消失。

### S4.5 獨立出去時的欄位與屬性

獨立出去的是一篇真筆記，可以有欄位（`node_attributes`）。留在原處的段落**這版沒有自己的屬性**（`block-nodes.md` 提過的 `{重要, 狀態: 草稿}` 屬性寫法不做，維持「以後」）。因此：獨立出去時沒有屬性要搬；收回時筆記**有屬性則擋下**（`child_has_properties`，沿用現行擋下條件），避免把屬性丟掉。

### 1.2 哪些功能依賴 `^id`

- `[[筆記#^id]]` 連結與 `![[筆記#^id]]` 嵌入（`index.ts` `linkTarget`、`remarkBlockRefLabels`、`extractBlock`）。
- 摘錄（`excerpt.ts`）：引用區塊以 `> ^id` 結尾，`![[筆記#^id]]` 嵌入。
- 任務：`block_nodes.task_id`；`TaskRow.block_ref` 由 `block_nodes` 取（`tasksStore.ts`）；點任務開筆記捲到那一行。
- 被引用次數 `blockCitations`（「被引用 N 次」）。
- 段落節點的標籤、繼承、複習、技能（`block_nodes`、`block-nodes.md`）。
- 段落歷史、最近存的段落（`recentBlocks`，只存筆記 id＋`^id`）、AI 建議沿用原 id、@ 提及的工作階段（`anchor_block_id`）、簡報的頁面鍵（標題的 `^id`，`modules/slides/pages.ts`）。
- 匯出：匯出的 Markdown 現在保留 `^id`（`block-nodes.md`：「Obsidian 認得」）。

### 1.3 id 什麼時候產生：不是每段都有

用現行 `assignBlockIds` 實測（腳本見附錄 A）：

```
普通段落                      → 沒有 id
- 普通清單項                  → 沒有 id
- 貼了標籤的項 {重要}         → 補 ` ^aaaa01`

## 標題 {a}                   → 補 ` ^aaaa02`
> 引用 {q}                    → 補 `\n\n^aaaa03`（自成一行，在引用之後）
#hashtag 段落 ^obs001         → 原樣保留（Obsidian 寫法）
```

`parseBlocks` 只認「有 `{標籤}` 或 `#標籤 ^id`」的區塊為段落節點；沒標籤的區塊只有在下列情況才有 id：

1. 貼標籤、`{task}`（存檔時 `withBlockIds` 補）；
2. 被引用：複製段落連結、貼段落連結時才補；
3. 任務放進筆記（`placement.ts`）；
4. @ 提及要建工作階段（`agentSessions.ts`）；
5. 摘錄引用、段落搬成子筆記；
6. 使用者或匯入的檔案自己寫 `^`。

所以「全部段落都有隱藏 id」不是事實。這很重要：新語法的重點是**少數**區塊多一行，不是每段都多一行。

### 1.4 現行有的三種寫法（遷移要全部認得）

| 形式 | 例 | 用在 |
|---|---|---|
| 行尾 | `- [x] 吃飯 {task} ^d8f47e` | 段落、清單項、標題 |
| 自成一行（空行後） | `> 引用\n\n^q00001` | 引用、清單整體、表格（Obsidian 對結構區塊的寫法） |
| 引用最後一行 | `> ^id` | 引用（摘錄） |

## 2. 錨點表

### 2.1 一句話

> 段落身分不寫在正文裡，寫在 `block_anchors`；正文是純 Markdown，沒有任何記號。錨點在 Onden 裡有效，匯出時才選擇性寫成 ` ^id`（§10）。

### 2.2 欄位（草圖；實作時以遷移檔為準）

| 欄位 | 內容 |
| --- | --- |
| 工作區、筆記 | 與 `content_nodes` 同一工作區；筆記刪除（進垃圾桶）時錨點留著，復原時一起回來 |
| 錨點 id | 6 個十六進位字元起（沿用 `newBlockId`）；在工作區內唯一（`UNIQUE (workspace_id, anchor_id)`） |
| 種類 | 這版只有 `block`（單點：起點在區塊開頭，當身分；範圍與父子照排版即時算，見 §S1.2）。`range`（範圍）業主決定這版不需要，欄位預留 |
| 起點 | UTF-16 code unit 位置（與 `textPatch.ts` 同單位，欄位名帶 `_utf16`），**附 `at_body_hash`／事件游標**：這組位置對應哪一版內文 |
| 原文 quote、前後文 | 建立或最後一次確認有效時的原文；前後各一行。是找回、核對、連結後援文字的依據 |
| 狀態 | `valid`（有效）／`maybe`（可能在這裡，待使用者確認，附候選位置）／`lost`（找不到，附最佳猜測） |
| 子節點 | 若這個錨點有 `{…}`，`block_nodes.anchor_id` 指向它（1:1，§S4.2）；沒有 `{…}` 的錨點只是被連結的段落 |
| 別名 | 一段可有多個錨點 id：兩段接成一段時兩個 id 都指到合併後的區塊（`merged_into` 或同一列多個 id；實作時選較簡單者）。**舊 id 永不重用**：id 一旦發出就留在表裡（`lost` 也保留），新 id 避開表內所有 id |
| 最後搬移 | 時間與原因（編輯器搬／差異搬／找回／使用者確認），給除錯與「可能在這裡」畫面 |

### 2.3 一致性規則

- **位置與內文同一交易更新**：寫內文的交易內搬錨點，提交時內文版本與錨點的 `at_body_hash` 一致；不存在「新內文配舊位置」的瞬間。失敗一起回滾。
- 搬移只在內文寫入的共用入口做（`applyBodyChange`／`nodeUpdate`，§4.3），其餘入口不自己動錨點表。
- 讀取權限跟著筆記：能讀筆記才能讀它的錨點（沿用 `services/readPolicy.ts`），錨點表不另立可見性規則。寫入（建立、確認、重新指定）需要該筆記的編輯能力。
- 錨點的建立、確認、遺失、重新指定都是領域事件（一般事件，文字用白話，不帶 id），可進歷史與復原。

### 2.4 別名與「舊 id 永不重用」

連結只認 id。兩段接成一段時兩個 id 都有效；拆成兩段時見 §5。先例：Akoma Ntoso 的 eId／wId、立法「插入 12A 不重編號」、維基百科 `{{anchor}}`（皆見 §16，未驗證）——對外的名字不因結構變動而換，變動時多一個名字而不是替換。表內保留所有發過的 id，所以不需要另設「已退役 id」表。

### 2.5 比較過的兩種設計

| | A. 正文記號（上一版：`<!-- ^id -->`） | B. 錨點表（本版） |
| --- | --- | --- |
| 輸入法 | 要處理隱藏行與組字，真機驗收風險高 | 正文沒有東西，沒有這類風險 |
| 合併 | 記號行與鄰行可能衝突；遷移期要正規化 base | 內文合併不變（逐行 diff3）；錨點由搬移處理 |
| 範圍、拆段、接段 | 要成對記號或只能指整段 | 起訖位置，字元級精確 |
| 外部工具 | 其他軟體看到註解 | 完全乾淨；代價：錨點只在 Onden 裡有效 |
| 新成本 | 低 | 新表、同步、備份、匯出入都要帶；搬移邏輯與守門 |

採 B：業主接受「錨點只在 Onden 裡有效」，B 的新成本是一次性的工程，A 的成本是每天的使用問題。

## 3. 編輯器精確搬（M3）

### 3.1 存檔請求多帶什麼

現行存檔帶 `markdown_patch`＝`{ base_hash, hunks: [{ at, del, ins }] }`。新增（欄位名草圖）：

```ts
body_change?: {
  changes: unknown;        // CodeMirror ChangeSet.toJSON()，相對 base_hash 那一版
  device_id: string;       // 裝置識別（寫入端既有的 client id，不新增新概念）
  actor_kind: "user" | "agent";
  parent_version: string;  // 這組改動建立在哪一版之上（事件游標或 body hash）
}
```

- `changes` 與 `hunks` 描述同一件事；伺服器**以 `hunks` 為準還原內文**（現有路徑不變），`changes` 只用來搬錨點。`changes` 套到 base 後必須等於伺服器還原出的新內文，否則丟掉 `changes`、改走 M2（編輯器送的不可信）。
- 沒有 `changes`（舊客戶端、離線佇列重送、非編輯器寫入）→ 直接走 M2，不是錯誤。
- 事件裡記父版本與裝置（見 §3.4），之後可以直接餵給 Eg-walker。

### 3.2 伺服器怎麼搬

1. 還原新內文（現有 `resolvePatched`），驗證 `changes` 套 base 後與新內文相同。
2. 對該筆記每個有效錨點：起點 `mapPos(pos, 1, MapMode.TrackDel)`，終點 `mapPos(pos, -1, MapMode.TrackDel)`。回傳 `null`（端點落在被刪區間）或範圍變空 → 該錨點走 M2 找回。
3. **核對（報告 §6 缺的那道）**：取搬完的新範圍文字，與 quote 比相似度（字元二連詞 Dice，與 §4 同一個函式）。≥ `keep`（起始 0.5）→ 有效並更新 quote；< keep → 這是「位置還在、內容被換掉」（報告 §4 第 4 點），改走找回，**不沿用位置**。
4. 起點 `assoc 1`、終點 `-1` 的效果：在範圍邊界打字**不納入**範圍（範圍不向外長；Peritext／Automerge `expand: none` 的預設）。這是產品規則，列入 §15。

### 3.3 為什麼不信編輯器送的位置

我們不讓編輯器送「搬完的位置」，只送 `ChangeSet`，由伺服器自己搬——舊版客戶端或離線佇列重送可能讓編輯器的錨點狀態過期。伺服器只信「改動」，並用 quote 核對搬移結果；兩層都對不上才降級。

### 3.4 之後：Eg-walker 的地基（只列，不在本批做）

業主希望之後自己實作 Eg-walker（只在伺服器、先跑影子模式）。本批只做**事件格式**的準備：

- 每次內文寫入事件記：**父版本**（這次改動建立在哪個版本之上）與**裝置／代理識別**。兩者在 M3 本來就要（`parent_version`、`device_id`），所以不是額外負擔。
- 這樣事件圖（誰在哪個版本上改了什麼）已完整，之後可以離線重放成 Eg-walker 的輸入，與現行逐行 diff3 的結果並排比較（影子模式：算但不採用，只記差異）。
- **本次內文合併規則不變**：逐行 diff3（業主 2026-10-17 決定）。換成逐字合併需要業主另行同意；重疊才算衝突的政策也在那時才定。
- Loro 之類的 CRDT 函式庫只在要做多人即時編輯時評估（§13）。

## 4. 伺服器補救（M2）

### 4.1 什麼時候走這條

沒有可信 `ChangeSet` 的所有內文寫入：三方合併後的結果（兩台裝置的改動合併，位置要相對**合併後**內文）、AI／MCP 工具、匯入、任務模組直接改內文、復原／回到舊版、背景寫入、舊客戶端。

### 4.2 演算法

1. **逐行差異**（`diffArrays`）：沒變的行直接搬；被取代的區塊與錨點重疊 ≥ 一半就把新行納入；範圍內部的插入納入、邊界上的插入不納入。
2. **改過的區塊內再做字元差異**（`jsdiff`；相隔 <4 字元的相等片段併成一次取代）→ 建成 `ChangeSet`，之後和 M3 同一條 `mapPos` 路徑。**不要整篇做字元差異**（報告 §6：175k 字大改要 198 ms，700k 字太慢；逐行再區塊內字元差異在 175k 字小改約 1 ms、大改 22 ms 內）。
3. **核對**：新範圍與 quote 的相似度 < keep（0.5）或整段消失 → 找回。
4. **原文找回**：在全篇找最像 quote 的連續行（字元二連詞 Dice 係數；`diff-match-patch` 的 `match_main` 有 32 字元樣式上限，不採用，這點報告未實測）。

### 4.3 三段結果與門檻

| 找回相似度 | 候選 | 結果 |
| --- | --- | --- |
| ≥ 0.9（起始值；實驗掃 0.9～0.95，見下） | 唯一（並列的用前後文分，分不出就算不唯一） | **有效**：直接放上，更新 quote |
| 略低（0.5～0.9），或 ≥0.9 但候選不唯一 | 一個以上 | **可能在這裡**（`maybe`）：存候選位置，UI 一鍵確認（§7） |
| 再低，或只對上一個關鍵詞 | — | **找不到**（`lost`）：保留 quote 與最佳猜測，UI 附猜測（Brush 等 MSR 2000/2001 的先例，§16，未驗證） |

**永不默默指到別處**：只有「有效」會改變連結實際落點。

門檻依據（報告 §5 掃描）：find 0.8→0.9，M2 歷史指錯 180→153、找不到 6→30；0.95 再少 3 個指錯、多 20 個找不到。指錯比找不到嚴重（使用者會信任錯的連結），所以起始值 0.9；**這是建議起始值，上線前用日常筆記重調**（§14）。keep 0.5 是平衡點（0.7：指錯 −15、找不到 +63）。

### 4.4 搬移只在共用入口做＋守門

- 在內文寫入共用入口（`applyBodyChange`，由 `services/nodeUpdate.ts` 等共用）寫入內文後、同一交易內搬錨點。報告 §6 列出的寫入路徑，**都只負責走共用入口**：`nodeUpdate`、`eventRestore/restore.ts`、`history/rewind.ts`、`history/agentRunUndo.ts`、`agentTools/updateNode.ts`、`suggestEdit.ts`、`editArgs.ts`、`aiSuggestions.ts`、`agentRuntime/api/tools.ts`、`deliver.ts`、`modules/importers/markdown/note.ts`、`importers/notion/database.ts`、`modules/rss/save.ts`、`modules/tasks/{focus,placement,lines}.ts`、`services/dayNotes.ts`、`dispatcherQueue.ts`、`noteDuplicate.ts`。（報告說這份清單是 `grep` 結果、沒逐一讀過；批 0 要逐一確認，並找出清單外的。）
- **守門測試**（`src/test/guards/*.guard.test.ts`，預設拒絕）：寫 `content_nodes.markdown`／等價欄位的程式，不經 `applyBodyChange` 就失敗；例外清單只准減。
- **找回有每次存檔的上限**：整篇掃描 175k 字約 50 ms、700k 字約 200 ms，所以每次存檔最多找回 N 個（起始值 5，實測調整），超過的標 `maybe`/`pending` 並延後到背景工作（走既有 outbox／系統工作，不新增各自提交的流程）。背景工作寫入前重驗筆記版本（內文又變了就用新版重算）。

### 4.5 複製筆記

`noteDuplicate.ts`：新筆記的錨點要不要一併複製是產品決定（§15）。建議預設**不複製**（新筆記是新身分，別處的連結仍指向原筆記）。

## 5. 搬一半、拆段、剪貼

**標明：本節整體是推論，要實測。**

### 5.1 App 內建的搬移

拖段落、移動到…、獨立出去、收回原文（原「搬成子筆記／展開回內文」，§S1.3）：這些操作本來就知道「哪一段去了哪裡」，直接把錨點的筆記與位置一起更新（同一交易，經 `applyBodyChange` 的「帶錨點搬移」參數），不靠找回。沿用 `services/blockChildNote.ts` 的邊界；`block_nodes` 列（含任務、複習進度）跟著錨點一起搬，不是刪除＋新建（與 `block-nodes.md` 已決定 2 不同，列 §15）。

### 5.2 編輯器剪下→貼上

- 剪下與貼上是兩個動作，伺服器看不出關聯，所以**用剪貼簿帶**：CodeMirror 的 `userEvent` 為 `delete.cut` 時，把被剪範圍涉及的錨點（id、被剪的相對範圍、quote）放進剪貼簿的私有格式；`input.paste` 時讀回，把錨點重新建在貼上的位置（可能在另一篇筆記）。
- **剪走的部分佔原文 ≥50% 且夠長（起始：≥12 字）才跟過去**；否則錨點留原處（Word 書籤的行為；git `-M 50%` 的先例）。
- 各半不確定（例如各約一半）→ 錨點兩處都標記，連結顯示「這段已分成兩處」，讓使用者選其中一處（§7）。
- 貼到沒有 Onden 剪貼簿資訊的地方（外部）→ 錨點留原處，貼出去的是純文字。複製（不是剪下）：預設不帶錨點，新位置得到新 id 才有意義——**待實測**；或維持舊行為「複製段落連結」另有入口。

### 5.3 拆開一段

**兩種段落，兩種規則。**

**沒有 `{標籤}` 的段落**：在段中按 Enter（有空行時）：單段錨點留在**前半**（連結文字存的是段落開頭），後半段需要時再「複製段落連結」。Enter 本身維持原本的行為（段內換行）。要在真機上確認手感。

**有 `{標籤}` 的段落（業主 2026-11-08 同意「好」，批 3 實作）**——段落因為 `{標籤}`（行內功能／主題寫法，只認段落最後一行的結尾，`block-nodes.md` §2）才是一個項目（任務、複習卡、有標籤的段落），所以：

1. **Enter 在段落任何位置都把它切成兩段**（插入空行），不是段內換行。
2. **段落的身分跟著含 `{標籤}` 的那一半**：錨點、`block_nodes` 那一列（複習進度、任務狀態、標籤）、指向它的連結與綁定都留在有 `{標籤}` 的那一半。標籤在後半時身分搬到後半，前半變成沒有身分的新段落（沒有錨點、沒有列、沒有進度）。
3. 沒有 `{標籤}` 的段落照上面的做法：錨點留在前半。
4. 在沒有身分的那一半再打 `{標籤}` → 建一個新項目（新錨點、新列），**不複製**任何進度。
5. **Shift+Enter**＝段內換行（同一段、同一個身分）。
6. **手機**（觸控鍵盤沒有 Shift）：Enter 一律切段。
7. **輸入法組字中（IME composition，例如注音選字）的 Enter 完全不處理**，交給輸入法。
8. 游標落在 `{…}` 裡面按 Enter：不切壞標籤，在標籤結尾 `}` 之後切（標籤留在前半，後半是空段落）。一段裡有多個 `{標籤}` 分在兩半時，身分跟著第一個標籤。

實作（一個規則、兩端共用，都在 `@onden/markdown` 的 `blocks.ts`）：
- `splitTaggedParagraph(markdown, offset)`：Enter 要在哪裡插入什麼、游標放哪裡；不是「頂層、有 `{標籤}` 的段落」就回 `null`，其餘 Enter 行為不變。
- `splitAnchorSpan(before, after)`：被切開的段落，身分在哪一半（有 `{標籤}` 的第一半，否則前半），回傳錨點現在涵蓋的範圍。**這是「身分在哪一半」唯一的判斷**：編輯器的錨點狀態（`lib/editorAnchors.ts`，邊打邊更新）和伺服器搬錨點（`services/blockAnchors/mapping.ts`）都呼叫它。原本就跨多段的錨點（舊範圍）與非純段落（清單項、標題）不縮。
- 伺服器對應區塊列仍是「起點落在該區塊的錨點」（`parseBlocks` 的 `withAnchorRefs`），所以錨點的起點在後半，後半就得到那一列；連結只認錨點 id，點過去落在有標籤的那一半。
- 沒帶編輯器 ChangeSet 的存檔（離線佇列、舊用戶端、其他寫入者）：行差異會把「後半文字刪掉再貼回」算成一個離散的改動，位置追蹤只會把錨點留在前半；所以位置追蹤前先在段落起點用 `cutParagraphAt` 認「原文只多插了空白」這個形狀，認得就走同一條規則。
- 邊角情況（照實寫，不猜）：標籤在第一行以外的行不算標籤（原本就是）；清單項、標題、引用內的段落不在本規則內（它們的 Enter 原本就開新項或保留記號）；游標在段首時前半是空行，身分仍在有字的那一半；多個 `{標籤}` 分在兩半時，後半原有的標籤項目仍是同一列，但前半那組 `{…}` 會因為成了段落最後一行而生效，身分給前半（第一個標籤）。要在真機（Android 注音）確認手感。

### 5.4 接合兩段

Backspace／Delete 接合：兩個錨點都指向合併後的區塊（別名，§2.4）。沒有 `ChangeSet` 的情況（如外部編輯）由 M2 處理，M2 單段只能指到整行（報告表 3：M2 在「接成一段」錨在前段時多半無法指對，M3 6/6）。


## 6. 連結語法：標準 Markdown 連結，認 id 不認名稱

### 6.1 格式（業主決定 6）

```markdown
[吃飯紀錄 › 17:45–21:15 吃飯](吃飯紀錄#d8f47e)
```

- **方括號**＝被連段落的開頭（給人看；`筆記名 › 段落開頭`，同篇連結省略 `筆記名 › `）。長度與截斷沿用 PR #1159 的 `blockLinkLabel`（見 §0.4，尚未合併）。
- **位址**＝`筆記#錨點id`。**位址裡的筆記名稱只是提示，認的是 `#` 後的 id**（像 Notion 網址、Stack Overflow 網址：名字可以錯，id 對就到得了）。筆記改名、段落搬到別篇或獨立出去（§S1.3）後連結都不用改寫；`#` 之前的名稱只在 id 查不到、一般檢視器顯示時當後援。
- 在一般 Markdown 檢視器裡是一條普通連結，文字可讀；位址點下去至多落空。**錨點只在 Onden 裡有效**。
- 整篇筆記連結 `[[筆記]]` **不變**。
- 同篇連結是 `(#d8f47e)`。

### 6.2 實測：位址部分的編碼（沿用舊版，仍適用）


用 commonmark.js、markdown-it、marked(GFM)、Onden app 與 published（`ondenMarkdownCore`，未帶 `wikilinkHref`）轉成 HTML，五個渲染器結果一致（腳本見附錄 A）。

| 輸入位址 | 結果 |
|---|---|
| `(吃飯紀錄#d8f47e)` 裸中文 | ✅ 五者皆成連結，`href` 為 `%E5%90%83…#d8f47e`（渲染器自行 percent-encode，`#d8f47e` 保留為片段） |
| `(吃 飯 紀錄#d8f47e)` 含空白 | ❌ **五者皆不成連結**，整段顯示成原文 |
| `(<吃 飯 紀錄#d8f47e>)` 用 `<…>` 包住 | ✅ 五者皆成連結，空白變 `%20` |
| `(%E5%90%83…%20…#d8f47e)` 已 percent-encode | ✅ 五者皆成連結，不重複編碼 |
| `(Note (v2)#d8f47e)` 括號成對、裸 | ❌ 五者皆不成連結（有空白） |
| `(Note (v2#d8f47e)` 括號不成對、裸 | ❌ 不成連結 |
| `(<Note (v2#d8f47e>)` 括號不成對、`<…>` | ✅ 成連結，`href="Note%20(v2#d8f47e"` |
| `(C# 入門#d8f47e)` 標題含 `#`、裸 | ❌ 有空白，不成連結 |
| 方括號文字含 `]`：`[a \] b](…)` | ✅ 跳脫後成連結 |
| `(onden:note/<uuid>#d8f47e)` 自訂協定 | 前三個渲染器成連結；**Onden app 與 published 的 sanitizer 把 `<a>` 的 `href` 丟掉**（`<a>x</a>`），所以任何自訂協定都要在 sanitizer 之前由我們的 remark 外掛先轉成合法 `href` |

**定案的寫入規則**（`blockLinks.ts` 一個函式 `blockLinkHref(noteName, anchorId, { embed })`，其他地方不自己拼）：

1. 筆記名先把 `%`、`#`、`<`、`>` 與換行寫成 percent-encode（`%25`、`%23`、`%3C`、`%3E`、`%0A`），讀取時先以**最後一個 `#`** 切出 id，再 decode 筆記名；
2. 筆記名含空白或 `(`、`)` 時，整個位址用 `<…>` 包住；否則寫裸字（中文與英數字不需編碼，可讀性最好）；
3. 方括號文字裡的 `[`、`]`、`\` 一律用反斜線跳脫；
4. **讀取寬鬆**：接受裸字、`<…>`、percent-encode 三種，與其他軟體貼進來的連結相容。

### 6.3 位址用名稱還是 id：認 id，名稱當提示

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 位址寫筆記標題、認 id（**採用**） | 一般檢視器看得懂、與 `[[…]]` 外觀一致；id 撐住改名／搬移／獨立出去，不必重寫引用端 | 名稱可能過時（無害，下次編輯引用端時順便更新，§7.2） |
| B. 位址寫筆記 id（`onden://node/<id>`） | 改名不壞 | 位址有 uuid（業主規則：id 不給人看）；一般檢視器看不懂；sanitizer 要放行 |
| C. 改名時重寫所有引用端 | 位址永遠對 | 離線多裝置大量合併變動（§17），不採用 |

查找順序：先用 `#` 後的 id 查 `block_anchors`（工作區內唯一，取代現行 `blockRefLookup.findBlockHome` 的 20 個候選上限）→ 查不到才依名稱找筆記，名稱也找不到就是 `lost` 畫面（§7.3）。

### 6.4 嵌入：同樣寫法加連結標題 `"嵌入"`

```markdown
[吃飯紀錄 › 17:45–21:15 吃飯](吃飯紀錄#d8f47e "嵌入")
```

- **不用 `![]`**：一般檢視器會把 `![](…#id)` 當圖片，載入失敗顯示破圖；連結標題是 CommonMark 標準語法，一般檢視器只當成滑過連結的提示文字。
- 判斷嵌入的規則只有一條：連結標題等於 `嵌入`（`embeds.ts` 的單一判斷函式；寫入同樣經 `blockLinkHref`）。圖片 `![](圖.png)` 完全不受影響，不需要「位址有沒有 `#id`」的猜測。
- 獨自成段才當區塊嵌入；夾在句子中間的帶 `"嵌入"` 連結視為普通連結（降級而不是壞掉）。
- 獨立出去的子節點，父筆記原處就是這條（§S1.3、§S4.2）。

### 6.5 標題也用錨點（改標題不斷）

標題連結不再用 `[[筆記#標題]]` 的標題比對，而是「連結標題時建立標題的錨點」：`[筆記 › 標題](筆記#id)`。標題改字、改層級，id 不變，連結不斷（Obsidian 多年做不到的事，`block-nodes.md` §7 原本靠存檔時解析達成，這裡改成錨點一種機制）。

- 標題建立錨點的時機：被連結（`((`、複製段落連結）時，與其他段落相同；簡報頁面鍵需要時自動建立（§S5）。
- 既有的 `[[筆記#標題]]`：**讀取仍接受**（找標題），在遷移（§11）時對解析得到唯一標題的改寫成錨點連結；解析不到的原樣保留。`[[筆記#標題]]` 與錨點 id 同為 `#` 後字串時的衝突規則：先查錨點表，查不到再當標題（錨點 id 是 `a-zA-Z0-9-`，標題多含中文，實務上極少撞）。

### 6.6 建立入口

- `((` 選段落與「複製段落連結」（`ParagraphMenu`）改成**建立錨點**：該段若已有有效錨點就沿用，否則建立（經 `blockAnchorCreate` 領域操作，同一交易寫表＋事件）。沒有 `{…}` 的錨點不建 `block_nodes` 列（§S4.2）。
- **拿掉行尾打 `^` 的「為這段建立連結」入口**（`lib/editorCompletion.ts`、`lib/i18n.zh-TW.late.ts`），行尾 `^` 變成普通字元。
- 貼上段落連結時 `pasteBlockLink` 改用錨點，不再補行尾 id。
- 段落選單其他入口（「做成複習卡」「設為任務」「標記這段」）**這版不做**，見 §13。

## 7. 連結文字、找不到的畫面

### 7.1 App 裡永遠即時顯示目標內容

渲染與編輯器 widget 都讀目標段落現況，不讀存的文字（沿用 PR #1159）。存在連結裡的文字只當後援：一般 Markdown 檢視器、匯出、發布網站、目標讀不到時（離線、無權限不外露）。

### 7.2 何時更新存的文字（學 InDesign 交互參照）

- **不在目標存檔時改寫引用端**：§17 實測，改寫會與引用端同一行的其他編輯衝突；一個被很多筆記引用的段落，一次編輯就讓每篇引用端多一個事件。
- **只在使用者自己編輯並離開引用端那篇時順便更新**：該篇所有區塊連結，若目標讀得到且現況開頭與存的文字不同，就改寫文字（並把位址標題更新成現名）。不在打字當下改；沒編輯過的筆記、背景工作、agent 寫入都不改；走一般領域寫入。
- 只更新「文字等於某個自動產生格式」（以 `›` 分隔、前半是筆記名）的連結；使用者自訂的文字不覆蓋。列 §15。

### 7.3 找不到時的畫面

錨點狀態決定畫面（對應 §4.3 的三段）：

| 狀態 | 畫面 |
|---|---|
| `valid` | 連到那一段 |
| `maybe` 可能在這裡 | 連結照樣點得進筆記，顯示候選段落預覽與一鍵「就是這段」（確認後轉 `valid`；有編輯能力的人才能確認，其他人只能看預覽） |
| `lost` 找不到，筆記還在 | 退成連到整篇筆記，旁邊小字「段落已不存在」；若有最佳猜測，顯示「也許是這段」供有編輯能力者一鍵確認 |
| 段落被刪、有存的原文 | 顯示「已刪除的段落」，把存的原文加**刪除線**，不可點 |
| 筆記也不在（含垃圾桶） | 同上，顯示「已刪除的段落」 |
| 讀者沒有權限看那篇 | 「無法存取的內容」（沿用 `wikilink-token--unavailable`），**不比對、不洩漏標題或原文** |
| 拆成兩處（§5） | 「這段已分成兩處」，列兩個候選預覽讓使用者選 |

原則：永不默默連到別處——任何狀態都不把連結改指向另一個看起來相近的段落；改指必須是使用者的一次確認。這是 Excel `#REF!`、GitHub outdated 的做法（§16，未驗證）。

### 7.4 刪除前提示

刪掉有人引用的段落前提示「有 N 處連到這段」。範圍：使用者在編輯器裡一次刪掉含有效錨點、且被引用數 > 0 的整段文字（或 App 的「刪除段落」動作）時；提示可略過，略過後錨點轉 `lost` 並保留原文（讓「已刪除的段落」畫面可顯示）。被引用數來自 `blockCitations`（§8）。批次、匯入、復原、agent 寫入不彈提示（沒人在看），只在事件裡記「有 N 個被連到的段落找不到」。

### 7.5 介面任何地方不顯示 id

逐項（沿用上一版，改為以錨點表為前提）：

1. 拿掉行尾 `^` 入口（§6.6）。
2. **版本歷史差異不露出 id**：正文已沒有記號，只剩舊版內文（遷移前的歷史）與連結位址裡的 `#id`。差異顯示前先經一個函式把 `(筆記#id)` 的位址換成連結文字、把遷移前舊記號行去掉；遷移事件只在摘要說「整理了段落連結」。要檢查的地方（以 main 為準）：`components/history/RewindNoteDiff.tsx`、`BlockHistorySheet.tsx`、`RewindPreview.tsx`、`WorkspaceHistoryUndoCard.tsx`、`components/NoteVersionHistory.tsx`、`lib/history/charDiff.ts`、`blockHistory.ts`、`lib/lineDiff.ts`。這個函式放 `@onden/markdown`，不要每個畫面各寫一份。
3. 事件文字走 `eventTypeLabel`，新增「建立段落連結」「確認段落位置」「整理段落連結」等白話名稱，不寫 id。
4. 編輯器：連結用 widget 顯示成目標段落開頭，游標進入時展開成 Markdown——**這時看到 `(吃飯紀錄#d8f47e)`**，位址裡有 id。建議把位址部分折疊成小圖示，只在「編輯連結」時顯示筆記名，id 不顯示。列 §15。
5. 搜尋摘要、全文索引片段、匯出預覽、剪貼簿、發布網站：連結只留文字。
6. 錯誤訊息與 tooltip 不帶 id。

## 8. 其他用 `^id` 的功能一起換

逐項對應移到 §S5（含鍵、做法、注意事項），這裡只留原則：

- `{…}` 照舊留在行尾（使用者自己打、看得到），由 §S2 規定其意義；「這一段有沒有身分」不再看行尾 `^id`，而看錨點表。
- 功能資料以 `block_nodes.id` 為鍵，不以位置或文字 id；錨點非 `valid` 時資料保留（§S4.4）。
- 每一項在批 1 完成前宣告「錨點狀態不是 `valid` 時的行為」，不得退回字串猜測。

## 9. 同步與離線

- **`block_nodes.detached_note_id` 隨子節點列同步**；**錨點表進同步**：bootstrap 帶可讀筆記的錨點；增量（`/sync` delta）帶變動的錨點列。屬於可讀筆記的內容增量，可讀集合隨筆記（`membership_epoch` 與可讀集合核對沿用，撤權與重連後錨點跟著筆記消失／出現，要測）。
- **離線也要能顯示連結文字**：本機副本存錨點的 id、筆記、quote 前綴（顯示後援）。**本機資料庫 worker 的大小預算幾乎用完**（`patch-writes.md`：剩約 240 B），所以解析（連結 → 目標段落、用位置取開頭）放**主執行緒**，worker 只存取資料列。
- **離線建立的錨點**：只相對於客戶端手上的 base。上線重送時帶 `base_hash`、錨點（位置＋quote），伺服器先把它從 base 搬到目前版本（合併已在做 base→current 的差異，重用），再套上。base 已遠離而 quote 找不到 → **建立失敗，保留使用者輸入並明確回報**，不默默建在別處。重試沿用原冪等鍵。
- 保存確認區分「伺服器接受」與「離線佇列已持久化」（沿用 `writeLifecycle.ts`）；錨點的確認／重新指定是領域 writer，不自創重試。
- 舊客戶端：遷移後強制重新載入（§11）。

## 10. 備份、匯出、匯入、歷史還原

| 單篇匯出（`useNoteExport`） | `{…}` 本來就留在文字裡，主題與功能名稱原樣帶走，不需要選項。段落連結另給三種選項（`export-preview` 前後端同版）：(1) 預設「筆記連結＋段落文字」（`[吃飯紀錄](吃飯紀錄)：17:45–21:15 吃飯`）；(2) 「**轉成腳註附原文**」（思源 issue #2833 的先例，未驗證）：連結處放腳註標記，腳註內寫筆記名與該段原文；(3) 「**Obsidian 相容**」：在**匯出當下**把被連的段落寫入行尾 ` ^id`、連結寫回 `[[筆記#^id]]`。匯出檔不是真相來源 |

## 11. 遷移（一次切換）

業主是正式站唯一使用者，所以可以一次切換，不需要新舊並存期。

### 11.1 遷移檔與系統工作

1. **遷移檔**（編號從 161 起、取當時下一個可用；載入器只認 `.sql`，每支在一個交易）只做：建 `block_anchors`、`content_nodes` 加進度欄（例如 `anchor_form smallint NOT NULL DEFAULT 0`，1＝已轉換）。**不改任何正文**——SQL 無法正確解析 Markdown（程式碼區塊、引用內縮排、巢狀）。
2. **系統工作**（`spine/systemJobs.ts` 新增一項，宣告可發的事件與可動對象）逐篇處理 `anchor_form = 0` 且含舊記號／舊連結的筆記：
   - 對每篇走領域寫入（取工作區事件鎖、`spine/mutate.ts`）：同一交易內，把正文裡現有的 `^id`（行尾、自成一行、`> ^id`）轉成錨點列（位置＝該區塊範圍、quote＝區塊文字）、**從正文拿掉**；`[[筆記#^id]]` 改寫成標準連結；事件為一般的 `NODE_UPDATED`。
   - 沒有任何記號或連結的筆記只標記 `anchor_form = 1`，不寫事件。
   - 可重啟、冪等（已轉換的筆記不產生變更也不寫事件）。
3. **為什麼走領域寫入而不是 SQL `UPDATE`**：歷史的「某時間點正文與現在是否相同」會比較文字（`services/history/pointInTime.ts`），直接改寫會讓所有含記號的筆記看起來「之後改過」且沒有事件可解釋；事件的反向補丁也要靠寫入時產生。
4. **舊的搬成子筆記**：B5 搬出去的子筆記沒有記錄「它是從哪段搬的」（只有父筆記的 `![[子筆記]]` 與子筆記的 parent）。遷移時對「子筆記 ＋ 父筆記裡獨自成段的 `![[子筆記]]`」建立 `block_nodes` 列（`detached_note_id` 指向子筆記）與錨點，成為「已獨立出去」的子節點；找不到對應嵌入行的子筆記不動（它只是一般子筆記）。
5. 現有 `{task}`、`{複習}` 等的正文**不改**（§S2.1）；遷移只把行尾 `^id` 轉成錨點、`block_nodes.block_ref` 改對應 `anchor_id`。
6. 影響量**未量測**：實作前先估含舊記號的筆記數與跨筆記重複 id 的分布（見下 SQL）；重複 id 在遷移時要換新 id（錨點 id 工作區唯一），舊連結改寫要指向正確的那一個。

```sql
SELECT block_ref, count(*) AS notes
FROM note_block_refs GROUP BY workspace_id, block_ref HAVING count(*) > 1
ORDER BY notes DESC LIMIT 50;
```

### 13.1 第二份獨立實驗的補充（PR #1175，數字只記在這裡）

## 17. 合併實驗：標準連結與逐行合併（沿用舊版）

用同一個 `threeWayMergeBody(base, incoming, current)`，連結是 `見 [吃飯紀錄 › 17:45–21:15 吃飯](吃飯紀錄#d8f47e)`（腳本見附錄 A）：

| 情境 | 結果 |
|---|---|
| B 在別行續打，A 不動 | 乾淨 |
| B 在連結後續打、A 在同行前面加字 | 乾淨：`先見 […](…#d8f47e) 好` |
| A、B 在同一行不同位置各加一條連結 | 乾淨，兩條連結都在 |
| B 改連結文字（引用端編輯）、A 改同一篇另一行 | 乾淨 |
| A、B 都改**同一條**連結的文字 | 1 個衝突（與一般同位置改字相同） |
| B 刪掉連結那行、A 在該行續打 | 1 個衝突（與一般刪行相同） |
| **A 因目標段落被編輯而改寫連結文字**、B 在同一行續打 | **1 個衝突**：base 的連結文字被 A 改了，B 在同行尾端加字，diff3 無法判定 |
| 舊寫法對照：`[[吃飯紀錄#^d8f47e]]` 前面加字＋後面續打 | 乾淨 |
| 舊寫法對照：兩邊把同一個 id 改成不同值 | 1 個衝突 |

結論：(1) 新連結格式本身不引入新的合併問題，與舊寫法行為相同；(2) 倒數第三列正是業主第 4 點「不要在目標存檔時改寫引用端」的實測理由——引用端的文字只在它自己的作者編輯時才動，離線多裝置才不會因為「目標被改」而在每一篇引用它的筆記製造衝突。
