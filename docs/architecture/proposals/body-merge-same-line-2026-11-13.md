# 提案：同一行兩邊加字，什麼時候該判衝突

> 狀態：提案（2026-11-13）。**只寫文件，不含程式**；要給業主與負責同步的工作階段看過才會實作。
> 起因：#1464 第四輪複審；#1566 的第一版把規則收緊，被審查退回（太粗），本文取代那一版。
> 依據：`origin/main` 的 `bodyMerge.ts` 與下面的隨機實驗（**用本機腳本跑，沒有放進測試**）。

## 1. 要解決的問題（最小重現）

使用者與 AI（或兩個裝置）在**同一行**各自「只加字」時，合併會把兩邊的字貼成誰都沒寫過的字：

| base | 一邊 | 另一邊 | main 的結果 |
| --- | --- | --- | --- |
| `一行` | `一行B` | `一行A` | `一行AB`（乾淨合併） |
| `cat` | `cats` | `cated` | `catsed`（乾淨合併） |

AI 建議走 `onConflict: "refuse"`，希望的結果是「標成過期」，一般儲存則走現有的衝突處理（保留較晚存檔、另一邊由 `BODY_CONFLICT` 帶回）。
目前的設計是刻意的（`decisions-core-sync.md` F03／F04）：兩邊只加字、沒刪改字元，就兩份都留，同一點的兩段依 code unit 排序。
會混出新字的只有這條「純加字」路徑；任一邊刪或改了字元本來就是衝突。

## 2. 候選規則

「判衝突」＝較晚存檔的留在內文，另一邊走衝突處理。每個規則都只影響字元層級的合併（`mergeChars`），行層級不變。

**A. 不改（main）。** 兩邊只加字就都留。
- `我喜歡貓`：一邊加「很」、一邊加「咪」→ `我很喜歡貓咪`。`一行` + `A`／`B` → `一行AB`。

**B. 兩邊碰到同一個「詞」就衝突。** 詞＝連續的字母／數字／底線（漢字也算）；加的字貼著詞的邊或落在詞中間算碰到。同一點兩邊的加字，若其中一邊碰到詞也衝突；一邊包含另一邊的視為同一段打字，不算。
- `我喜歡貓`：「很」加在「我」後、「咪」加在「貓」後 → 兩處都落在同一串沒有標點的漢字裡 → **衝突**（`我很喜歡貓` 對 `我喜歡貓咪`）。
- `今天` → `今天天氣很好` 對 `今天天氣`：一邊包含另一邊 → 乾淨，取 `今天天氣很好`。
- `cat` + `s`／`ed` → 衝突；`ab cd` + `abX`／`Ycd` → 乾淨 `abX Ycd`。

**C. 只有「同一點、兩邊字面相接」才衝突。** 同一點兩邊加了不同的字，且相接處兩邊都是詞的字元（`s`＋`ed`、`A`＋`B`）才衝突；不同點、貼不貼詞都照舊。
- `一行` + `A`／`B` → 衝突；`我喜歡貓` + 「很」／「咪」（不同點）→ 照舊乾淨 `我很喜歡貓咪`。
- 擋得住「兩邊對著同一個點打字」，擋不住「不同點但在同一個詞裡」（`bXrown` 與 `browns`）。

**D. B 但漢字／假名不算詞的字元。** 英文照 B；中日文照 A（沒有空白可以判斷詞界，所以不判）。
- `我喜歡貓` → 乾淨；`cat` + `s`／`ed` → 衝突。

## 3. 隨機實驗

單行 base（英文 3 句、中文 3 句），兩邊各 1–2 處隨機位置加隨機片段（英文：`s`、`ed`、` very`、`! `、`-`、` x`、`Q`、`ing`；中文：`很`、`咪`、`，`、`天氣`、`好`、`的`、`。`、`也`），各 20000 組。
「混出新詞」＝合併結果中有一串連續字母／數字（漢字也算），不在任何一邊出現過；分母是全部 20000 組。

| 規則 | 英文：乾淨合併 | 英文：混出新詞 | 中文：乾淨合併 | 中文：混出新詞 |
| --- | --- | --- | --- | --- |
| A（main） | 100.0% | 45.2% | 100.0% | 80.5% |
| B | 54.1% | 0.0% | 18.3% | 0.0% |
| C | 94.0% | 39.2% | 88.1% | 68.5% |
| D | 54.1% | 0.0% | 100.0% | 80.5% |

- 這組片段刻意常常直接貼在詞上，所以「混出新詞」比真實打字高很多；數字用來比規則，不代表正式站的比例。
- B 把中文的乾淨合併降到 18%，與 #1566 審查看到的方向一致（那邊是 70%，片段不同）。C 幾乎沒有效果；D 沒有解決中文。
- 「兩邊改動的字元範圍真的重疊才算衝突」：兩邊都只加字時，加字的位置不重疊就不會重疊，等於 A；位置相同的情況等於 C。所以這個方向本身沒有新規則，要有就必須像 B 那樣用「詞」。

## 4. 規則改動如何跟協定版本走

`distributedSync/materialize.ts` 也呼叫 `threeWayMergeBody`：每個副本自己重算內文。所以**合併規則是協定的一部分**：新舊版副本對同一串操作會算出不同內文（也包含 #1566 合併進來的「兩段之間補空行」）。
分散式同步目前關著，所以 #1566 現在可以改；**開啟之後再改這類規則必須跟協定版本走**。結論（負責同步的工作階段）：
1. **用整數版本當閘門**：改合併規則＝協定加版，先併進現有的同步協定版本，不另開一套。舊版副本照現有路徑停下並提示更新，不用舊規則算出分歧的內文。
2. **結果雜湊不當閘門，當偵測用**：操作記下合併後的雜湊，副本重算後不符就停下並回報（代表兩邊規則不同或有 bug），不用它決定要不要套用。
3. 版本升級須與一次發布配合；自架者升級說明（`release.md`）要寫明哪個版本改了規則。
4. 不在版本機制之前單獨改規則；#1566 是例外，因為同步關著。

## 5. 候選 E：只在「接受 AI 建議」處保守判斷（待業主決定；#1566 不實作）

一般存檔與同步**維持 A**（兩邊只加字就都留）。只在「接受 AI 建議」的呼叫點（`services/aiSuggestions.ts` 的存檔）加一個保守判斷：
**建議提出之後，使用者改過建議所在的同一行 → 把那一項建議標成過期**，不走字元合併。
- 例：AI 建議把 `我喜歡貓` 改成 `我喜歡貓咪`；使用者在建議提出後把同一行改成 `我很喜歡貓`。照 A 會合成 `我很喜歡貓咪`；照 E 這一項建議標成「已過期」，使用者的行不動。
- 好處：只影響 AI 建議這條本來就要「寧可過期也不混」的路徑；一般存檔、同步、復原的合併行為不變，不碰協定。
- 兩個前提：
  1. 判斷只看**那台節點當下的資料**（建議的原文與現在的筆記），不經 `materialize`；所以不同節點對同一行可能各自得出不同的「是否改過」。
  2. 「標成過期」是對 `ai_edit_suggestions` 項目的決定，**那張表會複製**。兩邊對同一項做了不同決定時，照來源標記設計：較晚的決定不生效並告知使用者（見 `causal-stamps-2026-11-12.md`）。
- 派工者與負責同步的工作階段都傾向 E；待業主定。

**待業主與同步工作階段決定：** 是否做同行規則的收緊、選 A／B／C／D／E 哪個。
