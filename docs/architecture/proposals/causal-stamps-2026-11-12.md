> 上層文件：[上線前把資料模型做成之後能長成分散式](distributed-ready-2026-11-12.md)（方向、七項、規則）。本文是其中第 2 項。

## 1. 要達成什麼

每一筆會被複製到其他節點的資料，都要回答得出三個問題：**最後是哪個節點改的、是那個節點的第幾筆、邏輯時鐘是多少**。
被刪掉的東西也要回答得出來（不然另一個節點分不清「被刪了」和「還沒看過」）。

上線前只做到「**每次寫入都留下標記**」。沒有任何東西讀這些標記來做決定，所以現在的使用行為完全不變。合併規則、節點之間交換，是上線後的事；到時候資料已經都有標記，不用回頭補。

## 2. 標記長什麼樣

一個標記＝`(origin, seq, hlc_wall, hlc_counter, author, device)`：

| 欄位 | 意思 |
|---|---|
| `origin` | 接受這次寫入的節點（這個資料庫）。每個資料庫第一次啟動時產生一次，之後不變 |
| `seq` | 這個節點的第幾次寫入，從 1 連續遞增 |
| `hlc_wall`、`hlc_counter` | 混合邏輯時鐘（沿用 `distributedSync/hlc.ts`，搬到共用位置）。跨節點比較先後用它，不用裝置時鐘 |
| `author` | 做這件事的人（actor）。之後「照當時的權限重新判斷」靠它 |
| `device` | 送出這次寫入的裝置（上線前第 1 項的裝置編號；沒有就空） |

**一個交易一個標記。** 同一次操作改到的所有東西帶同一個標記，連鎖產生的寫入也是。

## 3. 標記放哪裡：一張表、一個機制

所有標記放在同一張新表 `sync_stamps`，由資料庫 trigger 維護：

```
sync_stamps(workspace_id, table_name, row_key, field, origin, seq, hlc_wall, hlc_counter, author, device, deleted)
主鍵 (workspace_id, table_name, row_key, field)
```

- `field = '*'` 代表「整列」。一列剛建立時只有這一筆；之後某個欄位被單獨改過，才多一筆該欄位的標記。讀的時候「該欄位有自己的標記就用它，否則用整列的」。這樣最大的表（筆記）平均每列只多一到兩筆。
- `deleted = true` 就是墓碑：資料列被真的刪掉之後，標記留著。
- 為什麼不在每張表加欄位：有三類需求欄位做不到——同一列裡不同欄位各自的標記（筆記的標題、內文、父層、排序）、JSON 裡各個鍵各自的標記（檢視、標籤設定、空間開關）、以及刪除後的墓碑。既然這三類一定要旁表，全部用同一個機制比較好推理、好測試、之後好傳。
- 先例：schema 裡已有兩張由 trigger 維護的旁表（`node_tag_states`、`node_event_meta`），以及寫入入口設定交易內變數、trigger 讀取的做法（`onden.actor_space`）。

**標記怎麼產生**：`spine/mutate.ts` 在根交易開始時配一個標記，放進交易內的設定；各表的 trigger 把它寫進 `sync_stamps`。

**所有寫入都走統一入口，但「要不要進歷史」分開講（業主 2026-11-12 決定）。** 盤點發現有一批寫入不經過 `mutate`：複習進度、帳號偏好、RSS 訂閱設定、外部行事曆、已讀狀態等。
讀程式裡的說明，這大多是刻意的——它們是個人資料或設定，「不是對共用筆記的修改」「沒有需要復原的歷史」，記成事件會讓歷史頁被洗版。問題在於統一入口同時做兩件事（管交易＋記事件），不記事件就連帶沒有來源資訊。
做法是把兩件事拆開，入口只有一個，呼叫時明講要哪一種：

| 寫入的種類 | 上鎖、重讀操作者、檢查權限、配來源標記 | 記進事件帳本 |
|---|---|---|
| 改共用內容（筆記、標籤、白板…） | 要 | 要 |
| 個人資料與設定（複習、偏好、已讀、訂閱設定、行事曆） | 要 | **不要** |

- 沒選「全部記成事件但前端不顯示」：這幾類寫入很頻繁，事件帳本只增不減；每台裝置同步都要掃事件；「不顯示」必須在伺服器端每個讀事件的地方都擋（歷史、活動、收件匣、回溯、AI 稽核、同步、背景工作），漏一處就洩漏個人資料及其舊值；記事件還要搶工作區的寫入鎖。
- 做完後加一條守門：**資料表只能透過統一入口寫**（現在因為有這批例外而立不起來）。
- trigger 發現交易裡沒有標記時自己配一個（作者空白）這個後備留著當保險，正常情況不會用到。
- 例外：**圖譜上的位置是共用資料**，現在沒有事件比較像漏掉；比照白板卡片的位置，改成記正常的、看得到的事件。

節點自己的編號、下一個序號、時鐘放在一張單列的表（現有引擎的 `ds_node` 是同樣的東西；新表另取名，引擎拆除時一併清掉舊的）。

## 4. 逐表分類

每張表歸到三類之一。**這份分類會變成一個守門測試：schema 裡出現沒有分類的新表就失敗**，之後加功能的人必須先回答「這在兩台離線裝置上會怎樣」。

### 4.2 不複製，每個節點自己算
`note_block_refs`、`note_link_index`、`node_embeddings`、`node_event_meta`、`node_tag_states`、自動產生的連線、`block_nodes`（任務與拆出的區塊身分除外，另議）、由內文算出的屬性、`rss_staging`（文章，可重抓；id 改成算出來的）、外部行事曆的事件、段落錨點的位置。

`domain_events`（歷史與復原的帳本）、`idempotency_keys`、`outbox`、`agent_sessions`、`ai_credentials`、`publish_snapshots`、登入與工作階段、`rate_limit_hits`、備份還原的工作紀錄。其中 AI、發布、備份相關的屬於值班節點（上層文件 4.6）。

- `blobs`：以內容雜湊為鍵，天生不會衝突；要不要每個節點都存一份歸在「附件」題目，上線後決定。
- `media_uploads`、`imported_media`：附件，上線後。
- `actors`：身分，只能在主伺服器上改（上層文件 4.13）。

## 5. 墓碑留多久

上線前：**一直留著。** 墓碑只有鍵和標記，沒有內容（永久刪除一則筆記後留下的只是它的 id），量很小。
清理墓碑需要知道「所有節點都已經看過這次刪除」，那要等節點之間能交換之後才有辦法做，屆時再定。

## 6. 既有資料

現有的每一列補一個「創世」標記（固定的來源名、時鐘為零），和現有引擎的創世匯入同一個做法：同一份資料在兩個節點各自補，結果相同。
這是新增一張表的內容，**不改寫任何既有資料**；回退就是把那張表清空（migration 202 實作；`structure_log` 是只增不減的表，基準行刪不掉，留著無害，要回退就還原升級前備份）。

## 7. 成本

- 空間：每列一筆整列標記，被單獨改過的欄位各多一筆，每次刪除留一筆。估計是現有資料列數的一到兩倍筆數的小列。
- 寫入：每次寫入多一到數筆旁表更新，都在同一個交易、同一把鎖裡。要量：存一則筆記、套一個標籤、搬動一百則的時間，改之前和之後。
- 節點的那一列（序號與時鐘）每次寫入都會更新。經過統一入口的寫入本來就排在工作區的寫入鎖後面，不會多出等待；不經過入口的那些會在這一列上短暫互等。

## 8.5 結構變更紀錄：讓「回到某一天」連位置和標籤都還原（業主 2026-11-12）

業主的要求：「回到某一天」除了標題與內文，也要顯示並還原每則筆記當時**放在哪、排第幾、在哪個空間、有哪些標籤**，以及**白板上每張卡片的位置**。「想要連位置和標籤都還原，很合理吧。」

**現況為什麼做不到**（`services/history/pointInTime.ts` 的說明）：建立筆記的事件不一定記父層；搬動經過好幾條路徑（換空間、合併標籤、升級成獨立筆記…），事件不是都帶舊位置；白板版面的事件只記張數（`boardWrites.ts` 的 `CANVAS_UPDATED`／`BOARD_UPDATED`），`node_positions` 是原地覆寫。所以回溯只能讓位置與標籤維持現狀。手寫不受影響：每次存檔的整份筆跡都留在 blob 裡，任何一天都讀得回來。

**做法：標記的 trigger 順手多記一筆「舊值 → 新值」。** 來源標記只記每個欄位目前的值是誰改的，不留舊值。在同一個 trigger 裡，結構性欄位改變時往一張只增不減的表 `structure_log` 寫一列：

```
structure_log(workspace_id, table_name, row_key, field, old_value, new_value, origin, seq, hlc_wall, hlc_counter, author, device, at)
```

| 來源 | 記哪些欄位 | 屬於哪個任務 |
|---|---|---|
| `content_nodes` | 父層、排序、所屬空間、刪除狀態 | S1 |
| `node_tags` | 套用、移除 | S2 |
| `node_positions`（白板卡片） | 位置、大小、顏色、折疊、子白板；卡片被移出白板 | S2 |
| 白板分組框（`_canvas_sections` 屬性） | 動工時先確認：若屬性事件已帶完整新舊值就不重複記；`boardStore` 有不經統一入口的寫法，要一併確認 | S2 |

- **靠結構成立，不靠每條路徑記得**：不管程式從哪裡寫，資料表一變就記到。現在還原不了，就是因為有幾條路徑忘了帶舊值。
- **基準**：S5 給既有每一列補創世標記的那一刻，同時記下當時的完整結構。**之後的每一天都精確；之前的日子修不回來。**
- **測試**：從基準重放 `structure_log` 必須等於現在的結構（隨機操作測試）；這也是 trigger 本身的驗收。
- **白板拖動很頻繁**：同一張卡片在短時間內的連續移動只留頭尾（由寫入端合併或由 trigger 更新上一筆未封口的紀錄，動工時擇一並量測）。回到某一天看到的是那天結束時的樣子。
- **排序**：整數時代拖一次會重編好幾列，紀錄會很吵，所以排序欄位的紀錄等「排序改成不會撞的鍵」。migration 200 已做：`structure_log` 現在也記排序欄位（欄位名 `sort`，值是新舊 `order_key`），一次搬動一筆；舊的 `sort` 標記照舊有效。
- **還原是新的操作**：回到某一天時，位置與標籤的還原要經過統一的寫入入口、依現在的權限執行，不能把舊值直接寫回去。遇到不再成立的情況（會造成迴圈、目標父層已不存在或在別的空間、標籤已刪除）就跳過那一項並告訴使用者，其餘照做。
- **不外傳**：`structure_log` 和事件一樣是各節點自己的歷史帳本，不複製給其他節點。
- **分工**：這張表與寫入由本文這條線負責；`pointInTime.ts` 的讀取端與歷史頁的畫面由歷史那條線負責。
