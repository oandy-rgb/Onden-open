# 提案：上線前把資料模型做成「之後能長成分散式」

> 狀態：現行（最後確認 2026-11-12）

> 2026-11-12。**設計提案**；只寫文件，不含程式。第 4 節的規則業主已於同日逐條決定（4.1–4.4、4.6、4.9 是選出來的，其餘照建議）。**尚未動工**：第 2 節的七項要業主說開始才派工。

> 前情：[分散式同步（beta）](../distributed-sync.md) 的第 1 步與第 2a 步已實作、預設關閉。2026-11-12 與業主討論後的方向是
> **只留主線一套程式**，把那個引擎裡證明可行的東西搬到主線上，其餘刪掉。本文是這個方向的範圍與規則草稿。
> 依據：同日三份唯讀盤點（事件流水號用在哪、現有引擎做了什麼、哪些規則只在單一伺服器下成立）。盤點是讀程式得出的，**沒有執行驗證**。

## 1. 方向

1. **一套程式。** 寫入只有現在這一個入口（`spine/mutate.ts` → `domain_events`）。伺服器、瀏覽器版、桌面版都是「節點」，跑同一套。
2. **分散式＝資料在節點之間複製，每一筆帶著來源標記。** 節點交換的是資料本身（筆記、屬性、標籤關係…），每一列或每個欄位帶「哪個節點最後改的、該節點的第幾筆、混合邏輯時鐘」；
   兩邊都改過時照標記與第 4 節的規則合併，內文照舊三方合併。收到時用自己這邊現在的權限重新檢查，過了才套用，不過就當成建議留給人決定（和 AI 的修改同一條路）。
   **事件不外傳**，繼續當各節點自己的歷史與復原帳本（理由見第 5 節）。
3. **主伺服器是一個節點。** 特別之處只有三點：永遠開著、大家預設信任、第 4.6 節「只做一次的事」由它負責。
4. **不變的承諾。** Markdown 是內文唯一的真相；兩邊改到同一句就問人，不自動混；保存狀態不說謊。

業主的理由（2026-11-12）：「畢竟第一版還沒上線，萬一之後想改會更困難。」上線後資料在別人的硬碟裡、協定在別人的客戶端裡，格式就很難再動。

## 2. 上線前做什麼、不做什麼

要分開兩種東西：**格式**（資料長什麼樣、事件怎麼編號、同步怎麼講話）上線後很難改；**功能**（節點直接對齊、簽章、附件怎麼傳）可以在既有格式上慢慢加。上線前只做格式。

| # | 內容 | 規模 | 對現在使用的影響 |
|---|---|---|---|
| 1 | 裝置編號：每台裝置一個固定編號，每次寫入帶上（現在客戶端完全沒有） | 小 | 無 |
| 2 | 資料列與欄位帶來源標記（來源節點、該節點的序號、混合邏輯時鐘），刪除留下墓碑；約十來張表（筆記、屬性、標籤關係、連結、指標、檢視、白板位置、空間與成員、功能引用）。事件也帶同一組標記。現有的事件流水號原樣保留，繼續當「這個節點自己的帳本位置」 | 中偏大 | 無 |
| 3 | 同步協定帶版本；不相容就明確拒絕並請使用者更新，不靜靜繼續 | 小 | 無 |
| 4 | 自動建立的唯一項目改用算出來的固定 id（第 4.5 節） | 中，要搬現有資料 | 無（id 會變，內容不變） |
| 5 | 同層排序改成各節點各自產生也不會撞的值（第 4.7 節） | 中，要搬現有資料 | 無 |
| 6 | 現在用裝置時鐘決定誰贏的三處（屬性、帳號偏好、複習進度）改用邏輯時鐘 | 小 | 無 |
| 7 | 第 4 節的規則定案並寫進這份文件 | 只寫文件 | 無 |

**上線後才做**：每張表、每個欄位的合併規則逐一實作並進故障模擬、節點之間不經伺服器直接對齊、桌面版當值班節點時讓其他裝置連進來（配對）、簽章、附件、第 4.1 節的「需要伺服器的空間」開關。

**流水號為什麼不用動**：盤點結果是同步游標、即時通知、背景工作排隊、發布快照、其他表存的事件編號，都只需要「本節點的帳本位置」。真正需要跨節點順序的只有回溯（「這之後有沒有人改過」）、AI 執行的復原順序、內文版本的前後關係，以及上表第 6 項。歷史頁現在照伺服器收到的時間排，要改成照邏輯時鐘排（約十個查詢）。

## 4. 規則（業主 2026-11-12 已決定）

有伺服器當裁判時，下面這些情況第二個人會立刻被拒絕。分散式下兩台離線的裝置當下都會成功，碰面時才發現。每條都要有「碰面時怎麼辦」。
共同原則：**能確定地合起來就合；會改變意思的就問人；任何一邊的輸入都不丟。**

### 4.1 撤銷成員（已決定，2026-11-12）
- 預設：**撤權只對之後有效。** 他裝置上已經有的內容收不回來；之後收不到新的，他之後的修改也不被接受。移除成員的確認畫面要用白話講這句。
- 可按空間打開「需要連上伺服器才能讀寫」：移除立刻生效、之後的內容他一律拿不到；代價是這個空間在沒有伺服器的節點上完全不提供。上線後才做。

### 4.2 同一層出現兩個同名標籤（已決定 A，2026-11-12）
標籤的名字就是它的身分：內文裡的 `#名字` 靠名字找標籤。
- **決定 A**：兩個都留。較早建立的保有名字，`#名字` 指向它；較晚的顯示成「名字 (2)」，並對能管理標籤的人提示「這兩個標籤同名」，一按可合併（沿用現有的合併標籤）或改名。
- B：自動合併成一個（成員取聯集）。省事，但兩個人各自建的同名標籤可能根本是不同的東西，合併後很難分開。
- C：較晚的那個不生效，掛在它底下的筆記變成沒有這個標籤。會丟東西，不建議。

### 4.3 網址代稱重複（已決定 A，2026-11-12）
代稱出現在公開網址與 `[[連結]]` 裡。現在重複時伺服器自動加 `-2`、`-3`，誰拿到哪個取決於先後。
- **決定 A**：較早建立的保有原代稱，較晚的加尾碼；**已經對外發布過的網址永不改變**（發布過的那一則優先保有，另一則加尾碼）。與[網站穩定網址](site-stable-urls-2026-11-04.md)一致。
- B：代稱一律帶一小段筆記 id，永遠不會撞，但網址比較醜。

### 4.4 同一個人同時有兩個進行中的專注（已決定 A，2026-11-12）
兩台離線裝置各開了一個專注計時。
- **決定 A**：兩筆都留；較早的那筆視為在較晚的開始時結束，時間不重複計算。
- B：兩筆都原樣保留，總時數可能重疊。

### 4.5 自動建立的唯一項目
收件匣標籤、任務標籤、功能模組的標籤、網站設定的筆記與標籤、個人空間、預設空間，現在第一次用到時才建立、id 是隨機的。兩台離線裝置會各建一個。
- **建議（不需要選）**：id 改成由「工作區／空間／用途」算出來的固定值，兩邊各建一次就是同一個。日記和每個空間的任務筆記已經是這樣做的，照同一個做法。
- 需要業主知道：現有資料裡這些項目的 id 會被換成新的固定值（內容不變），要寫 migration，上線前做最便宜。
- **已做（2026-11-14，migration 201）**：收件匣標籤、技能標籤、網站設定的標籤與筆記、頁面標籤、系統空間、預設空間、個人空間，新建時用算出來的 id（`@onden/markdown` 的 `DERIVED_ID_NAMESPACE`／`derivedIdName`，與日記相同的 v5 做法）；既有資料由 migration 201 換 id 並更新所有引用（清單與保留不動的項目寫在 migration 檔頭與 PR 說明，檔頭有只讀的預覽查詢）。有兩筆候選、或算出的 id 已被別的資料列用掉時不猜，原樣保留並列在預覽。預設空間與個人空間由資料庫自己建（`onden_space_id`），算出的 id 被占用時退回隨機 id。
- **還沒做**：`function_refs` 自己的 id 仍是隨機（自然鍵 `(持有者, 功能, 實例)` 已唯一，但合併時兩台各建的同一個引用 id 不同；見 causal-stamps 第 4 節表）；已存在的歷史事件仍記舊 id（append-only，不改）。

### 4.6 只做一次的事（已決定 C：值班節點，2026-11-12）
AI 執行（花錢、會寫回覆）、提醒、重複任務產生下一筆、發布網站、備份到 GitHub、抓 RSS 與外部行事曆。現在靠「只有一個伺服器在跑」保證不重複。
- **決定 C：每個工作區有一個「值班節點」負責這些事。** 預設是主伺服器；沒有主伺服器的人，值班的就是他的桌面版（桌面版本來就內含整個後端）。
  - 值班的那台不在時，這些事先不做，等它回來；畫面上用白話說明「要等值班的那台裝置上線才會執行」。其他裝置照常記筆記與同步。
  - 金鑰只放在值班的那一台。
  - 換值班必須舊的與新的兩台同時在線才能完成，避免兩台各自以為自己值班而重複執行。
  - 不論誰值班都成立的細節：重複任務的下一筆、RSS 文章用算出來的固定 id，哪個節點產生都是同一筆；提醒由各裝置自己發，同一個任務同一個時刻只顯示一次。
  - **已做（2026-11-14，migration 201 同一個 PR，只改新建）**：重複任務的下一筆 id＝v5(`task-successor/<上一筆的 id>`)，已經有這個 id 就不再建；RSS 文章 id＝v5(`rss-article/<訂閱 id>/<guid>`)。既有的任務與文章不改 id（不需要：任務靠事件記錄判斷已建過，文章靠 `(訂閱, guid)` 唯一）。提醒「同一個任務同一個時刻只顯示一次」還沒做。
- 沒選的：A（只能是主伺服器；沒有伺服器的人用不了 AI、發布、備份）、B（誰發起誰做；金鑰要放在每台裝置，容易重複執行）。A 是 C 的特例。
- 桌面版當值班節點時，別的裝置怎麼連到它（同一個區域網路、私人網路、中繼站）是上線後的事。**先決條件**：桌面版內建的後端現在對所有網路介面開放（2026-11-12 審查發現，與程式註解不符），要改成預設只對本機開放，使用者明確打開並配對後才讓其他裝置連入。

### 4.7 同層排序（已實作，migration 200，2026-11-14）
以前排序值是客戶端決定的整數：兩台各自排過，合起來會交錯，搬一則筆記還要重編鄰居。現在改成**可以在任兩個值之間插入的鍵**。

- **鍵**：短字串（分數索引 fractional indexing，公有領域演算法，自己寫在 `@onden/markdown` 的 `orderKey.ts`，不加依賴），
  欄位 `order_key`，內容與前後端都用同一份程式：`keyBetween(前, 後)`、`keysBetween(前, 後, n)`、`isValidOrderKey`、`compareOrdered`。
  **比較一律逐位元組**：資料庫用 `COLLATE "C"`，JS 用純 `<`，不用語系排序、不用 `localeCompare`（`orderKeyAgreement.integration.test.ts` 用隨機鍵驗兩邊一致）。
- **搬動或插入一則只寫一列**：新鍵放在新鄰居的鍵之間；不再重編鄰居。沒有說位置的新筆記、新指標、複本放在同層最後。
- **兩筆最後鍵相同（兩台在同一個位置各插一則）時的順序規則（成為同步格式的一部分）**：
  先比 `order_key`，再比 `order_stamp`（設定那把鍵的那次寫入的混合邏輯時鐘，固定寬度字串 `wall(15 位)counter(6 位)`；沒有標記的列是空字串，排在前面），最後比列 id。
  每個節點照這個算，所以結果一致；它不保證符合任何一邊的原意。`order_stamp` 由資料庫自己在鍵改變時從同一個寫入標記複製進該列（外來標記被採用時，複製的就是外來的那個），並隨列一起送到客戶端。
- **鍵太長**：超過 `ORDER_KEY_RESPACE_LENGTH`（32 字元）時，在**同一次寫入裡**把整個同層重新平均配鍵（`respaceSiblings`：多列、同一個交易、同一個標記），保留現有順序，含垃圾桶裡的列；讀取從不做。其他列的鍵變了卻沒有各自的事件，所以同一個交易另記一筆 `NODE_UPDATED`（payload `order_respaced`＝哪一組），同步增量看到它就把整個同層的列一起送出（`sync/delta.ts`），送出這次寫入的裝置與其他裝置因此拿到相同的鍵。重新配鍵**之前**的搬動事件記的是舊鍵：撤銷時不寫回舊鍵（沒有別的欄位要還原就回「後續編輯已改回」，與遷移前整數事件同一個處理，`eventRestore/restore.ts` `withoutStalePlace`）。限制：最上層（沒有父層）的指標重新配鍵時，其他指標要等下次完整載入才更新。
  在尾端或前端連續插入，一萬次最長 4 個字元；一直插在同一個縫隙，一萬次的原始鍵長達約 1,670 字元，有 32 字元上限後最長 33。
- **舊整數**：`sort_order` 欄位留著、不再讀寫（新列為 NULL），讓回退有舊順序可看。舊客戶端與離線佇列裡還在送整數時，伺服器收下並翻成鍵
  （`translateLegacySortOrder`：對還帶著舊整數的同層列，放在最後一個比它小的後面）；`CLIENT_PROTOCOL` 升到 4，舊頁面不能再寫入同步（426），佇列保留，重載後以新協定重送。
- **標記與紀錄**：標記欄位名稱仍是 `sort`（舊標記照舊有效）；`structure_log` 現在也記排序欄位的新舊鍵（§8.5 說要等這一項）。
- 沒選的：由伺服器依「放在誰後面」的意圖算鍵（離線時客戶端仍要自己算鍵才能顯示，兩邊要有兩份演算法）；每台各算一個數字再用時鐘決勝（沒有「兩個值之間」，搬動仍要重編）。

### 4.8 檢視同名
同一個標籤或筆記底下出現兩個同名的已存檢視。
- **建議**：較晚的自動改名成「名字 (2)」。檢視的名字不是身分，改名不影響內容。

### 4.9 一邊刪除、另一邊編輯（已決定，2026-11-12）
這是唯一一條兩邊意圖直接相反的規則。原則：**刪除照樣生效；但別人寫的字一個都不丟，而且會告訴他去哪裡找。**
- **一台刪了筆記，另一台改了它**：筆記在垃圾桶，編輯的內容照樣併入；復原時拿到含那次編輯的版本。改的人下次同步時收到通知「你改過的這則筆記已被刪除，修改保留在垃圾桶」，可一按復原。同一個人在兩台裝置上做的不通知。（沒選：編輯讓刪除失效、筆記回到原位。）
- **一台刪了父筆記，另一台在它底下新建了一則**：新建的那則保留，跟著父筆記一起在垃圾桶，復原父筆記時一起回來；通知建立的人。（沒選：移到最上層；不生效——現有引擎的 `parent_deleted` 拒絕會丟掉新筆記，搬到主線時要改。）
- **一台永久刪除，另一台改了它**：筆記不回來；晚到的修改變成一份復原副本還給改的人（沿用「存不進去的輸入保留成復原副本」的既有做法）。（沒選：丟掉；永久刪除只准在值班節點上、等所有裝置同步後才執行。）

### 4.10 搬動造成迴圈
一台把甲搬進乙，另一台把乙搬進甲。
- **建議（現有引擎已是這樣）**：較晚的那次搬動不生效，筆記留在原位，並告知做這個動作的人。

### 4.11 兩邊改同一個屬性欄位
- **建議**：較晚的贏（照邏輯時鐘，不照裝置時鐘）；輸的那個值留在歷史裡，並照現在的做法標成一筆衝突讓人看得到。

### 4.12 兩邊改同一則筆記的內文
- **不變**：三方合併；改到同一行就問人。字元級合併（Eg-walker）是另一條線，照原計畫，不受本文影響。

### 4.13 擁有者轉移、邀請、登入
- **建議**：這些只能在主伺服器上做。它們牽涉身分，離線各做一次沒有合理的合併方式。

### 4.14 離線很久的裝置
重送去重用的紀錄現在保留 30 天。
- **建議**：離線超過這個期限的裝置重新連上時，待送的修改不自動送出，逐筆列給使用者確認。

### 4.15 「今天」
時區與換日時間是工作區的設定，本身也會同步。
- **建議**：各節點照自己手上的設定算；重複任務的下一筆因為用固定 id（4.6），兩個節點各滾一次也只會有一筆。

## 5. 還沒查清楚的事

- **已查（2026-11-12，讀程式、未執行）：主線的事件不能當成可複製的帳本，也不該外傳。** 約 100 種事件裡只有少數幾類帶完整的新值（屬性、標籤套用、刪除、搬空間、功能引用、連結）；檢視、白板版面、網站設定、AI 建議、段落錨點的事件只記了改了什麼欄位。事件裡的復原資訊（改之前的內容）外傳會把對方加入之前的舊內容送出去。
  現有的客戶端同步本來就是傳資料：伺服器只用事件找出哪些筆記被動過，再送它們目前的樣子，並只送對方看得到的。所以第 1 節採「資料帶來源標記」而不是「複製事件」。代價是放棄「照當時的順序重新判斷誰有權限」，要靠每個標記上保留作者與邏輯時鐘來補。
- 晚到的撤權在沒有「整份重算」的情況下怎麼讓它之後的寫入作廢（現有引擎靠重算做到）。
- 現有的雙裝置同步模擬器和引擎的故障模擬怎麼併成一套。

## 6. 驗收條件

沿用業主 2026-11-01 定的那條：同一串操作，星狀（裝置只跟伺服器同步）與網狀（裝置互相同步）跑完，每個節點每個空間的狀態必須相同。上線前的七項每一項都要在現有的使用方式下行為不變，並有測試證明。
