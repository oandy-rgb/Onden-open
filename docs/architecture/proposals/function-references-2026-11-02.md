## 0. 結論

1. **現在「這個東西有什麼功能」散在五個地方**：`tag_schema.module`、`tag_schema.extends`、舊的 `tag_schema.behaviour.modules.<id>.enabled`、
   `content_nodes.collection_views`、筆記身上的隱藏模組標籤（`node_tags`）。空間完全沒有；功能只有整個工作區的開關（`workspaces.modules_off`）。
   每個消費者各算一次（`tagAbilities`、`viewModules`、`noteViews`、`useNoteSwitch`……）。
2. **建議：一張 `function_refs`（功能引用表）＋一個服務入口 `services/functionRefs.ts`。**
   一列＝「某個引用者（空間／標籤／筆記，之後加段落）引用某個功能，帶一份設定」。
   這張表取代上面五處；`tagAbilities.ts` 的 `effectiveTagModules`、`tagExtends` 與 `viewModules.ts` 的 `syncViewModuleExtends` 都消失。
3. **視角就是功能的一種引用**：加視角＝加一列（月曆的「用哪個日期欄位」放在這一列的設定）。標籤、筆記、空間用同一個入口，
   不再有「標籤要先 extends #月曆 才算有月曆」這種雙向要同步的間接層。視角種類（#月曆 #看板…）不再以標籤出現。
4. **個人狀態＝同一張表多一個擁有者欄位**：`owner_actor_id` 為空＝大家共用的引用；有值＝只有這個人的引用（例如「稍後讀只是我的」）。
   進度類資料（複習排程、已讀）繼續用遷移 092 的分人表，不搬。
5. **一條硬規則**：功能只作用在「直接引用它的那一層」，不往下繼承——標籤的引用只給直接帶這個標籤的筆記／段落，
   筆記的引用不傳給子筆記，段落同理。**空間是唯一例外的語意**：空間引用＝「這個空間裡有這個功能」（可用、可看），
   不是「裡面每篇筆記都變成這個功能」。這樣空間、標籤、筆記、段落四層規則只有一句話，並與段落錨點 §S3.2「功能不往下繼承」一致。
6. **分五批**（第 7 節），每批可單獨合併、可回退；先做「引用表＋標籤層」，段落放最後（等錨點批 1）。
   遷移編號從 **166** 起（main 最後是 160；段落錨點保留 161、163–165，事件雜湊 162，RSS 170–171），
   本線用 166、167、168、169，之後 172 起。

**歸納成四件事（本案的設計依據，各家都沒有全做到）：**

1. 「類型帶功能、類型可 extend」是 Tana、Anytype、Logseq DB 的共同做法 → 標籤引用功能。沒有人讓「空間」引用功能（Anytype 是空間擁有類型定義，語意不同），
   所以第 4 節的空間語意是 Onden 自己要定的，沒有現成答案。
2. 視圖應該是「引用」，可放在任何宿主（Notion 連結資料庫、Obsidian 嵌入 base、Craft 集合區塊）→ 視角＝功能引用。
3. 個人狀態要和共用內容分開存（Notion 我的最愛、Craft 個人收件匣）→ 沿用 092 分人存法，加上「個人引用」。
4. 區塊也能帶類別的先例只有 Logseq → 段落當引用者是可行但少見，要小心範圍。

## 3. 功能引用表

### 3.1 四種功能與四種引用方式

業主已定：功能給下面四種東西之一。引用表不改這個分類，只是把「誰引用它」統一。

| 功能給的東西 | 例 | 引用者引用了之後 | 設定（`config`） |
| --- | --- | --- | --- |
| 一個**頁面** | 日記、閱讀、網站 | 引用者那裡出現一個入口（見 §6 空間；標籤與筆記不引用頁面型功能） | 少有 |
| 筆記上的一個**開關** | 稍後讀、技能、收件匣 | 筆記資訊欄多一列開關 | 少有 |
| **欄位／動作** | 複習、任務 | 帶這個標籤的筆記／段落得到欄位或動作 | 例如複習的每日新卡上限 |
| 一種**看法**（視角） | 月曆、看板、畫廊 | 引用者頁面多一個視角分頁 | **視角功能會問它需要什麼**：月曆問哪個日期欄位；看板問哪個欄位當分欄；另有名稱、篩選、排序 |

表格是每個節點內建的，不是引用（但**另外命名、加了篩選的表格視角**是引用，與其他視角同一種）。

### 3.2 表的形狀（草圖；實作時以遷移檔為準）

```
function_refs
  id              uuid PK
  workspace_id    uuid NOT NULL
  function_id     text NOT NULL        -- 模組 id，如 review、calendar；不存在的 id 保留不刪（同 setTagModules 的既有規則）
  instance        text NOT NULL DEFAULT ''   -- 同一個引用者可以多次引用同一功能時的區分（視角用視角 id；單例功能為空字串）
  config          jsonb NOT NULL DEFAULT '{}' -- 功能自己宣告的設定（月曆：date_field、name、filters、sort、pin_order）
  holder_node_id  uuid REFERENCES content_nodes(id) ON DELETE CASCADE   -- 筆記或標籤（標籤本來就是 class_tag 節點）
  holder_space_id uuid REFERENCES spaces(id)        ON DELETE CASCADE   -- 空間（獨立表，不變成節點）
  owner_actor_id  text                 -- 第 3 批才加；NULL＝共用，有值＝只有此人（§5）
  created_by / created_at / updated_at
  CHECK (exactly one holder_* is not null)
  UNIQUE (holder…, function_id, instance, owner_actor_id) -- NULL 視為相同，用 COALESCE 的唯一索引
```

- **引用者為什麼是兩個欄位，不是 `holder_kind + holder_id`**：空間是獨立表、筆記與標籤是 `content_nodes`，
  各自要真的外鍵與連帶刪除；用 `kind+id` 兩欄就得靠觸發器或應用程式清孤兒。比較過的兩種設計：
  - **甲（建議）**：每種引用者一個可空欄位＋ CHECK 恰好一個；有外鍵、有連帶刪除；段落到第 5 批多一欄。
  - **乙**：`holder_kind + holder_id`，欄位少、之後加引用者不用遷移；但沒有外鍵，要自己寫清孤兒與權限範圍，
    與 `readPolicy` 的 SQL 範圍難對齊。
  - 結論：甲。多一欄遷移是一行，換來資料庫幫我們擋孤兒。
- **`instance`**：視角需要「同一個標籤有兩個月曆」；單例功能（複習）空字串。這是現有 `collection_views` 陣列裡每個視角有 id 的直接對應，
  遷移時**保留視角 id**，連結、釘選與事件歷史不斷。
- **不放 `enabled` 欄位**：引用存在＝開；拿掉＝刪除這列。功能的資料（複習排程、任務屬性）本來就不在這裡，刪引用不會刪資料，
  與現行「Removing enrollment does not erase module state」一致。

### 3.3 與現有五處的關係（每一處最後都消失）

| 現在 | 變成 | 遷移怎麼做 |
| --- | --- | --- |
| `tag_schema.extends` 裡指向模組標籤的項目 | 標籤引用該功能的一列 | 逐筆轉成 `holder_node_id = 標籤, function_id = 模組` |
| `tag_schema.module`（#複習 這種模組標籤本身） | 標籤本身不再是功能的「身體」；功能本身只存在於模組登錄 | 模組標籤上的設定（複習的上限等）移到「功能的工作區設定」（§3.6） |
| `tag_schema.behaviour.modules.<id>.enabled`（舊） | 同上，標籤引用該功能 | 一次轉成引用，欄位刪除 |
| `collection_views` | 每個視角一列，`instance` ＝原視角 id，`config` ＝原視角內容 | 標籤與筆記一起轉；`syncViewModuleExtends` 與視角模組標籤（#月曆 #表格 #看板 #卡片）一併刪除 |
| 筆記身上的隱藏模組標籤（`node_tags`） | 筆記引用該功能的一列（共用或個人，§5） | 依功能逐個轉，轉完把隱藏的模組標籤從 `node_tags` 移除 |
| `tag_schema.extends` 裡指向使用者自己的標籤的項目（舊的標籤對標籤延伸，#360、D105） | 見第 9 題 | 建議攤平：把被延伸標籤的功能複製成這個標籤自己的引用 |

**模組標籤節點本身怎麼辦**：它們是標籤樹外的 `class_tag` 節點（遷移 129）。引用表之後沒有「模組標籤」這個概念，
這些節點在遷移中**刪除（進垃圾桶可復原）**，其上的內容（說明文字、欄位範本）若有使用者改過，遷移前逐一盤點、不覆蓋。
這是本案風險最高的一步，放在第 3 批，先在副本資料庫整份跑一次。

### 3.4 繼承規則（一句話：只作用在直接引用的那一層）

| 引用者 | 這個引用作用在哪 | 往下繼承嗎 |
| --- | --- | --- |
| **筆記** | 這篇筆記自己 | 不；子筆記不因父筆記有功能而有功能 |
| **標籤** | 直接帶這個標籤的筆記（以及直接帶這個標籤的段落） | 不沿筆記樹往下；標籤自己的「主題」也不往下繼承（2026-11-09 改，`block-nodes.md` §5） |
| **空間** | 這個空間本身：空間頁與空間導覽有這個功能；空間裡的筆記**看得到**這個功能的開關與視角入口，但**不會自動變成**這個功能 | 不 |
| **段落** | 這一段 | 不（段落錨點 §S3.2） |

- **空間和標籤層為什麼語意不同、而且要說清楚**：標籤是「分類」，帶標籤的東西就是那一類，所以引用「作用」在成員身上（#單字 的卡片就是複習卡）；
  空間是「地方」，同一個空間裡有各種筆記，把整個空間的筆記全變成複習卡或任務不合常理。所以空間引用只表示「這裡可用」。
  空間裡想讓**某一類**筆記有功能，做法是標籤引用（標籤本來就能跨空間；§6 說明例外）。
- **標籤 extends 標籤的傳遞閉包不再有**：現在「#A extends #B extends #複習」會讓 #A 得到複習（廣度優先、最近者勝）。
  第 9 題的建議（攤平）之後，標籤的功能只看自己的引用，不再有「最近者勝」的設定覆蓋規則——設定就在引用那一列。
- 一個筆記的**有效功能**＝自己的引用 ∪ 它直接帶的每個標籤的引用 ∪（只用於「可用」判斷）所在空間的引用。
  同一功能多處引用時，設定「最近者勝」：筆記自己 > 標籤（多個標籤衝突時，依標籤名稱排序取第一個，並在標籤頁顯示衝突提示）> 空間。
  這個衝突規則取代現在 `effectiveTagModules` 的廣度優先。

### 3.5 一個服務入口取代各自計算

`services/functionRefs.ts`（寫入走 `spine/mutate.ts`、讀取走 `readPolicy`）：

```ts
type FunctionHolder =
  | { kind: "node"; id: string }    // 筆記或標籤
  | { kind: "space"; id: string }
  // | { kind: "block"; id: string } // 第 5 批

// 寫（領域操作，各自一個事件、一個交易、可復原）
addFunction({ actor, workspaceId, holder, functionId, config?, personal? }): Promise<{ refId: string }>
removeFunction({ actor, workspaceId, refId })
setFunctionConfig({ actor, workspaceId, refId, config })          // 月曆換日期欄位

// 讀
functionsOf(actor, holder): Promise<FunctionUse[]>                // 有效功能，含來源（「來自 單字」）與設定
functionHolders(actor, functionId): Promise<HolderRow[]>          // 功能頁：誰引用了它（含來源）
functionIndex(actor, workspaceId): Promise<FunctionIndex>         // 一次載入給批次判斷（取代 loadTagAbilities）
```

呼叫範例：

```ts
await addFunction({ actor, workspaceId, holder: { kind: "node", id: bookTag }, functionId: "kanban",
                    config: { name: "閱讀狀態", groupBy: statusFieldId } });
await addFunction({ actor, workspaceId, holder: { kind: "node", id: note }, functionId: "read_later", personal: true });
const uses = await functionsOf(actor, { kind: "node", id: note });   // 筆記頁、資訊欄、視角分頁列都只問這一個
```

- 權限：引用在標籤或空間上＝定義「這類東西能做什麼」，與現行 `setTagModules`／`setTagExtends` 一致，要 `principal_admin`；
  引用在筆記上且共用＝能編輯這篇筆記（沿用 `noteViews` 的 `write_node`）；**個人引用**＝只要能讀這篇筆記，自己決定自己的。
  角色與 token 照 `spine/currentActor.ts` 在事件鎖後重讀。
- 事件：`FUNCTION_REF_ADDED`／`REMOVED`／`CONFIG_CHANGED`，目標是引用者（標籤與筆記的事件只有讀得到該節點的人看得到，
  與現行 `target_type: "node"` 一致）；個人引用的事件只給擁有者。復原走 `restoreEvent`，逆向操作檢查逆向權限。
- **這個入口取代**：`tagAbilities.ts` 的 `effectiveTagModules`／`tagExtends`／`tagsExtending`／`loadTagAbilities`／`moduleTagExists`、
  `tagModules.ts` 的 `setTagModules`／`setTagExtends`／`changeTagExtends`、`viewModules.ts` 的 `syncViewModuleExtends`、
  前端 `lib/tagModules.ts`、`useTagStructure` 的功能部分、`useNoteSwitch`。
- 功能模組只多宣告一件事：`FunctionSpec = { kind: "page" | "switch" | "fieldAction" | "view", holders: ("space"|"node")[], personalByDefault?: boolean, config?: 設定的欄位宣告 }`，
  放在既有的模組登錄裡（不新增外掛框架）。月曆的 `config` 宣告「需要一個日期欄位」，加視角的對話框依這份宣告問使用者。
- 前端對應一個 hook `useFunctions(holder)`，標籤頁、筆記資訊欄、視角分頁列、`TagFunctionPicker` 都用它。

### 3.6 功能自己的設定放哪

現行有三層：模組預設 → 標籤設定 → 個人覆蓋（`actor_module_settings`，鍵是模組標籤 id）。模組標籤消失後：

- 模組預設：留在模組登錄。
- **標籤／空間／筆記層設定＝引用那一列的 `config`**（複習：#單字 的每日新卡上限）。
- **工作區層設定**（原本放在模組標籤上、全工作區一份的）：新增小表 `workspace_function_settings (workspace_id, function_id, settings)`，第 3 批遷移。
- 個人覆蓋：`actor_module_settings` 的鍵從 `tag_id` 改成 `(function_id, 引用 id 或空)`，同批遷移。

## 4. 空間引用功能

**一句話**：空間開了某功能＝「這個空間有這個功能」。

| 功能種類 | 空間引用的意義 |
| --- | --- |
| 頁面（日記、閱讀、網站） | 這個空間的導覽出現入口，頁面只列這個空間的內容。個人空間有日記、共用空間不開，是自然的用法。 |
| 開關（稍後讀、技能、收件匣） | 這個空間裡的筆記，資訊欄**看得到**這個開關；沒引用的空間看不到（開關不顯示、現有狀態保留）。 |
| 欄位／動作（複習、任務） | 這個空間可以使用（標籤頁的「＋加功能」清單、筆記的「當成卡片」入口都出現）；**不會**自動把筆記變成卡片。要一類筆記自動有，請用標籤引用。 |
| 視角 | 空間頁多一個視角分頁，列這個空間的筆記（月曆＝這個空間所有筆記依日期欄位排）。 |

**與 `workspaces.modules_off` 怎麼共存**（兩層、各管一件事、不互相複製）：

1. 工作區層＝**總開關**，沿用不動：`modules_off` 的功能在整個工作區隱藏，其下所有引用保留但不生效（資料留著、重新開啟即恢復），
   `modules_confirmed`、`requires`、`alwaysOn` 照舊。
2. 空間層＝**這個空間有沒有**：只能在工作區開著的功能上加，不能把已被工作區關掉的功能「開回來」。
3. 有效可用 ＝ 工作區開 ∧（功能不需要空間引用 ∨ 該空間引用了它）。哪些功能需要空間引用才算有，是「功能種類」決定的：
   **預設建議**：頁面型與開關型需要；欄位／動作型與視角型不需要（工作區開著就可以在任何空間用，空間引用只是「放進這個空間的導覽」）。
   這避免一次升級後所有空間的現有功能都消失——遷移不必替每個空間補引用，只要為已有導覽入口的頁面型補。見第 9 題。
4. 預設空間沒有任何引用時＝行為與今天完全一樣（工作區開著的功能全可用）。這是「升級不改變現有行為」的根據。

## 5. 開關與每個人自己的狀態

### 5.1 哪些開關是個人的

| 開關 | 建議 | 理由 |
| --- | --- | --- |
| **稍後讀** | **個人** | 「這篇我晚點讀」只關自己的事；共用空間裡別人的稍後讀不該出現在我的清單。「已讀」本來就是個人（`read_later_done`）。 |
| **收件匣** | **個人** | 「我還沒整理」是個人待辦。共用空間的收件匣要不要讓全員看見是另一個問題（見第 9 題）。 |
| **技能** | **共用** | 技能是給 AI 看的筆記，由誰呼叫與可否寫入走 MCP／權限，不是個人偏好。 |
| 複習（這篇是不是卡片） | 共用；**排程個人** | 「這是一張卡」是內容的性質；何時複習早就分人存（`review_states`、`block_review_states`）。 |
| 任務（這篇是不是任務） | 共用 | 任務是團隊共見的內容；完成狀態另有屬性。 |

`FunctionSpec.personalByDefault` 宣告預設；使用者按開關時不問「共用還是個人」，介面只呈現該功能的既定語意
（例如稍後讀的列名是「我的稍後讀」，技能是「當成技能」），避免讓使用者學一個新概念。

### 5.2 存法

- **不另開個人表**：個人開關＝`function_refs` 一列，`owner_actor_id` ＝自己。與 092 的分人資料同一種原則（以 actor 分），
  只是這裡的「事實」是「我引用了」，不是進度數值。
- 進度類資料（`review_states`、`read_later_done`、`rss_seen`、`block_review_states`）**不動、不搬**。
- 個人引用**只對擁有者可見**：`functionsOf`／`functionHolders` 的 SQL 範圍＝共用列（受引用者的可讀範圍約束）∪ `owner_actor_id = 自己`。
  成員看不到別人的個人引用，管理員也看不到；這個範圍放在 `readPolicy` 的公開介面，不在各入口各寫一次。
- **成員移除**：`memberRemovals.ts` 加刪除該人的個人引用（與 092 相同）。
- **撤權**：失去某筆記讀取權的人，個人引用留著但不生效（讀取走筆記的可讀範圍，與 `read_later_done` 的做法一致）。
- **同步**：個人引用只送給擁有者；共用引用隨它的引用者送。沿用既有 `membership_epoch` 與可讀集合核對，撤權與重連後以可讀集合為準。
- **備份**：共用引用隨工作區匯出；個人引用只出現在擁有者自己的匯出（與 092 的進度資料相同處理方式，實作時對齊現行備份範圍）。
- **事件**：個人引用的 `FUNCTION_REF_*` 事件只歸擁有者；復原也只能復原自己的。

### 5.3 從隱藏模組標籤遷移

1. 每個「筆記帶有某模組標籤」的 `node_tags` 列 → 一列引用（共用或個人依 §5.1）。
   - 個人化的稍後讀／收件匣：**原本的標籤是全員共用的**，所以遷移時要決定「誰的」。建議：**歸給當初套用標籤的人**
     （`node_tags` 有套用者就用；沒有紀錄的歸工作區擁有者）；找不到對應 actor 的列保留為共用並在遷移報告列出數量，不靜默丟棄。
   - 這一步會讓某些人原本看得到的「別人的稍後讀」消失，是**預期內的行為變更**，要在 `changes/` 用白話說明，並先給業主看遷移報告再上正式站。
2. 遷移後移除那些隱藏標籤的 `node_tags` 列與標籤節點。
3. 前端 `lib/noteSwitch.ts`／`useNoteSwitch` 改呼叫 `addFunction`／`removeFunction`；「加減隱藏標籤」的做法整個拿掉。
4. 任務與複習不是「開關」而是帶標籤才有的欄位／動作；它們的標籤引用在第 1 批處理（標籤層），**筆記直接帶「任務」的方式**
   （現在是筆記上有 `#task`）在第 3 批處理，因為牽動任務查詢，單獨一個 PR。

## 6. 視角就是功能

- **加視角＝加一筆引用**。標籤、筆記、空間用同一個入口 `addFunction({ functionId: "calendar", config: { dateField, name } })`。
  標籤頁與筆記頁的視角分頁列都是 `functionsOf(holder).filter(kind === "view")`，不再有「標籤要同步 extends #月曆」的雙向一致問題：
  只有一份事實，沒有另一份要同步。
- **雙向一致的意思**：從標籤頁的「＋加功能」選月曆，與在視角分頁列按「＋」加月曆，是同一個操作、產生同一列；
  功能頁「月曆」列出所有引用它的標籤／筆記／空間（取代今天「#月曆 標籤頁收集所有 extends 它的標籤的筆記」）。
- **視角功能會問它需要什麼**：`FunctionSpec.config` 宣告需要的設定；日期欄位的候選＝引用者「成員」的日期型欄位
  （標籤：標籤欄位；筆記：子筆記共同有的欄位；空間：空間內筆記常見的日期欄位）。取代 `calendarGrid.ts` 的 `pickDateField` 依名稱猜
  （views-as-modules 已記為 GAP-157）。
- **`collection_views` 如何收進來**：每個視角一列，`instance` ＝視角 id，`config` ＝名稱、版面、篩選、排序、釘選順序、版面參數。
  `executeView`（`collectionViewQuery.ts`）不動，只改它從哪裡拿視角定義。`tagViews.ts`／`noteViews.ts` 的路由保留
  （介面「改名／刪除視角」仍是使用者要完成的事），但內部都轉呼叫 `functionRefs`。遷移完成後欄位 `collection_views` 刪除。
- **視角模組標籤與規則 6 消失**：視角種類永遠不以標籤出現（業主）；`ViewModuleTagError`、`assertNotViewModuleTag` 與
  `viewModuleOfTag` 隨之刪除，「不能把 #月曆 套到筆記上」這件事不再存在。
- 空間的視角分頁是新的（今天空間沒有分頁列）；第 4 批才做，先決定空間頁要不要有分頁列（第 9 題之一）。

## 7. 與段落錨點批 1 的接縫

段落錨點設計（PR #1165，§0.5 與 §S2–§S5）已定：`{主題}` 與 `{{功能}}` 分開；標籤可以帶功能；主題往下繼承、功能不繼承；
寫了功能的段落出現在功能頁；功能資料以 `block_nodes.id` 為鍵；段落的功能「來自 單字」要標來源。
這等於**段落是第三種引用者**。兩條線要共用的入口：

| 共用什麼 | 誰擁有 | 做法 |
| --- | --- | --- |
| 「這個段落有哪些功能」的問法 | `functionsOf({ kind: "block", id })` | 段落錨點批 1 **不自己再寫** `{{功能}}` 或「標籤→功能」的判斷，只呼叫這一個 |
| 功能頁「列出誰用了我」 | `functionHolders(functionId)` | 回傳筆記、標籤、空間、段落同一種列，含來源（直接寫的／來自 某標籤） |
| 功能名稱解析（`{{複習}}` 認不認得） | 模組登錄（既有） | 兩邊都問登錄，不各存一份名單 |
| 標籤帶功能 | 標籤引用（本案第 1 批） | 段落錨點的「來自 單字」＝段落所帶標籤的引用 |
| 功能不繼承 | 本案 §3.4 | 一句話規則，錨點 §S3.2 的表格直接引用它 |

**段落引用與其他引用有一個本質差別**：段落的 `{{功能}}` 的事實來源是**正文**（「功能頁與正文永遠一致」「按取消會拿掉正文的 `{{…}}`」），
不是使用者在畫面上按出來的一列。所以段落的引用列是**由存檔流程派生的索引**（存筆記時依正文重建該筆記各段落的引用，沿用現行區塊索引的 `replace_for` 做法），
`addFunction`／`removeFunction` 對 `block` 引用者**不開放**；功能頁的「取消」是改正文，再由存檔重建。這一點寫進 `FunctionHolder` 的型別註解與守門測試，
避免有人從 API 直接寫段落引用造成與正文不一致。

**誰先做**：建議**本案第 1 批（引用表＋標籤層）先於段落錨點批 1 的「功能」部分**，原因：段落錨點批 1 的主要工作是錨點表與編輯器精確搬（遷移 163–165），
與功能引用互不依賴；但批 1 要做「`{{功能}}` 與標籤帶功能」時，若引用表還不在，就得先寫一個只給段落用的「標籤有哪些功能」讀法，
等於再生出第六處計算。順序：

1. 本案 B1（166，標籤層＋唯一入口）——小、可回退。
2. 段落錨點批 1（161、163–165，錨點與搬移）——**可與 B1 並行**，因為這時段落還不碰功能。
3. 段落錨點批 1 的功能部分與本案 B5（段落引用者）合為同一批，由 `functionsOf` 提供讀、存檔流程提供寫。

若業主要段落線先上，退路是：段落線自己的功能部分暫放在**一個**叫 `blockFunctions(blockId)` 的函式後面，B5 時整個換成 `functionsOf`；
不准在多處各讀各的（用 ratchet 限制呼叫點數）。

| **B5 段落引用者** | `holder_block_id`（FK `block_nodes(id)`）；存檔流程派生段落引用；`functionsOf` 與 `functionHolders` 支援段落；功能頁含段落；「來自 單字」來源標示 | **173**（等段落錨點批 1 合併後） | 段落引用只能由存檔流程寫（型別與守門測試）；功能不繼承（父段有功能、子段沒有）；標籤帶功能時只給直接寫了該標籤的段落；`lost` 錨點時引用不丟（沿用 §S4.4）；與 `block_review_states`、`block_nodes.task_id` 的鍵一致 | 單獨 revert（段落線的功能部分一起退） |

註：本案「遷移」以**加新表／加新欄、搬資料、再刪舊欄位**為順序；刪舊欄位（`collection_views`、`tag_schema.module` 等）放在**同一批的最後一個遷移**，
而不是同一個遷移裡，這樣上線一版之後才真正不可逆。具體順序與資料量在實作批時以遷移檔為準。

**每批共同的驗證**（`testing.md`）：允許／拒絕案例、workspace 與空間邊界、撤權；交易涵蓋事件回滾與重試去重；復原涵蓋後續編輯與衝突；
政策有逐筆與集合兩種實作時兩者一致（`functionsOf` 與 `functionIndex` 要有一致性測試）；資料庫整合測試用隔離資料庫並確認實際執行。
改介面的批要跑桌面與手機尺寸檢查與 `layout:audit`。每批加守門測試：新程式不可再讀 `tag_schema.module`／`tag_schema.extends`
（功能目的）／`collection_views`／隱藏模組標籤；`entrypoints.catalog.json` 加入 `functionRefs.ts` 與 `useFunctions`。

## 9. 要業主決定的事

> 業主 2026-11-02：全部照建議（10 題）。第 6 題的「哪些模組標籤被使用者改過」報告在 B3 之前給業主看。

每題：問題 → **建議** → 一句影響。

1. **標籤對標籤的延伸（舊的 extends，指向使用者自己的標籤）怎麼辦？** → **攤平**：遷移時把被延伸標籤的功能複製成這個標籤自己的引用，之後不再有標籤 extends 標籤。
   影響：少一個「最近者勝」的繼承規則；但「#A extends #B 之後 #B 的成員查詢也列 #A 的筆記」（`tagsExtending`）這個效果會消失，需要先盤點有多少標籤在用。
2. **功能完全不往下繼承、空間只表示「可用」，可以嗎？** → **可以**（§3.4）。影響：整個系統「功能作用在哪一層」只有一句規則；代價是「整個空間的筆記自動變任務／卡片」做不到，要用標籤。
3. **稍後讀、收件匣個人化、技能共用？** → **是**（§5.1）。影響：遷移會讓共用空間裡「別人的稍後讀」從我的清單消失，並要決定舊資料歸誰（建議歸套用者）。
4. **共用空間裡的收件匣，管理員要不要看得到別人的收件匣？** → **不要**（個人引用誰都看不到）。影響：沒有「幫忙整理別人收件匣」的管理功能；日後想要再另做明確的授權。
5. **空間層要不要遷移替每個空間補引用？** → **只為已有導覽入口的頁面型功能補**；欄位／動作與視角不需要引用（§4）。影響：升級後所有空間行為不變；代價是「空間有哪些功能」的畫面只呈現頁面型與開關型。
6. **模組標籤節點（#複習、#月曆…）遷移時刪除？** → **刪除（進垃圾桶，可復原）**，使用者改過的說明與欄位先逐一盤點不覆蓋。影響：這是最大風險，建議 B3 之前先給業主看一份「哪些模組標籤被使用者改過」的報告。
7. **要不要「完全沒有過渡」？** → **不要**：分批、每個功能一個時間點只有一種讀法，舊讀法藏在同一個入口內、ratchet 只減不增、B4 刪光。
   影響：B1～B3 期間內部仍有舊讀法；若堅持一次大遷移，改動面橫跨標籤、筆記、視角、任務、複習，單一 PR 風險與審查成本很高，不建議。
8. **空間頁要不要有視角分頁列？** → **要**，與標籤頁、筆記頁同一個元件。影響：空間第一次有「月曆／看板看整個空間」；需要決定空間頁的版面（B4 前出簡圖）。
9. **同一功能在筆記、標籤、空間多處引用且設定不同時誰優先？** → **筆記自己 > 標籤 > 空間**；多個標籤衝突時依標籤名稱取第一個並顯示提示。
   影響：行為可預期；少數同時帶兩個設定不同的標籤的筆記會看到提示。
10. **誰先做：引用表還是段落錨點？** → **引用表 B1 先、錨點批 1 可並行、段落的功能部分與 B5 合併**（§7）。影響：避免再生出第六處「有哪些功能」計算；錨點線的功能部分會晚一批。
