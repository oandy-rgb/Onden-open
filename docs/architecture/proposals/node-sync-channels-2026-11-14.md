# 提案：節點對節點同步，中間的通道可以換（不假設有常開的機器）

> 狀態：提案（方向已同意；筆記的快照與修改包已做，通道、信箱、歷史跟著走還沒做）

> 相關：[資料帶來源標記](causal-stamps-2026-11-12.md)、[傳到我的手機](send-to-phone-2026-11-12.md)（中繼的雛形）。

## 1. 為什麼要補

上層文件的方向是「伺服器、瀏覽器版、桌面版都是節點；主伺服器是一個永遠開著、大家預設信任的節點」。業主 2026-11-13 指出兩點：

1. **對一般使用者，「有一台常開的」不成立。** 他們有的是會開開關關的手機和筆電，頂多一台常開但不是 24 小時的桌機。
2. **換主會掉歷史。** 同步只傳資料現在的樣子，歷史是各節點自己的帳本；主要的那台換掉，舊主上的版本歷史不會跟過去。
   「衝突時輸的值留在歷史裡」這個保證因此只在「記下它的節點還在」時成立。現有的「搬移整個工作區」原本明寫不搬版本歷史與操作紀錄（2026-11-14 起版本歷史可選擇帶；操作紀錄仍不搬）。

## 2. 一句話

**每台裝置都是完整的節點；節點之間交換同一種「修改包」；中間走哪條通道，看那台中間的機器是誰的。**

- 自己的機器（自架伺服器、家裡的桌機）當中間：它是完整節點，看得懂內容，能合併、存完整歷史、發布、跑排程。
- 別人的機器（我們營運的中繼、使用者的雲端硬碟）當中間：它是信箱，只暫存加密過的修改包，看不懂、不合併、不判斷。
- 同一個網路裡的兩台裝置：直接互傳，不經過任何人。

使用者不選模式，有什麼就得到對應的能力。資料格式與合併規則在三種通道下完全相同。

## 3. 這樣算不算分散式

判斷標準：中間那個東西消失或說謊時會怎樣。

| | 中間消失 | 中間說謊 |
|---|---|---|
| 現在（伺服器是權威） | 正本沒了，裝置上的副本彼此合不起來 | 它說什麼就是什麼 |
| 本提案 | 每台裝置都有完整資料與歷史，換一條通道繼續 | 信箱看不懂內容，改了會被驗出來；最多扣住不轉交 |

沒有任何一台說了算，任何一台壞了系統仍然正確——這是「沒有權威」的分散式，業界通常稱作本機優先。它**不是**「沒有中間人」：純點對點要求兩台裝置同時在線，一般使用者做不到，只當成第 2 節的第三種通道。

## 4. 修改包（上線前要定的格式）

節點之間交換的唯一單位。直接連是「當場交換」，信箱是「放著等人來拿」，內容相同。

- **內容**：一段連續的、帶來源標記的資料列變更（[來源標記](causal-stamps-2026-11-12.md)的 `origin`、`seq`、混合邏輯時鐘、作者、裝置），加上刪除的墓碑。
- **不可變、只寫一次**：以「來源節點＋序號範圍」或內容雜湊命名。沒有任何兩個節點會寫同一個名字，所以不需要鎖。
- **外層**：格式版本、最低可讀版本、加密方式的代號、金鑰的代號。
- **容忍缺漏與亂序**：先到第 7 包、後到第 6 包不能出錯；每個節點記自己讀到哪裡。
- **快照**：定期寫「到某個狀態為止的完整樣子」，新裝置從快照起步，不必重播全部。清理舊包時只刪自己已經讀過、而且所有已知節點都確認過的。
- **不認得的欄位或操作**：保留並原樣轉交，不丟掉。
- **版本閘門**：低於某版本就明確拒絕同步並請使用者更新，不靜靜繼續（上層文件第 3 項，擴大到包的格式與合併規則——合併規則變了，不同版本的節點會算出不同的內文）。

業界踩過的坑，本設計避開：共用的可變檔案與鎖定檔（Joplin）、每則筆記一個檔案導致被雲端限速（Joplin）、把保留天數的刪除同步給所有裝置（Joplin）、把活的資料庫檔放進同步資料夾（Zotero）。

## 5. 歷史要跟著走

推翻上層文件「歷史只留在各節點」的一部分：

- **內文的版本歷史在同一個擁有者的節點之間同步。** 版本本來就有獨立的編號與雜湊，適合傳。
- **操作紀錄（事件）仍然不外傳。** 理由不變：大多數事件只記改了哪個欄位，重建不出資料；事件裡的「改之前的內容」外傳會把對方加入之前的舊內容送出去。
- **衝突時輸掉的值**隨修改包一起傳（它就是一筆帶標記的變更），所以任何節點都留得住，不依賴某一台。
- **多人時**：只同步對方看得到的那部分版本，規則和資料相同。
- **近期可做、不必等**：搬移工作區與備份可以選擇帶上版本歷史（只限擁有者、只進新工作區）。這不動同步格式。**已實作（2026-11-14）**：備份格式 3，見 [backup-move.md](../backup-move.md) 的「版本歷史」。
- **退役一個節點前**提示「這台上有別處沒有的歷史」。

## 6. 金鑰與裝置（上線前要定的格式）

只有走信箱通道才需要加密，但金鑰的層次要先定，之後才加得上去：

- 資料用隨機產生的資料金鑰加密；資料金鑰再用密碼、復原片語或各裝置的金鑰包起來。**不直接用密碼加密資料**，否則改密碼要全部重新加密。
- 金鑰有世代：裝置遺失時換新世代，之後的修改包用新金鑰。
- 新裝置加入：由已加入的裝置核准（[傳到我的手機](send-to-phone-2026-11-12.md)的配對流程可以沿用），或用復原片語。
- 全部只組合現成、經過審查的函式庫；不自己寫密碼學，實作前後都要獨立審查。
- 多人共用若要不靠任何節點當裁判，每筆變更要帶裝置簽章；簽章欄位先留位置，功能之後再做。

## 7. 需要常開機器的功能，老實列出來

| 功能 | 沒有常開機器時 |
|---|---|
| 同步、合併、歷史、搜尋、複習、任務 | 完整可用 |
| 抓 RSS、AI 排程、語意搜尋索引 | 有裝置開著時才做，開機後補做 |
| 提醒 | 改由裝置本機的通知 |
| 發布網站 | 由某台裝置產生後推到主機空間；沒有裝置開著時不會更新 |
| 給外部 AI 隨時連進來的入口 | 沒有 |
| 多人共用的權限裁決 | 需要一台大家信任的完整節點 |

**背景工作由誰做**：不做「選一台當領導」。工作的編號由輸入與時段算出，兩台都做了也只會得到同一筆結果；有外部影響的工作（發布、寄送）由使用者指定一台主要裝置負責。

## 8. 業主已確認（2026-11-14）

1. 目標定為：每台裝置資料平等、任何一台或任何服務壞了都不丟資料與歷史、中間的通道可以換；需要常開機器的功能照第 7 節明列。
2. 版本歷史在自己的節點之間同步（第 5 節），並先做「搬移與備份可帶歷史」。
3. 信箱通道的先後：先做我們營運的中繼與自架（兩者技術相同，已有雛形），使用者自己的雲端硬碟放最後或不做（業界沒有主流筆記產品做成）。這牽涉到要不要營運一個服務。
4. 一般使用者版先不承諾多人共用的細緻權限（只能建議、不能改），只承諾「能不能看」。

## 10. 業界的做法（2026-11-13 調查摘要）

四類：

- **檔案放在別人的雲端硬碟**（Obsidian 搭 iCloud、Joplin 的同步目標）：不需要廠商伺服器；不會合併，衝突產生副本檔。
- **加密的修改紀錄經過中繼**（Anytype、Actual Budget、Evolu、Obsidian 官方同步、Standard Notes）：穩定即時，中繼看不到內容；要有東西常開，預設由廠商營運。
- **伺服器是權威**（Apple 備忘錄、Zotero 的資料同步、現在的 Onden）：權限、發布、排程最簡單；沒有無伺服器模式。
- **純點對點**（Syncthing、Secure Scuttlebutt）：中間不存東西；實際上都又長出常開的節點。

和我們最像的是 Actual Budget：每個欄位帶混合邏輯時鐘、較晚的贏、伺服器只存和轉。它的弱點是紀錄只增不減。
調查到的產品裡，沒有一家對一般使用者做到「不需要伺服器、每台平等、加密、還能自動合併」；Anytype 改權限需要它的協調節點在線；不靠任何節點的多人權限仍是未完成的研究。
Onden 的不同處：後端本來就能在瀏覽器與桌面版裡完整地跑，每台裝置已經是完整節點，所以能走「節點對節點＋多種通道」，不必在「伺服器權威」與「客戶端加信箱」之間二選一。
