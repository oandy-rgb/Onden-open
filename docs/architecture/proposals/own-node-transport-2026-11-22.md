## 0. 結論（先看這裡）

1. **第一階段的節點只有兩種：VPS 伺服器（中心）與桌面版。** 瀏覽器版晚一批、不算進「丟一台不丟資料」（第 8 節第 3 題）。手機／平板維持**伺服器網頁＋本機鏡像**，不是節點（第 1 節）。
2. **交換只用現有的三樣東西**：第一次加入用快照，之後用「從 `have` 起的修改包」，起點接不上（`bundle_gap`）就改拿快照（＝重新加入，第 3.5 節）。
   新的只有一層薄的：一張「我的裝置」表、`/api/peer/*` 幾條路由、一個排程。**不新增第二條合併路徑、不新增第二個收件入口**：收一律是 `applyChangeBundle`、讀一律是 `readChangeBundle`（第 2 節）。
3. **永遠由不能被連的那一台打出去**：桌面版與瀏覽器版呼叫伺服器；伺服器從不主動連裝置。全程走業主自己的網路（Tailnet），**不經過碰面點或任何外部服務**（第 2.1 節）。
4. **配對**：新裝置的畫面顯示 QR，業主用手機（已登入伺服器網頁）掃、在手機上重新輸入密碼確認（第 3 節）。裝置憑證**不是一個人**（型別上就不是 `ActorCtx`），只能打 `/api/peer/*`。遺失時在「我的裝置」移除；那台之後送來的一律拒收，要再用只能重新加入（清空、換新的節點編號）。
5. **交換之前，引擎本身還有一段路**（第 1、2 輪審查指出、我確認過）：收進來的修改今天**沒有任何畫面看得到**（不寫領域事件、不更新衍生資料，`/api/sync` 只看領域事件），而且本機的「存檔之後」那串工作把衍生的與會被複製的寫入混在一起，不能整串重跑（第 2.12 節的分割表）；快照帶的表裡有 9 張修改包不帶，而且必須在**第一台加入之前**接上（第 2.11 節）；包沒有上界、在 PGlite 上會讓存檔排隊失敗，分段收的前提是收的一方先把整包存好（第 2.10 節）。這些都排在交換之前（第 6 節第 4–6 批）。
6. **「接上傳輸前必須完成」31 項**（main 18 項＋#1907 的 13 項）逐項分到三類：**16 項必須先修**、**12 項在「整個工作區、只有業主一人」時不會發生**（由機器檢查擋：假設不成立就不交換）、**3 項是成本**（附變成必修的數字）。另外列出這份清單沒有、但第一階段一定碰到的 **12 項**（第 4.3 節）。這是本文最重要的一節。
7. **這個傳輸單獨做完，還達不到業主 2026-11-19 的目標**：今天的快照與修改包**不帶版本歷史、手寫舊版本、圖片與附件**（`domain_events` 是 `node-local`、`blobs`／`ink_chunks`／`ink_manifests` 是 `separate`：`packages/backend/src/spine/syncClasses.json:176-179`、`:256-267`；快照拒絕 `history`／`blobs` 層：`packages/backend/src/services/stampedSnapshot.ts:86`）。
   歷史複製是另一份提案；本文只規定交換要留給它的介面（第 2.9 節）。**在那兩層接上之前，畫面不說「這台有完整副本」**。

| **手機／平板**（伺服器的網頁；也有 Capacitor 的 Android 外殼：`packages/frontend/capacitor.config.ts:3-9`） | 本機鏡像是 sql.js，存在 IndexedDB（`packages/frontend/src/lib/localDb.ts:4-12`）；表只有目前狀態（`packages/frontend/src/lib/localDbSchema.ts`：沒有版本、事件、圖片、手寫舊版的表） | 不能 | 鏡像留著；待送佇列留著 | **不是節點，維持鏡像**（下面說後果） |

**手機維持鏡像的後果，照實說**：

- 手機的寫入一律經伺服器（`/api/sync`，`packages/backend/src/app.ts:373`）。伺服器不在時手機照常離線可用，寫入排在待送佇列，伺服器回來才送出——**和今天一樣**。
- 鏡像只從伺服器的**領域事件**找變動（`packages/backend/src/services/sync/delta.ts:94-101`）。所以桌面版推上來的修改，要等第 4 批（收包時寫本機的領域事件）之後，手機才看得到（第 2.12 節）。
- **伺服器整台不見時**：手機只有「目前的筆記」（沒有歷史、沒有圖片的原檔），不是完整副本，也沒有路把鏡像送給任何人。能把伺服器的筆記補回來的是**桌面版**（第 3.6 節的路 甲；但那條路會失去伺服器上的版本歷史與附件，所以伺服器有可用的備份時，預設是還原備份、桌面版重新加入）。
  所以「丟掉伺服器」能不能不丟資料，取決於**桌面版上次交換到哪裡**：手機經伺服器寫的、桌面版還沒拉到的那一段，會隨伺服器一起不見【推論】。要縮小這段，桌面版要常開，或讓它在背景跑（第 8 節第 4 題）。
- 為什麼不讓手機當節點：手機的瀏覽器儲存空間**沒有任何量測**——我在 docs 裡找不到手機的配額或被清除的實測數字；`docs/research/browser-trial/README.md` 第 151 行的配額測試（T7）只是計畫、沒有結果；第 230–233 行 Chrome、Firefox、Brave Android 的保存條件都標「未查證」；
  `docs/research/full-feature-audit.md` 第 410 行用 CDP 把配額壓到 4,096 位元組時，IndexedDB 寫入以 `QuotaExceededError` 中止。在量到之前，手機上的副本不能算「丟一台不丟資料」的那一份。
- 業主要的「每台裝置都有完整副本」，在第一階段**由 VPS＋桌面版兩份**做到（加上既有的備份，第 7 節）；手機要成為節點，前提是先在業主的手機（Android 上的 Brave、平板的 Samsung Internet；#1798 第 4 節記的業主裝置）量儲存空間，另開一批。

## 2. 交換協定（只用已有的東西）

### 2.1 誰打給誰

```
  桌面版（PGlite，只聽本機）──HTTPS over tailnet──▶ VPS（Postgres，中心）◀──HTTPS（網頁）── 手機鏡像（不變）
  瀏覽器版（之後）        ──HTTPS over tailnet──▶
```

- **裝置一律打出去，中心只回答。** 中心從不主動連裝置（裝置聽不到：第 1 節）。
- 走業主自己的 tailnet，網址就是伺服器今天的 Tailnet HTTPS 網址。沒有碰面點、沒有中繼、沒有 STUN；#1798 的碰面點（Cloudflare）**不在這條路上**。
- 裝置打給中心時**不用** `services/safeFetch.ts`：它擋 CGNAT 範圍（檔頭第 6–8 行），而 tailnet 的位址正是 100.64.0.0/10【推論：tailnet 位址範圍是我的背景知識】。
  改用一個只准連「配對時記下的那一個中心網址」的呼叫者（新寫的薄層；不是讓使用者輸入任意網址的通用 fetch）。
- 瀏覽器版的請求是跨來源的（頁面來自公開的瀏覽器版網域，打的是 tailnet 網址）：伺服器的 `CORS_ORIGIN` 要列出瀏覽器版的來源（`packages/backend/src/app.ts:120-131`）；帶 bearer 憑證的寫入不受來源檢查（`app.ts:146`），所以**不必放寬來源檢查**，只要讓瀏覽器讀得到回應【推論】。

### 2.2 一次交換是什麼

一次交換＝**先問、再拉、拉完整再推**，全部由裝置發起。每一步都是既有函式包一層路由：

| 步 | 裝置做 | 中心做（入口） | 既有函式 |
| --- | --- | --- | --- |
| 問 | `GET /api/peer/have`：中心的節點編號、`have`、中心此刻的時鐘 | 讀 | `readHave`（`packages/backend/src/spine/stampedBundle.ts:55`） |
| 拉 | `POST /api/peer/pull`，帶裝置的 `have` | 在一個唯讀快照裡讀「裝置缺的」 | `readChangeBundle`（`packages/backend/src/services/stampedBundle.ts:18`）→ `readBundlePages`（`spine/stampedBundle.ts:90`） |
| 裝置收 | 把回來的頁合成一包、一段一段收下（第 2.10 節） | — | `bundleOf`（`spine/stampedBundle.ts:155`）→ `applyChangeBundle`（`spine/stampedImport.ts:618`） |
| 推 | 拉完整之後，在本機讀一包；`POST /api/peer/push` 送出 | 收下 | 裝置端 `readChangeBundle`；中心端 `bundleOf` → `applyChangeBundle` |

**欄位**（沿用現有的格式；第 5 批把 `have` 改成逐標籤，見下）：

```ts
// GET /api/peer/have    回應
{ node: string, have: Have, dataShape: number, wall: number }     // wall：中心此刻的時鐘（毫秒），裝置拿來比自己的（第 2.5 節）

// POST /api/peer/pull   請求
{ have: Have }
// 回應：NDJSON，每行一頁；最後一行是結尾（與快照的串流同一種寫法：services/stampedSnapshotStream.ts 檔頭）
{ "kind": "page", page: ChangeBundlePage }               // layer: "changes", dataShape, workspaceId, scope: "stamped", sender, cut, base, upTo, pages, page, items
{ "kind": "end", pages: number }
// （#1907 合併後，頁頭多 holds；收的一方記到 upTo 為止）

// POST /api/peer/push   請求：同 pull 的回應格式
// 回應（成功）
{ taken: true, advanced: ... }                           // applyChangeBundle 的 BundleReport.advanced（stampedImport.ts:531-535）
// 回應（拒絕）：既有的錯誤格式，帶代碼（stampedImport.ts:605-614 列的那些，加上第 2.5 節的幾個）
{ error: "bundle_gap" | "stamp_clock_ahead" | ..., detail: "..." }   // detail 只進紀錄，不顯示

// Have：今天是 { [origin]: number }，每個來源取所有標籤的最小值（heldOfAll，spine/stampedBundle.ts:60、:70-72）。
// 第 5 批改成 { [label]: { [origin]: number } }（每個標籤自己的進度；sync_origins.have 本來就是逐標籤存的：migration 206），並升 SYNC_DATA_SHAPE_VERSION。
```

- **為什麼要逐標籤**：今天 `have` 是所有標籤的最小值，所以之後補上任何一張表（一個新標籤），每個來源都掉回 0，下一次就是整份重送（第 1 輪審查第 2 點）。逐標籤之後，補一張表不會讓其他表重送；但**補上的那張表本身**要走第 2.11 節的「整份對齊」，逐標籤進度不夠（第 2 輪審查第 3 點）。已存的 `sync_origins.have` 本來就是逐標籤的（migration 206 第 44 行），現有進度不會丟。
- **為什麼每次先問**：包的 `base` 必須是收的那一方說它握有的（`spine/stampedBundle.ts:7-8`）。存著的舊數字只會多送、不會少送，仍每次問一次，因為很便宜；同一個回應也帶中心的節點編號（裝置拿來確認中心沒有被換掉，第 3.6 節）與時鐘。
- **快照與包的格式都留著簽章的位置**：今天不簽（決定 4）；之後要加，是在頁頭加一個欄位並升 `SYNC_DATA_SHAPE_VERSION`（現在是 4：`spine/syncDataShape.ts:17`），收的一方 `bundle_data_shape` 拒收舊格式（`stampedImport.ts:555`）。
- **時鐘上限**：收的一方拒收時鐘超前它自己 10 分鐘以上的包（`spine/stamps.ts:38-42`、`:178`；`stampedImport.ts:624`）。注意這是**收件那台的時鐘**和標記比：時鐘慢的那台什麼都收不下（第 2.5 節）。

### 2.10 包要有上界（分段）

**為什麼**：今天一包沒有上界（`readBundlePages` 讀完所有變動，`spine/stampedBundle.ts:90`），收是一個交易（`stampedImport.ts:620`）。PGlite 只有一條連線（`dbPglite.ts:6-10`），排隊 10 秒就失敗（`db.ts:93`）：大量匯入之後的第一次交換，桌面版的每一次存檔都會在收包期間失敗；在中心，事件鎖（`withEventTransaction`）擋住手機的存檔。

**要成立的性質**（第 2 輪審查第 2 點）：**收的一方在套用第 1 段之前，已經把整包持久地握在手上，能自己做完**——不再需要寄的那一台、也不需要再拉一次。原版「已收的段記在 `sync_peers.partial`、中斷後從那裡接著收」不成立：中心已提交第 1..k 段之後裝置死了，中心握有高於 `have[裝置]` 的裝置標記，而 `upTo` 來自 `have`（`spine/stampedBundle.ts:104`），之後任何整列送到那些標記的包都在 `stampedImport.ts:587` 被拒，包括那台裝置自己的下一次拉；重拉的切點與分組不同，段號沒有意義；`peer_busy` 會永遠擋住別台。

**做法（提議）**：讀還是一個唯讀快照、一個切點（切點的正確性靠它：`spine/stampedBundle.ts:12-17`），讀完就放開。**收**分三步：

1. **收件匣**（新的 `node-local` 表 `sync_inbox`，第 6 批建）：頁一頁一頁寫進去，每頁一個短交易；最後一行到了、`bundleOf` 檢查過（`spine/stampedBundle.ts:155-169`）、形狀檢查過（`checkBundleShape`，`stampedImport.ts:553`），才在一個交易裡把這包標成「完整」並寫下**計畫**：分段（下面）、每則筆記最後的 slug（第 2 輪第 7 點：在整包上算一次，見下）。對寄件者的回答是「收下了」（`taken: queued`），不等套用。
2. **套用**：照計畫一段一個交易，每段在同一個交易裡記「做完第幾段」；行程重開時由後端自己接著做（啟動時看收件匣），**不靠寄件者**。
3. **收尾**（最後一段之後、同一個交易）：每包一次的步驟——`expand`（`dbRows.ts:281`）、`ANALYZE`（`:439`）、`orphansOf`（`:500`）、第 2.12 節的事件與衍生資料——在**整包碰到的列**上做一次，然後才推進 `have`（`advanced`）、清掉收件匣。

分段：第一段 `workspaces`、`spaces`、`space_members`、`actors`（別的列都指向它們，它們不指向筆記）；第二段標籤筆記；其餘依「互相指向」分組（在包裡用外鍵或「跟著筆記走」連著的列：父層、筆記的錨點與段落列、屬性、位置；包裡的搬動造成的環在同一組；**同一個 slug 的交接也算連著**：一則改名離開某個 slug、另一則改名拿到它，兩則同一組），組照順序裝進每段（例如 2,000 列或 4 MB）。一個組比上限大就自己一段。

**收件匣不是空的時候**：這一台**不讀包給任何人**（它握有超過 `have` 的標記，讀出的包會被 `:587` 拒），對拉與自己的推都回 `peer_busy`；因為套用只靠本機，這段時間有上界（＝本機套用的時間），不會因為寄件者不見而永遠卡住。

**我替它找的反例與對策**：

- 子筆記在第 1 段、父層在第 3 段 → 子筆記建不起來（外鍵 `missing-ref`，`spine/stampedMerge/dbRows.ts:520-527`），之後也不會重試。對策：同一組。
- 所有筆記都指向空間 → 一個巨大的組。對策：空間先寫；指向「已在前一段寫好的列」的外鍵不算連著。
- **slug 跨段**（第 2 輪第 7 點）：`assignSlugs`（`dbRows.ts:586-603`）對資料庫裡現有的列解衝突。A 在第 1 段改名成 foo，id 較小的 B 還握著 foo、它的改名在第 3 段 → A 永遠是 `foo-<id8>`，寄件那台是 `foo`。對策：slug 在計畫時對「本機現有的列＋整包的最後狀態」算一次，各段照計畫寫；交接的兩則同一組。
- 延後檢查（#1907 的 `content_nodes_check_space`）每段 COMMIT 時跑：組內一致就過；跨組的父子關係不會在同一包裡同時改變，否則它們就是同一組。
- 4.10 的環與 #1907 的「切環之後的子女」讀資料庫裡不在包裡的列：那些列已在本機，不受分段影響；收尾在整包上再做一次推導。
- **收尾那一個交易仍和包的大小有關**（推導、事件、衍生資料在整包碰到的列上）：它是成本。第 6 批量：桌面版上收尾超過 2 秒，就要把收尾也分段，並重新證明「分段的收尾＝一次的收尾」。
- **讀那一端仍是一個快照、沒有上界**：在 PGlite 上讀一大包的期間，桌面版的存檔照樣要等。成本：桌面版讀業主最大的一次匯入超過 5 秒就要再分（每組各讀一次，切點的論證要重寫）。

證明（第 6 批）：在 PGlite 上，收一包 5 萬列期間，每 200 毫秒一次的本機存檔沒有一次失敗；**在任一段之後殺掉收的那一台、寄的那一台再也不回來**，重開後自己做完，結果與一次收完逐位元相同（標記、頭、slug、推導的空間、事件、衍生資料）；每一種分組反例各一則測試；收件匣不空時對拉回 `peer_busy`，空了就照常。

**已做**（第 6 批，PR 見第 6 節表）：`spine/stampedImport.ts` 的 `receiveChangeBundle`（開機時 `resumeChangeBundles`，`server.ts`）、收件匣與計畫在 `spine/stampedInbox.ts`、migration 228 `sync_inbox`（`node-local`）。和上面寫的不同的地方：

- **slug 不在計畫時另算一次**：交接 slug 的筆記（一則在這台離開它的 slug——改名、搬走、丟進垃圾桶、永久刪除；搬走時連同它底下的筆記——另一則想要它）放進同一組；只是想要同一個 slug 的新筆記不綁（4a 的 `settleSlugs` 讓「名字」輸的一方拿 `-<id8>`，哪個順序都一樣），所以每一個 slug 的決定都在同一段裡、由和一次收完同一條規則（4a 起是 `spine/noteSlugs.ts` `settleSlugs`）做。理由：不寫第二套 slug 規則；證明是「slug 跨段」那則測試（把分組拿掉它就變紅）。
- **指向別列不再一律「連著」**：只有同一列的項目、跟著筆記走的列（錨點、段落列）與它的筆記、交接 slug 的筆記、互相指向的組（搬動造成的環）是同一組；其他指向（子筆記指父層、屬性與標籤指筆記、筆記指空間與標籤）只是**順序**：被指的那組放在同一段或更前面的段。所以一棵新建的子樹、一個空間的幾千則、一個標籤底下的幾千則都不是一個交易。空間與標籤不必另排「第一段、第二段」，順序自己就把它們放在前面。
- **收尾不在整包上再做一次**：`expand`、`ANALYZE`、`orphansOf`、推導空間與 slug 都在每一段（對那一段的整組）裡做，和一次收完的結果逐位元相同（測試比對）；收尾那個交易只推進 `have`、讓時鐘跟上、清空收件匣，語句數和包的大小無關（量到 14 個）。所以「收尾超過 2 秒就要分段」不會發生。
- **4a 的衍生在每一段裡做，不在收尾**（4a 合併後補）：連結、段落列的顯示、垃圾桶與永久刪除的清理、型別、網站、成員 epoch（`services/receivedDerivation.ts` 的 `before`／`after`）和那一段的列在同一個交易裡、經同一個接縫（`stampedImport.ts` `mergeBundleItems`，一次收完也走它）。所以每一段只衍生一次、跟著那一段一起提交或一起回滾；任何已提交的狀態裡，收進來的列都已有它的衍生資料，使用者或別的請求在段與段之間讀到的不會是「列換了、連結或網站還是舊的」（網站下架也不會被拖到收尾）；行程在段之間死了，也沒有「還沒衍生」的東西要記。跨段的連結：第 1 段的筆記指向第 3 段才建的筆記時，第 1 段先衍生成指向不存在的名字，第 3 段建出目標時 `relinkTarget`（本機寫入用的同一個）把指向它的連結接上，結果和一次收完相同（`stampedInbox.integration.test.ts`「a link to a note of a later segment」，同一則也查每一段的衍生沒有寫任何單位，即 4a 的 P1）。代價：成員 epoch 可能多跳幾次（客戶端多核對幾次，不影響結果）。slug 照 4a 的 `settleSlugs`：讓出的筆記拿第一個沒人用的 `-2`、`-3`，所以 `foo-2` 這類 slug 在有筆記叫 `foo` 時和 `foo` 同一組。
- **收件匣卡住時**（第 1 輪審查第 2 點）：一段沒有代碼地失敗（連線斷了、鎖等太久、資料庫自己的錯）算一次，標頭記下次數；開機時與伺服器跑著時每五分鐘（`server.ts` 的週期工作）各再試一次；第五次之後放棄：收件匣清空，留一列 `outcome`，裡面有一句白話（給之後「我的裝置」畫面讀），這台馬上又能收包、讀包給別台。有代碼的拒絕（含 4a 的衍生失敗、`derivation.before` 現在也包在 `deriving` 裡）立刻放棄，一樣留那一句。
- **連結指向的筆記先收**（第 1 輪審查第 3 點）：內文帶 `[[…]]` 的筆記排在包裡被它的連結指到的筆記（依標題或 slug，和 `wikilinkEdges.ts` 比對的規則相同）之後，所以它的連結是在那些筆記改名、丟進垃圾桶、還原、新建之後才算，和一次收完相同（隨機內文帶連結、標籤、任務行的測試；拿掉這條順序它就紅）。屬性比它的標籤成員資格晚到另一段時，屬性的型別也照算（`receivedDerivation.ts` 對收進來的屬性的筆記也跑 `retypeGoverned`，一次收完的結果不變）。
- **兩段之間的本機存檔**（第 6 點）：計畫寫完時這台的時鐘就跟上包裡最高的讀數（不再等收尾），所以兩段之間存的東西蓋的標記在包裡每一筆之後，和「收完之後才存」一樣贏；測試在兩段之間改名，這台的改名贏、兩台交換後相同。
- **計畫到一半被殺**（第 4 點）：計畫的第一個交易在標頭寫一個記號，之後計畫的每一筆寫入都在標頭的鎖下比對記號（第二個執行者會讓第一個停下）；重新計畫時先刪掉舊計畫的所有段。
- **收件匣存了什麼、備份與還原**（第 8 點）：頁在任何檢查之前原樣存下，所以每頁至多 8 MB、一包至多 512 MB（`bundle_too_large`），之後的路由（第 9 批）要先做接納與請求大小上限；計畫寫完之前頁與段會同時在（之後頁就刪掉）。整個資料庫的備份帶著它；標頭記著計畫時的節點編號，還原成新編號的資料庫開機時放棄那個收件匣（`inbox_node_changed`），不接著收。
- **拒收：做了選項 A，信任界線等擁有者決定**（第 1 輪獨立審查第 1 點）：形狀、寄件者、缺口、時鐘，以及每一段的列的合併檢查（`checkMergedRows`，即 `checkReceived`）在計畫時就查完。只有寫的時候才會出現的拒絕（`storeMergedRows` 裡沒宣告的唯一鍵 23505、CHECK、`deriveNoteSpaces`、`expandTouched` 的 OD215、`checkDeferredNow` 的延後檢查、4a 的 `bundle_derivation_failed`），在第一段寫入之前由**試跑**找：每一段單獨收一次再回滾，每次試跑握事件鎖的時間和那一段一樣（同一個上界），總時間約多一倍（數字在 PR #1987）。不倚靠前面一段的段在試跑被拒，整包就被拒、什麼都不留；倚靠前面一段的段，試跑不算數、不誤拒。試跑也看不到、仍會留下前面幾段的四種情形，以及留下的狀態滿足的四個性質，列在 [stampedMerge README](../../../packages/backend/src/spine/stampedMerge/README.md)「接上傳輸前必須完成」。[信任界線](../../decisions/sync-trust-line.md)要不要放寬成「只留下各自通過全部檢查的段」由擁有者決定。
- **頁沒收齊時行程死了**：開機時整包放棄（還沒收任何東西），寄件那台下次重送。收件匣有東西時另一包的頁一樣回 `peer_busy`。

### 2.12 收進來的修改要看得到（2b-2b）

**今天**：`applyChangeBundle` 不寫領域事件、不更新衍生資料（`spine/stampedImport.ts:616`）；`stampedBundle.integration.test.ts:597-603` 用 `it.fails` 釘住：`[[連結]]` 的索引、段落引用、領域事件都不在收件那台出現。而 `/api/sync` 只從 `domain_events` 找變動（`services/sync/delta.ts:94-101`），所以桌面版推上來的修改，手機鏡像永遠看不到；桌面版拉下來的，自己的畫面、搜尋、連結也是舊的。

**要交出的性質**：收一包之後，每一個讀者——`/api/sync` 的用戶端、這台自己的畫面、搜尋、`[[連結]]` 與段落引用、樹與清單——看到的，和「同樣的寫入在這台本機做」一樣；而且**收包不產生任何帶標記的寫入**。

**不能整串重跑本機的那條路**（第 2 輪審查第 1 點）：一次內文寫入之後的 `applyBodyChange`（`services/bodySideEffects.ts:60-93`）把衍生的工作和**會被複製的寫入**交錯在一起。情境：桌面版離線加一行 `- [ ] milk` 推上去；中心若重跑整串，`syncBlockNodes` → `syncBlockTasks` 會用 `randomUUID` 再鑄一個任務（`modules/tasks/blockTasks.ts:71-75`），錨點與段落列也會以中心的來源再蓋一次標記 → 兩個任務、`block_nodes` 的任務唯一鍵重複，然後兩邊來回。

第 3 輪審查把這一節拆成三批：**4a 衍生**、**4b 事件**、**4c 跨單位的關係**（第 2.14 節，另一頁設計）。下面是 4a 與 4b 要成立的性質。行號是 `origin/main` 3c64672（已含 #1907）。

#### 2.12.1 從內文寫出的屬性：規則（4a 之前要定）

原版分割表說「dispatcher 屬性：複製，不重做」：**錯**（第 3 輪第 1 點）。存檔之後那一串（`bodySideEffects.ts:85-92` → `services/nodes.ts:174`、`:203`）寫的屬性，來源是 `markdown`／`frontmatter`，不是 `dispatcher`；觸發器只替 `ui`、`explicit`、`dispatcher` 蓋標記（`services/attributeChange.ts:108` 的 `STAMPED_SOURCES`），包也只帶這三種（`spine/stampedMerge/dbUnits.ts:172` 的 `where`）。所以桌面版存了 `due:: 2026-12-01` 或 frontmatter 的 `aliases: [X]`，中心拿到內文、沒有屬性：依 `due` 篩的檢視兩台不同，`[[X]]` 的反向連結永遠解不出來（`services/wikilinkEdges.ts:42-56` 讀 `aliases`）。

### 2.13 有外部效果的背景工作只在中心跑

桌面版跑的是同一份 `server.js`，所以每個背景工作也在桌面版跑：訂閱抓取（`modules/rss/fetch.ts:338`）、外部行事曆（`modules/external_calendars/refresh.ts:110`）、推播提醒（`modules/tasks/pushReminders.ts:151`）、任務排程（重複任務建下一次，`modules/tasks/scheduler.ts:205`）。
它們的「只有一個在跑」是同一個資料庫裡的鎖（`backgroundJobs.ts` 檔頭的 `exclusive`；`scheduler.ts:197` 的 leader lock），兩台各有自己的資料庫，所以**兩台各跑一次**：提醒推兩次、外部行事曆的列各寫一次。
（更正原版：原版說「重複任務在兩台各建一次下一次、兩個 id」——不對。下一筆的 id 是算出來的（`services/tasksStore.ts:411-414`），兩台建的是同一列；問題在第 2.12 節的「建過沒有」讀了本機事件。）

**要成立的性質**（第 2 輪審查第 11 點）：「只做一次」的工作屬於**一台指名的節點**（值班節點，shared-space-home 第 20 行），預設是中心；其他節點不啟動它們。
值班節點記在**複製的狀態**裡（工作區的一個單位，例如 `workspaces.duty_node`），所以每台對「誰值班」有同一個答案；改它是一筆普通的寫入。
**中心永遠不見時**：裝置畫面說「週期任務、提醒、行事曆更新在伺服器上跑；已經 N 天連不到伺服器，它們暫停中。［改在這台跑］」。業主按下去＝在這台寫 `duty_node = 這台`。
中心之後又回來：它收到那筆寫入（較晚的標記贏）就停下；在它收到之前的那一段，兩台可能都跑——提醒可能多推一次，算出來的 id 讓任務不會多一份。畫面不必說這一點；文件記著。
證明（第 9 批）：兩個行程跑一天的模擬時間，提醒只推一次；把值班移到裝置、中心回來後只剩一台在跑。

## 3. 接納與憑證

### 3.1 配對：共同的步驟

1. 新裝置：「加入我的裝置」→ 輸入伺服器網址（使用者自己輸入的網址，可以顯示：AGENTS.md 的例外）。
2. 新裝置產生一個 32 位元組的祕密 `S`，打 `POST /api/peer/pair/request`（不需登入）：帶它的節點編號、種類、名字、`S` 的雜湊。中心記一筆請求（10 分鐘到期、同時最多 3 筆、每來源限流），回 `requestId`。
3. 新裝置顯示 **QR**（內容：中心網址＋`requestId`；**不含 `S`**）與一組六位數（由 `requestId` 與 `S` 的雜湊導出，兩邊算得一樣）。
4. 業主用**手機**（已登入伺服器的網頁）掃 QR → 手機打開伺服器的確認頁：「要把『辦公室的筆電（桌面版）』加入你的裝置嗎？」顯示同一組六位數。業主核對、輸入密碼（新鮮確認，用途 `admit_node`）、按「加入」。
5. 中心：`admitSyncNode(工作區, 新裝置的節點編號)`（`stampedImport.ts:544`，唯一讓一台裝置成為寄件者的路），寫 `sync_peers` 一列，產生裝置憑證（只存雜湊，標 `unused`）與一次的加入額度。
6. 新裝置每 2 秒問一次 `POST /api/peer/pair/collect`（帶 `requestId` 與 `S`），被確認後拿到憑證。**回應丟了可以再領**：只要憑證還是 `unused`，同一個 `S` 再領一次，中心換一把新的（舊的雜湊作廢）；第一次用過之後 `collect` 一律拒絕。
7. 新裝置用憑證拉快照、加入（下一節），完成後 `POST /api/peer/joined`（帶切點），中心記 `joined_cut`、作廢加入額度。之後照第 2 節交換。

為什麼 QR 不放 `S`：拍到 QR 的人只拿到一個請求編號，沒有 `S` 就領不到憑證；而領憑證的那一台就是產生請求、顯示 QR 的那一台。六位數讓業主確認「手機上看到的請求就是螢幕上這台的」。
配對重放：請求、確認、領取各只能成功一次，到期作廢；被移除的裝置由 `stampedImport.ts:628` 與 `revoked_at` 完全擋住（第 1 輪審查第 10 點也沒找到重放）。

### 3.2 桌面版 ↔ 伺服器

- 桌面版第一次開、或設定 › 我的裝置 › 「加入我的裝置」。
- **桌面版必須是空的**才能加入（`decideJoin`：有自己的筆記就 `join_not_empty`，`stampedImport.ts:137-155`）。業主的桌面版**已經有自己的筆記時怎麼辦**是第 8 節第 6 題。
- 快照從中心串流進桌面版自己的後端：中心 `GET /api/peer/snapshot`（裝置憑證＋加入額度）→ 桌面版呼叫本機的 `importSnapshotStream`（`services/stampedSnapshotStream.ts:125`；服務呼叫，不經網路）。中途斷掉：加入沒完成，`cancelJoin` 留下可用的空資料庫（`services/stampedJoin.ts` 檔頭第 7 行），重新按一次。
- 加入之後，桌面版的 `sync_origins` 有中心（`vouched_by = 'snapshot'`），中心有桌面版（`'admitted'`）：兩邊都收對方的包（`stampedImport.ts:628`）。

### 3.3 瀏覽器版 ↔ 伺服器

同 3.2，差別：清空走「重新開始」同一條清除（#1756 的 `eraseBrowserCopy`，那個 PR 還沒合併）；請求是跨來源（第 2.1 節）；確認發生在伺服器上（手機），所以要密碼。晚一批（第 8 節第 3 題）。

### 3.4 伺服器 → 全新的伺服器

全新的伺服器有網頁：業主在任何一台電腦的瀏覽器打開它的第一次設定頁，那一頁顯示 QR，手機（登入舊伺服器）掃、確認——**和桌面版同一條路**，新伺服器就是「新裝置」。
**前提**：舊伺服器收過任何一台裝置的包之後就**不能再被快照**（`snapshot_foreign_origin`，`services/stampedSnapshot.ts:55-72`）——第 4 節第 7 項必修（第 2 批）。第 2 批還要讓加入的一方知道快照裡**別台裝置的來源**：今天 `markJoinDone` 只記來源與它的舊編號（`stampedImport.ts:477-485`），`checkPage` 拒絕沒被擔保的來源（`:289`）。
做法：快照第一行多帶「來源握有的其他來源與號碼」（和 `former` 同一種形狀與上限：信任界線第 44 行，最多 32 個），每頁相同、標記不得超過它報的號碼，加入的一方各記一列 `sync_origins`（`vouched_by` ＝ 來源；是帶來的來源，不是寄件者）。
把「中心」的角色移到新伺服器是另一件事（第 6 節第 12 批，預設關閉）。

### 3.5 移除、重新加入

- **移除**：手機或任何登入的頁面，「我的裝置」→ 那一台 → 「移除這台」。中心：`sync_peers.revoked_at` 寫上、憑證作廢；`sync_origins` 那一列的 `vouched_by` 從 `'admitted'` 改成 `'revoked'`（`applyChangeBundle` 只收 `'snapshot'`／`'admitted'` 的寄件者：`stampedImport.ts:628`，不改收件入口就生效）。**不刪** `sync_origins` 那一列：它記著中心握有那台到第幾號。
- **被移除的那台之後送來的**：一律拒絕（401，或 `bundle_unknown_sender`），什麼都不寫。這比「晚到的撤權一律成為建議」（shared-space-home 第 28 行）更嚴：自己的裝置被移除＝當成遺失。要不要讓它們可以變成建議是第 8 節第 7 題。**已經在那台上的內容收不回來**（distributed-ready 第 57 行）。
- 移除不需要新鮮確認（是收緊的方向）。
- **重新加入是唯一的回頭路**，`bundle_gap`、找回被移除的裝置、第 3.6 節的路 乙 都走它：
  1. **清空之前先整份留下**：舊的整個資料庫原封不動移到 `backups/`（桌面版；瀏覽器版先存一份整份的檔案），不是只匯出「還沒送出的」。
     原因（第 2 輪審查第 9 點）：「還沒送出的」不能從 `have` 算——分身之後中心已經從另一份「有」了序號 ≤ N；第 3 批的還原之後，沒送出的標記帶著舊的節點編號；`last_peer_have` 只是顯示用。
  2. **清空這台**：桌面版把 `<userData>/pgdata` 換成一個新的空資料庫，瀏覽器版走 `eraseBrowserCopy`。空資料庫第一次寫入時取**新的節點編號**（`sync_take_node_id()`，migration 213），所以不會撞到被移除的那個編號；
  3. 照 3.1 重新配對、加入。
  4. **人看得到哪些筆記不同**：加入之後，這台把留下的舊副本和現在的內容逐則比（內文雜湊），列出「清空前這台的版本和現在不同」的筆記；每一則可以打開看兩份、按「放回這一份」。放回＝人看過兩份之後的一筆普通寫入，所以**絕不蓋掉沒看過的較新的值**。
     不用備份的「合併進去」匯入做這件事：【推論，沒驗證】它替每則筆記重新蓋標記，會蓋掉中心較新的值。
  今天沒有這條路：`decideJoin` 拒絕任何已有 `sync_join` 列的資料庫（`stampedImport.ts:141`），`packages/desktop/src` 沒有清空的動作；`admitSyncNode` 是 `ON CONFLICT DO NOTHING`（`stampedImport.ts:548`），同一個編號被移除後永遠停在 `'revoked'`——所以**一定換編號**，不做「把 `'revoked'` 改回來」。
  證明（第 10 批）：被移除的裝置重新加入，新編號照常交換、舊編號送來的一律被拒；`bundle_gap` 之後重新加入，清空前與中心不同的筆記都列出來；在中心較新的筆記上按「放回」之前，中心的值不變。

### 3.6 中心被還原之後（每台裝置的狀態機）

原版說「在手機重新確認、不必重拿快照」：**撤回**。第 1 輪審查第 3 點對：還原後 `sync_peers`（`node-local`，跟著備份回到舊的樣子）的 `joined_cut` 倒退或不見，中心換了編號，裝置的 `have[中心]` 是 0，A3 永遠拒絕；而推用的是中心倒退的 `have`，等於一次大的重送。
另外【推論，沒驗證】還原一份比某個「蓋起始標記」的 migration 還舊的備份（例如 215 之前），開機時那個 migration 在舊的列上重新蓋起始標記；裝置握有的起始標記是在較新的列上蓋的 → 兩邊都是起始標記、值不同，每一列都成為衝突（合併核心 README：「創世對創世而值不同……兩個都留成衝突」）。所以**被還原的中心不能和握有較新狀態的裝置直接交換**。

**偵測**（兩邊各一個，都是自動的）：

- 裝置：`GET /api/peer/have` 回的中心編號 ≠ 配對時記下的 → `peer_hub_changed`，什麼都不送也不拉。
- 中心：`sync_peers.own_node_at_pairing` ≠ 現在的節點編號（這一列是還原前留下的）→ 對那台一律 `peer_hub_restored`。

**狀態機**（裝置那一邊）：

```
  同步中 ──(偵測到中心換了)──▶ 停下：「你的伺服器從備份還原了」，並列出兩邊各有、對方沒有的筆記數
                                │
          ┌─────────────────────┴──────────────────────┐
  路 乙（預設）：備份才是對的                       路 甲：這台比較新（要確認警告）
  這台重新加入（第 3.5 節）：                       用這台重建伺服器：
   1. 這台整份留下                                  1. 警告：伺服器上的版本歷史與附件會沒有
   2. 清空、換新編號、從伺服器加入                    2. 這台存成一個快照檔（今天的路）
   3. 列出和伺服器不同的筆記，逐則決定               3. 新的空伺服器開那個檔（今天的路）
   4. 同步中                                        4. 這台與伺服器「已加入」配對（新的路由）
                                                    5. 同步中
```

- **預設是路 乙**（第 2 輪審查第 4 點）：版本歷史與附件今天只在伺服器上（`domain_events` 是 `node-local`、`blobs` 是 `separate`：第 0 節第 7 點），路 甲會清掉唯一握有它們的那一台。在歷史複製做完之前，路 甲不是預設，畫面一定先說：「用這台重建，伺服器上的版本歷史、手寫的舊版本、圖片與附件都會沒有；這台沒有這些。」要業主打勾確認。
- **路 甲走得通的路由**：桌面版聽不到外面（`127.0.0.1`），所以不做「伺服器來拉」也不做新的上傳路由——用今天就有的「帶到另一台裝置」：桌面版在自己的畫面存成快照檔（`GET /api/snapshot`，桌面版自己的登入與新鮮確認：`routes/stampedSnapshot.ts:29-32`），在空的新伺服器上開它（`POST /api/snapshot`，`:34-36`，伺服器上的業主登入）。前提是第 2 批（握有別台標記的節點也能被快照）。
  之後桌面版與伺服器要「已加入」的配對：同 3.1 的流程，但確認時中心檢查**自己的 `sync_join.source_node` 就是這台裝置**，不發加入額度、直接記 `joined_from = 這台`。這是第 3.8 節表裡多的一種確認，第 10 批做。
- 第二台以上的裝置（第一階段大多沒有）：路 甲之後，它們走路 乙。
- 因此分類不變：第 4 節的 A3、A4 在還原之後仍然成立（還原過的中心不和任何握有較新狀態的裝置交換），第 15 項仍是 (2)；擋住它的是假設 **A5** 與 **A6**（第 4 節）。

### 3.7 複製資料夾＝分身

複製 `<userData>`（第 7 節原版就叫人這樣備份）＝同一個節點編號、同一份 `secrets.json`。桌面版沒有任何地方換號（還原在 `packages/desktop/src/safeUpdate.mjs:364-370`、`main.mjs:207-218`；第 3 批已派的分支 `fix/restore-always-renews-node-id` 只管還原）。
情境：落後中心 `have` N 的那一份往後寫，序號 ≤ N 的寫入永遠不送（中心以為已經有了），也沒有任何拒絕。

**偵測：輪替碼**。中心每一次成功交換給裝置一個新的隨機碼（中心存雜湊，`turn_pending`）；裝置下一次交換帶它來，中心才把它變成 `turn`。

- 中心接受 `turn` 或 `turn_pending`（回應丟了的那一次，裝置還握著舊的）。
- **在待確認的碼被帶回來之前，中心一直重發同一個**（第 2 輪審查第 10 點）：帶 `turn` 來而已有 `turn_pending` 時，回同一個 `turn_pending`，不另產新的；帶 `turn_pending` 來時才把它升成 `turn`、產下一個。
- **每台裝置同時只有一個交換在跑**（本機一個鎖；排程的拉、去抖的推、手動、關掉前那一次都經過它）。原版的誤報：排程的拉與去抖的推同時帶 c1，中心把待確認的 c2 換成 c3，裝置最後存下 c2 → 下一次被當成分身。上面兩條各自就擋住它。
- 兩份副本：第一份交換後碼輪替；第二份帶的是兩輪前的碼 → `peer_clone_suspected`，**兩份都停**（中心把那一列標成可疑），畫面請業主選「哪一台是真的」，另一台走重新加入。
- 反例：回應丟了，真的那台與分身都握著同一個舊碼 → 誰先到誰過一次；另一份下一次到時一定是兩輪前的碼 → 被抓到。分身一次都沒交換之前抓不到（它也還沒造成什麼）。
- **只有一份也可能被報成兩份**：作業系統或備份軟體把 `<userData>` 倒回較早的時候。畫面說：「可能有兩份『辦公室的筆電』，或這台的資料被倒回到較早的時候。」兩種的出口相同（選一份、另一份重新加入）。
- 備份的說法改成：**用桌面版自己的備份與還原**（第 3 批之後還原會換號）；手動複製資料夾只在 Onden 關著時做，而且同時只開一份。

證明（第 9 批）：複製資料夾、兩份都開、各寫各的：第二份第一次交換就被拒，資料庫不變；回應丟掉的那一次不誤報；排程的拉與去抖的推同時觸發一百次，不誤報。

| `POST /api/peer/push` | `PeerCtx`，通過假設檢查與輪替碼，且**包的 `sender` 必須等於憑證那台的節點編號** | — | `applyChangeBundle` 能寫的一切 |
| `GET /api/me/devices`、`PATCH …/:id`（改名）、`DELETE …/:id`（移除） | 業主的登入（不是裝置憑證） | 裝置清單與狀態 | 名字、`revoked_at` |

要點：

- **裝置憑證＝讀寫整個工作區**（它能拉到業主看得到的一切）。所以它只發給業主確認過的、業主自己的機器（決定 4），而且它不是任何路由的 `actor`（第 2.7 節第 4 點）：不能開 AI、不能管成員、不能發布、不能打 `/api/snapshot`。
- `push` 的 `sender` 檢查是新的、必要的：`applyChangeBundle` 只問「寄件者是不是被接納的」（`stampedImport.ts:628`），不知道請求是誰送的；沒有這條，A 的憑證可以送一包自稱 B 的。
- 臨時工作階段、MCP 權杖、一般的登入都**不能**打 `pull`／`push`／`peer/snapshot`。
- 依[信任界線](../../decisions/sync-trust-line.md)第 40 行，這幾批（配對、憑證、決定什麼能離開這一台的程式）用較強的模型寫，並做獨立審查。

### 4.1 第一階段的假設與機器檢查

- 關開關＝停止排程、`/api/peer/*` 回 404；每台留著自己的副本，**之後各寫各的**。再打開時照 `have` 接著交換，關掉期間雙方寫的都會合併（衝突照留）；前提是沒有任何一邊被還原（A5）、沒有超過 90 天（決定 5）。
- 想回到「打開之前」的樣子（例如交換弄壞了東西）：用打開之前的備份還原 VPS——中心換了新編號（A5 不成立），裝置自動停下、走第 3.6 節：選路 乙（裝置重新加入、先匯出）。**這會丟掉打開之後在伺服器上寫的東西**（匯出的那份可以手動找回），所以只在資料真的壞掉時用。
- 不提供「把某台的合併撤銷」：合併不是可以單獨撤的操作；要救的是個別筆記時用版本歷史（但版本歷史今天不跨裝置，第 0 節第 7 點）。
