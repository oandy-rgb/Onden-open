## 1. 要解決什麼

今天的並排是兩套東西湊成一個畫面：

- 左邊是 app 本身。右邊是另外寫的窗格（`components/splitView/SplitPane.tsx`、`hooks/useSplitView.ts`、`PaneTarget`）。
- 右邊要靠一堆特別規則才不撞到左邊：`panesConflict`、「右邊讓位」、「同一個功能頁兩邊都開會被拒絕」、
  筆記內文只讀＋「記一下」。
- 版面跟著**視窗**：`@media` 寬度規則、`vw`／`dvh`、`useIsMobile`。窗格只有半個視窗寬，
  但畫面還以為自己有整個視窗，所以內文被切掉、左右溢出。

業主要的是反過來：每個窗格就是一個頁面，頁面自己知道自己多寬。並排就不再是特例。

## 3. 目標模型（一頁）

### 3.1 窗格是什麼

一個窗格 ＝ **位置 ＋ 歷史 ＋ 尺寸等級**。

- **位置**（`Location`）：就是 `locationToSearch` 今天已經在用的那組——`view`、`nodeId`、`lens`、`viewTab`、模組位置、圖焦點。
  一個型別，兩個窗格共用。`PaneTarget` 是它的子集，之後刪除。
- **歷史**：這個窗格自己的連結軌跡（現在的 `navStack`）。瀏覽器歷史仍只有一份（3.4）。
- **尺寸等級**：由窗格**自己的盒子寬度**算出，不看視窗。

一般情況（沒有並排）就是「只有一個窗格的視窗」。同一條路，不是兩種模式。

### 3.2 畫面怎麼知道自己多寬

兩個入口，同一套數字，不新增斷點：

1. **CSS**：窗格根元素 `container-type: inline-size; container-name: pane`，畫面寫 `@container pane (max-width: 599px)`。
   數字沿用 600／900／1280（`BREAKPOINT_PX`），換成窗格寬度。
2. **TS**：`PaneSizeContext` ＋ `usePaneSize()` 回傳 `"phone" | "narrow" | "wide"`（用 `ResizeObserver` 量窗格根元素）。
   取代 `useIsMobile()` 在**畫面內**的用法。

| 等級 | 窗格寬度 | 長相 |
| --- | --- | --- |
| `phone` | 視窗本身是手機版面（≤900，單一窗格）時整個窗格 | 今天的手機版面，不變 |
| `narrow` | 桌面視窗裡寬度 ≤ 900 的窗格 | 單欄、工具列收進 ⋯（資訊面板只有一個，在視窗右側，見 3.9） |
| `wide` | 寬度 > 900 | 今天的桌面版面（≥ 1280 另有「寬」的細節） |

重點：**單一窗格的桌面視窗，窗格寬＝視窗寬扣掉側欄**，等級與今天的 `@media` 結果一致，所以單窗格畫面不變。
**手機外殼**（底部列、單窗格）仍由視窗判斷，這是唯一留在視窗層的版面問題。
`useIsMobile` 留在手機外殼與鍵盤這類真的屬於視窗的地方。

### 3.3 網址怎麼放兩個位置（連結不能壞）

- 左窗格 ＝ 今天的 `?view=&node=&lens=&tab=`，一個字都不變。舊連結、重新整理、分享連結全部照舊。
- 右窗格 ＝ `right=`，兩種寫法：
  - 簡寫：`note:<id>:<tab>`、`page:<mode>`（今天的格式）。位置能用簡寫表達時，**寫出來的位元組與今天相同**。
  - 完整：位置超出簡寫（有模組位置、圖焦點）時，`right=` 放一段 URL 編碼的 `view=…&node=…` 查詢字串。
  - 讀取兩種都收；`decodePane` 變成「簡寫讀取器」，保留。
- 帳號偏好 `splitPane`：仍只存簡寫（後端 `PREF_SCHEMAS.splitPane` 不改）。「更深的位置」只在網址，不進偏好——偏好只記「右邊放哪個目的地」。
- 「左右」是版面順序，不是身分（見 3.6）。⇆ 之後網址的左右互換。

### 3.4 「上一頁」做什麼（**已定案**）

每個窗格有**自己的歷史**（連結軌跡＋它走過的頁面）。

- **系統返回／瀏覽器返回／Alt+←／滑鼠側鍵**：作用在**使用中的窗格**（最後碰過、或正在打字的那邊），退那一邊的上一頁。
- 那一邊**沒有可退的**了：再按一次才是**關掉並排**（剩下的窗格變成唯一窗格，內容不變）。
  只剩一個窗格之後，返回就是今天單窗格的行為（先關浮層，再退上一頁，最後離開 app）。
- 先關最上面的浮層（`useDismiss`，2026-11-14 規則）不變，它在視窗層、排在窗格返回之前。
- 手機沒有並排，行為不變。
- 與業主規則「上一頁＝我之前在的那一頁」的關係：「之前」是**這個窗格**之前所在的頁。

**怎麼做到（要先確認的設計，這是風險最高的一步，見 5.2c）**：

瀏覽器只有一條歷史，窗格各一條，所以要有一個對應：
- 每個窗格的歷史是 app 自己記的堆疊（今天的 `navStack` 與歷史項目序號的做法延伸），瀏覽器歷史項目只是「載體」：
  每走一步仍推一筆（維持今天的「新一頁＝新一筆」表），項目裡記**哪個窗格動的**與**兩邊當下的位置**。
- 按返回時，`popstate` 到達的是時間上前一筆；`useUrlLocation` 看**使用中的窗格**：
  若前一筆是另一邊動的，就**不照它還原**，改成退使用中窗格自己的堆疊，並用 `replace` 把網址校正成「兩邊現在的位置」，
  再用 `history.go` 把游標對回載體（細節要先做原型確認；做不到的瀏覽器退回「按時間順序退」並在計畫裡標明）。
- 沒有東西可退（窗格堆疊空、前一筆也是這個窗格的第一步）：關閉並排，寫成「取代」不新增歷史。
- 前進（Forward）對稱處理；沒有可前進時照瀏覽器預設。

不選的做法：視窗一條按時間退的歷史（較簡單，但兩邊輪流操作時返回會跳到另一邊，違反定案的「作用在使用中的窗格」）；
兩顆返回鍵並存（使用者會不知道按哪顆）。

### 3.5 焦點（兩個窗格時誰接受動作；**已定案**）

- **使用中的窗格**＝最後被點、被打字或被聚焦的那個（窗格根元素上的 capture 階段 `pointerdown`／`focusin`）。
  窗格上緣一條細線標示是哪一邊。
- **側欄點筆記、指令面板／搜尋開筆記、新增筆記、頂列導覽、快捷鍵（`Alt+←`、`Ctrl+\` 之外的都在內）、返回**：作用在使用中的窗格。
  取代今天「側邊欄永遠開在左邊」。
- **Ctrl／⌘ 點連結、拖曳到另一半、選單的「開在另一邊」**：**明確指定**開在另一個窗格；不看焦點。
- 一般點連結（含功能頁裡點筆記）：開在**點的那一邊**（同單窗格的行為；今天功能頁的「開在另一邊」規則刪除）。
- 新增、刪除筆記後的「落到哪」：用單頁既有規則，在使用中的窗格內發生。
- 兩個窗格都空時，使用中的是左邊。

### 3.6 ⇆ 怎麼運作

窗格有**穩定的身分**（`paneA`、`paneB`），「左／右」只是它們的版面順序。⇆ ＝ 互換順序（CSS `order` 與網址的左右），
**不重新掛載**：編輯器的游標、IME、捲動位置都留著。
今天的 ⇆ 是「右邊的目的地變成左邊、左邊的變成右邊」，會重新掛載左邊的編輯器；新做法是同一個結果、少了一次重掛。
網址以「取代」寫入（互換版面不是導覽）。焦點跟著內容走。

### 3.7 同一則筆記兩邊都開（**已定案：兩邊都能編輯**）

資料只有一份（app store 的節點）。兩個窗格各有自己的位置、分頁、捲動、寬度，所以各自折行、各自視角。
「兩邊重複時右邊讓位」的規則拿掉；「右邊只讀＋記一下」也拿掉。

- **兩個編輯器，一份內容**：每個窗格掛自己的編輯器（各自的游標與選取）。
- **游標與輸入法組字只屬於正在打字的那一邊**。另一邊**只更新內容**，不動它的輸入狀態。
- **另一邊怎麼更新**：與「別台裝置改了這則筆記」**同一套機制**（編輯器收到外部內容變更，把自己的游標依變動位置換算，不打斷組字）。
  不新發明第二條路：這邊打字 → 草稿 → 另一邊的編輯器照「外部變更」處理。
- **草稿改成每則筆記一份**（`overviewDraft` 現在是單例，6 檔 18 行）；自動存檔、基準版本（`baseMarkdown`）、離線佇列各筆記一份，兩個窗格開同一則時共用同一份草稿與同一條存檔。
- **組字中不被打斷**：另一邊的外部變更若落在組字的那一邊，要等組字結束再套用（與別台裝置變更到達時的處理一致；先確認現有機制已經這樣做，否則在 3c 補上並測）。
- 復原堆疊歸**筆記**（兩邊共用一條）；建議，3c 開始前用原型確認 CodeMirror 的 history 能這樣掛。

風險：外部變更與本機打字交錯的換算、組字中不丟字、兩個編輯器的記憶體。緩解：3b 先上「不同筆記」，3c 才碰「同一則」；3c 以性質測試（隨機交錯的兩邊輸入，最後兩邊內容與草稿一致、無丟字）把關。

### 3.8 浮層屬於窗格還是視窗

| 種類 | 歸誰 | 為什麼 |
| --- | --- | --- |
| 對話框、確認、設定、指令面板、全視窗的提示（`position: fixed` 的 `ui-layer`、`sitePreview`） | **視窗** | 擋住整個 app；返回先關最上面（`useDismiss`）；兩個窗格都不可操作 |
| 手機底部面板（sheet） | **視窗**（只有手機外殼，沒有並排） | — |
| 選單、彈出層（錨在某個按鈕） | **視窗層渲染、錨在窗格內元素** | 用 portal 才不被窗格裁掉；最大寬高以**窗格**為界，不以視窗為界 |
| AI 面板、尋找列、浮動格式列 | **窗格**（畫在窗格盒子內） | 它們屬於那個窗格的筆記 |
| 資訊面板（只有一個） | **視窗**（右側，跟著使用中窗格） | 已定案，3.9 |
| 鍵盤高度、`visualViewport` | **視窗**（事實屬於裝置） | 窗格拿到的是「這個窗格被鍵盤遮住的底部高度」 |
| 提示（toast） | **視窗** | 一份 |

### 3.9 資訊欄與側欄（並排時；**已定案**）

- **側欄**屬於視窗：並排時**收成窄條**（與現在相同）；一份清單、點了作用在使用中的窗格。
- **資訊面板只有一個**，跟著使用中的窗格（顯示使用中那一則筆記的資訊）；位置在視窗右側，不是每個窗格一份。
  今天並排時資訊欄一律收起（`useWorkspacePanes` 的 `sideBySide`）：改成「可以開，開了顯示使用中窗格的」。
  開著時兩個窗格的寬度是**扣掉側欄窄條與資訊面板後**的，所以尺寸等級自然變小（第 3.2 節）；寬度不夠（窗格低於下限，問題 2）時資訊面板不能開。

## 5. 步驟

每一步是一個大小可以審閱的 PR，做完 app 都能用、單窗格畫面不變。
「開機 JS」欄是**估計值（未量測）**；每個 PR 實際跑 `npm run build`，在說明寫下量到的數字（見第 8 節）。

### 第 1 步：尺寸等級＋筆記頁改讀容器寬度

- **檔案**：新 `lib/paneSize.ts`（等級與門檻，只放常數與純函式）、`hooks/usePaneSize.ts`（context ＋ `ResizeObserver`）；
  `components/workspace/NotesWorkspace.tsx` 提供 context 與 `container-type`；
  `OverviewEditor.css`、`NoteBreadcrumb.css`、`settings/appearance.ts`（`note.measure` 的 `100vw` → `100cqw`，在已派出的小修之上）。
- **風險**：低。單窗格時窗格寬＝今天主區寬，`@container` 與 `@media` 結果要一致；容器查詢在容器自己的內距上有差一點的情形，需要用數字驗。
- **驗證**：版面稽核在 390（Pixel 5 ＝ 393）／1000／1280／1920 數字不變（稽核現有寬度 1280、1440、1920、1100、900、Pixel 5；補上 1000 與 390）；

  新稽核規則 **R-pane**「任何窗格內沒有橫向溢出、沒有被切掉的文字」，對並排狀態各寬度執行（此步先對現有右窗格的筆記內文跑）；

- **業主看到**：右邊筆記內文不再被切；單窗格完全沒變。
- **開機 JS**：+0.3～0.5 KiB（一個 context、一個 hook）。

### 第 2 步：窗格的位置與歷史（藏在現有畫面後面）

拆成三個 PR，因為 `useUrlLocation.ts`（634 行）和 `useWorkspaceFocus.ts`（457 行）都是核心。**2c 風險最高，自成一個 PR、單獨驗收。**

- **2a 一個位置型別與網址的雙位置寫法**：`Location` 型別（今天 `locationToSearch` 的參數）、`encodeLocation`／`decodeLocation`；
  `right=` 簡寫與完整寫法；歷史項目帶「兩個位置＋哪邊動的」。畫面仍是左邊 app、右邊 `PaneTarget`（轉成 `Location`）。
  **驗證**：`useUrlLocation.test.ts` 加雙位置；舊網址（只有 `right=note:…`、`page:…`）寫出來的位元組不變；重新整理、分享連結、舊偏好還原。
- **2b 窗格範圍的狀態**：每個窗格一份 `{ location, trail }`，用環境 context 提供；`useSelectedId()`、`useUiMode()`、`useWorkspaceFocus()`
  在窗格內讀的是**這個窗格**的（25 個呼叫端不必改）；窗格外（對話框、指令面板、側欄）用「使用中的窗格」，並加上細線標示與 `pointerdown`／`focusin` 的使用中判斷。
  每則筆記一份草稿取代 `overviewDraft`。
  **驗證**：單窗格行為測試不變；`selectedId` 相關測試加「兩個窗格各自選」；草稿測試（兩則筆記各自存檔、重試、離線）。
- **2c 每個窗格自己的上一頁（3.4）**：窗格各自的歷史堆疊、返回作用在使用中的窗格、沒有可退時關閉並排。
  **先做原型**確認 `popstate`／`history.go` 的對應在 Chrome、Safari、Firefox 都成立；做不到的瀏覽器退回「按時間順序退」並寫在 PR 說明。
  **驗證**：`backNavigation.property.test.ts` 擴成兩個窗格——隨機序列：開、換分頁、連結、⇆、關、換使用中窗格、打字、返回、前進、重新整理；
  斷言：①返回只動使用中的窗格；②那邊沒有可退時才關閉並排；③關閉後單窗格行為與今天一致；④先關浮層；⑤重新整理後兩邊位置還原。
  另有 `useUrlLocation.test.ts` 的逐案例測試，並在 Chrome 與 Android PWA 的真機清單裡標明（手機沒有並排，真機只驗單窗格不退步）。
- **風險**：2a、2b 中；**2c 高**（網址與歷史的唯一擁有者）。緩解：2a、2b 不改畫面；2c 單獨一個 PR，加實驗開關（預設關）先給業主試，再預設開。
- **業主看到**：2a、2b 沒有畫面改變（2b 會多一條使用中的細線，只在並排時）；2c 的返回行為改變（返回只退使用中的那一邊）。
- **開機 JS**：2a 約 +0.4 KiB，2b 約 +0.6 KiB，2c 約 +0.4 KiB（窗格 store、context、窗格歷史堆疊進核心；`useSplitView` 的部分功能被吸收，抵一些）。

### 第 3 步：右窗格畫的就是左窗格那個頁面

- **3a 功能頁、標籤頁、已存檢視**：兩邊都走同一個 `PaneView`（今天這幾種右邊本來就用同一批元件，只是包在 `SplitPane` 裡）。

  IME 測試（組字中另一邊的變更不打斷）；**性質測試**：隨機交錯的兩邊輸入，最後兩邊內容與草稿一致、沒有丟字。

### 第 4 步：各畫面從「視窗」改成「窗格寬度」，一組一個 PR

順序（先影響並排最明顯的）：筆記工作區 → 編輯器（剩下的）→ 標籤頁 → 任務 → 日記／今天 → 閱讀 → 複習 → 歷史 → 資訊欄 →
白板／看板／圖（含白板窗格化，刪 2a 的第 8 條）→ 設定與網站／簡報（多半是整頁，維持視窗，只清掉誤用）→ 共用元件 ＋ 全域樣式表（先按畫面拆開再搬）。

- **每個 PR**：`@media` 寬度 → `@container pane (…)`；`vw`／`dvh` → `cqw`／`cqh` 或百分比；`useIsMobile()` → `usePaneSize()`；
  該組的 `fixedLayer` 逐個分類成「視窗」或「窗格」（3.8）。
- **風險**：中，視覺回歸。容器查詢單位 `cqw` 要在該畫面的容器內量。
- **驗證**：該畫面在 390／1000／1280／1920 的稽核數字不變；R-pane 對該畫面的並排各寬度；
  **寬度隨機的性質測試**：隨機窗格寬度（320–1920）渲染該畫面，斷言沒有橫向溢出、關鍵控制項可見；
  守門 `window-width-deps-baseline.json` 該組降下來。
- **業主看到**：該畫面放在窄窗格裡不再擠壞、不再因為視窗寬而「以為自己是桌面」。
- **開機 JS**：約 0（CSS 改寫；`usePaneSize` 取代 `useIsMobile` 的呼叫）。

### 第 5 步：移除特別規則

- 刪 2a 標「刪」的全部：`panesConflict` 與 `refuseRight` 與提示、`useSplitView` 的讓位／右邊被刪／`openBeside`、`PaneTarget`、
  `SplitView.css` 的 `.split-pane`、`useWorkspacePanes` 的 `sideBySide`、`QuickNote` 的字串。
  加守門測試（`src/test/guards/*.guard.test.ts`）：`PaneTarget`、`panesConflict` 不得再出現；`SplitPane` 的 import 為 0。
- **風險**：低到中（前面步驟已經讓它們沒用處；刪除時抓遺漏）。
- **驗證**：`npm run unused:check`、`dup:check`、`ratchet:check`；整個前端測試；e2e。
- **業主看到**：不再有「右邊讓位」「同一個頁面已在左邊開」的提示。
- **開機 JS**：約 −0.8～−1.2 KiB。

### 第 6 步：收尾的測試
