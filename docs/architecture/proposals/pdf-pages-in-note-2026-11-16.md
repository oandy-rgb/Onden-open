## 0. 業主已定的

1. 沒開任何筆記時拖進一個 PDF，或拖到側欄：新筆記，標題是檔名；PDF 變成這則筆記「手寫」分頁裡的**頁面**
   （分頁裡放的是 PDF 頁時名字可以叫「PDF」，「分頁的名字跟著內容」）；筆記開在那個分頁。
   **補充（業主，2026-11-16，在 #1749 的留言：「最左邊就顯示 pdf 啊可以新增內容檢視這樣」）：這種筆記的分頁列最左邊（第一個）就是「PDF」，
   一開始沒有「內容」分頁**；想寫字時從「＋」加上「內容」（加上之後它是一般的文字）。預設分頁、記住的分頁、不帶分頁的網址都落在 PDF。
   區域引用需要落點時，引用當下若沒有「內容」，在那一刻提供加上它。轉換後的舊 PDF 筆記是同樣的樣子（見第 2.5、4 節）。
2. 拖到某則筆記的「手寫」分頁：接在現有頁面**後面**。
3. 拖進筆記的文字裡：**加進這則筆記的手寫檢視，文字裡放下的位置留一個縮圖**（業主 2026-11-16 晚間改定：「PDF放到手寫檢視」「留縮圖吧」；取代原本的「預設開成新筆記，這裡放縮圖，另一個選項加進這篇的頁面」）。不另建筆記，也不跳選項。所以 PDF 不管拖到哪裡，去處都是某一則筆記手寫檢視的頁面：沒開筆記＝新筆記的；手寫檢視＝這一則的最後；文字裡＝這一則的，並在文字留縮圖。
4. 「一起轉」：既有的 PDF 筆記（現在是 `pdf_url` 屬性讓「內容」分頁變成 PDF 檢視器、墨水畫在上面、不顯示文字）轉成同一個形狀。

業主在手機示範上看過、沒有反對的規則（本提案照這個做）：「手寫」分頁的「＋ 新增一頁」可選「空白頁」或「PDF…」；
PDF 放在**你現在這一頁的後面**，不是最後；可以選哪幾頁（預設全部）、可以選好幾個檔；PDF 頁是鎖住的背景、你在上面寫；
任兩頁中間（包括兩個 PDF 頁中間）都能插空白頁；PDF 檔存在 Onden、墨水另外存、PDF 檔永遠不被改。

幾個對設計有影響的事實：

- 伺服器**沒有 PDF 函式庫**（`packages/backend` 的相依套件裡沒有 pdf.js 等），所以伺服器不知道一個 PDF 有幾頁、每頁多大；
  只有瀏覽器／桌面版（pdf.js）知道。`units` 只記有墨水的頁。
- `ink_data` 一出現，「內容」分頁就變手寫頁；所以 PDF 的墨水不能原地變成手寫分頁的墨水，要搬到 `note_ink`。
- 備份帶的是整份當前值、不帶墨水歷史；`ink_chunks`／`ink_manifests` 不在備份（`backupInventory`）。
- 埋在 `node_attributes` 的值**都是蓋章的**（`syncClasses.json`：`node_attributes` ＝ stamped）；`ink_chunks`／`ink_manifests` 是 separate，不蓋章。
  蓋章只對 `source` 是 ui／explicit／dispatcher 的寫入（`194_stamps_s2.sql`）。
- 上傳後如果建筆記失敗，檔案留在媒體區沒人認領；**沒有定期清未被引用的上傳檔**（只有永久刪除筆記時才清）。這是今天就有的限制。

**建議 A2。** 理由：頁面清單是小而常被問的事實（分頁叫什麼、有幾頁、哪個檔），筆跡是大而常被寫的值，分開存才不會每畫一筆就重存清單、也不必為了顯示分頁名稱先載 MB 級的墨水。
A1 的優點（一個值、合併已有）靠的是不分開，但「PDF 頁數」這個伺服器本來就不知道的事，在 A1 裡仍得由某個地方記，所以省不了。C 之後若有需要（例如檔案要有標題與權限）可以在 A2 的 `file` 欄位旁加，不衝突。

### 2.2 契約（只是草圖，不是最終碼）

```ts
// @onden/markdown 新檔 notePages.ts（前後端共用，與 inkPages.ts 並列）
type PageRun =                                    // 一「段」＝同一個檔案裡連續的幾頁，或一張空白頁
  | { id: string; kind: "blank" }                 // 一張空白頁；頁 key ＝ id
  | { id: string; kind: "pdf"; file: string;      // file：媒體網址，與今天的 pdf_url 同一種字串
      from: number; to: number | null };          // 來源的第 from…to 頁；to 為 null ＝ 到最後一頁（檔案不會被改，所以安全）
interface NotePages { version: 1; runs: PageRun[] }
// 第 n 個來源頁的頁 key ＝ `${run.id}:${n}`。舊 PDF 筆記的段 id 固定叫 "pdf"，頁 key 就等於今天的 `pdf:<n>`，
// 所以 `page_text`、`page_images`、`units` 的鍵一個字都不用改。

// 領域操作（前端 lib/data/pagesWriter.ts；後端同一份規則）—— 說的是使用者要做的事
insertPdfPages(noteId, { afterPageKey: string | "end", file: string, pages: number[] | "all" }): Promise<{ addedKeys: string[] }>
insertBlankPage(noteId, { afterPageKey: string | "end" }): Promise<{ key: string }>
```

呼叫範例：把 PDF 拖到某則筆記的手寫分頁。
`const file = await uploadMedia(pdf); await insertPdfPages(noteId, { afterPageKey: "end", file, pages: "all" });`
在第 3 頁後面插：`afterPageKey` 傳第 3 頁的 key，若這頁落在一段的中間，操作把那一段切成兩段（兩段各自保留原本的 `id`，後半 `from` 變成 k+1，所以後半每一頁的 key 不變）。
刪一頁、在兩個 PDF 頁中間插空白頁也是同樣的「切段」。這就是為什麼用「段」不用「一頁一筆」：清單只有幾十個位元組，與 PDF 幾頁無關，
而**伺服器不知道頁數，轉換時沒辦法替每一頁寫一筆**；頁數與每頁大小仍由瀏覽器讀檔得知（如今天的 `usePdfPageShapes`），插入時順便讀到的比例不寫進清單，維持「檔案是唯一真相」。

| 兩台裝置同時加頁 | `note_pages` 是蓋章屬性（最後寫的贏），會吃掉另一台剛加的頁。要加入 `MERGED_KEYS`（與墨水一樣三方合併），規則：依段 `id` 聯集、順序用基底的相對位置。因為每段有唯一 id，這比墨水簡單。**這是第 1 步的一部分，不是以後再說。** 合併怎麼進同步核心（note-cf 2026-11-16 回覆，已定）：
`note_ink` **今天不進 #1733 的核心**，它的三方合併發生在存檔路徑（`MERGED_KEYS`：client 帶 base、伺服器合併），與內文的 `mergeBody` 一樣是「同一台伺服器上的併發」；核心裡目前只有內文有對應的東西（`stampedMerge/body.ts`，合併函式由呼叫者傳進來，因為 spine 不能 import services／modules）。
2b 會把它一般化成一張表——「這個單位有多個頭時，用一個函式合成一個值，而不是留成衝突」——登記內文、`note_ink`、`note_pages`。所以本提案的純函式照這個形狀：
`mergeNotePages(base: string | null, incoming: string, current: string): { merged: string; clean: boolean }`（與 `BodyMergeFn` 相同），放在 `@onden/markdown`，**第 1 步只登記 `MERGED_KEYS`**，核心那一邊由 2b 接。note-cf 要求它保證並用**屬性測試**證明三件事：
(a) 純函式、同輸入同輸出；(b) **與順序無關**：三個以上的頭照任何順序兩兩合，結果相同（依段 id 聯集可以做到；「順序用基底的相對位置」要加一個不看到達順序的決勝規則，用段 id）；(c) `base` 為 null（沒有共同基準）時也有定義：新增的段聯集、刪除不做（沒有基準分不出「刪了」和「沒看過」），`clean: false`。
合成的結果是**檢視**，不是新的寫入；要存回去時由核心用「從這些頭導出的 id」蓋章，函式不用管 |
| 清單與墨水不一致 | 加頁先寫清單、再寫墨水（沒墨水的頁本來就沒紀錄）。**清單沒列、但有墨水的頁（另一台把頁拿掉時有人在上面寫；清單那一筆被拒或遺失；本子在有清單前就有自己的頁）不會被任何一次存檔刪掉**：它們是算出來的顯示——排在清單的頁後面、標示「這頁不在頁面清單裡」，存檔時原樣帶著。筆跡只在「親手刪頁的那個人在自己畫面上刪頁」這個操作自己的寫入裡離開 `note_ink`（第 3 步）。（2026-11-16 審查後改；原寫「下一次存檔一併丟掉」會讓上述三種情形丟墨水） |

### 4.2 墨水座標還有效嗎

有效。PDF 頁的墨水本來就以頁面單位存（寬 1000、高 1000·h/w，`pdfPageRecord`），是同一種 `InkPageRecord`，手寫分頁的 `PageBook` 也是同一份；
轉換只是把 `units` 整個搬進 `note_ink`，筆畫一筆不改（驗證：搬前後同一頁 SVG 逐字相同，測試見第 6 節）。
**會改座標的只有劃線紀錄**（文字／區域劃線，目前以「劃下當時的畫面像素＋頁寬高」存在 `annotations`）：它們要換成頁面單位才能留在新本子裡（`x × 1000 ÷ 頁寬`，與墨水同一個公式，`pageUnits.ts` 已有）。
換成頁面上的一種「標記」層（`InkDocument` 多一個選用欄位，舊 app 照格式演進規則 1 原樣帶著走）。**這是整個提案裡格式變動最大、最沒驗證的一處（做法已由業主決定，第 9 節；驗證缺口在第 10 節）。**

**建議 2。** 前提與細節：

- **一則筆記一個交易**（`withTransaction`），寫的屬性走 `spine/mutate.ts`（不是直接 SQL），所以事件、蓋章、`membership_epoch` 都是既有機制。操作者是機器身分，**不是**假裝使用者。這是「一般的有作者寫入」，不是 `202_stamps_genesis` 那種補蓋章。
  **誰寫、用什麼來源（note-cf 2026-11-16 回覆，已定）**：
  - **只在持有完整資料的那一台（伺服器）跑一次，其他節點不自己轉**，從同步收到結果。每台各轉一次，同一個單位會出現幾個沒有人寫過的頭（調查紀錄 `docs/research/sync-design-vs-literature-2026-11-16.md` 第 6 項：衍生的修正與 migration 不能在每個節點各跑一次並各蓋一次標記）。
  - 寫入**蓋章**（真的資料變更，要傳出去、要能贏過舊值），走 `mutate`、`source: "explicit"`，作者是**系統參與者**（不是業主本人、不是 `dispatcher`；#1698 之後 `dispatcher` 是歷史來源），裝置＝伺服器的節點。`saw` 由觸發器照常算，不需要特例；`shellIsEmpty` 與創世規則不受影響（轉換只動既有筆記的屬性）。
  - 2b 之後有一條規則：**系統作者的寫入不能解決衝突**。所以轉換遇到某個單位（`pdf_url`、`ink_data`、`note_ink`、`note_pages`）已經有其他的頭時，**跳過那則筆記並列進報告**，不硬寫（現在資料庫裡不可能有其他的頭，因為還沒有傳輸；這條是為了之後重跑）。
  - 歷史裡這些寫入顯示成「系統（PDF 頁面轉換）」，不是「你」。
- **轉換的時機（note-cf 回覆，已定）**：因為只有伺服器轉、別台不轉，「每台各轉一次」不會發生；真的第二個節點帶著真的筆記交換，還在業主另一道關卡後面，轉換步驟**照本提案的排程，不需要提早**。
  note-cf 會加一道保險：**修改包帶「資料形狀的版本」，版本不同不交換**，所以「還在用舊形狀畫的節點」和「已轉換的節點」不會互傳，`pdf_url`／`ink_data` 的墓碑對上舊形狀的一筆（一邊刪、一邊改）就不會發生。**轉換那一步要把這個版本加一**（實際的常數名稱等 2b 定名後 note-cf 告知；第 8 節第 5 步的相依）。
- **需要的新東西只有一張紀錄表**（additive migration，只新增，編號用當時下一個空號；#1742 目前佔 205）：`pdf_page_conversions(node_id, converted_at, pdf_url, body_moved)`。用途：(a) 歷史歸屬（`inkEventSql` 把這則筆記轉換前的 `ink_data` 事件歸成「PDF 墨水」，仿 172 的 `board_ink_moves`）；(b) 轉回腳本；(c) 預覽與驗收的計數。**不是重跑的依據**，重跑看形狀。
- 破壞性（`pdf_url` 與 `ink_data` 被刪、內文可能被搬）：依 [migrations.md](../../agents/migrations.md) 第 4 條要業主明確同意（第 9 節第 7 項：先看過預覽數字再另行同意）、紀錄檔頭註解寫清楚、`-- drill: allows ink_data_rows, ink_bytes, attributes`（如 179），並更新 `drillInvariants` 的「墨水總量不能少」讓它跨 `ink_data` → `note_ink` 計算。升級前備份是唯一回頭路；轉回腳本 `restorePdfPages.sql`（仿 `restoreBoardInk.sql`）。
- **本機副本**：因為有事件，增量同步會把 `pdf_url`／`ink_data` 的刪除與新屬性送到各副本；`pdf_url` 在開機同步裡（`ink_data` 不在，按需載入）。**仍然驗收要用一台已經有副本的裝置開一次**（2026-11-15 的規則，`docs/deploy-log.md` 該列）：瀏覽器版、桌面版**與平板的瀏覽器**（業主主要在平板上用 PDF）各一，確認分頁列最左是 PDF、沒有「內容」（或依 4.5 仍顯示）、頁面看得到。若業主偏好 SQL migration，則必須把 `MIRROR_SCHEMA_VERSION` 從 4 升到 5。

### 4.5 內文與「內容」分頁怎麼起頭

今天的內文是上傳時抽出的全文（`createKinds` 的「上傳」路徑則是空的）。伺服器**不能重新抽**（沒有 pdf.js），只能搬現有的字。
業主已決定「PDF 在最前、沒有內容分頁」（第 0 節補充），所以轉換後機器抽的字**不能留在內文**（沒有「內容」分頁就看不見也改不了），原本「複製」那個選項取消。

- **內文從上傳後沒被人存過**（歷史裡沒有任何內文儲存事件，`bodyEventSql`；或本來就是空的）：當成機器抽的字，搬進 `pdf_text`（以「全部頁」一段記，按頁切分等下次開啟時由前端重新抽取補上）、內文清空、「內容」那一列標 `hidden`。完成後樣子與新拖進來的一樣。
- **內文被人存過**：不動、不隱藏。分頁列是「PDF」在最前、「內容」第二（仍顯示），預設分頁仍是 PDF；報告數量給業主逐則決定。不替人藏他寫過的字。
- 嵌入這些筆記的 `![[筆記]]` 會從「顯示那段機器全文」變成「空」（4.4 已說明）；這是上面決定的直接結果，預覽第 10 項與第 6 項會給數字。

- **`file` 只准本站媒體路徑**（`/api/media/<id>`，與 `mediaRefs.ts` 同一個判斷），頁數、檔案數有上限（單檔 10,000 頁、一份清單 20,000 頁、50 個檔案），展開也有上限。
- **不認得的 `note_pages` 版本**不合併、不覆蓋；有基底的寫入遇到時伺服器回 409 `pages_version`。合併結果不合法時回傳伺服器現存的清單（`clean: false`）。
- **合併的限制**：每個裝置自己的頁序一定保留；三個以上的頭，分散式合併核心要**先照固定順序（依值排序）再折**才保證與到達順序無關。兩兩任意順序折，頁集合相同，但「被某台刪掉的基底頁兩側、兩台各加一頁」與「沒有基底」兩種情形，位元組可能不同（屬性測試裡以 `it.fails` 釘住並寫明原因）。
- **`pdf_text`**：這一步沒有任何程式寫它，所以伺服器文字搜尋**沒有**接它（拿掉了：子查詢無索引、pgroonga 分支會讓所有搜尋的排序退化）；等真的寫入的那一步連同索引與查詢計畫一起做，並與 #1777 的「PDF 文字放哪」用同一個答案。`pdf_text` 最多 2 MB，也還沒有走墨水那種快照外移（`eventLog/attributeSnapshot.ts`），同樣留到寫入那一步。
