# 傳到我的手機：配對與加密（`@onden/pairing`）

> 狀態：現行（最後確認 2026-11-12）

> 2026-11-12。對應[提案](proposals/send-to-phone-2026-11-12.md)第 3 節。實作：`packages/pairing`。碰面點服務見[碰面點](send-to-phone-relay.md)。
> **這個模組在上線前需要一次人工的安全審查。** 本文最後一節列出審查者最該看的 5 個點。

## 1. 用什麼、為什麼

| 用途 | 原語 | 函式庫（鎖定確切版本） |
| --- | --- | --- |
| 金鑰交換 | X25519（RFC 7748） | `@noble/curves` 2.4.0 的 `x25519` |
| 金鑰導出 | HKDF-SHA256（RFC 5869） | `@noble/hashes` 2.4.0 的 `hkdf`、`sha256` |
| 加密與完整性 | ChaCha20-Poly1305（RFC 8439） | `@noble/ciphers` 2.4.0 的 `chacha20poly1305` |

- 選這一組的理由：三個套件都是純 TypeScript、沒有相依其他套件（`curves` 只依賴 `hashes`）、不用 DOM 與 Node 專屬模組，頁面、手機網頁與桌面版跑同一份；
  同一作者的一組，API 風格一致；授權都是 MIT；程式碼小、好讀。
  不選 HPKE 函式庫：本流程是兩個臨時金鑰互換加上一把導出的對稱金鑰，不需要 HPKE 的單向封裝；不選 libsodium：WASM 檔較大，也要多處理載入。
- 第三方審查：noble 系列有公開的審查紀錄（作者在 README 與 GitHub 上列出 Cure53、Trail of Bits 等對 curves／hashes／ciphers 的審查），
  但**本任務在沙箱內查不到那些報告的原文**（外部網站被擋），所以這裡只能寫「作者聲稱有審查，報告未逐份核對」。人工審查時請一併核對。
- 大小：`src/index.ts` 以 esbuild 壓縮打包（瀏覽器、ES2022）約 51 KB、gzip 後約 20 KB（2026-11-12 量測）。
  模組**不在開機路徑**：前端目前沒有任何檔案 import 它；將來只能用動態 `import()` 在使用者進入「傳到我的手機」時載入（見 AGENTS.md 開機包規則）。
- 測試向量（`src/vectors.test.ts`）：X25519 用 RFC 7748 §6.1、HKDF 用 RFC 5869 附錄 A.1、ChaCha20-Poly1305 用 RFC 8439 §2.8.2、
  權杖雜湊用 FIPS 180-2 的 `abc`。向量是透過本模組用的同一個函式庫入口跑的。

## 2. 訊息格式

全部是二進位或 base64url（RFC 4648 §5，無補齊字元）；碰面點只收 `application/octet-stream`。

| 訊息 | 誰給誰 | 內容 |
| --- | --- | --- |
| 邀請（QR 文字） | 頁面 → 手機（經 QR） | `stp1:` + base64url(JSON `{v:1, r:碰面點網址, s:工作階段編號, k:頁面公鑰}`)。**不含秘密。** 工作階段編號 16 位元組隨機（base64url 22 字元），公鑰 32 位元組 |
| hello | 手機 → 頁面（經碰面點 `PUT /v1/s/<編號>/hello`） | 1 位元組版本（1）＋手機公鑰 32 位元組，共 33 位元組 |
| 進度清單 | 頁面 → 手機 | 物件 `m.progress`：版本 1 位元組（1）＋序號 8 位元組（大端）＋隨機 nonce 12 位元組＋密文。只用來顯示進度，**不可據以匯入** |
| 最終清單 | 頁面 → 手機 | 物件 `final`：格式同上，序號固定 0，用另一把金鑰。**唯一**決定匯入什麼的來源 |
| 檔案塊 | 頁面 → 手機 | 物件 `c.<項目編號>.<塊序號>`：只有密文＋16 位元組標籤。位置（項目、序號）在物件名稱上，並被 AAD 驗證 |

清單明文是 JSON `{"items":[{id, kind:"note"|"file", name, size, chunks, chunkSize}]}`，項目編號 `[A-Za-z0-9_-]{1,64}` 且不重複，
`chunks` 必須等於 `max(1, ceil(size / chunkSize))`，`chunkSize` 在 1–4 MiB。筆記與檔案走同一條路（筆記是單塊的小檔）。

## 3. 金鑰與權杖怎麼導出

```
shared  = X25519(自己的臨時私鑰, 對方公鑰)                     ← 低階點（會得到全零）由函式庫拒絕，我們回 bad_key
master  = HKDF-SHA256(ikm = shared,
                      salt = 工作階段編號（16 位元組）,
                      info = len‖"onden-stp/v1/master" ‖ len‖頁面公鑰 ‖ len‖手機公鑰, L = 32)
derive(用途, 長度, 脈絡) = HKDF-SHA256(ikm = master, salt = 無,
                      info = len‖("onden-stp/v1/" + 用途) ‖ len‖脈絡, L = 長度)
```
（`len‖` 是 4 位元組大端長度前綴，所以不同欄位組合不會編成同一串位元組。）

| 東西 | 用途字串 | 脈絡 | 長度 | 誰用 |
| --- | --- | --- | --- | --- |
| 確認碼 | `confirm` | — | 4 位元組 → 大端整數 mod 10⁶，補零成 6 位 | 兩邊螢幕核對 |
| 寫入權杖 | `write-token` | — | 32（base64url） | 頁面寫碰面點 |
| 讀取權杖 | `read-token` | — | 32（base64url） | 手機列出、取回、確認刪除 |
| 每檔金鑰 | `file-key` | 項目編號（UTF-8） | 32 | 該檔每一塊 |
| 進度清單金鑰 | `manifest-key` | — | 32 | `m.progress` |
| 最終清單金鑰 | `final-manifest-key` | — | 32 | `final` |

- 寫入與讀取權杖是同一把 `master` 的兩個獨立 HKDF 輸出：知道其中一個推不出另一個，也推不出 `master`。
- 碰面點存的是權杖的雜湊（小寫十六進位 SHA-256，函式 `tokenHash`），頁面第一次寫入時用 `Authorization: Bearer <寫入權杖>` 與 `X-Read-Token-Hash: <讀取權杖雜湊>` 登記兩者。
- **塊加密**：ChaCha20-Poly1305，key＝每檔金鑰；nonce＝12 位元組＝4 個零位元組＋塊序號（8 位元組大端）；
  AAD＝長度前綴串接 `"onden-stp/v1/chunk"`、工作階段編號、項目編號、塊序號、最後一塊旗標（1 位元組）。
  每檔一把金鑰、序號不重複，所以（key, nonce）不會重複。
- **清單加密**：同演算法；key＝上表；nonce＝12 位元組隨機（放在訊息裡；頁面重載後序號會重來而金鑰不變，所以不用計數器）；AAD＝`"onden-stp/v1/manifest"`、工作階段編號、`"progress"`或`"final"`、序號。
  序號由 `ManifestWriter` 依呼叫次序發出（只用於 AAD 與顯示），最終清單在同一個 writer 只能產生一次。
- 塊大小：1–4 MiB，可設；空檔案＝一個空的最後一塊（密文只有標籤）；剛好整數塊＝不多出空塊。

## 4. 解密端拒絕什麼（每項都有測試，`src/stream.test.ts`）

| 情況 | 結果 |
| --- | --- |
| 亂序（跳過一塊） | `out_of_order` |
| 重放（同一塊再收一次） | `replay` |
| 缺塊 | `missing_chunk`（一次解完的函式）或 `out_of_order`（逐塊收） |
| 被截斷（少了最後一塊） | `truncated`（`finish()`）；把倒數第二塊冒充最後一塊 → `bad_chunk`，因為最後一塊旗標在 AAD 裡 |
| 別的工作階段的塊 | `bad_chunk` |
| 同工作階段別的檔案的塊 | `bad_chunk` |
| 密文或標籤被改、塊序號或最後一塊旗標被改 | `bad_chunk` |
| 長度不對（非最後一塊必須剛好 `chunkSize`） | `bad_chunk_size`（解密前就擋） |
| 不在最終清單上的項目 | `unknown_item` |
| 把進度清單當最終清單，或反過來 | `bad_manifest`（金鑰不同） |
| 別的工作階段或被改過的清單；第二份最終清單（寫入端） | `bad_manifest` |

## 5. 威脅模型（照提案第 3 節）

| 威脅 | 結果 |
| --- | --- |
| 旁人拍到 QR | 只拿到公開資料（碰面點網址、工作階段編號、頁面公鑰）。搶先配對會讓兩邊確認碼不同，使用者核對時發現 |
| 碰面點不可信 | 看得到大小、時間、IP；可以扣住不給、拒絕服務、整個刪掉；讀不到內容、改不了（AEAD） |
| 借來的電腦被動過手腳 | **擋不住**：在上面打的字它都看得到，也能直接把頁面端金鑰拿走。但它拿不到工作區原有的任何東西（第一階段單向） |

### 不防禦的事（明確列出）

1. **頁面所在的電腦被入侵**：鍵盤、螢幕、記憶體、頁面端私鑰與所有明文都在它手上。
2. **使用者沒有核對確認碼**就按確定：換掉 hello 的人（碰面點或知道編號的人）就能在中間。確認碼 6 位數，一次猜中機率 10⁻⁶，只擋「沒有雙方即時核對」之外的攻擊，不擋被騙著按確定的人。
3. **拒絕服務**：知道編號的人可以搶先放 hello（先到先得）、在頁面第一次寫入前搶先登記權杖、塞滿流量或把工作階段占滿；碰面點也能扣住不給。加密不防這些，只有速率與上限減輕。
4. **流量分析**：大小、時間、塊數、IP、使用頻率可見。沒有補長度的措施。
5. **前向保密只到「臨時金鑰」層級**：兩邊金鑰是這次工作階段的臨時金鑰，用完即丟；但在頁面開著期間頁面記憶體被讀走，整個工作階段就沒了。沒有定期換金鑰。
6. **進度清單的回滾與重放**：碰面點可以給舊的進度清單；它只用來顯示，匯入只看最終清單。
7. **最終清單之前就結束的工作階段**：手機沒有最終清單就不匯入；已上傳但不在清單上的塊會被忽略（匯入端需遵守）。
8. **手機端被入侵、手機掃到惡意 QR**：邀請裡的碰面點網址由頁面決定；手機端要提示並只連 https。本模組只檢查是 http(s)。
9. **側通道**：依賴函式庫的常數時間實作（noble 聲明是），沒有另外量測。
10. **隨機數**：用平台安全隨機（`crypto.getRandomValues`，經 `@noble/hashes` 的 `randomBytes`）。沒有可用的安全隨機時函式庫會丟錯而不是退回弱隨機。
11. **檔案內容的格式與惡意檔案**：解密成功只代表是頁面寫的，不代表安全；匯入端要照一般上傳規則檢查。
12. **權杖在 HTTP 標頭**：碰面點端的紀錄若記下標頭，只會洩漏已經公開的雜湊對應的權杖；使用者應只用 https 的碰面點。

## 6. 給審查者：最該看的 5 個點

1. **導出綁定**（`pairing.ts` 的 `deriveSession`）：`master` 是否真的綁定雙方公鑰與工作階段編號；掉包 hello 時兩邊的確認碼與權杖是否一定不同（`pairing.test.ts` 有一個固定種子的測試，但它是測試不是證明）。HKDF salt 用工作階段編號、info 用長度前綴的欄位，請確認沒有欄位混淆。
2. **nonce 與 AAD**（`stream.ts`、`manifest.ts`）：塊 nonce＝塊序號（每檔一把金鑰）是否在所有使用情境下都不會重複——特別是頁面端重新整理或重送時，是否可能用同一個檔案編號加密不同內容（編號由呼叫端產生，模組不去重）；清單已改用隨機 nonce，所以序號重來不會造成 nonce 重複；塊仍是計數器 nonce，安全靠「項目編號每次新產生」，請確認呼叫端不會對不同內容重用編號。
3. **確認碼的強度與使用者流程**：6 位數只有約 20 位元；攻擊者若能在一次配對裡嘗試多次（碰面點 hello 先到先得，其實一次工作階段只有一次機會，但攻擊者可以讓使用者反覆重掃）是否足夠。決定是否改成更長或加上嘗試次數限制。
4. **截斷與最終清單的完整性**（`FileReceiver.finish`、`FinalManifest.receiverFor`）：匯入端是否只依最終清單、是否每個項目都跑完 `finish()` 才匯入；本模組提供原語，但「不在清單上的塊要忽略、沒收完不匯入」是呼叫端的責任，請在匯入任務的審查中核對。
5. **權杖與碰面點**（`relay`）：寫入／讀取權杖分離、權杖只在第一次寫入登記（先到先得，見上面「不防禦」第 3 點）、錯誤回應是否真的不洩漏工作階段是否存在（`relay.test.ts` 有比對測試，但時間差沒有量測）。
