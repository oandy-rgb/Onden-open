## 本批選擇與完成條件

比較兩種請求方案：

| 方案 | 呼叫者需理解的知識 | 問題與相容性 |
| --- | --- | --- |
| 每次寫入先呼叫 session API，再送正式請求 | 每個 writer 或共用傳輸需編排兩次請求，讀取／原始回應入口也需一致使用 | 兩次請求間 cookie 仍可改變，不能保證正式請求仍是原操作者 |
| 頁面固定預期 user ID，由正式請求的 cookie 驗證結果比對 | 領域仍呼叫既有 `api`／`apiFetch`；登入邊界建立一次預期 | 增加一個只會拒絕的 header；同頁換帳號須重載；舊客戶端沒有 header 時保留原行為 |

選第二種。`requestAccount.ts` 保存頁面預期；`AccountSessionBoundary` 在孩子掛載前建立它，
不同 user ID 不可重綁。匹配時返回原工作區，同帳號刷新不卸載編輯器；不同時隱藏原工作區，
顯示「登入帳號已變更」和重新載入入口。元件使用既有連線提示的布局與主題。

`api` 改由既有 `apiFetch` 統一送出，保留 JSON／FormData、Content-Type、原冪等鍵與 credentials。
兩種傳輸都附 `X-Onden-Expected-User`，呼叫者不能以額外 header 覆寫已綁定的頁面預期。
原生入口沒有此 web session 預期，保留既有契約。

後端在目前 cookie 驗證後、actor 查找／建立之前核對 user ID。不一致或沒有 session 都回
401 `account_changed`，不寫狀態、成功事件或冪等 claim；bearer／native 不能替代這個 cookie 身分。
這個 ID 不是憑證，也不會改變角色或權限。前端沿用 authentication 錯誤分類並提示回到原帳號。

完成條件是匹配者仍可依原政策讀寫，不匹配者在領域操作前被拒絕；原帳號可用同鍵重試，
新帳號不直接接手舊頁面的 module state。沒有新增每個領域的 session 判斷或額外輪詢器。

## 真實 cookie 與 PostgreSQL

新增 `requestAccount.integration.test.ts`，使用真實 better-auth 註冊／登入 cookie，
組裝完整 Hono app，並為測試建立獨立 workspace、A/B actor 與節點。

- A 建立筆記後，A 預期搭配 B cookie 的 PATCH 回 401；title 保持原值，事件只有 A 的建立。
- A 使用相同 idempotency key 重試兩次，只有一次修改事件，操作者仍為 A；拒絕未吞掉合法重試。
- GET 同樣拒絕不匹配；B 預期搭配 B cookie 仍可正常讀寫開放節點，成功事件歸 B。
- 限制 `write_node: editor` 的標籤節點，B 降為 viewer 後，帶／不帶匹配預期均為 403，內容不變。

測試初稿曾錯把無政策節點當作 viewer 不可編輯；目前政策對未定義操作回退到 viewer，
查明後以明確標籤政策驗證，沒有為了測試改變既有允許／拒絕結果。

HTTP 組裝測試另驗：GET／PATCH 不匹配不進 actor SQL、匹配 cookie 使用真實 actor 查找、
native 無 cookie 拒絕、bearer 不能滿足人類預期。新增 5 個 HTTP 案與 3 個 PG 案；專項 37 項通過。
