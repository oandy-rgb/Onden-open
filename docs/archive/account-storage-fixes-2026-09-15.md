# 帳號本機副本分區與切換實測

> 狀態：歷史紀錄（最後確認 2026-11-01）

日期：2026-09-15。基線：`0e93619` 加既有未提交審核變更。
案例：ACC-06、NOTE-03、DATA-04、DATA-08、SYS-03、UX-01。接續第十九批的 GAP-21。

本批修復新版本本機副本的帳號分區。實際 A 待同步 → B → A 重載、手機追加及恢復同步通過。
無帳號標記的舊資料保留原處、不自動認領；安全取回介面仍未提供，ACC-06 保持部分完成。

## 本次使用案例與設計取捨

不變條件：A 尚未提交的文字不能由 B 讀取或重播；回到 A 後，原輸入與重試鍵仍可使用；
不能為分帳號而刪掉舊資料，不能把讀取故障當成空白資料庫重新保存。

比較兩種方案：

| 方案 | 呼叫方式與必須理解的知識 | 相容成本 |
| --- | --- | --- |
| 共用 SQLite，每列／每個查詢加入 owner | `getPendingWrites(owner)`、搜尋、鏡像、游標、canvas 等都須攜帶並篩選帳號；漏一個入口就混入其他帳號 | 所有資料表與查詢都得遷移，舊列仍無法推定擁有者 |
| 整份副本依伺服器＋user ID 分區（採用） | 登入邊界一次 `bindAccountStorage(userId, getApiBase())`；功能仍使用 `addPendingWrite(...)`、`loadBootstrap()`、`getRecoveryWrites()` | 新增儲存 namespace 與備份帳號標記；舊未綁定資料隔離保存，不能自動接手 |

採第二種，因為工作區鏡像、同步游標、待同步與被拒絕輸入共用同一個擁有者，不需要領域 writer
各自知道分區鍵或新增 owner 參數。頁面與 worker 都只綁定一次，延遲工作不能改綁 B。

## 已實作的契約

- `accountStorage.ts` 將正規化的伺服器 URL 與驗證後 user ID 作為儲存身分；web 在登入前拒絕開啟私有副本。
  `AccountSessionBoundary` 先建立請求與儲存歸屬才掛載孩子；換帳號或伺服器須重新建立頁面。
- `localDb` 在 RPC 帶固定 storage scope，worker 第一個請求後固定它。IndexedDB 的 SQLite key
  按 scope 分開；鏡像、FTS、屬性、canvas、待同步／拒絕列及游標自然在同一份副本內隔離。
  查不到當前 key 不會回退讀舊 `db`；讀取故障會拒絕，不能用空白庫覆蓋已確認的輸入。
- `writeRecovery` 的 localStorage 未確認輸入、資料夾 handle 與儲存偏好使用同一分區。
  `BuilderApp` 的儲存偏好判斷移至驗證之後，避免登入前就決定使用舊帳號目錄。
- 新 SQLite 保存 `local_account` 標記。冷啟動及匯入都核對；同工作區也不能匯入另一帳號或另一伺服器的佇列。
  拒絕與落盤失敗保留原副本。這是本機防誤用檢查，不是簽章、加密或後端授權。
- 初次資料夾選取拒絕已含 `onden.sqlite3` 的目錄；取消是正常結果，失敗顯示錯誤並保留選擇畫面。
  啟動時讀取／匯入資料夾失敗不啟用該 handle 的背景輸出。設定中的帳號不匹配錯誤有明確說明。
- 開啟頁面後更換伺服器設定，`apiFetch` 不會將原工作送往新伺服器，沿用 authentication 失敗處理。
  第十九批後端帳號預期仍生效；本批未修改後端政策。

## 舊資料的處理

舊 IndexedDB `onden-storage/sqlite/db`、舊 `onden.lostWrites`、未分區的目錄 handle／偏好均保留，
不從它們猜測登入者、不搬移或刪除、不自動顯示內容，也不重播舊佇列。
新帳號副本從目前伺服器可讀資料初始化。首次儲存畫面及「你的資料」說明這個差異。

目前 UI 不能將沒有帳號標記的 SQLite 直接還原，亦沒有安全認領舊未同步內容的流程。
知道同一 workspace ID 不能證明它屬於目前登入者。後續須設計可驗證的取回操作，不能為了便利
直接指定目前帳號或移除檢查。不要清除網站資料來「完成遷移」，那會丟失尚未取回的舊輸入。
不同伺服器 URL／別名視為不同副本，不自動合併。

## 實際瀏覽器結果

使用既有隔離資料庫 `onden_import_audit_test`，前端 `127.0.0.1:5100`、後端 18788；
沿用測試帳號 A／B，未使用正式資料。控制後端只有筆記 PATCH 回 503，auth 與讀取仍正常。

1. B 初次使用新版先出現儲存選擇。320×720 文字、兩個按鈕與底部說明可讀，卡片沒有橫向超出；
   說明改為「瀏覽器保存＋額外資料夾副本」，避免暗示資料夾一定是即時主資料庫。
2. 桌面 1440×900，A 在既有測試筆記 `1c4e2cc0-7211-4f4e-87ee-8a272b979f23` 追加
   「0915 A 帳號專用待同步文字」，畫面顯示 1 筆等待同步。PG 查詢確認伺服器沒有這段文字。
3. 登出 A、登入 B，先顯示換帳號需重載；重載後 B 無該文字、無 A 的待同步數量，
   先前出現的「第二輪：權限拒絕」舊復原文字亦未出現。390×844 得到相同內容結果。
   既有可讀的伺服器正文正常顯示，未把共享筆記當成本機洩漏。
4. 再登入 A 並重載，390×844 仍能讀到 A 的原待同步文字；實際補寫「0915 手機補寫」後再重載，
   兩段均保留。桌面顯示 2 筆待同步，PG 再次確認兩段尚未提交。
5. 恢復 PATCH，A 點立即同步後佇列清空。PG 兩段文字均存在，新增事件 446、447 都是
   `NODE_UPDATED`，操作者都是「帳號隔離測試 A」；前一事件仍為舊帳號事件 434。
   此最後頁面的 console error 列表為空。測試分頁與 viewport override 已清理。

這是手機 viewport／桌面瀏覽器測試，不是真機、觸控鍵盤或實體資料夾 picker 的驗證。
測試期間的開發熱更新曾重建登入頁，因此 A→B→A 的核心測試在停止修改執行碼後重新進行。

## 剩餘範圍與新缺口

- GAP-21 的新版本機隔離已修；舊資料安全取回仍缺，不能宣稱帳號全流程已完成。
- 同帳號多分頁仍共用一份 SQLite snapshot，並行保存可能互蓋；本批不是跨分頁併發控制。
  登出前尚未確認落盤的記憶體草稿、所有晚到回應、搜尋／recent 指標及 sessionStorage 偏好仍需逐項盤點。
- GAP-20 完全離線冷啟動仍受登入檢查阻擋，沒有新增離線身分認證或繞過登入。
- 新記 GAP-22：390px 更多選單沒有帳號／登出入口，頂欄隱藏也使 2 筆待同步數量不可見。
  手機可編輯且資料保留，但不能據此宣稱保存狀態與帳號操作已和桌面等價。
- Native 保留原未分區 adapter 的契約，沒有完成 Android 真機測試；未認證的公開頁不因此取得私有快取。
- 儲存 key 與 SQLite owner 都不是安全憑證；同一瀏覽器 profile 的開發者工具仍能讀取網站儲存。
