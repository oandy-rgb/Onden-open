# 卡住驗收列的缺口修正（2026-10-09）

> 狀態：歷史紀錄（最後確認 2026-11-01）

功能驗收迴圈在 tick 53 後只剩三列「部分」：NOTE-03、COL-10、CAN-09，分別被
GAP-20／185／186、GAP-162、GAP-249 擋住。使用者要求全部修正。本文記錄每項的設計取捨、
契約、驗證與剩餘限制；逐列證據仍在 [全功能盤點](../research/full-feature-audit.md) 與
[驗收迴圈紀錄](feature-loop-2026-10-07.md)。

驗證環境：隔離 e2e stack（:5199，`onden_test`，約 2 700 篇，達 slim 門檻）與乾淨小型 stack（:5299），
Playwright Chromium 1280×800；後端整合測試用拋棄式 `onden_test`（127.0.0.1:55432）。沒有真機。

## GAP-162：嵌入查詢從未渲染

- `MarkdownRenderer` 的 `code` 覆寫用 `/language-(\w+)/`，把 `onden-query` 截成 `onden`；
  改為與 `pre` 覆寫相同的 `[\w-]+`。單元測試確認 `onden-query`／`onden-base` 渲染為區塊。
- 修好後浮現 **GAP-266**：`tags: reading`（單一標籤，最基本的寫法）解析成字串，API 只收陣列而回 400。
  `OndenQueryBlock` 的 `tags` 一律送陣列。

## GAP-249：冷啟動重播整份事件歷史

- **契約**：`/api/bootstrap` 回傳 `last_event_id`（十進位字串），在讀任何資料列之前取得，
  所以之後的變更一定會被同步重送；可能重收已反映的事件（冪等），不會漏掉 payload 沒有的變更。
  與既有 `/api/sync` 一樣，未處理「較小 ID 的交易較晚提交」的序列競態。
- **採用規則**：本機 `sync_state` 沒有游標時才採用（`ON CONFLICT DO NOTHING`）；
  已有游標永不被 bootstrap 移動，因為 slim bootstrap 只合併、不重播刪除。
- **第二個原因**：瀏覽器實測仍從 0 同步——SSE 一連線就觸發 `sync()`，比 bootstrap 落地更早。
  `sync()` 現在等開機流程寫入 bootstrap（或結束）後才讀游標；沒有走 init 的呼叫者不受影響。
- **結果**（:5199 乾淨 profile）：冷啟動 `/api/sync` 由 22 次、6.1 MB、2 439 份正文降為 1 次、0.32 MB、0 份。

### 副作用與後續：大型工作區的離線正文

修正前，大型工作區冷啟動其實把所有正文都載入了（就是 GAP-249），所以「離線開啟沒開過的筆記」與
「合併子筆記」碰巧可用。修正後回歸在 :5199 出現兩類失敗（:5299 小型工作區全過）：

1. **合併子筆記會遺失文字**：slim 子筆記 `markdown ""`，合併只放進標題後就刪除子筆記。
   `mergeChildrenIntoNote` 先向伺服器讀所有缺正文的子筆記，任一失敗就不合併、不刪除；
   母筆記正文仍在載入時也不合併。
2. **離線打不開沒開過的筆記**：比較「背景下載到本機」「只保留開過的並明確提示」「設定開關」，
   使用者選擇背景下載：
   - 後端 `POST /api/sync/bodies {ids ≤ 200}`：讀取快照內套用 `readableNodeIdSet`，
     刪除、不可讀與任務節點不回傳。
   - 前端 `downloadBodiesForOffline()`：開機與重連後在閒置時分批下載，**只寫本機 SQLite**
     （`storeDownloadedBodies` 不覆蓋已有文字或有待送寫入的筆記），記憶體 store 保持 slim。
   - 本機 `nodes.body_len` 區分「尚未下載」（>0）與「真的是空」（0）；NULL 為舊版資料。
     slim 列寫入（例如只改標題）不再把本機已存正文清成空字串。
   - `hydrateNode` 在網路錯誤／5xx 時改讀本機正文；4xx 仍是伺服器的答案，不退回本機副本。
   - 大型工作區從本機冷啟動時也 slim 畫面（`bodies: "none"`），有待送寫入的筆記保留全文。
   - 離線且沒有本機正文時顯示「尚未下載到這台裝置，連線後即可開啟」，不再是無限載入；重連自動補讀。
   - 下載以「最近更新優先」分頁，並在 slim bootstrap 寫入後立即開始（與開機同步並行；正文來自伺服器目前可讀集合，
     被核對移除的列不會被回填）。開機後數秒內就離線時，最近的筆記最先可用。
   - 實測：12 批、2 296 份正文；離線開啟與離線冷啟動都顯示從未開過的筆記正文。

### 大型工作區效能（2026-10-10 量測與調整）

同一份 2 819 篇資料庫（`pg_dump` 複製），同一支探測（`zzPerfLarge`、`zzPerfOpenTrace`、`zzPerfReloadTrace`），
Chromium 1280×800、本機 Docker；修正前為 `a2c663d`。各跑兩次，數字為範圍。

| | 修正前 | 修正後（最終） |
| --- | --- | --- |
| 新裝置冷啟動到可用 | 8.3–8.6 s | 2.1–2.6 s |
| 冷啟動 API 流量／同步次數 | 6.1 MB／24 | 0.6–0.9 MB／1 |
| 背景下載全部正文 | 無（冷啟動已全量載入） | 12 批，開機後約 2.8 s 完成，總流量約 0.95 MB |
| JS heap（GC 後） | 33 MB | 22–23 MB |
| 已有本機資料時重新整理 | 1.05–1.42 s | 1.02 s |
| 線上開啟筆記（探測含導覽與編輯器掛載） | 35–80 ms | 80–100 ms |
| 離線開啟筆記 | 21–96 ms | 33–46 ms |

量測後做的兩項調整：

- **本機優先開啟。** 第一版開啟 slim 筆記必須等伺服器讀取。現在 `hydrateNode` 先顯示本機已存正文，再向伺服器確認；
  伺服器的結果只在該列自讀取開始後未被改動時才採用，避免較早讀到的回應蓋掉期間的保存；4xx 時收回已顯示的本機副本。
  追蹤顯示正文在伺服器請求發出前（50–75 ms）就出現；本機回應只要約 5 ms，所以在 localhost 上差異很小，
  實際網路的往返才是主要節省。開啟時間在下載剛完成時略高（約 90 ms），推測是 worker 正在寫出快照，未再拆分量測。
- **只有沒有游標的裝置才等 bootstrap。** 修正後重新整理變慢（1.8 s）。對照時序：修正前 SSE 觸發的同步與權限核對和
  slim bootstrap 並行，第一版的 GAP-249 閘門讓它們排在 bootstrap 之後。改為只有本機尚無事件游標時才等待，
  重新整理回到 1.0 s；新裝置仍只從 bootstrap 游標同步一次（`fix7-cursor-order.log`）。

## GAP-185：離線快速捕捉的筆記打不開

- 比較「捕捉繼續用原始佇列 POST、另補本機投影」與「改走 note writer 的樂觀建立」，選後者：
  與「新增筆記」同一路徑，筆記立刻進 store 與本機 mirror。`noteWriter.create` 新增可選 `id`／`parent_id`；
  帶 `id` 時它同時是冪等鍵，重試不會建立第二篇。失敗由 writer 回報，捕捉框不重複通知。
- 側欄「+」離線可用；選單中只有「Note」可點，草圖、手寫、PDF、圖片、書籤與模組建立需要伺服器而停用並說明。
- 實測：離線捕捉後編輯器立即開啟該筆記，上線後仍在。

## GAP-186：開啟中的編輯器保存會覆蓋他人修改（P0）

- **根因**：保存送出的 `base_markdown` 取自 store 目前的列。同步把他人的新正文放進 store 後，
  草稿仍是舊文字，伺服器三方合併把他人新增的行當成「我刪除的」。
- **修正**：`draftActions` 追蹤草稿真正的來源（`draftBase`）：切換筆記、保存接受、合併回填與復原時更新，
  保存一律以它為 base。沒有未保存輸入時，遠端新正文／標題直接換進編輯器（`applyRemoteNode`）；
  有未保存輸入時保留草稿，交給伺服器合併並把合併結果推回。
- 實測：兩裝置不同行同時修改，A 的編輯器顯示 B 的修改；A 再改並保存後伺服器仍保留 B。離線重放同樣保留遠端行。
- 未處理：同一行雙方都改時只有既有的「已與其他人的修改合併」提示，沒有逐段衝突介面。

## GAP-20：完全離線冷啟動進不了筆記

第十八批刻意「不以本機資料解鎖」，等帳號隔離契約完成（第十九、二十批已完成請求帳號預期與本機副本分區）。
使用者這次選擇「離線可讀寫」：

- `accountStorage` 記錄此裝置上次**經伺服器驗證**的帳號（依伺服器網址）。只由已驗證 session 寫入；
  確認登出與伺服器回 401 時清除。
- `LoginGate`：無法確認登入（網路、5xx 等，非 401）時，若有記錄就以該帳號開啟本機工作區；
  沒有記錄維持鎖定畫面。網路恢復時重新檢查 session；檢查進行中保持工作區掛載。初次檢查仍不先顯示快取。
- 離線請求照常失敗為離線；佇列寫入帶 `X-Onden-Expected-User`，若之後換帳號，伺服器以 401
  `account_changed` 拒絕，401 不消耗佇列，不會以另一帳號重播。
- 一併修正：大型工作區有本機快取、slim bootstrap 取不到時，原本仍當成線上 slim session，
  停在「Checking your workspace…」；現在走既有離線冷啟動處理。
- 實測：離線重開直接進入工作區並可編輯（待同步 1）；上線後送出 1 次，伺服器恰 1 份。
- 限制：拿到這台裝置的人離線時可閱讀該帳號的本機副本；登出後離線重開被鎖、換帳號 401 只有單元測試，
  沒有瀏覽器實測（會讓 e2e 帳號登出）。
