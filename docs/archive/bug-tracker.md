### [C1] Sync cursor advances past in-flight / mid-request events → permanent event skip (data loss)
- **area**: backend/sync  | **kind**: data-loss  | **status**: ALREADY FIXED (96e019b) — pg_advisory_xact_lock event-append at root mutate (verified spine/mutate.ts:285)
- **evidence**: src/routes/sync.ts:34-48 and 82-84. The event window and the max-id are TWO separate, non-snapshotted pool.query calls: `eventsRes` = `SELECT id... FROM domain_events WHERE id > $2 ORDER BY id ASC LIMIT 500`, then a separate `maxIdRes` = `SELECT COALESCE(MAX(id),0)...`. The cursor returned to the client is `const lastEventId = eventsRes.rows.length > 0 ? eventsRes.rows[last].id : currentMaxId;` and the client persists it via setLastEventId whenever it exceeds `since` (frontend useAppData.ts:376-378, even on an empty delta).
- **repro**: Two concurrent writes A and B where B's txn obtains a higher domain_events.id than A but commits first (or any write that commits in the gap between sync.ts:34 events query and sync.ts:44 maxId query while the client is caught up). Client syncs, receives last_event_id covering B, persists it, and never receives A's event.
- **fix**: Derive the cursor from a snapshot consistent with the events window and never advance past a possibly-in-flight id. Options: (a) wrap the events+max reads in one REPEATABLE READ / SERIALIZABLE transaction and, in the empty-window branch, only advance to a high-watermark that excludes ids of transactions not yet visible (e.g. use `SELECT min(id) FROM ... WHERE id NOT visible` / pg_snapshot xmin, not bare MAX(id)); (b) simplest safe fix: set `lastEventId` only to the id of the last row actually RETURNED by the window, and when the window is empty leave the cursor unchanged (return `since`) rather than jumping to MAX(id) — accept the audit-#3 'empty governance window' cost via a separate, monotonic, gap-safe watermark. The current `eventsRes.rows.length>0 ? lastRow.id : currentMaxId` must not be used as a durable cursor over a bigserial log with concurrent writers.
