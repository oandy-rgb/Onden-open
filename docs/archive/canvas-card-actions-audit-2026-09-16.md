# 白板卡片操作與移除實測（2026-09-16）

> 狀態：歷史紀錄（最後確認 2026-11-01）

對應 CAN-02、UX-01；前一批為[布局重新核對](canvas-reconciliation-fixes-2026-09-16.md)。本批只驗收卡片操作入口及移除擺放，不代表整個白板或右鍵選單的所有操作已驗收。

## 問題與改動

- 手機沒有明確的卡片操作入口，只能依賴右鍵／裝置的長按行為。選取卡片後，白板右上現在顯示「卡片操作」，與精簡切換並排；未選取時不占用這個空間。
- 舊選單直接採用點擊座標，沒有處理視窗邊界。現在依可用 client 尺寸定位，隨選單內容和視窗大小重算；過高時內部捲動，手機操作至少 44px。
- 實際截圖發現色票被 `.ctx-menu button` 的背景與邊框規則蓋掉，留下空白。現在以 20px 色塊呈現，手機點擊範圍仍為 44px。
- 移除原本立即關閉選單。現在保留 Promise，等待伺服器接受或本機佇列持久化，等待中停用同選單其他操作；拒絕時保留選單並共用 `reportWriteFailure`，不重複通知。
- 移除選項補上「筆記仍保留在資料庫中。」；不呼叫刪除筆記操作。成功後若仍停在原白板、原選取卡片，將 editor 模式的網址選取回白板，避免重載意外開啟剛移除的筆記。拒絕不改選取。

以上記為 GAP-34。原先關於白板成員與筆記本體的區分保持不變。

## 責任切分與方案比較

比較兩種入口：

1. 每張 CardNode 放操作按鈕／選單：呼叫 `onNodeContextMenu(id, x, y)`，但每張卡片都要知道觸控顯示規則，控制項會跟著 React Flow 縮放，且精簡卡片更擠。
2. 白板上固定大小的單一入口：KnowledgeWorkspace 只傳選取 ID 與螢幕座標，重用 ContextMenu。選單擁有開啟期間的等待、定位和焦點返回；既有 useCanvasActions／canvas writer 處理保存與回復。

採第二種。公開的移除 callback 為 `(nodeId) => Promise<unknown>`，正常完成包括 durable queued，並不等於已同步；共用同步列繼續區分狀態。Builder 的收尾只處理成功後選取，使用目前白板／畫面與選取檢查；不把導航放進 writer。新版選單按每次開啟的 target／座標建立生命週期，舊完成不關閉新選單，關閉與 Escape 可在等待期間使用。

新增入口不必理解 HTTP 分類、佇列格式或回復快照。其他舊選單操作仍維持各自既有保存契約；本批沒有把整個 ContextMenu 改成通用操作平台。

## 瀏覽器實測

CUA、真實隔離 PostgreSQL 與 API；既有 viewer 測試帳號，未改角色或政策。使用同一個 20 卡／35 語意邊白板，加上既有「0915 啟動首頁驗證」作為臨時擺放；不新增或修改筆記正文。手機為瀏覽器 viewport，沒有宣稱實體手機驗證。
