# 白板重播拒絕後的布局核對

> 狀態：歷史紀錄（最後確認 2026-11-01）

日期：2026-09-16。承接 [加入選單盤點](canvas-note-picker-audit-2026-09-15.md) 的 GAP-33；對應 CAN-02、PER-03。

## 問題與完成範圍

前一批已重現：加入卡片先進離線佇列，重播遭拒後，伺服器仍只有原本 20 張卡片，本機重開卻仍有第 21 張。筆記本身依然可讀，所以一般 node membership 核對不會刪除這份擺放；白板清單只更新 metadata，也不會替換布局。

本批完成條件是目前開啟白板的布局重新核對，包含拒絕後重試、冷啟動、待同步保護與晚到讀取。不是所有白板／多分頁／跨裝置合併已完成。

## 邊界與方案比較

| 方案 | 呼叫端知識與風險 |
| --- | --- |
| 畫面在拒絕後刪卡片，或強制呼叫 selectCanvas 重開 | 必須知道拒絕對象、既有同 ID 是否可讀、何時可覆蓋本機，以及導航生命週期；會把寫入與同步知識放進 UI |
| 白板 writer 提供 refreshOpenCanvas，由同步流程等待 | 呼叫者只要求重新核對；writer 擁有讀取、目前選取、更新版本、待同步／未確認輸入與本機布局 |

選第二種。既有 canvasActions 相容入口暴露 `refreshOpenCanvas(): Promise<void>`，sync 在讀完 node delta／可讀集合後、解除畫面 gate 前呼叫；手動 refresh 也沿用此操作。

契約：

- 只讀取當下開啟白板，不逐一抓取所有白板布局。
- 該白板仍有 queued 或 unconfirmed 輸入時保留本機布局；其他白板的 queue 不阻止本板核對。`sync.ok` 不代表所有佇列均已提交，原有待同步數量仍顯示。
- 已遭拒的輸入留在 recovery；它不能持續被當作目前布局。
- `inWriteOrder(canvas:id)` 涵蓋讀取與本機更新。讀取開始時記錄 writer revision／selection，讀取及副本更新後再次核對；新編輯、切換白板和晚到失敗不覆蓋目前畫面。
- 404 表示此 canvas 已不可取得，清除它的 canvas 副本與選取；不刪筆記正文，也不自行推導授權。
- 讀取或副本更新失敗向同步邊界傳遞，不解除本次拒絕核對的 gate。刪副本失敗保留目標，讓下次能重試。
- 冷啟動 select 若開始時尚未連線，完成本機讀取時已上線，會再次檢查待同步輸入並取得伺服器布局，避免錯過先完成的同步。
- 同步在布局核對開始時捕捉拒絕 revision；讀取期間又有拒絕，必須再跑一輪，不能用舊回應解除 gate。

相較原本，增加的是白板 writer 的完整讀取責任；picker 與畫面沒有新增拒絕 ID、快取格式、事件游標或重播流程。

## 回歸與限制

新增 writer 與實際 sync 編排測試涵蓋：queued POST／PATCH／DELETE、未確認保存、遭拒 recovery、正常核對、後續拒絕的回滾基準、讀取中追加編輯／queue、更新副本中追加編輯、切換及晚到失敗、404 清除與失敗重試、冷啟動上線競態、同 epoch 拒絕及讀取中的晚到拒絕。完整前端 192 檔／1,421 項通過，0 跳過；TypeScript、lint 與 production build 通過。已套用 Docker 前端，部署細節見下。

保留限制：

- 本批只主動核對開啟的白板。其他白板在上線開啟時取得遠端布局；未經上線核對的離線副本仍可能較舊。
- 每次完成同步會增加一筆目前白板 GET；未量測極大型白板／大量同步下的成本。
- 現有 canvas PATCH 仍提交完整布局。本批保留較新的待同步快照，沒有把它重寫成逐卡片操作，也沒有替不同分頁合併布局。
- 拒絕發生前，若後續完整快照已把相同擺放送到伺服器並被接受，本批不逆轉該成功提交；後續仍需盤點相依建立、跨分頁與並行操作。
- 多白板共用筆記、新建成功、手機移除入口及真機仍未完成 CAN-02 全矩陣。
