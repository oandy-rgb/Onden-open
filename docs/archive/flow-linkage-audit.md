# Onden Linkage-Feel Plan: Make element-to-element traversal smooth

## 1. The core diagnosis

The substrate is right (node=connection, stable IDs, event-sourced backlinks, offset computation, an already-built `pendingCursor` handoff). The *feel* layer is missing because of five cross-cutting root causes — not isolated bugs:

- **Navigation replaces context instead of layering it.** Every hop (wikilink / backlink / mention / palette / citation / graph node) is a destructive full-surface swap of a single `appStore.selectedId` register. There is no peek / side-panel / hover-preview anywhere in the *editing* app, so "is this the right reference?" always costs your reading position. The popover machinery already exists but is gated to `linkStyle==='published'`.
- **The path you walked is unrecoverable.** Node/lens hops use `history.replaceState` ("avoid history spam"), so browser Back and any in-app Back never return to the note you came from. The breadcrumb is `parent_id` ancestry, not visit history. There is no back-stack at all.
- **The system computes the exact landing spot, then throws it away.** `findBacklinkSnippet`/`findMentionSnippet` return `linkStart/linkEnd`; `pendingCursor` restore is already consumed on editor mount and scrolls-to-center. But the inspector nav calls `onSelectNode(id)` with the id only, and mount-restore *prefers* the last caret — so you always land at the top and hunt.
- **Following a link is a mode switch.** `[[Title]]` is inert text in CodeMirror; traversal only works in Preview or the published renderer. The most common gesture forces Edit→Preview.
- **Two divergent "open" paths and a save-gated, hidden return edge.** `handleClickWikilink` sets only `selectedId` (no `setMode`), while `openWikilink` does it correctly — same gesture, two outcomes. And backlinks only wire on the *next* save and live behind the collapsible inspector, so a freshly-created link has no visible way back.

Net: the hard substrate is done; almost every fix is *wiring existing capability across the in-app traversal path* and *consolidating onto one canonical open chokepoint*.

## 2. The Notion/Tana mechanics worth stealing

A small set of primitives collapses most seams at once:

- **Peek ladder** (Notion: hover-preview → side-peek → center-peek → full page; parent stays mounted) — kills the destructive-swap root cause for glances *and* quick edits.
- **Real history + Back / Cmd+[** (Notion) and **zoom-in clickable breadcrumb of the path traversed** (Tana) — makes every traversal reversible; the structural fix that makes all others cheap to undo.
- **Jump-to-mention** (Notion/Obsidian scroll-to + highlight the referencing block; Tana zoom to the precise node) — land *on* the link, not at the top.
- **Inline Cmd/Ctrl-click on a rendered link while editing** (Obsidian live-preview / Tana) — removes the mode switch.
- **Live two-way mirror refs the instant the link exists** (Tana) — no save delay, no hidden panel.
- **One canonical "open this thing"** that always lands you on the rendered surface — single chokepoint for cursor-handoff + back-stack wiring.

## [1/5] Capture with @date → becomes due_date + surfaces in agenda/today

_Connects: QuickCapture @date leg → due_date attribute write → TasksMode agenda / TodayLens "due" bucket / day.ts_

- **[high]** @date → agenda/today (the headline promise). The capture writes a plain attribute named 'due_date', but every due-surface (agenda + day-lens) sources exclusively from #task nodes carrying _task_due. So a captured @date task NEVER surfaces in Tasks or Today — the handoff is not merely rough, it is severed.
    - evidence: QuickCapture.tsx:250-258 writes PUT /attributes/due_date (key 'due_date'); tasksStore.ts:55-62 TASK_JOIN_SQL requires #task class_tag + _task_status + _task_due ('${K.due}'='_task_due'); day.ts:157-160 reuses the same join. 'due_date' ≠ '_task_due', and no #task tag/_task_status is ever applied at QuickCapture.tsx:219-258.
    - Notion/Tana: In Tana, @tomorrow on a captured line sets a real date field and the node immediately appears in every live 'search-node' query / calendar that matches it — one substrate, no second 'task' concept to opt into. In Notion, a captured row with a Date property shows in any Date-filtered Today/Calendar view with zero extra steps. Onden should either (a) parse @date into a REAL task (#task + _task_status='todo' + _task_due) like POST /api/nodes/:id/tasks does, or (b) make the agenda/lens query also include nodes whose plain due_date attr is set — so the one promise the placeholder makes ('@today', QuickCapture.tsx:315) actually lands somewhere visible.
- **[high]** Post-capture navigation drops you on the node BODY in notes mode, never near the surface the @date targeted.
    - evidence: BuilderApp.tsx:1804-1808 onAfterCapture: refresh(); setSelectedId(nodeId); setMode('notes'). No path to Tasks/Today; no toast linking to the agenda.
    - Notion/Tana: Notion's 'open as page' and Tana's 'zoom-in' both keep you oriented and offer the destination view in one click. After dating a capture, Onden gives no breadcrumb to 'see it on the agenda' and (per seam #1) it wouldn't be there anyway — a double dead-end.
- **[med]** No refresh propagation to the agenda surface even in the (hypothetical) success case. TasksMode loads its agenda once on mount; capture's refresh() rebuilds the node tree but does not touch TasksMode's local agenda state.
    - evidence: TasksMode.tsx:148-152 load() runs only in useEffect([load]); BuilderApp.tsx:1805 refresh() reloads bootstrap data, not TasksMode's agenda. TasksMode is lazy and unmounted while in notes mode, so it reloads on next switch — but there's no live two-way link from a capture to an already-open Tasks view.
    - Notion/Tana: Tana mirrors/live search-node results update in place the instant the underlying node changes; you never manually re-open a view. Onden's agenda only re-queries on a mode switch, so a capture made while Tasks is conceptually 'open' would not stream in.
- **[med]** The 'due_date' attribute is invisible on the very surface you land on. After capture you're on the node body, but the editor/body shows no due-date chip; the value is buried as a raw CustomRow that only appears if you manually open the attributes inspector.
    - evidence: grep: no frontend reads a raw 'due_date' attribute except as a generic custom attr (NodeAttributesPanel.tsx:187). The editor body has no due_date affordance. QuickCapture stripped the @token from cleanText (captureSyntax.ts:113-116), so it's not even visible as text anymore.
    - Notion/Tana: Notion shows the Date property inline at the top of the page; Tana shows the field on the node. In Onden the structured value you just set vanishes from the line AND isn't shown on the page you're dropped onto — the user has no confirmation the date was captured at all.
- **[low]** Offline @date is silently lossy in a second way: tags are preserved in the body when offline (QuickCapture.tsx:192-194) but the @date is still STRIPPED from text while its attribute PUT is merely queued — so offline the date disappears from the visible line with no fallback marker.
    - evidence: QuickCapture.tsx:192-195 keeps #tags in firstLine when offline but always uses cleanFirst's stripped form for the @date token; QuickCapture.tsx:250-258 queues the PUT. If that queued attr write later fails terminally, the date is gone from both the text and (per seam #1) every surface.
    - Notion/Tana: A capture-first tool should never let a structured token evaporate; Tana/Notion keep the date as a first-class field that round-trips. Onden's offline path keeps #tag recoverable in-body but gives @date no equivalent in-body safety net.
