# Tag / type / class as a first-class node

> 狀態：歷史紀錄（最後確認 2026-11-01）

> **Thesis anchor.** A node is the home; canvas / graph / table / inbox / timeline are *lenses* on a node's maturity. A tag *is* a node — `class_tag` is a `content_node` that happens to carry schema, policy, and behaviour. The question this section answers: if the substrate already believes "tag = node = class," why does the surface still treat tags as a separate mode, and what would it look like to collapse that mode back into the node space?

## Onden today

**The substrate already wins.** There is no `tags` table of record. `GET /api/tags` (`packages/backend/src/routes/tags.ts:62`) reads `content_nodes WHERE node_type='class_tag'`, aliasing the node-native columns into the legacy tag shape — `n.title → name`, `n.tag_color → color`, `n.tag_schema_id → schema_id` — and deliberately exposes `markdown / created_at / updated_at` "because class_tag IS a node" (comment A1.7, `tags.ts:154`). Every endpoint (`GET /:id`, `/:id/export`, `PATCH /:id`, `/import`, the query/publish/actors joins) is keyed on `node_type='class_tag'`. Tags form a real tree via `parent_id` on `content_nodes` (`tagHierarchy.ts`: `resolveOrCreateTagPath`, `descendantsOf` via recursive CTE, `fullTagPath`). Application is a `node_tags(node_id, tag_id)` join; the bootstrap surfaces `class_tag_ids` per node and feeds tag policy into a recursive-ancestor read-visibility CTE (`index.ts:205`). Every apply/remove/attribute op funnels through `tagDispatcher.ts` — depth-guarded, actor-attributed, event-sourced. The three governance axes (Schema / Policy / Behaviour) do **not** live on the node itself; they live on a linked `collection_schemas` row referenced by `tag_schema_id`, lazily created on first `PATCH /:id/schema`.

**The surface throws the win away.** The topbar (`AppTopbar.tsx:47`) renders five *co-equal* mode buttons — Notes / Tags / Tasks / Website / Timeline — backed by `useUiMode.ts` (`AppMode = "notes" | "tags" | "tasks" | "website" | "timeline"`). Selecting "Tags" swaps the entire workspace for `TagsMode.tsx`, a full-window surface with its *own* internal tab bar (All / Editor / Library / Inspector / View). The "Editor" tab embeds the legacy `TagsPanel.tsx` (an ex-overlay whose `onClose` is a no-op when embedded): a list→detail editor with Schema / Policy / Behaviour sub-tabs, debounced `PATCH /api/tags/:id/schema`, a visual ECA handler-tree builder, and a client-side dry-run mirroring the backend `previewHandler`. "Library" drag-drops `.tagpack.json` to `POST /api/tags/import`; "Inspector" lists what's tagged `#X`; "View" runs saved `collection_views`.

The decisive IA weakness: **a `class_tag` is not openable as a node in Notes mode.** `TagsMode`'s `onSelectNode` jumps to Notes only for tagged *members*; the class node itself has no Notes-mode editor route, and its node-native markdown body — which the backend explicitly serves — is never surfaced anywhere. Editing a class means *leaving the node space*, entering a peer mode, and operating an embedded list→detail panel. A tag can be "pinned" to top nav (`usePinnedTagViews.ts`, localStorage), which renders a `#tag` button that deep-links back into `TagsMode` via a `#tag-view=<id>` hash (`BuilderApp.tsx:542`) — so even the "shortcut" is a shortcut *into the mode*, not into the node. On the member side, `NodeAttributesPanel.tsx` renders one fields block per applied class tag, read from `schema_fields`. Tag application from prose is plain markdown `#tag` (`useAppData.ts` → `PUT /api/nodes/:id/tags/:tagId`).

So Onden has built the right *ontology* and the wrong *navigation*: the model says "a class is just a node with a schema lens," and the UI says "a class is a destination you teleport to."

## How the field does it

| App | Approach | What's good |

| **Anytype** *(vendored, verified)* | A type IS an editable object (smartblock `SmartBlockTypeObjectType`, key prefix `ot`; relations `rel`, options `opt` — `core/domain/uniquekey.go`). The schema lives **on the type-node's own details** as `RecommendedRelations / RecommendedFeaturedRelations / RecommendedHiddenRelations / RecommendedLayout` (`objecttype.go:27`) — no separate schema row. The type also *embeds a Dataview block* templated from its own recommended+featured relations with `TargetObjectId = ot.Id()` (`dataviewTemplates()`, `objecttype.go:208`), so opening the type shows the live member-set. You open a type as a normal page; you edit its schema in a sidebar "type" page (`sidebar/page/type.tsx`) whose sections are title / plural / layout / template / relation, where `rootId` *is* the type object. Featured relations render in the object header (`block/featured.tsx`). No "Types mode." | The cleanest realization of class=node=member-view in one surface. Editing the class is "open the node + a relations lens." The type carries its own live table of members. This is the model Onden's *substrate* already implements but its *surface* does not. |
| **Logseq (DB version)** *(vendored, source-verified — `logseq-master/deps/db/src/logseq/db/frontend/class.cljs`, `…/entity_util.cljs`)* | A class **is a page node**, distinguished only by carrying the built-in `:logseq.class/Tag` in its own `:block/tags` — the predicate `class?` is literally `(has-tag? entity :logseq.class/Tag)` (`entity_util.cljs:28`), and `page?` *includes* `class?` (`entity_util.cljs:45`), so a class is a kind of page, not a separate table. A class is created from a page-map via `build-new-class` (`class.cljs:188`) and gets a `:db/ident` in the `user.class` namespace. Its schema is the property `:logseq.property.class/properties` ("Tag Properties", `property.cljs:172`) held on the class node itself — no separate schema row. Inheritance is the property `:logseq.property.class/extends` walked by `get-class-extends` (`class.cljs:167`); built-in classes like `Journal`/`Whiteboard` extend `:logseq.class/Page`. `get-class-objects` (`class.cljs:209`) returns the class's members *including subclass members* by querying `:block/tags` over the class and its structured children. | The strongest open-source match to Onden's substrate: class = tagged page node, schema (`:…class/properties`) and inheritance (`:…class/extends`) live **on the node**, and the node carries its own live member-set query. Same shape as Anytype — and the same one Onden's *surface* fails to realize. The `extends` relation maps directly to Onden's `parent_id` tag tree. |
| **Trilium** *(vendored, source-verified — `Trilium-main/packages/trilium-core/src/becca/entities/bnote.ts`, `…/fattribute.ts`, `…/promoted_attribute_definition_parser.ts`)* | No dedicated "class" object — instead a **template note is just a `BNote`**, and any note becomes an instance by pointing a `~template` (or `~inherit`) relation at it. Inheritance is computed in `bnote.ts:384-400`: a note pulls in the template note's attributes (skipping the `template`/`workspacetemplate` markers). The "schema" is **promoted attribute definitions** — labels like `#label:status` / `#relation:…` parsed by `promoted_attribute_definition_parser.ts` (types `text/number/boolean/date/url/color`, `single`/`multi` multiplicity, `inverse=` relations) — that live as ordinary inheritable attributes on the template note. Attributes are only `label` or `relation` (`fattribute.ts:6`); relations are named typed edges to other notes (`targetNoteId`). | A class is a fully authorable note (its own body + children), and "schema" is just inheritable promoted attributes — closest in spirit to Onden's "the class node carries its own markdown body." Validates the "open the class as a normal node and edit it in place" recommendation: in Trilium there is *no* mode to leave. First-class named/typed relations exceed Onden's current `node_tags` join. |
| **Tana** *(web docs, partially uncertain)* | Everything is a node, including supertags themselves. A supertag = an "is-a" typed template of fields. Supertags support **Extend** (inheritance) — one supertag uses another as a base and inherits its fields/template. | The "type page" is itself a working node you author content on, plus a member-set, plus a schema editor — all one surface. | **Notion** *(web docs)* | A database is itself a page; its schema = its property set, edited inline (property-header `⋮⋮` menu or "Edit properties"). Templates are sub-pages that pre-fill values. It is a syncable label with a title — no markdown body, no schema, no policy, and tags are effectively flat. | Contrast case: tags are durable, syncable label-items but still not authorable nodes or classes. ## The gap

The gap is **not** ontological — Onden's backend is, by this comparison, closest to **Anytype and Logseq's DB version** (both make the class a node carrying its own schema + inheritance) and ahead of AFFiNE / AppFlowy / Notion (field-scoped per-instance schema) and SiYuan / Blinko / Joplin (tag is a label, not a class). It has a globally reusable class that is literally a node. The gap is purely **interaction / IA**:

1. **The class node is unreachable as a node.** Anytype, Logseq (DB), Trilium, Tana, Capacities, and Notion all let you *open the type/class as a page and edit it in place* — and in Trilium there is no separate mode to leave at all, since a template is just a `BNote`. Onden alone forces a mode-switch to a dedicated `TagsMode`, and even then never opens the class node itself — only an aliased editor panel over its `collection_schemas` row.
2. **The node-native body is dead surface.** The backend serves the `class_tag`'s `markdown`; no UI renders it. Anytype, Logseq (DB), Trilium, and Tana all treat the type/class/template node as *authorable content* (description, instructions, extra tabs, child notes). Onden discards a capability it already paid for.
3. **No "members of this class" lens on the class.** Anytype's embedded Dataview (`TargetObjectId = ot.Id()`), Logseq's `get-class-objects` (which returns members *including subclass members*, `class.cljs:209`), and Tana's tab-1 member table all make "what is this class's population" a first-class view *on the class node*. Onden has the data (`node_tags`, `collection_views`, the Inspector "what's tagged #X") but only inside `TagsMode`, divorced from the node.
4. **Co-equal mode-switching fragments one mental model into five.** "Tags" as a peer of "Notes" contradicts the thesis. The schema/policy/behaviour editor is a *lens*, not a *place*.

## Recommendation for Onden

**Collapse `class_tag` into the node space; demote the editing surfaces to lenses.** Concretely:

1. **Make a `class_tag` openable in Notes like any other node.** Its node-native markdown body becomes its editable home content (description, usage notes, agent instructions) — exactly the capability the backend already serves and the UI currently wastes. This is the literal payoff of "tag = node = class": there is nothing to migrate in the substrate, only a missing route on the surface. `TagsMode`'s pinned-tag deep-link should resolve to *opening the class node*, not jumping into a mode.

2. **Turn Schema / Policy / Behaviour into a lens on the open class node, not a separate mode.** When the open node is a `class_tag`, the same editing affordances that `TagsPanel` provides (the debounced `PATCH /:id/schema`, the ECA handler-tree builder + client dry-run) attach as a side lens on that node — the way `NodeAttributesPanel` already attaches fields to member nodes. This mirrors Anytype's sidebar "type" page where `rootId` *is* the type, Logseq's `:logseq.property.class/properties` held directly on the class node, and Trilium's promoted-attribute definitions living as inheritable attributes on the template note. The three axes stay on the linked `collection_schemas` row (no schema change); only their *presentation* moves from "mode" to "lens."

3. **Add a member-set lens on the class node.** Reuse the existing `collection_views` / `/:tagId/views/:viewId/exec` machinery and the Inspector's "what's tagged #X" query, but render them as the **table / canvas / graph / timeline lenses on the class node itself** — the same lens vocabulary the thesis applies to every node. This is Anytype's embedded-Dataview pattern (`TargetObjectId = ot.Id()`) and Logseq's `get-class-objects` (members + subclass members) expressed in Onden's lens model: a class node's "table lens" *is* its population; its "graph lens" *is* its members and sub-classes (`parent_id` tree). The maturity-loop reading: a class node matures from a bare `#tag` (capture) through a populated set seen on-board (diverge) into a governed, schema-bearing class with policy and ECA hooks (converge) — all without leaving the node.

4. **Retire "Tags" as a topbar peer mode.** It violates the one-unified-mental-model rule. There is no "Tags place"; there are only nodes, some of which are classes, all opened the same way and viewed through the same lenses. The schema/policy/behaviour lens and the member-set lens are *what a class node looks like*, not *where you go to manage tags*. (`Website` gets the parallel treatment in its own section — a publish gesture, not a peer mode — leaving the topbar's five modes to collapse toward the single node-space + lens model.)

5. **Keep the governance edge.** The Schema/Policy/Behaviour lens is precisely where the single-human-plus-one-AI-agent contract lives: every schema/policy/ECA change is an actor-attributed event through `tagDispatcher`. Surfacing this *on the node* (rather than buried in a mode) makes the governance visible at the point of authorship — the precondition for unconstrained AI collaboration the product thesis demands. The lens should show the audit trail (who changed this class's policy, when) inline, because the class node is now a normal node and the event log already covers it.

**Net:** the work is almost entirely deletion and re-routing on the frontend — remove `TagsMode` as a destination, add a class-node route + two lenses (schema/policy/behaviour, member-set) to the existing node surface. The backend is already correct; the recommendation is to make the UI finally tell the truth the substrate already tells.
