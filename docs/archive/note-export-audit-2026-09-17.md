## 問題與責任決定

1. GAP-61：`BuilderApp` 未提供 `copyNoteMarkdown`，指令可以選卻沒有動作。
2. GAP-62：筆記選單 Markdown 使用草稿，HTML／PDF 與指令面板卻直接 GET 伺服器版本；
   尚未保存的標題／正文會被漏掉。PDF 原本開啟帶 attachment 的匯出 URL 再嘗試列印，也沒有有效的失敗回饋。
3. GAP-63：320×740 實測選單 x=-61、寬280，左側操作被裁掉。原匯出飛出選單也依賴 hover。

比較兩種做法：

| 做法 | 呼叫端必須知道的事 | 成本與問題 |
| --- | --- | --- |
| 各入口先保存，再連到伺服器匯出 | 草稿歸屬、保存是否真的同步、讀取版本是否一致、列印視窗 | 匯出變成寫入；持久佇列接受不等於伺服器已接受，拒絕草稿也無法取出 |
| 共用當下快照，HTML 使用原排版器做唯讀轉換（採用） | `exportNote(format)`／`copyMarkdown()` 完成或拒絕 | 增加一個唯讀轉換端點；前後端須一起更新，不能只套前端 |

`useNoteExport` 統一快照、補讀、等待、下載／剪貼簿／列印與錯誤；選單和指令面板只提供操作意圖。
`readOverviewDraft(nodeId)` 只提供該編輯器擁有的文字，不保存、不改變保存狀態。
當文件編輯器不在畫面中，使用目前節點正文，避免把隱藏的舊編輯器快照蓋過白板已更新的文字。
空字串是有效草稿，不能用 `draft || savedBody` 取代。

`POST /api/nodes/:id/export-preview` 接受 `{ title, markdown }`，沿用 `canReadNode`、
`buildSingleNoteHtml`、既有主題／安全過濾／CSP。它不 PATCH 筆記、不發布、不加入離線寫入佇列、
不記成功變更事件；錯誤沿用 HTTP 邊界。原 GET 匯出仍保留相容性。

下載是操作開始時的快照；等待時繼續輸入，不影響既有快照或新文字。
切換筆記／工作區、移除節點、經過可讀範圍 gate 或卸載後，晚到結果不再輸出；A→B→A 也取消。
已交給剪貼簿的系統操作無法撤回，只有等待前的輸出及晚到通知受生命週期保護。

PDF 明確標為「列印／另存 PDF」：同一手勢先開空視窗，轉換完成載入後才呼叫列印；
被阻擋或轉換失敗有回饋並關掉自己開的空視窗。呼叫列印不代表使用者已存出 PDF，取消也不應回報已下載。
圖片仍是連結，HTML 將相對 URL 解析回來源伺服器；不嵌入媒體、不繞過媒體授權，並非完整離線備份。
