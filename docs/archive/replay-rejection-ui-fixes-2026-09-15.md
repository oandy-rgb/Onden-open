## 已拒絕的新筆記仍留在畫面（GAP-29）

修改前從側欄「新增節點 → Note」建立，測試 API 暫回 503，建立與文字都入列。
恢復後端後，真實 viewer 政策拒絕建立 403，後續編輯回 404；queue 清空、recovery 增加，
卻仍有可選的樂觀節點與編輯器。伺服器 epoch 沒變，也沒有成功建立事件，因此原本 epoch-gated
membership 檢查略過了清除。本例 ID 為 `aeb77f76-e14e-4f16-b191-9e8ef0017173`。

比較直接依被拒絕 POST 的 ID 刪除快取，與要求同步重新確認可讀集合，採後者：同 ID 也可能是既有可讀筆記，
請求失敗不是刪除它的充分條件。queue 只在拒絕輸入已持久化後推進 process-local revision；
sync 在檢查開始時捕捉 revision，成功後才確認它。期間若另一筆重播遭拒絕，必須再檢查一次。
清除復原副本不改 revision，重新載入仍使用原有冷啟動完整核對，不將此值當成後端權限版本。

- 桌面修正案例 `99e1c666-c5fa-4169-93b1-55354061f84f`：保存建立與文字後恢復真實 403／404，
  另注入 `/api/sync` 503。未確認資料被 gate 遮住，workspace 同時 inert／aria-hidden；
  鍵盤能到「重新檢查」，重試失敗保留提示，切到 320px 後按鈕高 44px。
  解除故障再按重試，gate 消失，目標不再是可編輯的本機筆記。
- 手機獨立案例 `2a5c0906-151a-470d-9bd0-9f41ddc02868`：503 時輸入與 2 筆待同步保留；
  真實拒絕後回到清單，復原面板保留標題與「手機建立遭拒絕後，回到清單並保留這段輸入。」；重開仍在。
- 重新檢查只呼叫原有 sync，由 sync 決定是否解除 gate；UI 不因按鈕完成而自行解除。
  例外沿用 `reportWriteFailure`，沒有另一套重試或 HTTP 分類。
