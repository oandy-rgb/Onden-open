# 變異測試報告：核心程式碼哪些真的被測試保護（2026-10-24）

> 狀態：歷史紀錄（最後確認 2026-11-01）

## 這份報告回答什麼

專案有約 1,300 個測試檔，大多是 AI 分批寫的。測試檔存在、測試通過，都不代表程式碼被保護。
變異測試的做法是：故意改一行程式碼（把 `>` 改成 `>=`、把條件改成 `true`、刪掉一個呼叫），再跑測試。
有測試失敗，這個改動就被「殺掉」；全部測試照樣通過，這個改動就「存活」，代表那一行可以被改壞而沒人發現。

本次用 StrykerJS 對下列核心檔案做變異測試，補上測試把重要的存活變異殺掉，並記錄哪些既有測試太弱。
**沒有修改任何正式程式碼。**

## 結論先講

- 核心檔案合計（不含 `delta.ts` 與還在被其他 PR 修改的前端三個檔案）的分數明顯提升，見下表。
  最大的缺口原本在權限：`spine/authority.ts` 只有 72%，工作區設定的保護、`principal_admin` 的 token 拒絕、
  「垃圾桶裡的筆記不能貼標籤」這幾條都可以被刪掉而所有測試照樣通過。補上以拒絕原因為斷言的測試後是 98.9%。
- `localDbJournal.ts` 的 IndexedDB 寫入／讀取／刪除（72 個變異完全沒有測試經過）原本由整個被 mock 掉的測試帶過，
  現在用真的 IndexedDB 行為測，44% → 88%。
- `sync/delta.ts` 只有 56%，且不是雜訊：同步增量的大部分事件種類（邊刪除、任務、屬性刪除、標籤目錄變動、清除）沒有測試。
  這個檔案、`draftActions.ts`、`writeQueue.ts`、`storeOps.ts` 正被其他 PR 修改，本次**只報告、不補測試**，列在最後的後續清單。
- 發現 1 個已經紅燈的測試（寫死原始碼文字）、1 段沒有任何呼叫者的程式碼、數處被別的規則遮蔽的防線，列在下面「疑似問題」。

## 範圍與做法

| 套件 | 檔案 | 測試怎麼選 |
| --- | --- | --- |
| backend | `services/eventLog/bodyMerge.ts`、`spine/authority.ts`、`services/readPolicy.ts`、`services/spaceAccess.ts`、`services/spaceScope.ts`、`spine/idempotency.ts`、`services/sync/delta.ts`、`services/parentKind.ts`、`services/nodeTree.ts` | 只跑 `vitest.mutation.config.ts` 列出的 103 個測試檔（會 import 或點名這些函式的測試，加上名稱對應的測試；其中 4 個在沙箱跑不起來而排除，實跑 99 個），資料庫為 Postgres 16 |
| frontend | `lib/data/draftActions.ts`、`lib/data/writeQueue.ts`、`lib/data/storeOps.ts`、`lib/localDbJournal.ts` | 整個前端測試（jsdom），排除 1 個已紅燈的檔案 |
| markdown | `sanitizeSchema.ts`、`mediaSanitize.ts`、`mediaEmbed.ts`（含 `isAllowedEmbedSrc`、`toEmbedUrl`） | 整個 markdown 套件測試 |

後端只跑測試子集的原因：完整後端測試約 9 分鐘（3,500 多個測試），而存活變異要把所有涵蓋它的測試都跑完才能確定，
光是一次完整後端變異測試就超過一小時。子集沒有包含「只經過 HTTP 路由間接碰到這些檔案」的測試，
所以後端分數**可能比用整個測試套件跑時低**，不會更高。

設定上的取捨（都寫在各套件的 `stryker.config.mjs`）：

- 用 `perTest` 涵蓋分析，每個變異只跑涵蓋它的測試；開增量模式，重跑只重算有變動的部分。
- `ignoreStatic`：後端與前端開啟。模組載入時就執行的變異（常數、錯誤類別名稱）每個都要跑全部測試，後端有 186 個、估計佔八成時間，
  已略過。markdown 的 schema 檔案整個是載入時建立的，不能略過，所以該套件關閉。
- `inPlace`：vitest 設定用相對於套件的路徑指向 `../markdown/src`，複製到 `.stryker-tmp` 會讓路徑失效。
  代價是變異測試執行期間工作目錄的原始檔會被暫時改寫，正常結束或中斷後會還原；執行中不要編輯或 commit。
- 後端只開 1 個 worker：整合測試共用同一個資料庫並在 `beforeAll` 清表。

### 測試環境的限制（要知道才能正確解讀）

- 沙箱沒有 AGE、pgroonga、pgvector。`db/schema.sql` 去掉這三個擴充及其索引後載入 `onden_test`（向量欄位改 `real[]`）。
  完整後端測試因此有 15 個檔案、53 個測試失敗（全文搜尋、語意搜尋、遷移相關），與本次改動無關。
- 變異測試的第一次完整測試必須全綠，所以另外排除了：後端 `searchNodesReadPolicy`、`tokenAgentConvergence`、
  `compositionLaws`、`embeddingsReadScope`（需要 pgroonga／pgvector）；前端 `MarkdownRendererParity`（在 main 上就是紅的，見下）。
  這幾個檔案原本會保護 `readPolicy.ts` 與 `authority.ts`，所以那兩個檔案的分數在有完整擴充的環境可能略高。
  用環境變數 `ONDEN_MUTATION_SKIP_TESTS` 列出，預設不排除任何檔案。
- 資料庫累積資料會讓測試失敗：變異測試跑到一半時共用資料庫已有約 9,400 個 actor、1,400 個 workspace，
  `spaceOverview`、`spaceAccess` 的測試因此逾時失敗；重建資料庫後全綠。正式環境的資料量下這類測試（會掃整個預設工作區的所有 agent）也不可靠。
  每次後端變異測試前要重建資料庫。
- `actorWriteAuthority`「refuses an actor whose deleted changed while waiting」在已被前一輪測試用過的資料庫上會失敗
  （刪除 actor 時撞到 `workspaces_owner_actor_id_fkey`），全新資料庫上通過。測試檔宣稱可在殘留資料上重跑，這條不成立。
- Stryker 對「模組載入時定義、被 `export` 的常數」的變異有時回報存活，但手動改那一行再跑測試會失敗
  （例如 `mediaSanitize.ts` 的 `SAFE_DATA_MEDIA_SRC` 去掉 `^`、`mediaEmbed.ts` 的 `EMBED_IFRAME_SANDBOX` 改成空字串）。
  這兩條已手動確認被新測試保護；報告的分數沒有因此調高。
- `sync/delta.ts` 的分數兩次執行差 1.3 個百分點（56.9%→55.6%，本次沒有為它加測試），
  代表那些同步測試有一點不穩定，分數有約 ±1.5 的雜訊。

### 權限（`spine/authority.ts`）

## 疑似問題與多餘／不可達的程式碼

沒有發現「變異後的版本其實更正確」的案例。下面是需要有人看一眼的：

1. **`frontend/src/lib/data/storeOps.ts` 的 `patchTask` 沒有任何呼叫者**，也沒有測試。是已經匯出但沒人用的死程式碼。建議確認後刪掉。
2. **`MarkdownRendererParity.test.tsx`「the RSS reader keeps dollar amounts as text」在 main 上就是紅的。**
   它用 `readFileSync` 讀 `RssReaderPanel.tsx` 的原始碼，要求裡面有一字不差的 `<MarkdownRenderer math={false}>`；
   #591 給那個元素加了 `resolveImage` 屬性之後測試就失敗了，但行為（美元符號不被當成數學）沒有壞，
   同一個測試的第二段是獨立的真渲染斷言，可以保留。這是「寫死原始碼文字」的典型：行為沒變，測試卻紅了。建議刪掉第一個斷言。
3. **工作區設定的保護被別的規則遮蔽。** 設定筆記在系統空間（遷移 096），擁有者本人也被空間規則拒絕，
   所以 `assertOwnerForConfig` 現在不是任何一個決定的唯一原因，只決定拒絕「原因」。這是好的縱深防禦，
   但過去沒有任何測試會在空間規則改動後發現它失效。本次新測試以拒絕原因（`reserved`）釘住它。
4. **`principal_admin` 的 `actor.tokenScope` 檢查是多餘的。** `isWorkspaceOwner` 對 token 本來就回傳 `false`，
   拿掉這段檢查結果還是拒絕，只是原因從 `principal` 變成 `owner`。保留沒有害處；新測試釘住原因。
5. **`assertReparent` 開頭的「移到自己底下」檢查是多餘的。** 後面的 `wouldCycle` 對自己也成立，結果與訊息相同。
6. **`toEmbedUrl` 的主機判斷沒有點邊界。** `host.endsWith("youtube.com")` 讓 `evilyoutube.com` 也被當成 YouTube：
   `https://evilyoutube.com/watch?v=dQw4w9WgXcQ` 會得到 `https://www.youtube-nocookie.com/embed/dQw4w9WgXcQ`，
   `classifyMedia` 回 `iframe`，而 `isAllowedEmbedSrc` 對同一個網址回 `false`。輸出一定是 YouTube／Vimeo 自己的播放網址，
   不是安全洞，但與函式註解「不在信任主機就回 null」不一致，一個連到別站的網址會被畫成影片。
   新測試只釘住「輸出一定是信任主機」這條安全性質，沒有釘住這個不一致。建議改成 `host === "youtube.com" || host.endsWith(".youtube.com")`。
7. **`toEmbedUrl` 第二個 `try/catch` 不可達**（`hostOf` 已用同一個字串成功建立過 `URL`）；
   `explainAccess` 最後的 `"not_member"` 備援在 gate 與 facts 一致時不可達（程式註解已說明）。
8. **等價變異（不是缺口）**：`sanitizeSchema.ts` 的 `defaultSchema.attributes?.x` 的 `?.`（預設 schema 一定有這些欄位）、
   `bodyMerge` 開頭的 `incoming === current || current === base` 捷徑（沒有它走一般路徑結果相同，只是省時間）、
   `overlaps()` 裡幾個邊界（依排序方式不會出現）、`hostOf` 的 `catch` 與 `!src` 檢查（之後的 `startsWith` 會丟例外、同樣被 catch）、
   `spaceAccess` 的 `actor?.id ?? ""`、`isSpacePermission` 的 `typeof` 檢查。這些沒有補測試。

## 既有測試中發現的弱點

先說明掃描方式：用 TypeScript 語法樹找 `it`／`test` 區塊，統計沒有任何斷言、只斷言呼叫、讀原始碼檔案的測試。結果是粗略的下限。

| 類型 | 數量 | 例子 |
| --- | --- | --- |

## 怎麼跑

```bash
# 後端：先重建測試資料庫（殘留資料會讓部分測試逾時）；沒有 AGE／pgroonga／pgvector 時設定 SKIP
cd packages/backend
export DATABASE_URL=postgres://…/onden_test ONDEN_TEST_DB_KEEP=1
export ONDEN_MUTATION_SKIP_TESTS=src/test/searchNodesReadPolicy.integration.test.ts,…   # 只在缺擴充時
npm run test:mutation                                   # 核心清單，約 1.5 小時（增量重跑只要幾分鐘到半小時）
npm run test:mutation:file -- src/spine/authority.ts    # 單一檔案

# 前端、markdown
cd packages/frontend && npm run test:mutation           # 約 45 分鐘
cd packages/markdown && npm run test:mutation           # 約 3 分鐘
```

輸出在各套件的 `reports/mutation/`（`index.html` 可逐行查看存活變異；已列入 `.gitignore`）。
執行期間原始檔會被暫時改寫，請不要同時編輯、commit。

## 限制

- 沒有跑完整的後端測試套件作為變異測試的基礎（只有 99 個檔案），沒有擴充時有 4 個相關檔案被排除。
- 分數有約 ±1.5 的雜訊（見 `delta.ts`）。
- 變異測試只說「有沒有測試會失敗」，不說測試的斷言對不對；等價變異無法自動排除，上面的判斷是人工看程式碼做的。
- 沒有用瀏覽器檢查任何介面，這次沒有介面變更。
