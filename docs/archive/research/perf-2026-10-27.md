# 效能量測 2026-10-27（對照 2026-10-21）

> 狀態：歷史紀錄（最後確認 2026-11-01）

量測與分析，沒有改產品程式。腳本與原始結果在 [perf-2026-10-27/](perf-2026-10-27/)，上一次是 [perf-logged-in-2026-10-21.md](perf-logged-in-2026-10-21.md)。

## 結論

**日常使用現在大致順手，10-21 最痛的「搜尋卡死後端」已經解決；但有三個隨資料量線性（或平方）變慢的後端問題，加上手機冷開仍然很重。**

- 指令面板搜尋：「演算法 期中」最後按鍵到結果，桌面 20k 從 40 秒降到 0.44 秒；伺服器單次 212 ms，事件迴圈只被卡約 0.1 秒（原本 17–20 秒）。#539 的修法有效。
- 登入頁 JS 從 512 KB 降到 254 KB（gzip），擋繪製的 CSS 從 143 KB 降到 32 KB；公開網站首頁沒有 JS（原本 318 KB）；bootstrap 原始大小減半（20k：23.5 → 11.5 MB）。

**現在最痛的三個**（依使用者感受排序；細節見〈前 5 個問題〉）：

1. **歷史頁要 9 秒才開得起來**（5k、20k 都是），其中伺服器 `/api/history/feed` 6 秒，是單一查詢裡的平方級子查詢（一天有 5k 篇被編輯時）；開完後瀏覽器主執行緒再卡 2.6–2.9 秒。1k 只要 1.4 秒。
2. **新增／改名一篇筆記的時間隨筆記數線性增加**：1k 79 ms → 5k 221 ms → 20k 734 ms（改名 756 ms）。原因是每次都掃整個工作區找「可能連到這個標題」的筆記，而且在工作區寫入鎖內，所以別人的寫入也一起排隊。
3. **20k 手機冷開約 10 秒、熱開約 5 秒，鏡像寫完要 33 秒**，主執行緒 long task 合計 4.3 秒。bootstrap 縮小了一半但仍是 1.8 MB gzip；`/api/events`、`/api/inbox` 每次輪詢都把全部可讀 id 讀進記憶體，20k 時 `/api/events` p50 153 ms（1k 22 ms）。

沒有解決的老問題：長筆記自動保存仍送出整篇內文兩次（50k 字 279 KB），手機一次保存來回 0.93 秒、最後按鍵到「已保存」2.5–2.7 秒，數字與 10-21 一樣。

## 重要限制（先讀）

- **機器不同，互動類數字不能直接比。** 10-21 是 16 核、7.6 GB；這次是雲端 4 vCPU（Intel Xeon 2.1 GHz）、16 GB，而且 backend、PG、nginx、Chromium 全在同一台上。這次打字、切換筆記、同步套用、桌面冷開 1k 的數字普遍比 10-21 慢 30–100%，無法分辨是機器還是程式變慢，因此對照表標「變差？（環境不同）」。要確定需在同一台機器上跑舊 commit；這次取不到（本機是淺複製，找不到 10-21 的 `d7e8b88e`），**未量**。
- **手機的「可操作」定義不同。** 現在手機開啟時直接進當天筆記，不再先顯示列表，所以「出現第一列」不存在；這次改成「底部導覽出現、沒有成員核對 gate、不是 inert、當天筆記的資料列出現」。與 10-21 的差異是定義造成的，標「定義不同」。
- **資料不是同一份。** 10-21 的快照拿不到，這次用 API 重建 5k（含連結、30 個標籤、100 個資料夾層級、每 50 篇一篇 24k 字長筆記、一篇 184k 字筆記），20k 用 SQL 把 5k 的「筆記 N」複製三份（`clone.sql`，連結與標籤一併複製，複本沒有事件，與 10-21 的做法相同）。差異：這次沒有「狀態／優先／截止」屬性（10-21 有約 45k 列），所以 attributes 與鏡像 DB 較小（20k 鏡像 70 MB，10-21 是 96 MB），edges 較多（20k 有 20,384 條，10-21 是 10,206）。
- **所有編輯事件都集中在「今天」。** 歷史頁因此是最壞情況（一天 5k 篇被編輯）；真實資料分散在多天時，單日量會小得多，但大量匯入或整理的那一天形狀相同。
- **未量：** 手機 20k 的「切換短筆記」（搜尋列沒有出現，原因未查）、手機的「展開全部」（手機版沒有這個按鈕）、手機的歷史頁（腳本沒寫入口）、離線熱開手機版（腳本在手機上沒有成功取得，數字缺）。

## 前 5 個問題

預估效果是**估計**，沒有實作驗證。

### 1. 歷史頁 9 秒（伺服器 6 秒＋瀏覽器 3 秒）

> 已處理（2026-10-30）：見 [perf-2026-10-30-history-relink.md](perf-2026-10-30-history-relink.md)。

- **現象：** 5k、20k 時從點「歷史」到出現清單 9 秒；1k 是 1.4 秒。`GET /api/history/feed` 5.8–6.0 秒，回應 1.9 MB（5k 篇筆記的當天清單，每篇附變更摘要）；之後瀏覽器 long task 合計 2.6–2.9 秒。
- **原因：**
  - 後端：`packages/backend/src/services/history/activity.ts:127-130` 的 `actors` 純量子查詢在每個輸出列上重掃整個 `edits` CTE（`FROM edits ed2 JOIN actors a …`），O(N²)。N＝當天被編輯的筆記數，5.1k 列要 4 秒。
  - 後端：`dayChanges`（`activity.ts:155` 起）對每一列各查兩次 `domain_events` 找前後內文 hash（`bodyEvents.ts:22` 的 `lastBodyHashBeforeSql`），1.5 秒，再讀 5k 份內文做 diff 摘要。
  - 沒有分頁：`feedByDay`（`activity.ts:249`）一次回傳 14 天內所有筆記。
  - 前端：一次渲染 5k 列。
- **建議：**
  1. 在 `edits` CTE 內順便 `jsonb_agg` 出每個（筆記、日）的 actors，或改成一次 `GROUP BY` 後 join，不要每列子查詢（S）。
  2. 每天只先回前 N 篇（例如 50）加「還有多少篇」，前端「顯示更多」再取；變更摘要只對這 N 篇算（M，需要改前端清單與 API 契約）。
  3. 清單用虛擬捲動，或限制初始畫出的列數（S–M）。
- **預估：** 做 1 可把伺服器 4 秒降到約 0.2–0.5 秒；做 1＋2＋3 後歷史頁在 5k／20k 應接近 1k 的 1.4 秒或更低。

### 2. 新增／改名筆記的成本隨筆記數線性增加

> 已處理（2026-10-30）：見 [perf-2026-10-30-history-relink.md](perf-2026-10-30-history-relink.md)。

- **現象：** `POST /api/nodes`：1k 79 ms → 5k 221 ms → 20k 734 ms；改名（PATCH title）756 ms。寫入在工作區事件鎖內，所以別人的保存也被排在後面（用 API 一篇一篇建 15k 篇筆記，吞吐從每秒 15 篇掉到 4 篇，所以 20k 要改用 SQL 複製建立）。
- **原因：** `packages/backend/src/services/wikilinkEdges.ts` 的 `relinkTarget`（約 168–226 行）：每次新增或改名都要找「哪些筆記可能連到這個標題」，查詢是掃整個 `content_nodes` 內含 `[[` 的列，對每列做 `strpos(lower(markdown), lower(名稱))`（約 190–207 行），也就是對所有含連結的筆記全文 lower() 與搜尋，20k 筆記、含 400 篇 24k 字長筆記時要約 0.7 秒。這個成本與筆記數、內文總量成正比，跟新筆記本身無關。
- **建議：**
  1. 新增一篇「新標題」時，只有「原本連不到、現在才連得到」的連結需要重算：維護「未解析連結文字」表（`node_edges` 已有 status），只拿標題去比這張小表（M）。
  2. 或用 pgroonga 索引過濾候選（`markdown &@ 標題`），再只對命中者做精確判斷（S–M，需對齊 `linkMatchesNodeSql` 的規則與測試）。
  3. 非標題改動（只改內文）不觸發 relink（現在的行為需要先讀 `noteCreate.ts` 與 `nodeUpdate.ts` 確認）。
- **預估：** 20k 的新增／改名從 0.7 秒降到接近 1k 的 80 ms；同時縮短工作區事件鎖的占用。

### 3. 20k 手機冷開／熱開仍重（約 10 秒／5 秒）

- **現象（手機 20k）：** 冷開可操作 9.9 秒（shell 1.1 秒 → bootstrap 下載 2.7 秒 → 解析、寫鏡像），主執行緒 long task 合計 4.3 秒、最長 1.06 秒；usable 之後鏡像又寫 33 秒（70 MB）；熱開 5.0 秒，成員核對 gate 1.9 秒。桌面 20k 冷開 3.6 秒、熱開 2.8 秒。
- **原因：** bootstrap 欄位已用 `lean2` 縮到 11.5 MB 原始（比 10-21 少一半），但仍是每篇筆記一列完整骨架：`nodes` 15.8 MB（`label_tag_ids` 1.3 MB、`recent_actors` 1.1 MB、`workspace_id` 1.1 MB、`last_actor` 1.0 MB、`space_id` 1.0 MB、`deleted_by_event_id` 0.5 MB、`tag_is_inheritable` 0.5 MB、`collection_views` 0.5 MB，一般 `lean` 格式量測；`bootcomp.mjs`），`edges` 5.3 MB；伺服器端 `services/sync/bootstrap.ts:145-158` 的 `evt_meta` 查詢 20k 要 419 ms。第一列要等 worker 寫完才出現（10-21 的結論，這次沒有重新定位到 `persistBootstrap`，**未量**）。
- **建議（沿用 10-21 F2、尚未做）：** `workspace_id`、`space_id` 等整份常數欄位移到檔頭；null 欄位省略；`recent_actors`／`last_actor` 延後載入（開啟筆記時才要）；先畫、再寫鏡像（需要處理 `persistBootstrap` 回傳投影的契約）；背景下載內文分批節流並限制手機流量。
- **預估：** 欄位瘦身可再減少約 30–40% 原始大小；先畫再寫可讓手機 20k 第一次可操作提早約 2–3 秒（估算）。

### 4. `/api/events`、`/api/inbox` 每次輪詢都載入全部可讀 id

- **現象：** 20k 時 `/api/events` p50 153 ms（5k 54 ms、1k 22 ms）、`/api/inbox` p50 102 ms；這兩個路由合計 579 次呼叫（每個開著的分頁會持續輪詢），取「可讀節點 id 全集」的 SQL 20k 時平均 15.2 ms、累計 42.7 秒，是全部情境裡總時間最大的一條 SQL。
- **原因：** `routes/events.ts:254`、`:328` 與 `routes/inbox.ts:269`／`services/inboxQueue.ts:69` 呼叫 `readableNodeIdSet`（`services/readPolicy.ts:20` → `spine/spaceScope.ts:30`），為了建 `eventAudience` 把整個可讀 id 集合（20k 個 uuid）撈到 Node 再傳回 SQL 當條件。這違反 `AGENTS.md` 的「讀取走 SQL 範圍、不先全量取出」，成本也隨筆記數線性增加。
- **建議：** `eventVisibleSql` 直接接受 `readableScopeSql` 的子查詢（保持同一條讀取政策，已有 `readableScope.integration.test` 對齊），不把 id 取回 JS（M）。或按（actor、`membership_epoch`）快取（S，但要處理失效）。
- **預估：** 20k 的 `/api/events` 與 `/api/inbox` 回到接近 5k 以下的 50 ms 左右；少掉每次輪詢的 20k 列傳輸。

### 5. 長筆記自動保存仍送兩份內文

- **現象：** 50k 字筆記每次保存 PATCH 279 KB（`markdown` 與 `base_markdown` 各一份），與 10-21 同；手機 4G 上傳 3 Mbps 下請求來回 0.93 秒，最後按鍵到「已保存」2.5–2.7 秒；桌面 100–160 ms。
- **原因：** `packages/frontend/src/lib/data/noteWriter.ts:182` 的 body 同時帶 `...changes`（含完整 `markdown`）與 `base_markdown: options.baseMarkdown`，讓伺服器做三方合併（`routes/nodes.ts`、`services/nodeUpdate.ts`）。
- **建議：** 送 `base` 的雜湊（或版本號）與差異（文字 patch），伺服器依雜湊從已存版本取 base；找不到 base 時才退回整份，沿用現有衝突處理。需改前端寫入佇列的離線重送與回復，以及 `nodeUpdate` 的契約（M–L）。
- **預估：** 一般輸入的請求從約 279 KB 降到數百 bytes，手機保存來回從 0.93 秒降到約 0.2 秒（受 RTT 150 ms 下限限制），最後按鍵到已保存約 1.7–1.8 秒（其中 1.4–1.5 秒是自動保存的 debounce）。

### 其他值得注意（未列入前 5）

- 手機打字延遲 50k 字 82 ms（p95 123 ms）、5k 字 43 ms，比 10-21 的 27 ms 高；若同機確認不是機器因素，這是互動上最明顯的回歸。
- 手機白板 200 張卡片：點分頁 20k 要 2.9 秒、平移 23–25 fps；桌面 20k 平移 p95 幀 100 ms。
- 手機 20 頁 PDF 捲動 26 fps（pdf.js 繪製成本），桌面 60 fps。
- `localDbWorker` 只剩 1.7 KB 預算。

## 方法與和 10-21 不同之處

### 環境

- 雲端沙箱：Linux 6.18、4 vCPU（Intel Xeon 2.1 GHz）、16 GB RAM、Node 22.22、PostgreSQL 16（pgvector 0.8.2、Apache AGE 1.6、PGroonga 3.1.0、pg_stat_statements）、nginx（gzip 設定同 repo）、Playwright 1.63 與預裝 Chromium。**沒有 docker**，用 `scripts/persona/boot.sh` 原生啟動（backend :8787、Astro SSR :4321、nginx :5099）。
- 程式版本：main 0114c033（部署紀錄 3838179f 之後）。
- `boot.sh` 缺 `@onden/site` 的建置步驟（新套件），第一次開機失敗，手動 `npm run build --workspace=packages/site` 後重跑才成功；這是開機套件的問題，沒有改它。

### 資料

- `seed.mjs`：用 HTTP API 建立 1k（1,032 篇）與 5k（5,139 篇）；`prep.mjs`（10-21 沿用）加「效能長筆記」50k 字與有 300 個反向連結的「效能樞紐筆記」；`prep2.mjs`（新）加「效能五千字筆記」、「效能短筆記」（有唯一詞彙，因為 5k 以上「筆記 N」搜不到完全相同標題的問題仍在）、200 張卡片的「效能白板」、20 頁 PDF「效能PDF」（Chromium 產生，87 KB）。
- `clone.sql`：5k → 20k（20,139 篇）。為什麼不直接用 API 建到 20k：每次 `POST /api/nodes` 都有 O(工作區) 的連結掃描（問題 2），5k 之後吞吐約 4 篇／秒，15k 篇要超過一小時。`POST /api/import/obsidian` 批次匯入也一樣慢（約 3 篇／秒）。
- 還原快照用 `pg_dump`／`pg_restore`（`snap.sh`）；**不能用 `CREATE DATABASE … TEMPLATE`**，因為 PGroonga 索引檔不會被複製，會出現「pgroonga: object isn't found」。
- 與 10-21 的差異：沒有狀態／優先／截止屬性；20k 的連結比 5k 多；所有事件都在同一天（歷史頁最壞情況）。

### 裝置與流程

- 桌面：Chromium 1440×900，不降速。手機模擬：390×844、isMobile、觸控、CDP CPU 4×、150 ms／9 Mbps／3 Mbps，與 10-21 相同。service worker 開啟。
- `measure.mjs`（10-21 腳本更新）：冷開、熱開、離線熱開、切換三篇筆記、50k 字打字與自動保存（這次補上實際請求 bytes）、⌘K 搜尋、同步。每個「資料量 × 裝置」5 次、每次全新 context。更新處：改用 `playwright`、短筆記改用「效能短筆記」、手機「可操作」定義（上述）、手機回到列表的等待條件（舊的 `.overview-mobile-tabs[data-level=browse]` 已不存在）。
- `measure2.mjs`（新）：側欄展開、5k 字打字（keydown→下一個 frame，加 Event Timing）、白板（分頁切換、畫布與卡片拖動的 rAF 幀間隔）、PDF（開啟、捲動 3 秒的 rAF 幀間隔）、歷史頁（更多 → 歷史）、短筆記與長筆記切換。
- `eventloop.mjs`（新）：每 20 ms 對 `/api/health` 發探針，搜尋時記錄探針最大延遲與超過 100 ms 的累計時間；每種查詢連續 7 次，緊接在 backend 重啟之後（10-21 的問題是「第 2 次起才慢」，所以連續多次）。10-21 用 CPU profile 直接量，這次用外部探針，只能看到「卡了多久」，不是原因。
- `create-latency.mjs`、`bootcomp.mjs`、`loggedout.mjs`、`sizes.mjs`、`publish-site.mjs`（發布 10 篇讓 `/site/` 有內容）：其餘輔助。
- 後端：backend log 的 `[http]` 行、`pg_stat_statements`（每個資料量開始時重置）、歷史 SQL 用 `log_min_duration_statement` 抓全文再 `EXPLAIN ANALYZE`。
- 離線熱開、手機分項缺的格子見上方〈限制〉。
