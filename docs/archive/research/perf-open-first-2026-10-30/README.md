# 手機打開更快：先能打字，背景再整理（2026-10-30）

> 狀態：歷史紀錄（最後確認 2026-11-01）

對應 [perf-2026-10-27](../perf-2026-10-27.md) 第 3 點。量測腳本 `open-timeline.mjs`（時間軸）與 `summarize.mjs`（中位數彙整）在這個資料夾，原始結果是 `timeline-*.json`。

## 量法與限制

- 手機模擬同 10-27：390×844、觸控、CDP CPU 4× 降速、150 ms RTT、9／3 Mbps；本機拋棄式環境（4 vCPU，backend、PG、nginx、Chromium 同一台）。資料用 10-27 的 `seed.mjs`／`prep*.mjs`／`clone.sql` 建（1k＝1,032 篇、20k＝20,138 篇）。
- 每次：全新 context、登入 → **冷開**（空儲存）→ 等鏡像寫完 → 關頁、等 10 秒 → **熱開**（有鏡像，有事件游標）→ **離線熱開**。每個資料量改前 3 次、改後 2～3 次，表中是**中位數**，單位 ms，起點是開始導覽。
- 「可打字」＝底部導覽出現、沒有成員核對 gate、工作區不是 inert、當天筆記的編輯器可見，且之後 2.5 秒內 gate 沒有再升起（冷開改前 gate 會在第一次可打字之後才升起，所以取最後一次進入可打字的時間）。之後腳本真的點進編輯器連續打字，量按鍵到下一個 frame（`打字延遲`）。
- 熱開前等 10 秒是因為關頁時 worker 還在存快照，馬上重開會多出一次「別的分頁存了新快照」的重載；不等的數字（`GAP_MS=0`）趨勢相同，但次數少且版本不完全相同，不放進表。
- 機器和 10-27 不同，絕對值不能和 10-27 的表直接比；同一份報告內改前改後是同環境、同腳本。

### 改前量到的三件事

1. **「先畫」在手機上沒有生效。** `paintThenPersist` 先把整份 bootstrap 交給 worker 寫，再讀待同步佇列；worker 一次只答一個請求，所以佇列讀取排在整份寫入後面，20k 時 `getPendingWrites` 等了 1.7 秒（7,565 → 9,240），畫面其實等於等寫入。寫入 `persistBootstrap` 本身 2.2 秒（含把 11 MB 複製給 worker）。
2. **冷開在畫面出來之後還會被 gate 擋 1～3 秒。** 沒有本機副本時，第一次成員核對照例先升起 gate（20k：12.2 → 13.0 秒；1k：4.8 → 5.9 秒），但畫面上的資料是剛從伺服器拿的。
3. **熱開的 gate（20k 約 3.8 秒）主要不是網路。** 成員 digest 在 1.9 秒就回來了（預取），之後是同一個 worker／主執行緒的排隊：離線內文下載（`missingBodyIds`／`storeDownloadedBodies`）在核對的同時開始，它們的請求排在核對的前面；邊、任務、屬性的分頁讀取（`loadLocalRest`）每合併一次就重畫整個 store（4× 降速下每次約 0.3～0.6 秒），發生在還看不到的 gate 後面。

### 改了什麼

- 冷開：先讀佇列 → 畫 → 才把 bootstrap 交給 worker 寫鏡像（`syncEngine.paintThenPersist`）。另試過「再等一個 frame、等 worker 安靜 1 秒」：量不出比單純換順序更好（20k 冷開約 10.0 秒 vs 9.9～10.1 秒），還讓 `multiTab.property.test.ts` 釘住的 KNOWN 重現序列失效，所以沒留。
- 冷開沒有本機副本、整份 bootstrap 剛落地時，第一次核對不先升起 gate；digest 不同、核對失敗、重試仍升起（`mirrorFilledThisSession`）。
- 熱開：離線內文下載改在開機核對之後、邊／任務／屬性分頁讀取改在核對之後。

### 沒做到

- **沒有「先顯示本機內容、核對在背景」。** 有快取的重開要顯示的是可能已被撤權的內容；第十五、四十一批決定的 fail-closed 就是為了這件事（內容不露出、離線編輯不寫進去），要改是改決定，不是效能調整，所以沒動。熱開的 gate 只縮短（20k 約 3.8 → 1.9 秒），沒有取消。
- **long task 沒有拆小。** 20k 冷開可打字前最長的三個仍各 0.7～1.4 秒：JSON 解析（約 0.75 秒）、`decodeBootstrapWire` 與投影（約 0.7 秒）、第一次整個 store 繪製（約 1.4 秒）。解析要換格式／API（任務明說不動），繪製要改成分批畫；而這幾段發生在畫面出來之前，拆小只改善回應性，不會讓可打字提早。
- 鏡像寫入開始得更晚（20k：約 7.1 → 8.8 秒，畫面之後），期間關掉頁面，下次仍是冷開。`persistBootstrap` 仍把整份 bootstrap 傳回主執行緒（約 0.2 秒反序列化）。
- 鏡像寫完後的快照存檔（IndexedDB，70 MB）沒有動；腳本量到的「寫完」時間在改前改後一樣。
- 熱開 `catchUpWithOtherTabs` 在 20k 時 RPC 時間約 1.8 秒，但 worker 內只花約 10 毫秒——時間是主執行緒忙著繪製、沒空收回應，不是它自己慢（探針量過，已還原）。
- 1k 熱開沒有差異（誤差內）。
