## T10 — 文字裡的 `#文字` 不是標籤

使用者決定（2026-10-16）：「不再自動把內文 #文字 建成標籤」，接著補充「標題的#也不算」，並移除快速捕捉第一行與 Tasks 快速新增的 `#tag` 語法（「也拿掉」），也決定不把既有只寫在文字裡的 `#文字` 遷移成 node_tags。

- 一則筆記是標籤 X 的成員，只看 node_tags（+標籤、匯入的 frontmatter、範本的預設標籤、API）。正文、標題、Markdown 標題行裡的 `#文字` 都只是文字。
- 前端：`lib/nodeTags.ts` 拿掉 `includeTextHashtags`，`tagMembers`／`tagMemberCounts` 只有一個答案；側欄不再有「只出現在文字裡的 #」小標籤和它的篩選（`activeTag`、`selectTagFilteredNodes`、`openTagByName` 一起移除）；標籤頁、標題下的標籤列、白板的「共同標籤」提示都只看真的標籤；編輯器 `#` 只提示既有標籤名稱，不再有「建立標籤」列（存檔本來就不會建立標籤）。快速捕捉與 Tasks 快速新增只讀 `@日期`（`parseCaptureLine`），`#文字` 原樣留在筆記或任務標題裡；`taskWriter.create` 不再接受 tags。hashtag 文法仍只在 `@onden/markdown` text.ts（D16），前端 `lib/hashtags.ts` 只剩呈現與輸入提示；`extractHashtags`、`extractTagPaths` 已無呼叫者，刪除。
- 後端：發布的 `tags`（`attachPublishedTags`）只列 node_tags；搜尋的 `#tag` 本來就查 node_tags。
- 原本的 T10（改名後只靠文字的成員掉出去）因此不存在了。已存在的 node_tags 不刪；只靠文字 `#` 的筆記會從標籤頁和側欄數字消失，不做遷移（使用者決定）。已發布的快照要重新發布才會更新標籤清單。

## T15 — 兩種建庫方式的資料不同

在 origin/main 上建兩個全新的資料庫，`schema_migrations` 都是 103 列：

| | `content_nodes` | `spaces` |
|---|---|---|
| 載入 `schema.sql`（initdb、CI、`compose.yaml` 的新安裝） | 0 | 1 |
| `migrate()` 從空資料庫重播全部 migration | 10 | 3 |

多出來的 10 列：`020_seed_builtin_tag_library` 的 #book、#meeting、#person、#project；`015_seed_policy` 的 #archive、#admin-only；帶 key 的 #page、#task、#workspace-config；Site Config 筆記。

- **(a)** 新安裝走 `schema.sql`，所以**沒有內建標籤庫**（#person、#book、#project、#meeting）；只有夠舊、重播過 020 的工作區才有。新安裝要不要附這組標籤是產品決定。**等使用者。**
- **(b)** 舊部署（prod 可能也是）可能還留著 015 的示範標籤 #admin-only。它的存取政策在 migration 094（空間）之後已經沒有作用。prod 讀不到，未確認。**等使用者。**
- **(c)** 整合測試假設資料庫是用 `schema.sql` 建的（測試自己建根層的 page、task 標籤）。用 `migrate()` 建的測試資料庫會撞上 `content_nodes_class_tag_workspace_parent_title_uq`，例如 `reservedTags.integration.test.ts` 3/5 失敗。建測試資料庫要照 CI：`git show origin/main:packages/backend/db/schema.sql | docker exec -i onden-pg-test psql -U onden -d <名稱>_test -q -v ON_ERROR_STOP=1`（主機上沒有 psql）。不要用 `CREATE DATABASE … TEMPLATE` 複製測試庫：pgroonga 索引在複本裡會壞掉（`PGrnLookupWithSize: object isn't found`），每個庫都要從頭建。
