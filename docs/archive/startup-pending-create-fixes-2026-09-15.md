## 設計與責任

比較兩種方案：

- 從撤權／刪除集合排除 pending POST 的 ID，直接保留整列快取：改動較少，但可能連同舊屬性、標籤、父層與關聯一起保留。
- 清除遠端不可讀副本，再從已持久化的建立請求重建自己的輸入：多一個本機投影結果，但能保留既有撤權保證。

採第二種。`pendingNoteProjection.missingPendingNoteCreations(nodes, writes)` 解讀既有 note writer 的
POST `/api/nodes`，只重建 content／canvas 的 ID、標題、正文、衍生 slug／長度及種類；不複製鏡像或任意 request 欄位。
後續 PATCH 的標題與正文依佇列順序套用，空字串有效；後續 DELETE 不再重建。其他領域格式不在此擴充。

`loadBootstrap`、`persistBootstrap` 與 `applySync` 都由 worker 讀取同一份 active queue。
full／slim 回傳可直接供 UI 使用的投影；slim 的舊副本清除移入保存交易，失敗一起回滾。
`AppliedSyncDelta.pendingCreations` 是 worker 產生的本機結果，並非服務端協定；即使 wire 有同名欄位也會被覆寫。
SQLite 與記憶體都先清除遠端刪除及其相依資料，再加入自己的新筆記輸入。
同批的 edge／task／attribute upsert 也不能把刪除的相依資料重新放回。

啟動頁只等待既有 membership gate，再從調和後資料選擇目的地。它不需要知道 queue 格式、SQL 或哪些請求是建立，
今日筆記、一般筆記、白板卡片的載入也不各自加保留例外。提交、重試鍵、錯誤分類與復原仍由既有 writer／queue 擁有。
