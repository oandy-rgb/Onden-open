# 共用空間的主場：擁有者的值班節點排成員順序、驗證權限、握有完整副本；不做簽章

> 狀態：現行（最後確認 2026-11-19）
> 涵蓋：無（擁有者對多人各有伺服器時的決定；尚未實作，沒有對應的程式）

| 項目 | 內容 |
| --- | --- |
| 日期 | 2026-11-19（業主決定：「就這樣」） |
| 實作狀態 | **尚未實作**（只是決定；多人各有伺服器這一段排在自己裝置之間的同步做完之後） |

## 這份決定管什麼情況

幾個人**各有自己的伺服器**、共用其中幾個空間、成員偶爾變動。
只有一個人自己的幾台裝置時，資料的合併不需要主場（每台對等，見[信任界線](sync-trust-line.md)）；幾個人連同一台伺服器時，那一台本來就是唯一的裁決者。

## 決定

1. **每個共用空間有一台主場。** 主場管三件事：成員變更的順序、驗證權限（別人的伺服器送來的每一筆寫入，由主場用它當下的權限檢查）、握有這個空間的完整副本。
   主場**不是**每一筆寫入的必經關卡：成員在自己的伺服器上照常離線讀寫，寫入先是暫定的、可以用，主場上線後才定案。
2. **主場就是空間擁有者的值班節點**（負責「只能做一次」的事的那一台，2026-11-12 的決定），不另外設一個角色。空間的主場由規則推出來，不另外存一筆；空間換擁有者時，主場跟著走。
3. **主場只在兩台同時在線時轉交，而且只轉給擁有者自己的其他機器。** 轉交是成員變更那條有序紀錄裡的一筆；新的那台確認收到之後才開始裁決，舊的那台從那一筆之後不再裁決。
4. **不做簽章，格式上留位置。主場不在時，成員的伺服器之間不直接交換這個空間的資料。**

## 為什麼

- **不做簽章就需要一個裁決者。** 一筆寫入若經過第三台轉手，沒有簽章就分不出它是不是真的由它聲稱的人寫的。有主場時，每一筆都由寫的那台直接送到主場，主場知道連線的是誰；其他成員拿到的都來自主場。
  2026-11-19 的文獻研究讀到的每一個沒有主場、多人、有權限的系統（Matrix、Keyhive、p2panda、localfirst/auth）都對每筆操作簽章並保留完整歷史；沒有找到「沒有主場又不簽章」的先例（是沒找到，不是有人證明做不到）。
- **把時間往前調，沒有主場就沒人擋得住。** 被移除的人可以宣稱某筆寫入發生在撤權之前；讀到的來源都承認偵測不了，只能靠「撤權優先」讓它沒有用。有主場時以主場收到的順序為準：撤權在主場生效之後才到的，一律成為建議（2026-11-19 遲到撤權的決定）。
- **遲到的撤權要退回已套用的修改。** 有主場時由主場寫一筆普通的修改把舊值放回去，其他台照收，不必每一台各自重算。
- **只同步部分空間需要一台握有全部的基準**（Cimbiosys 的參考副本）；刪除紀錄的回收也需要。
- **主場不該擋每一筆寫入**：由伺服器裁決每筆寫入的產品（Zero、PowerSync、Figma）都假設伺服器連得上，和「伺服器常常不在」相反；被拒的本機修改在那些產品裡預設是丟掉的。
- **合成一個角色**：值班節點與主場都是「同一時間只有一台、要是擁有者信任的機器、換手要兩台同時在線」，分成兩個角色只會多一套換手。
- **都是限制，之後放寬比收緊容易**：成員之間直接交換、簽章、把主場交給別人，都是在這個基礎上拿掉限制。

第 1 條與第 4 條有外部來源支持；第 2、3 條是設計上的推理，沒有外部來源。「這個組合最適合 Onden」是把多份來源拼起來的判斷，不是哪一篇來源的結論。依據與閱讀程度見 2026-11-19 的文獻研究報告（不在版本庫裡）。

## 沒選的

| 選項 | 為什麼不選 |
| --- | --- |
| 沒有主場，成員的伺服器互相直接交換 | 需要簽章、每人管金鑰、完整歷史、每台各自重判；是文獻裡到現在還沒完全解決的問題 |
| 主場裁決每一筆寫入（伺服器對帳） | 主場不在就不能寫；被拒的修改預設丟掉 |
| 主場與值班節點是兩個角色 | 兩套換手、使用者要理解兩個概念，而兩台都得是擁有者自己的機器 |
| 主場可以轉交給其他成員的伺服器 | 等於把空間的管理權交出去，接近「轉移擁有者」，信任界線要重畫 |

## 主場不在時

| 不受影響 | 延後到主場回來 | 停住（值班節點本來就有的性質） |
| --- | --- | --- |
| 每個人在自己伺服器上讀寫（寫入是暫定的）；每個人自己的裝置之間同步；私人空間；搜尋、連結、任務、複習 | 成員看到彼此的新修改；自己的修改定案；新成員加入；移除成員與改權限生效；新裝置或新伺服器取得這個空間的完整資料；刪除紀錄的回收 | 共用空間裡只能做一次、會對外產生效果的事（發布、推播、用金鑰跑的工作） |

畫面要讓人看得出來：共用空間的主場現在在不在線、上次同步是什麼時候、自己的修改是已定案還是在等主場。

## 例外／之後要重看的時候

- **主場永久壞掉（強制接手）沒有定。** 現在的答案是把那台機器從備份還原。沒有備份時，共用空間的成員管理會卡住（每個人手上的資料都還在）。要做強制接手時另外決定：只能由擁有者操作；舊主場沒同步出來的裁決會丟；舊主場又上線時哪一台讓位。
- **主場常關機時實際有多不方便沒有量過。** 沒有任何來源量過，只能等真的有兩三個人用起來才知道。
- 要重看這份決定的時候：要讓主場不在時成員之間也能交換；要讓不認識的人的伺服器成為對等節點；要做端對端加密（那時金鑰管理本來就得做）。
- 對自己的裝置：能用確定性的 id 讓「哪一台開著哪一台做」的事（重複任務、每日筆記），不綁在值班節點上；主要角色的切換盡量自動，不要求使用者手動交接。這是方向，細節未定。

## 跟著要做的事（都還沒做）

- 只同步部分空間（提案 #1769）從「延後」改回必做，排在傳輸之後。
- [信任界線](sync-trust-line.md)補上：別人的伺服器是成員、不是對等節點，只和主場交換；主場把它送來的每一筆都當成不可信的來檢查，包含權限。
- 轉交之後舊主場從舊備份還原的情況，要有測試（還原會換節點身分，重新同步後看得到轉交那一筆）。
