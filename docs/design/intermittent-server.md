### 瀏覽器版（#1164）已經涵蓋哪些

瀏覽器版的資料庫就在瀏覽器裡，沒有「伺服器」可以不在，所以它**不是**這份文件的解法，但它改變了兩件事：

1. **新裝置第一次打開、不需要伺服器**：瀏覽器版自己建立本機帳號，資料只存在那個瀏覽器（OPFS 或 IndexedDB），`browser-app.md` §4 已寫清楚最多可能丟多少。
2. 它列出了「沒有伺服器就不能用」的功能，正好是本文要的清單（`browser-app.md` §7）：

| 功能 | 瀏覽器版（沒有伺服器） | 伺服器版、伺服器關著時 |
| --- | --- | --- |
| 發布網站 | 預設關閉 | 網站關閉（見批 ②） |
| RSS | 預設關閉，抓取迴圈不啟動 | 不抓（見批 ③） |
| 推播提醒 | 沒有（`/api/push` 回「不可用」） | 不響（見批 ③） |
| AI／MCP | 預設關閉，路由擋掉 | 不能用（見批 ③） |
| 上傳圖片／檔案 | 沒有（朋友分支仍未開） | 不能上傳；已有的圖片離線多半看不到（見批 ①） |
| 其他成員 | 不適用（單人本機帳號） | 看不到別人的修改，回來才同步 |
| 新裝置第一次打開 | 可以（自己就是伺服器） | **不行**，必須連上伺服器登入並下載 |

這張表有一個可以直接用的做法：瀏覽器版是用後端自己的「模組閘門」把功能擋掉並回 `module_not_imported` 或 `browser_app_unavailable`，前端再轉成白話。伺服器關著時的「功能暫停」說明，可以沿用同一套說法（批 ① 的狀態面板），不用另外發明。

## 初稿結論（仍適用的部分）

1. **Onden 已經能撐「暫時斷線」，但還不能撐「伺服器每天關機」。** 筆記內文與手寫會自動存一份在本機，離線時能讀、能改、能新增，回來後自動送出並合併。壞掉或不清楚的是：圖片／PDF 離線看不到、沒有「伺服器上次在線」的說明、上傳附件、AI、發布網站、RSS、提醒都需要伺服器在線，而且畫面不會告訴你「為什麼不能用」。
2. **做法是補強而不是改架構。**（11/02 更新：「不做點對點」的立場已與分散式同步 beta 衝突，見 §7 Q1。）保留「伺服器是中心、每台裝置有本機副本、離線佇列、三方合併」。先把單一裝置離線做好並講清楚（批 ①），再讓網站能輸出成靜態檔（批 ②）、開機補做 RSS／提醒（批 ③）、寫自架等級說明（批 ④）。**不做點對點同步**（要換成 CRDT、權限守不住）。
3. **「加密轉交信箱」是最後一步、而且價值有限。** 它只解決「兩台裝置在伺服器不在時想互相看到對方的修改」，要新增金鑰配對與一個一直開著的轉交點，成本最高。建議先做 ①–④，用一個月實際使用後再決定要不要做 ⑤。

## 1. 現況盤點

**狀態圖例**：✅ 正常　🟡 劣化（還能用，但有限制）　❌ 壞掉　（**確認**＝我讀過程式；**推測**＝程式看起來如此但沒實跑）

「伺服器不在」分兩種，行為不同，下面都要看：

- **斷網**：瀏覽器知道自己離線（`navigator.onLine === false`），App 立刻切到離線模式。
- **假在線**：裝置有網路（例如連著 Tailscale 或 Wi-Fi），但伺服器關機或沒回應。瀏覽器**不會**觸發離線事件，App 要等請求逾時（寫入 25 秒）才知道；之後每 5 秒重試一次連線。這是筆電伺服器最常見的情況。

### 1.1 逐功能行為

| 功能 | 狀態 | 伺服器不在時使用者遇到什麼 | 依據 |

| 改筆記內文 | ✅ | 存進本機佇列，標題列顯示「離線—N 筆修改回來後同步」。 | 確認：`writeQueue.ts`、`SyncStatus.tsx` |
| 新增筆記 | ✅ | 同上，進佇列，ID 在本機產生。 | 確認：`offlineCommuteCapture.spec.ts` 等 e2e 有覆蓋 |
| 任務、時間軸、日記 | ✅ | 任務勾選、日記新增走同一條佇列；「今天」由裝置時間算。**時間軸（歷史）要伺服器**，離線看不到。 | 確認（佇列）／推測（歷史頁沒有離線資料） |

| AI／MCP | ❌ | AI 面板與 @ai 回覆、Claude 透過 MCP 連線都需要伺服器。離線時按下去的行為：**推測**為失敗訊息，沒有排隊。 | 確認（架構）／推測（畫面） |
| 多人空間 | 🟡 | 離線可改自己看得到的內容；**權限在回來時才判斷**。若期間被移出空間或權限被降，送出會被拒絕，輸入保留在「復原區」（FailedWriteRecovery）。別人的修改看不到。 | 確認：`writeQueue.ts` `drain`、`FailedWriteRecovery.tsx` |
| 備份 | ❌ | 備份 zip 由伺服器產生（`/api/backup/full.zip`）；本機副本另可匯出成檔案或寫到使用者選的資料夾（`localBackup.ts`）。**伺服器資料庫本身的備份不由 Onden 做**，自架者要自己備份。 | 確認：`routes/backup.ts`、`localBackup.ts` |

### 1.2 這張表告訴我們的四件事

1. **最大的洞不是同步，是「檔案」**：圖片、PDF、附件完全依賴伺服器。對資工學生，PDF（課程講義）離線可讀很重要。
2. **「假在線」是最常見、最難受的狀況**：現在要等逾時才知道，每次寫入可能卡 25 秒，且畫面不會說「是伺服器沒開」。
3. **伺服器端的工作（RSS、提醒、AI、發布）關機就停**，而且開機後的補做有限（提醒 12 小時、RSS 等一個週期）。
4. **佇列沒有上限是好事，但看不見也是壞事**：使用者不知道自己離線改了多少、哪些被伺服器拒絕。

### 1.3 沒能確認的部分（需實機或小測試）

- 伺服器關機時（有網路但沒回應）App 多久進入離線模式、期間輸入是否卡頓：**推測**會卡在 25 秒逾時；批 ① 的測試要量。
- 圖片離線是否顯示：**推測**不顯示；要在手機上用飛航模式實測。
- session 實際過期天數：要讀 better-auth 預設值或在實機測。
- 文件裡提到的「have 鍵」：**我在程式裡沒有找到叫這個名字的東西**。我當時把它理解成「重複送出保護鍵＋同步游標」。11/02 補充：分散式同步文件有一個 `have`（每個來源節點已持有的操作流水號區間，`distributed-sync.md` §6），業主指的很可能是它；那和主伺服器現有的游標是兩套東西。

## 2. 分級目標

做法：由小到大四級，每一級都可以單獨停下來，不依賴下一級。

| 級別 | 要達成什麼 | 伺服器不在時使用者能做到 | 不做 |
| --- | --- | --- | --- |
| (a) 單一裝置離線上限 | 這一台裝置在伺服器關機時，該能用的都能用 | 讀寫全部筆記、搜尋、看被標記為「離線也要用」的 PDF／圖片、手寫 | 離線上傳新附件到伺服器之外的地方 |
| (b) 裝置之間 | 兩台裝置在伺服器不在時，能互相看到對方的修改，而且不會弄丟 | 手機改的，Tab S9 也看得到（標示「待確認」） | 讓裝置自己決定最終版本 |
| (c) 對外功能 | 伺服器不在時，對外的東西不要一起消失 | 網站照常開、RSS 與提醒開機後補上 | 在筆電關機時推送提醒 |
| (d) 多人 | 界定清楚 | 見下 | 離線的多人即時協作 |

### 2.1 (a) 單一裝置離線上限

**目標**：一台裝置只要「同步過、而且你標了要離線用」，伺服器永遠不開也能完整使用，直到你需要上傳、AI、歷史這類必須伺服器的事。

| 項目 | 設計 | 理由 |
| --- | --- | --- |
| 內文、手寫、結構 | 沿用現況（全部預設存本機） | 已經做好，體積小 |
| 本機搜尋 | 沿用現有退回機制；補上「本機搜尋涵蓋全部已下載內文」的測試，並在結果頁標示「只搜了這台裝置上的內容」 | 現況只有標題與已下載內文，使用者看不出差別 |
| 附件（圖片、PDF）預設 | **圖片：預設存本機**（縮圖與原圖，總量有上限）；**PDF：預設不存**，只存「你標了離線也要用」的 | 圖片通常小而且常嵌在筆記裡；PDF 動輒數十 MB（上限 200 MB），全存會塞滿手機 |
| 「離線也要用」標記 | 每個筆記／PDF／資料夾可標記，標記的內容完整下載並保證不被清掉。伺服器在線時背景下載，進度可見 | 讓使用者決定，不替使用者猜 |
| 空間上限 | 設定頁一個「離線空間」：顯示已用／上限（預設 1 GB，可調），超過時**先清最久沒開過、且沒被標記的圖片**，不動被標記的與排隊中的修改。瀏覽器不給持久儲存時，直接在設定頁警告 | 佇列裡的修改是唯一副本，不能被清掉 |
| 儲存位置 | 附件放 Cache Storage 或 OPFS 專用區（不放進 sql.js 資料庫） | 資料庫要整份快照存檔，放大檔會讓每次存檔變慢（**推測**，批 ① 開工前先量） |
| 離線時上傳 | **仍不支援**（與現況一致），但按下去時說清楚原因、輸入保留。進階選項見問題 5 | 離線上傳等於要在佇列裡存大檔，容量與重複送出都難處理 |

### 2.2 (b) 裝置之間：改由分散式同步處理

初稿在這裡設計了「加密轉交信箱」，並因「要換成 CRDT、權限守不住」而排除點對點。2026-11-01 之後的情況變了：

- #1169 的分散式同步（beta）選擇**不換成 CRDT**：同步「操作」、內文仍用現有三方合併、權限由收方依自己的成員資料重驗。它直接回答了初稿的兩個擔心（`distributed-sync.md` §1 第 4 點）。
- 傳輸層它列了「HTTP 到伺服器」「加密中繼信箱」「WebRTC」三種，信箱就是初稿這一節。

所以這一節**不再獨立設計**，初稿的運作方式整理在文末〈給 distributed-sync.md 的一節〉，威脅模型留在附錄 C。要點仍然成立：信箱只遞送密文；寫的那台裝置負責送給伺服器；收到的信只放獨立疊層；被拒絕的進寄信那台的復原區。多人空間與大檔不在範圍內。

這個選擇與 `docs/decisions/no-p2p-intermittent-server.md` 衝突，見 §7 Q1。

### 2.3 (c) 對外功能

| 功能 | 設計 | 說明 |
| --- | --- | --- |
| 發布網站 | **靜態輸出**：按「發布」時，由伺服器（或本機）產出完整靜態檔，推送到外部空間（GitHub Pages 已有；補「輸出成 zip 自己上傳」與一鍵推到其他靜態空間）。網站網址改指向外部空間 | 伺服器關機網站照開。現況已有 `pagesPush.ts` 與 `/api/export-static`，只缺「預設就用它，並告訴使用者伺服器關機網站不會消失」 |
| RSS | **開機即補抓**：伺服器啟動後立刻做一次（現況要等一個週期），並記錄「上次成功時間」，若落差超過來源保留範圍，在訂閱頁寫「關機期間可能漏了一些」 | 小改動，效果直接 |
| 錯過的提醒 | **合成一則**：開機後，把 12 小時窗口之外、錯過的提醒合成一則「你錯過了 N 個提醒」，點開看清單；12 小時內的維持逐則補送 | 避免開機瞬間轟炸，又不讓提醒默默消失 |
| App 開著時的提醒 | 沿用現有本機提醒；補上：裝置上排好「未來 24 小時內的提醒」到本機通知（瀏覽器支援時），伺服器關機也會響 | **推測**瀏覽器對「排程通知」支援不一，Android 較可行；要實機測 |
| AI | **排隊**：離線／伺服器不在時按「請 AI 處理」，記成「待送出的請求」，伺服器回來才送；畫面標示「等伺服器回來才會執行」。仍受同一套 MCP 權限約束，**只提建議，不排隊直接寫入** | 符合 `AGENTS.md`：AI 只能提建議 |

### 2.4 (d) 多人：不做的部分

| 不做 | 原因 |
| --- | --- |
| 伺服器不在時的多人即時協作 | 需要點對點或中繼合併；與權限模型衝突 |
| 轉交信箱跨使用者 | 金鑰是帳號級；多人要做群組金鑰輪替、撤權，風險高 |
| 離線時的權限判斷 | 權限永遠由伺服器回來後判斷（現況）；UI 只標註「這筆修改尚未被伺服器確認有權限」 |
| 自動解決多人衝突 | 現有三方合併＋保留雙方（`BODY_CONFLICT`）已是上限 |

**會做**：多人空間在伺服器不在時，**自己看得到的內容照常可讀可改**，回來後被拒絕的進復原區；並在空間頁標「這個空間需要伺服器」之類的白話提示（不做功能，只說清楚）。

## 3. 使用者看得到的狀態設計

原則（遵守 `AGENTS.md` 的介面文字規則）：用白話；不出現 ID、錯誤碼、毫秒、JSON；同一件事只在一個地方說；可以按的就給按鈕。

### 3.1 狀態一覽

| 情況 | 頂端狀態列 | 點開後 |
| --- | --- | --- |
| 一切正常 | 不顯示（沿用現況：「已連線」不是新聞） | — |
| 伺服器沒回應（有網路） | **伺服器目前沒開，這台的修改先存著（12 筆）** | 「伺服器上次在線：今天 09:12」「[重試連線]」「這段時間可以做：讀、改、新增、搜尋　不能做：上傳圖片、AI、看歷史」 |
| 沒網路 | 離線—修改先存在這台（12 筆）（沿用現文，微調措辭） | 同上，但不說「伺服器」 |
| 伺服器回來，正在送出 | 正在同步 12 筆… | — |
| 有些修改被伺服器拒絕 | 有 2 筆修改沒被接受，輸入還在 | 進復原區（既有 FailedWriteRecovery） |
| 離線太久 | 這台已經 3 天沒有連上伺服器 | 「為了安全，建議盡快連線；你的修改都還在」。超過 session 可能過期的天數，加上「連線後可能要重新登入」 |
| 本機存不下 | 沿用現有「這台裝置存不了離線副本」 | 補「離線空間」入口 |
| 瀏覽器不給持久儲存 | 設定頁警告：「瀏覽器可能在空間不足時清掉離線資料」 | 附「安裝成 App」說明 |

「假在線」與「沒網路」要分開講的理由：使用者的行動不同（前者去開筆電，後者等網路）。

### 3.2 需要新增的資訊（來源）

| 資訊 | 從哪來 | 備註 |
| --- | --- | --- |
| 伺服器上次在線 | 本機記錄最近一次請求成功的時間，按帳號存 | 新增一個很小的本機欄位 |
| 「伺服器沒開」vs「沒網路」 | 瀏覽器有網路 + 連續請求逾時／連不上 → 伺服器沒開 | 現況只看瀏覽器事件 |
| 離線多久 | 同上 | — |
| 不能做的功能清單 | 每個功能登記「需要伺服器」（在模組登記資料裡加一個欄位），狀態面板自動列 | 避免寫死一份清單而漏掉 |

### 3.3 伺服器拒絕離線寫入（FailedWriteRecovery）

現況（確認）：被拒絕的修改**不會刪**，內容保留在復原區，不自動重送。要補的：

| 補強 | 說明 |
| --- | --- |
| 白話原因 | 「你已不在這個空間」「這篇已被刪除」「沒有編輯權限」，不顯示錯誤碼（沿用 `lib/serverErrors.ts`） |
| 一鍵處理 | 「複製成新筆記」「貼回原筆記」「放棄」；放棄需要確認 |
| 離線很久後的批次 | 一次被拒絕很多筆時合併成一個清單，不是跳很多個提示 |
| 排隊中的修改超過 30 天 | 送出前警告：「這些修改已超過 30 天，可能與伺服器已有的內容重複」（對應重複送出保護 30 天） |

## 4. 自架等級說明

給自架的人看的，放在 `docs/self-host/`（批 ④ 新增 `uptime.md`）。

| 等級 | 意思 | 適合 | 特色 |
| --- | --- | --- | --- |
| **推薦：一直開著** | 伺服器 24 小時在線（VPS、家裡小主機、NAS） | 想要全部功能的人 | 所有功能正常，提醒準時，RSS 不漏，網站不關 |
| **支援：會關機** | 伺服器就是筆電，用的時候才開 | 學生、個人使用 | 核心筆記功能照用，下表功能會停 |

### 關機時會停的功能

| 功能 | 關機時 | 緩解 |
| --- | --- | --- |
| 同步（多裝置） | 各裝置改各的，開機後合併 | 自動，無需處理 |
| 提醒（Web Push） | 不會響 | App 開著時本機提醒仍響；錯過的合成一則（批 ③） |
| RSS | 不抓 | 開機補抓（批 ③） |
| 發布網站 | 網站關閉（若用伺服器提供） | 改用靜態輸出到外部空間（批 ②） |
| AI／MCP | 不能用 | 請求排隊（批 ③ 之後） |
| 新裝置登入、上傳附件、看歷史、復原 | 不能用 | 無；說清楚即可 |

### 備份提醒

筆電會壞、會被偷，**會關機的伺服器更需要備份**：

1. 資料庫備份（`pg_dump`）和上傳的檔案資料夾要一起備；`docs/self-host/recovery.md` 之外補一份「備份與還原」。
2. 設定頁加「上次備份時間」，超過 7 天提示（備份由使用者下載 zip；Onden 不替人上傳到雲端）。
3. 關機前不需要特別操作（資料庫關機時會安全結束）。**例外**：強制斷電可能損壞最近的寫入，這是沒有 UPS 的筆電要知道的。

## 5. 測試計畫

目的：用**自動化**抓回歸，用**實機**驗感覺和真實環境。

### 5.1 自動化（Playwright 完整堆疊 e2e）

沿用現有 `packages/frontend/e2e/fullstack/` 與 `faultKit.ts`、`helpers.ts`（`setPageOffline`、`reloadColdStart` 等）。現有的離線 e2e 只涵蓋**分鐘級**斷線（`offlineFlakyNetwork.spec.ts`、`offlineCommuteCapture.spec.ts` 等）。

可參考但**尚未合併**的兩個 PR（我已讀過說明，沒有在這裡測試過它們的程式）：

- [#691](https://github.com/oandy-rgb/Onden/pull/691)：把故障注入（`@faults`）併入預設流程，獨立 project、序列執行、可用 `E2E_SKIP_FAULTS=1` 跳過；`run.sh` 只清自己的 runner。**批 ① 的新測試放進 `fullstack/faults/` 就會自動被收進去。**
- [#693](https://github.com/oandy-rgb/Onden/pull/693)：隨機化真瀏覽器同步／離線測試（兩分頁一裝置＋另一裝置，隨機打字／刪除／離線／重新整理，結尾檢查不變式；失敗會印種子可重播）。它的不變式（打過的字不丟、刪掉的不復活、各裝置與伺服器一致）正是本計畫要的。**建議：先合併這兩個 PR，再在其上加下面的情境。** 目前 #693 的說明自己寫「沒有對真實 stack 跑過」，第一次本機跑可能要小修。

| 情境 | 做法 | 檢查什麼 | 可自動化？ |
| --- | --- | --- | --- |
| **伺服器關 24 小時** | 把伺服器容器停止（不是 `setOffline`）。用可控時鐘快轉 24 小時（Playwright `page.clock`）；後端用假時間或直接調資料庫時間戳驗證 30 天界線 | 離線期間讀寫全部可用；佇列計數正確；重啟伺服器後佇列清空、內容一致；沒有重複事件 | ✅（停容器能做；真實 24 小時不必等） |
| **兩三台裝置各自改同一篇** | 三個 browser context，同一篇不同段落／同一行；伺服器停→各自改→伺服器啟 | 不同行：都保留；同一行：兩邊保留（`BODY_CONFLICT`）；沒有字消失（#693 的不變式） | ✅ |
| **「假在線」** | 讓伺服器**接受連線但不回應**（例如用代理延遲，或 `docker pause` 容器）；`navigator.onLine` 保持 true | App 在合理時間內顯示「伺服器沒開」；寫入不卡死畫面（逾時 25 秒後排隊）；伺服器恢復後自動送出 | ✅（`docker pause`） |
| **重開 App** | 排了 N 筆後關閉分頁／整個 context，再開（含冷啟動） | 佇列還在；`rememberUnconfirmedWrite` 的恢復有效；沒有重複 | ✅ |
| **session 過期** | 伺服器停著時，把 session 資料列改成過期，再啟動伺服器 | 排隊修改不丟；要求重新登入；登入後以同一把鍵送出 | ✅ |
| **佇列超過 30 天** | 把重複送出鍵的建立時間改成 31 天前 | 警告出現；行為符合設計（問題見 3.3） | ✅ |
| **離線空間滿** | 灌滿 OPFS／模擬 quota | 先清舊圖片，不動佇列；顯示提示 | 部分（quota 模擬只有 Chromium） |
| **圖片／PDF 離線** | 標記離線用→停伺服器→重新整理 | 圖片、PDF 顯示 | ✅（批 ① 完成後） |
| **提醒補發** | 後端整合測試：模擬停機 13 小時後啟動 | 12 小時內逐則、之外合成一則 | ✅（後端單元／整合） |
| **RSS 開機補抓** | 後端整合測試：啟動後立刻抓 | 不用等一個週期 | ✅ |

### 5.2 必須業主實機測

雲端沒有 Docker 也沒有真機；以下我**不會**宣稱通過。業主的裝置：Android Brave 手機、Tab S9、Linux 筆電（都在 Tailscale）。

| 項目 | 為什麼必須實機 | 怎麼測 |
| --- | --- | --- |
| 「假在線」真實感受 | 手機連著 Tailscale 但筆電伺服器睡眠／關機，是真實的網路行為 | 手機正常用 → 筆電蓋上睡眠 → 手機改筆記、貼圖 → 記錄狀態列文字、卡頓秒數 → 開蓋，確認送出 |
| Brave 的持久儲存 | Brave 預設較嚴，可能拒絕 `storage.persist()` | 設定頁看警告；清瀏覽器快取後佇列是否還在（**小心：只在測試帳號做**） |
| Android 本機提醒 | 瀏覽器排程通知的實際行為依系統而異 | 設一個 5 分鐘後的提醒 → 關伺服器 → 手機鎖屏 → 看會不會響 |
| 飛航模式下 PDF／圖片 | 真機快取與記憶體 | 標記離線用 → 飛航模式 → 開 PDF |
| 三台各改一篇 | 真實的多裝置 | 三台同時離線改同一篇的不同段落，開機後檢查 |
| 長時間（過夜）關機 | 只有時間能測 | 睡前關伺服器、手機照常用一晚，隔天開機 |
| 電池／發熱 | 離線期間每 5 秒重試連線的耗電 | 觀察一晚耗電（**推測**重試間隔可能需要退避，見批 ①） |

### 順序的不同意見

建議順序與業主提的一致，**只有三點微調**：

1. **④（文件）可以提前到 ① 一開始就寫，而且先發。** 文件只有 S 大小，又能馬上讓自架的人知道預期；②③ 完成後再補上緩解。理由：寫等級說明時會逼我們把「到底哪些會停」說死，反過來是 ① 的驗收清單。
2. **③ 的 RSS／提醒小改動可以比 ② 先做。** 它們各自只是幾行設定加測試，立即能感受；② 雖然多數已存在，卻要處理網址與認知問題，比較不急。若業主最在意網站不關，維持 ② 在 ③ 前也可以。
3. **⑤ 維持最後，且建議「做完 ①–④ 後用一個月再決定」。** 因為 ① 做完，單裝置的離線體驗和「看得到狀態」會解決大部分痛點；多裝置互看是否值得多週的投入，要看實際使用。

### B. 與既有文件的關係

- `docs/architecture/sync-protocol.md`（草案）寫「待送出佇列將併入本機事件紀錄」。**現況不是**：佇列仍是原始 HTTP 請求。本文的轉交信箱以**現況（HTTP 請求）**為準；若日後佇列改成本機事件，信的內容同步改，信箱本身不用變。
- `docs/architecture/membership-and-permission-epoch.md`：撤權後重連的行為。轉交信箱不改變它，因為權限只在伺服器判斷。
- `AGENTS.md`：UI 不顯示技術細節、保存確認要區分「伺服器已接受」與「只存在本機」、AI 只能提建議。本文第 3 節與 2.3 的 AI 排隊都以此為界。

### C. 轉交信箱的威脅模型（簡版）

| 威脅 | 處理 |
| --- | --- |
| 信箱被入侵 | 只看到密文、大小、時間；不能偽造（每封信帶認證標籤，AEAD） |
| 信箱重放舊信 | 收件端以「裝置編號＋流水號」記錄已看過；伺服器端以重複送出鍵去重 |
| 裝置遺失 | 在另一台裝置撤銷該裝置，輪換裝置群金鑰；舊信不再可解 |
| 信箱不可用 | 完全退回批 ① 的行為（各裝置各自離線），不影響資料安全 |
| 惡意裝置寄偽造的信 | 只有持有群金鑰的裝置能產生有效密文；信只進「待確認」疊層，不進正式資料 |

密碼學元件建議直接用瀏覽器內建的 Web Crypto（AES-GCM／ECDH），不引入新依賴。

### D. 外部資料

目前沒有引用外部論文或網站；若業主希望加入對照，建議的方向是 [Automerge](https://automerge.org/)／[Yjs](https://yjs.dev/)（CRDT，說明為何不採用）與瀏覽器儲存配額文件 [MDN Storage API](https://developer.mozilla.org/docs/Web/API/Storage_API)（持久儲存與配額）。這兩個連結我沒有在本次任務中逐頁查證內容，只作為延伸閱讀的起點。

## 給 distributed-sync.md 的一節（可直接貼進去）

> 建議放在 §6「傳輸抽象」之後，標題：**伺服器不常在線時的使用情境**。

伺服器（或任何「常在」的節點）不常在線時，裝置要靠下列行為仍能用，這一節是從 `docs/design/intermittent-server.md`（#1132）併入的：

1. **單一裝置照常用。** 每台裝置有完整本機副本，離線可讀、改、新增；回來後送出。這一點現有 `/api/sync` 與離線佇列已做到，分散式同步不改它。
2. **兩台裝置在伺服器不在時互看。** 手機與 Tab S9 都在身邊、伺服器關著：兩台直接交換操作（傳輸層可以是加密中繼信箱或 WebRTC，見 §6）。收方依自己的成員資料重驗權限（§5）；收到、尚未被伺服器確認的修改，在畫面上標「待確認」，伺服器回來後以伺服器為準（星狀＝網狀，§7）。
3. **信箱（若選它當傳輸）的限制**：信是加密後的操作，信箱只看到密文、大小、時間；單封 256 KB 上限、保存 30 天（與重複送出保護一致）；圖片等大檔不轉交；金鑰是帳號級，所以**不跨使用者**、不處理多人空間。
4. **被拒絕的修改**進寄信那台的復原區（`FailedWriteRecovery`），不自動重送。
5. **一定要說清楚的限制**：撤權收不回已送出的資料（§5）；時鐘偏差會決定併發結果（§3）；超過 30 天才送出的離線修改，可能被伺服器的重複送出保護（30 天）當成新的而重複套用——引擎的操作編號去重（`ds_ops`）能解決這一點，但在切換前現有佇列仍有此界線。
6. **測試**：#1132 §5 的情境（伺服器停 24 小時、三台各改同一篇、假在線、重開 App、session 過期）可作為 §8 模擬測試台之外的真瀏覽器 e2e；它們依賴 #691、#693 先合併。

威脅模型（簡版）見 #1132 附錄 C；簽章與惡意節點目前仍是 §10-1 的未解問題。
