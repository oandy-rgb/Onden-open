# 單點錨點的搬移成績（補量設計文件 §14 第 12 項）

> 狀態：現行（研究；最後確認 2026-11-02）。

問題：設計文件（`docs/architecture/proposals/block-anchors-2026-11-01.md` §2.2）把錨點說成「單點：起點在區塊開頭，當身分；範圍與父子照排版即時算」。
前一份實驗（`docs/research/block-anchor-mapping-2026-11-01.md`，PR #1174）量的卻是**帶起訖**的錨點，單點那一格是空的（§14 第 12 項）。
本文用同一個方法補量，並把批 0 實際出貨的程式（起訖錨點）放進同一張表。

**一句話結論**：只存區塊開頭的單點錨點，指對率比帶起訖的低約 6–11 個百分點（單看「開頭落在哪一行」也低約 6 個點）；
最大的原因不是搬移，而是**單看一個點算不出這個區塊到哪裡為止**（202／309 條鏈，開頭算出的區塊一開始就和被選的段落不同）。
所以批 0 照出貨的實作存起訖（`from_utf16`／`to_utf16`），不改成單點；若之後要單點，要先決定區塊範圍從哪裡來。

## 方法

沿用 PR #1174 的資料與判準，不另造：

- 資料：這個 repo `docs/**/*.md` 的 git 歷史，修改次數最多的 30 個檔案（`git log --follow`）；每個檔案兩個起始版本，每個起始版本選 6 個單段（長度 ≥ 12 字的段落、標題、清單項目），之後每個版本更新一次，最多 60 步。**這次的資料集比 PR #1174 當時大**（repo 的文件多了），共 **309 條單段鏈、3,538 步**（#1174：309 條、3,379 步）。
- 參考答案：`diff-match-patch` 整篇字元差異一路追蹤原範圍；存活比例 < 0.5 視為「已不存在」。
- 分類：結果範圍與參考答案的重疊率（IoU）≥ 0.8 → 指對；答案存在但回「找不到」→ 找不到；其餘 → 指錯。

| 代號 | 錨點形狀 | 怎麼搬 |
|---|---|---|
| M3s | 起訖（PR #1174 的 M3，對照組） | 字元差異建 `ChangeSet`，起點 `mapPos(assoc 1, TrackDel)`、終點 `mapPos(assoc -1, TrackDel)`；落在被刪區間或相似度 < 0.5 → 用原文找回 |
| P3 | 單點（只存區塊開頭＋原文） | 只搬開頭那一點；搬到哪就取那裡的區塊（連續不含空行的行）；區塊與原文相似度 < 0.5 → 用原文找回 |
| P2 | 單點 | 逐行差異只追開頭那一行，其餘同 P3 |
| PROD | **批 0 出貨的程式**（`services/blockAnchors/mapping.ts` 的 `moveAnchors`，起訖＋原文核對＋「並列不指」） | 無編輯器 `ChangeSet`（等於伺服器自己推的情形）；只有 `valid` 算「指到」，`maybe`／`lost` 一律算「沒指」 |

單點另外用兩種標準看：**整個區塊**（結果範圍對參考答案，與上表同一標準）和**只看開頭**（結果的開頭和參考答案的開頭在同一行；單點錨點當身分用時只需要這個）。

## 怎麼解讀

1. **單點比起訖差，且差距主要在「範圍」而不在「搬」**。同樣只看開頭，P3 仍低約 6 個點，是因為區塊一開始就算不準，搬了之後與原文比相似度（< 0.5）也常失敗，轉去找回時又可能找到別處。
2. **批 0 出貨的程式沒有退步**：PROD 指對 97.6%，指錯 1.7%，比 M3s 的指錯少，代價是 0.7% 找不到加上 maybe 不算指到（被修改碰到的步驟有 11.5% 沒指，換來指錯只有 3.5%）。這與設計的「寧可找不到、不可默默指錯」一致。PROD 沒用編輯器的 `ChangeSet`（本實驗沒有真實編輯器），所以是伺服器自己推的情形；編輯器精確搬的成績見 PR #1174 的表 1。
3. **兩個編輯器路徑的差別不大**：P3（`ChangeSet` 精確搬）與 P2（逐行差異）互相接近，單點的問題不在用哪一種搬。
4. **不能下的結論**：「單點一定不行」。P3／P2 是我定義的最簡單版本（區塊＝連續不含空行的行）；若單點錨點另存區塊的行數或結尾標記，成績可能接近起訖。本文只證明「只存一個點、再靠排版推範圍」這個版本不夠。

## 限制

- 資料是技術文件，不是日常筆記；沒有真實 CodeMirror 輸入（組字、貼上、多游標）；參考答案本身不完美（PR #1174 §3 的人工判讀：它對意見不一的案例只對 16／29）。
- 沒有碰任何正式站資料；沒有 Android／iOS 真機。
- PROD 欄的 `maybe` 一律算「沒指」，是保守的算法；實際產品裡 `maybe` 會讓使用者一鍵確認（批 2 之後）。
- 前一份報告當時的資料集較小（3,379 步）；這次重跑後 M3s 的數字（96.7%／3.2%／0.2%）與前一份的 M3（97.0%／2.8%／0.2%）相近，差異來自資料集變大。
