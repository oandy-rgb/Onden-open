# Eg-walker 合併到底多快（手機能不能用）

> 狀態：歷史紀錄（研究結論；是否進入影子模式由業主決定）（寫於 2026-11-01） 引用的路徑、函式與行號是寫作當時的，現況以程式為準。

研究問題：伺服器之後自己寫 Eg-walker（Gentle & Kleppmann, EuroSys 2025）取代現行行級 diff3（[`bodyMerge.ts`](../../../packages/backend/src/services/eventLog/bodyMerge.ts)），
而分散式同步 beta 裡手機也是節點、也得自己合併——速度與打包大小夠不夠？本文只做量測，**不改任何產品程式**（`packages/*/src` 沒動）；
測試台在 [bench/](bench/README.md)，可一行指令重跑；全部原始數字在 [bench/out/tables.md](bench/out/tables.md)。

## 1. 判準：50 ms 過了沒

**穩態過了，冷啟動沒有餘裕。** 判準情境：Chromium 4 倍降速、200 KB 筆記（UTF-8；約 11.3 萬個 UTF-16 單位）、兩邊各 1000 處（約 1.5–1.7 萬單位操作）、只處理分岔那段（情境 a）：

| 我們的 TS 原型 | 數字 | 對 50 ms |
| --- | --- | --- |
| 穩態中位數（完整跑一次） | **33.8 ms**（p95 43.9 ms） | 低 32% |
| 穩態中位數（之後獨立重跑 5 次，機器安靜） | 31.6–33.4 ms（p95 40.0–52.5 ms） | 低 33–37% |
| 冷啟動：頁面剛載入的第 1 次（7 個全新頁面的中位數） | **54.8 ms**（第 2 次 30.0、第 3 次 31.3） | **高 10%** |
| 同機對照：diamond-types（WASM） | 穩態 25.2 ms（重跑 26.1–29.8）；冷啟動第 1 次 50.0 ms | |
| 同機對照：現行 diff3 | 穩態 86.1 ms；冷啟動第 1 次 196 ms | 高 72%／290% |

- **差多少**：穩態有約三分之一的餘裕；p95 偶爾貼線（最差一次 52.5 ms）；冷啟動第 1 次超過約 5 ms。調整最後一個小地方之前，同條件稍早量過 52–68 ms，之後 A/B 重跑調整前的程式是 37–39 ms、調整後 31.5–36 ms（雲端 VM 是共用的，原因沒查明）。所以請把「穩態約 32–39 ms，偶爾更高」當成誠實的範圍，並在業主筆電與真機再量一次。
- **跟上限比**：作者的 Rust 版 WASM 在同條件下只比原型快約 1.2–1.3 倍（穩態 26–30 ms，冷啟動 50 ms 與原型相同）。50 ms 這條線本身離「WASM 的上限」只有約 2 倍，換 WASM 不會讓判準變輕鬆，卻多 **105 KB gzip**。
- **瓶頸**：成本跟**編輯次數**成正比、幾乎不隨文件大小變（10 KB 搭 1000 處在 Node 是 3.9 ms，200 KB 搭 1000 處是 6.7 ms；10→100→1000 處是 0.5→1.1→6.7 ms）。Node 上一次合併約 5.5 ms：建共同祖先之後 A 支的狀態 1.4 ms、回溯 A＋套 B＋寫文字 3.1 ms；
  CPU profile（扣掉產生資料與測試台後）：項目序列維護（找位置 `findByCurPos` 12%、依 LV 排序的索引 `register` 12%、切 run `split` 8%、切 chunk `fix` 3%）約 35%，文字緩衝 9%，GC 6%，套用／走訪約 15%。
  Chromium 跑同一份 TS 比 Node 慢約 1.4–1.5 倍（同一台機器、不降速；單獨跑該情境 9.1–9.9 ms 對 Node 6.7 ms；整套跑完、JIT 暖過後是 6.2 ms；diamond-types 的 WASM 兩邊都約 6 ms），降速 4 倍再疊上去。
- **要穩定過還需要什麼**（建議，尚未實作）：① 合併前先暖機（預先載入模組並空跑一次小合併；實測第 2 次就降到約 30 ms）；② 在 Web Worker 裡合併，50 ms 就不再等於卡一幀以上；
  ③ 降低每筆編輯的序列維護成本（`register` 的排序陣列 splice、`split` 的 `indexOf`＋splice；上面佔約 35% 的部分）；④ 1000 處是極端：100 處時 4 倍降速只要 7 ms，常態不是問題。
  ⑤ 不需要 B-tree：chunk 大小 16–256 結果相同，瓶頸不是掃描而是每筆編輯的簿記。

## 做法

### 量了什麼、怎麼量

- **三種操作**（每個數字都是多次執行的中位數與 p95，`harness.ts`；先暖機 1–2 次，至少 9 次且累計 1.5 秒，太慢的情境降到 3 次或 1 次，表中以 `*` 標示只量一次）：
  - **(a) 只處理分岔那段**：本機（伺服器或手機）已有 base＋A 分支的文字與歷史，遠端的 B 分支到來。這是我們真正的用法，也是 50 ms 判準看的那一格。
    原型只從最近共同祖先起算（佔位 run 代表 base，不重放 base 之前的歷史）；參考實作用它自己的 `mergeChangesIntoBranch`；diamond-types 用 `Doc.mergeBytes(補丁)`；diff3 用 `threeWayMergeBody(base, B, A)`。
  - **(b) 整份歷史從頭重放**：base 建立＋A＋B 全部重放成文字（diff3 沒有歷史，不適用）。
  - **(c) 載入既有文件＋套一筆遠端修改**：包含解序列化；遠端那筆與本機最後 10 筆編輯並行。原型用自己的格式、diamond-types 用 `Doc.fromBytes`、參考實作沒有格式（以 JSON 重建 oplog，這是它最直接的載入法）、diff3 只要三份文字。
- **環境**：Node v22（本機雲端 VM，Intel Xeon 2.1 GHz，4 核）；Chromium 153 headless（Playwright 1.63），用 CDP `Emulation.setCPUThrottlingRate` 降速 4 倍。
  每次輸出都附 `calibrationMs`（固定的 3000 萬次整數運算）：Node 約 70 ms、Chromium 不降速約 70 ms、降速 4× 約 300 ms，所以降速確實是約 4 倍；業主用自己的筆電重跑時用它對照。
  降速只讓主執行緒變慢，不等於真實手機（記憶體頻寬、big.LITTLE 排程、熱降頻都不同）。
- **記憶體**：每個 case 一個全新 Node 程序，量操作期間 JS 堆積的增加量（semi-space 設很大，幾乎不發生 GC，所以約等於「配置總量」，是峰值的上界）。
  WASM 線性記憶體不在 JS 堆積裡；RSS 峰值增量在準備階段已把峰值推高時會是 0，沒辦法分離，所以 diamond-types 的記憶體只能說「JS 端幾乎不配置」，WASM 端沒有可信的量法。
- **大小**：序列化後的歷史（原始與 gzip）、打包後（esbuild minify、esm、目標 es2020）的原始／gzip／brotli。

### 資料

- **論文的 trace**（`scripts/fetch-data.sh` 下載、固定 commit，不進版本庫）：單人長編輯 automerge-paper（約 26 萬次按鍵）、seph-blog1；
  多人並行 friendsforever、clownschool（各 2 人）、node_nodecc（git 歷史，約 95 萬單位操作）、git-makefile（約 35 萬）。四份多人 trace 都找到了，沒有換檔。
  單位是 trace 的 unicode 字元；非 BMP 字元換成 U+FFFD 讓一個字元＝一個 UTF-16 單位（位置不受影響；本次六份 trace 實際上一個非 BMP 字元都沒有）。
- **合成筆記**（`genNote.ts`，固定種子 `20261101`）：Markdown 10 KB／50 KB／200 KB（以 UTF-8 位元組算；中文一字 3 位元組，所以 200 KB 約是 11.3 萬個 UTF-16 單位），
  含標題、一段一行的多句段落、清單、任務清單、表格、程式碼區塊、中英混排、emoji（含非 BMP）。
  從共同版本分兩支，各自改 10／100／1000 處（`genFork.ts`）：插入詞、刪一段、改一個詞、加一句、刪一句、搬段落，再加約 10% 的**兩邊都碰的位置**（同行不同句、同句不同詞、同一詞改不同字、同處各插一句、一邊刪句一邊改句）。
  編輯先在 base 座標規劃、隨機排定套用順序，再換算成編輯器實際送出的逐步 `[位置, 刪除長度, 插入文字]`（UTF-16）；產生器自我檢查「逐步套用 ＝ 直接取代」。
  「1000 處」是編輯次數，以單位操作（字元）計是 1.5–1.8 萬個。10 KB 搭 1000 處是壓力測試（兩邊幾乎改遍整份），不是常態。

### 我們的 TS 原型（`bench/src/proto/`）

以參考實作為底（因果圖 `causal-graph.ts` 原樣沿用，演算法語意逐步對應：Fugue 版 rightParent、integrate 掃描、curState／endState），只加：

1. **run-length**：連續插入／刪除合成一個 `OpSpan`；序列裡一個 `Run` 代表一段連續編號、狀態相同的字元（參考實作一字一物件）。
2. **跳過沒有分岔的線性歷史**（論文的關鍵優化）：
   - 合併（a）：`findConflicting` 找到最近共同祖先；祖先之前的文件用**一個超大的佔位 run**代表，只在被碰到的位置才切開；祖先之前的歷史完全不看。
   - 重放（b）：先找出 critical version（之前的操作全是它的祖先、之後的操作全以它為祖先），線性區段直接套到文字、不建任何 CRDT 狀態；有分岔的區段才從 critical version 起建狀態、完成後丟掉。
3. **分段陣列取代線性掃描**：項目序列切成最多 64 個 run 的 chunk，每個 chunk 的「目前可見寬度」「最終可見寬度」放在型別陣列，找位置時先掃型別陣列再進 chunk（`seq.ts`）。沒有做 B-tree。
4. **一個 V8 欄位形狀的小調整**：佔位 run 的 LV 起點留在 31 位元整數範圍（2^29，避免 `lv` 欄位被升級成 double），run 的 `chunk` 欄位一開始就指向暫代物件而不是 null。Chromium 4× 的 200KB × 1000 處 A/B（各 3 次）：調整前 36.7–39.0 ms、調整後 31.5–36.3 ms；Node 看不出差別。

沒有分段（V1，單一陣列）時 200 KB／1000 處的 (a) 是 37.5 ms，分段後 6.5 ms（見 2.4 的消融表）。chunk 大小 16–256 差不多，64 是預設。

正確性：`npm test` 隨機產生 2–4 人的並行歷史（預設 150 個種子，我們另外跑過 1500 個），原型的五種設定（預設、不跳線性、單一陣列、極小 chunk、不合 run）的重放結果、
以及從舊版本分頭 `mergeIntoBranch` 的結果，都與參考實作逐字一致；六份論文 trace 中五份與預期文字一致。

### 同一句重疊怎麼在 Eg-walker 之上偵測（`analysis.ts`，已實作並測試）

1. 兩支各自對共同版本 base 做的事用 base 座標表示：刪除→base 區間 `[x,y)`；插入→base 的一個間隙 `p`。Eg-walker 本來就有這些：
   佔位 run 就是 base，被切開的片段順序就是 base 順序，每個刪除操作記得它刪了哪些 LV，每個存活的插入 run 之前累計的佔位單位數就是它的間隙 `p`。
2. base 切成句（句號類標點之後切、換行一定切）。刪除碰到的每一句、以及「落在句子內部（start < p < end）」的插入，算「這一支碰了這句」。插在句與句之間的邊界不算碰任何句。
3. 某一句被兩支都碰了＝同一句重疊＝依業主規則應為衝突；其餘（即使在同一行）可乾淨合。

這個判定只需要合併當下已經建好的狀態，額外成本是走一遍序列；產品化時要決定衝突發生後「留後存的一份並標示」要怎麼從 Eg-walker 的結果還原出「落選的那一份」（目前只能知道哪一句重疊，需要再從兩支各自的版本取出該句文字）。

## 4. 合併結果：diff3 與 Eg-walker（字元級）差在哪

手寫例子（[`src/examples.ts`](bench/src/examples.ts)；`npm run bench:compare` 會印出全部）。base 是
「今天完成同步功能的第一版，測試都通過了。接下來處理離線佇列的重試。最後整理文件。⏎下週開始寫研究報告。⏎」，A 為 diff3 的 current、B 為 incoming：

| 例子 | diff3 | Eg-walker（字元級） | 依「同一句重疊才衝突」 |
| --- | --- | --- | --- |
| E1 同一行、不同句：A「第一版→第二版」、B「重試→重送」 | **衝突**（留 B：「重送」，A 的「第二版」落到衝突清單） | 乾淨：「第二版」＋「重送」都在 | 不衝突 → **diff3 假衝突** |
| E2 同一句、不同詞：A「第一版→第二版」、B「測試→驗證」 | 衝突（留 B） | 乾淨：「第二版」＋「驗證」都在 | 衝突 → **Eg-walker 默默混合** |
| E3 同一個詞改不同字：「第一版」→A「第二版」／B「第三版」 | 衝突（留 B：「第三版」） | 乾淨：**「第二版第三版」**（兩邊的字拼在一起，多一個「版」） | 衝突 → Eg-walker 默默混字 |
| E4 同一點各插一句 | 乾淨：B 的句子在前 | 乾淨：A 的句子在前（次序由 agent 決定） | 不衝突（相鄰、不重疊） |
| E5 同一句中間同一點各插不同字：A「手機」、B「桌機」 | **乾淨**：「手機桌機」（現行 diff3 的 `mergeChars` 把同點的兩段插入都留下） | 乾淨：「手機桌機」 | 衝突 → **兩者都默默混合**（現行 diff3 本來就有這個漏洞） |
| E6 A 刪掉整句、B 改這句裡的詞 | 衝突（留 B：整句還在） | 乾淨但**壞掉**：「…通過了。重送最後整理文件。」（被刪句剩下「重送」黏在下一句） | 衝突 → Eg-walker 默默留殘字 |
| E7 不同行各改一處 | 乾淨 | 乾淨，結果相同 | 不衝突 |

重點：

- **Eg-walker 不會逐字交錯**：Fugue 系保證同一處並行插入的連續文字各自成段（E5 是「手機」「桌機」兩段完整的字）。但兩人改同一句時，它會**默默把兩邊的字都留下**（E2、E3），或留下被刪句的殘字（E6）——這類依業主規則都應該算衝突，所以必須在 Eg-walker 之上加判定（見「同一句重疊怎麼偵測」；`analysis.ts` 對 E1–E7 的判定與上表一致，有測試）。
- **diff3 的假衝突很多**：行級粒度使「同一行不同句」也衝突。合成情境（5 個種子加總；`bench/out/compare.json`）：

| 情境 | 兩邊都碰的句子（依規則應衝突） | diff3 衝突區 | 其中沒有任何重疊句的（假衝突，Eg-walker 能乾淨合） | 重疊句卻被 diff3 默默合併 |
| --- | --- | --- | --- | --- |
| 10KB × 10 處 | 0 | 3 | 3 | 0 |
| 200KB × 10 處 | 0 | 3 | 3 | 0 |
| 50KB × 100 處 | 30 | 71 | 41 | 0 |
| 200KB × 100 處 | 30 | 44 | 14 | 0 |
| 50KB × 1000 處 | 300 | 914 | 637 | 0 |
| 200KB × 1000 處 | 300 | 958 | 671 | 3 |

  （10KB × 1000 處是壓力測試：兩邊幾乎改遍整份，262 句重疊，diff3 衝突區 70 個，且 diff3 單次要 240 ms。）
- 兩邊都沒有衝突時（「同一句沒有重疊、diff3 也乾淨」的案例，10 KB／200 KB × 10 處各 2/5 個種子）結果完全相同；其餘情況 diff3 都有衝突，無從比。差別只在同點插入的先後次序（E4）。
- 合併後沒有出現孤立的代理字（emoji 被切半；有測試）。
- 限制：隨機情境沒有產生「句子中間同一點各插不同字」（E5）這種正好走 diff3 `mergeChars` 的編輯，所以「diff3 默默混合」的真實發生率這裡沒有量到，只在例子裡證明它存在。


## 5. 沒跑的、限制與要小心的地方

- **WebKit 沒跑**：雲端環境下載不到（`npx playwright install webkit` 失敗：`Failed to download WebKit 26.6 (playwright webkit v2359)`）。測試台已支援（`--browser webkit --throttle 1`），
  業主筆電請用 [bench/README.md](bench/README.md) 的 Playwright docker（`--cpus=0.7`）補量；該 docker 指令在這裡**沒有實際跑過**。Firefox 也沒跑。
- **沒有真機**：Chromium 的 CPU 降速只讓主執行緒變慢，不是真的手機（記憶體頻寬、big.LITTLE、熱降頻都不同）。請用輸出的 `calibrationMs` 對照不同機器。
- **雲端 VM 是共用的**：同一份程式不同時段差很多（4× 穩態曾量到 52–68 ms，後來 A/B 重跑只有 37–39 ms）。表中數字是最終版程式、安靜時段的一次完整跑，另附 5 次獨立重跑的範圍；p95 受 GC 影響大。
  Chromium 的計時器粗化到 0.1 ms。
- **參考實作在大情境只量一次或沒跑**：每個操作都要線性掃整份，200KB 情境的 (a) 10.5 s、(b) 38–49 s 只量一次（`*`）；Chromium 降速後超過 Node 3 秒的情境不重跑；
  >3 萬操作的 trace 不跑（git-makefile 另跑一次 128 s）。參考實作的列是在調整原型之前的同一個 session 量的（參考實作程式沒動；重跑的 84 筆輸出雜湊與調整前完全相同）。
- **diamond-types 的位置單位是 unicode 字元、我們是 UTF-16**：轉接層（`impls.ts`）換算；三者合併結果逐字相同（所有合成情境，ref／dt／原型）。(c) 的參考實作沒有檔案格式，載入用 JSON 重建 oplog（它最直接的做法）。
- **只有一個計時種子**（`SEED=20261101`）；結果比較用 5 個種子。合成編輯是我們設計的分布（含約 10% 兩邊都碰的位置），不是真實使用者行為。
- **記憶體**：JS 堆積配置量是上界；WASM 沒有可信量法（見上）。
- **原型不是產品程式**：沒有持久化、沒有權限／事件／復原整合，也沒有處理歷史修剪；`rightParent` 採參考實作的 Fugue 規則；git-makefile 上與 diamond-types 的差異是序號重編造成的（見 2.3 的更正）。
- 單人線性 trace 的重放，原型比 diamond-types 慢 6–8 倍（仍在 25 ms 內）；多人 trace 慢 1.2–3.5 倍。

## 6. 建議的下一步

1. **可以進影子模式**：伺服器端（Node）原型一次合併 5–7 ms（200 KB × 1000 處），比 diff3 的 25 ms 快；小情境本來就小於 1 ms，沒有效能風險。先把並行插入的先後規則定下來（2.3；已查明並建議一條規則，見 [tiebreak-findings.md](tiebreak-findings.md)），再存歷史。
2. **手機用 TS 原型、不用 WASM**：同樣在 50 ms 判準附近，延遲載入 8 KB 對 105 KB，程式也比較容易讓使用者理解與接手。合併放 Web Worker、先暖機。
3. **衝突判定**用「同一句重疊」（`analysis.ts`），Eg-walker 本身不判衝突。需要再設計：衝突後「留後存的一份並標示」要怎麼從結果還原落選的那一份。
4. 真機與 WebKit 再量一次（本文最大的缺口）；若冷啟動第 1 次在真機上仍超過 50 ms，優先做暖機與降低每筆編輯的簿記成本（`register`／`split`）。
5. 歷史格式與修剪策略單獨設計（本文的格式只是估量）：1000 處分岔約 +50 KB；單人 26 萬次按鍵的整份歷史約 0.7 MB（gzip 75 KB）。
