## 一個單位怎麼合（`mergeUnit`）

單位的狀態是它的**頭**（heads）：沒有人在「看過它之後」寫新值的那些寫入。通常一個；兩台互不知情改同一處時兩個以上。
值＝標記最大的頭（`hlc.ts` `compareOps`），其餘內容不同的頭＝一筆衝突，留著（帶它的值）直到有人看過它們再寫。
這是多值暫存器（multi-value register）：狀態只取決於「寫入的集合」，所以交換、結合、冪等，衝突紀錄在每個節點也相同。

規則（逐條對應提案）：

- 較大的標記贏；創世（origin `genesis`、seq 0）輸給任何真實寫入，不算衝突；墓碑是一種值。
- **內容相同不算衝突也不算修改，不管標記是否相同**：兩個頭都留，值與顯示的標記取較大的那個（兩邊一致）。
- 創世對創世而值不同（兩台資料不同源）：不靜靜選一邊，兩個都留成衝突（add-device-snapshot §5 的「未知」）。真實寫入贏過創世值（值照提案），但沒看過的創世值仍留成衝突。
- 同一個 `(origin, seq)` 內容不同、格式不合：**拒絕**，不是衝突，不改變任何東西。標記的時鐘超過本機時鐘 10 分鐘（`DEFAULT_MAX_SKEW_MS`，參數）：**延後**，見下。

### 介面設計比較

| | 甲：只比兩個標記 | 乙（採用）：寫入帶 `saw` |
| --- | --- | --- |
| 輸入 | 本機 `(值, 標記)`、收到 `(值, 標記)` | 同左，每個寫入多一個 `saw`（寫的人當時看過該單位各來源的最大序號） |
| 值與標記收斂 | 是 | 是 |
| 衝突紀錄收斂 | **否**（見下） | 是 |
| 知道「是後續修改」還是「互不知情」 | 不知道 | 知道 |
| 代價 | 無 | 標記多一欄；單位狀態是頭的集合（通常一個） |

甲的反例（`stampedMerge.test.ts`「pinned」那一項，標成預期失敗）：X、Y（看過 X）、Z（看過 Y）。節點 1 依序收到 X、Y、Z 沒有衝突；
節點 2 只有 X、收到 Z：只比標記時分不出 Z 其實接在 X 後面，記一筆衝突，且之後 Y 到達也撤不回。兩個節點的衝突紀錄因到達順序而不同。
`saw` 是**每個單位自己的**：把整列各欄位的 `saw` 合起來宣稱「看過」，會讓別人的修改被誤判成已被取代而丟掉（所以 `*` 只在建立與永久刪除時寫，見下）。
`meta` 放寫入的人才知道的事（搬動前的父層、刪除當時看過的內容），隨寫入走，不參與「內容是否相同」。

呼叫範例：

```ts
const r = mergeUnit(local, incoming, { nowWall: Date.now(), maxSkewMs: DEFAULT_MAX_SKEW_MS });
// r.outcome: "same" | "took" | "kept" | "conflict" | "rejected" | "deferred"（時鐘超前：稍後再送）
// r.write: 這一列顯示的值或標記要改；r.losers: 這次新留下的衝突（輸的值）；r.unit: 合併後的整個單位（要存）
```

## 整列 `*` 與欄位

- `*` 存「這一列怎麼建立的」（欄位名→值）或「永久刪除」（墓碑）。
- 欄位沒有自己的標記時**跟著 `*`**：值與標記就是 `*` 的。欄位自己被寫過就有自己的單位。欄位現在的樣子＝兩者合併（`effectiveUnit`）。
  所以兩邊一個改標題、一個改內文，兩個都留；建立之後寫的欄位贏過它看過的建立值，不贏它沒看過的寫入。
- 本機修改**不重寫 `*`**（只建立與永久刪除）：整列寫入說不出「每個欄位各看過什麼」，說錯就會讓別人的修改被當成已被取代。
- 儲存形式正規化：與「跟著 `*`」相同的欄位單位不存，所以握有相同寫入的兩個節點，存的內容逐位元相同。
- JSON 欄位＝一組叫 `key:<名字>` 的欄位；移除一個鍵＝該欄位的墓碑。

## 這個設計成立的前提（模擬與審查找到的）

- `saw` 只談**自己這個單位**：「來源 o 的序號 ≤ s 的、對這個單位的寫入，我都看過」。所以不同單位的寫入之間不能用 `saw` 比先後
  （兩列的 `config` 同一個鍵是兩個單位：`rules/functionRefs.ts` 把它們都當成互相同時；模擬抓過我自己寫錯的版本）。
- 跟著 `*` 的欄位，標記是 `*` 的、`saw` 是**空的**：建立值只說「我沒看過任何東西」，因為 `*` 自己的 `saw` 談的是 `*` 那個單位。
  這樣一列不必整列一起送，欄位先到、建立後到都成立（審查指出的「重建者看過較晚的 `*`，卻涵蓋掉別人較早的欄位寫入」因此不會發生）。
- 同一個來源對同一個單位的寫入，後一筆一定看過前一筆；所以「每個來源的最大序號」才能代表「看過到這裡為止」。
  這也是為什麼**系統寫入不寫到有衝突的單位**（`writeUnit(..., "system")` 原樣回傳）：只看過勝出的那個頭，`saw` 說不出來，
  之後任何看過這筆系統寫入的寫入都會被當成也看過同來源較早的頭。只有人的寫入（看過所有頭）能結束衝突。
  頂層筆記換空間時伴隨的 `parent`／`sort` 標記也只看過勝出的那一筆，但它寫在一個人的寫入裡，而且照 `saw` 說得出來的範圍把被蓋住的頭（勝出那一筆的來源較早的）在寫的那台也丟掉，所以每台相同（下面「筆記的空間跟著它的樹」）。
- 重新建立一列（`createRow` 遇到已在的列，例如永久刪除後在別台重建、算出來的 id 在第二台又建一次）：新的 `*` 涵蓋舊的 `*`，
  每個本機已有值的欄位另外帶同一個標記寫一筆，涵蓋該欄位的頭；沒看過的寫入留成衝突。
- 創世值也有「看過」：真實寫入的 `saw` 記它看過的創世值（以內容命名）。在 x 上寫 x2 取代 x，不取代另一台的創世值 y；y 留成衝突。
- 標記的時鐘超前超過上限是**延後**（`deferred`），不是拒絕：收件端的時鐘會追上，被延後的寫入要再送一次，而且不可把「我已有某來源到第幾號」記過它。
  一個單位裡只有超前的那一筆延後，其他的照收。拒絕只留給格式錯與同編號不同內容。
- S5 補的創世標記沒有 `saw`：到目前為止沒有任何交換，每個單位只有一個頭，而且是本節點寫的，補成 `saw = {}`（只涵蓋創世）是安全的，不需要重建。

## 跨列規則是「視圖」，不是寫入

`rules/` 的函式輸入是合併後的列，輸出是「要顯示成什麼」與「要通知誰」。不改資料，所以每個節點算出同一個答案、
之後使用者自己改名只是一般寫入。若呼叫者想把結果存成寫入，必須用由輸入算出的固定標記（內文提案 §5 第 5 項），否則兩台各存一筆，合併本身又成了下一個衝突。

## 接上資料庫（只到單位層；第 2a 批，migration 205）

`sync_stamps` 每個單位一列，現在多兩欄：`saw`（寫的人當時在這個單位上看過各來源的最大序號；寫在創世值之上的寫入，用 `genesis:<內容 sha-256>` 指名那個值，
內容文字的算法與 `unit.ts` `genesisContent` 相同：字串＝`s:`＋原文，其他＝`j:`＋canonical JSON）與 `meta`（目前只有筆記的搬動：`{"from": 原父層}`）。
舊的標記（含創世）`saw = {}`，不回填：至今沒有任何交換，每個單位只有一個頭，而且是本節點寫的。

### 兩種儲存設計與取捨

| | 甲（採用）：`sync_stamps` 加欄位，多出來的頭放 `sync_stamp_heads` | 乙：`sync_stamps` 的主鍵加 `(origin, seq)`，一個單位可有多列 |
| --- | --- | --- |
| 既有的讀取（快照、摘要、觸發器的 `ON CONFLICT`、202 的補標記、各測試） | 不變：一個單位仍是一列；「目前值」仍是這一列＋資料表的欄位 | 全部要改成「取較大標記那一列」，每個 `ON CONFLICT` 與 `DO NOTHING` 的意思跟著變 |
| 輸的值放哪裡 | `sync_stamp_heads.value`（欄位本身只放贏的） | 同表，但欄位值與標記的對應要靠另外的規則 |
| 讀「目前值」的成本 | 與以前相同（沒有多的 join） | 每次讀都要挑一列 |
| 代價 | 兩個地方有標記；觸發器寫入時要順手清掉 heads | 主鍵變大，既有的 upsert 全部重寫 |

畫面讀的「目前值」＝資料表的欄位＝標記最大的那個頭的值（`mergeUnit` 的 `unit[0]`）。其他內容不同的頭＝衝突，留在 `sync_stamp_heads`，直到有人的寫入看過它們。
觸發器（本機寫入）在蓋標記時從該單位目前的頭算出 `saw`，並清掉其他的頭（本機寫入看過這個節點握有的一切）。

### 單位的讀與寫

- `readUnit(workspace, address)`：資料庫裡某個單位 → 核心的輸入（`Unit`）。值一律是文字（欄位的文字形式）或 null；`*` 是 `{}` 或墓碑（建立值不存，所以兩個節點對「建立標記說了什麼」不會不同意）；沒有自己標記的欄位帶著所屬列的建立標記、`saw` 為空。
- `mergeUnitsIntoWorkspace(workspace, units, gate?)`（`spine/stampedImport.ts`，唯一讓觸發器讓開的入口，和快照匯入用同一個開關，`reason: "merge"`，計入 `sync_clock.merge_batches`）→ `storeMergedUnits`：逐單位 `mergeUnit`，有變的寫回（贏的值寫進欄位、標記與 `saw` 寫進 `sync_stamps`、其他頭寫進 `sync_stamp_heads`）；回報 `events`、`rejected`、`deferred`。**時鐘超前（`deferred`）不寫、不推進任何進度**，呼叫端晚點再送。
- 沒做：新增或移除整列、JSON 單位（`key:…`）、搬動以外的 `meta`、領域副作用（搜尋索引、連結、區塊錨點）、誰可以寫（來源的檢查在呼叫端）。
- 系統與背景工作的寫入：核心遇到有衝突的單位不寫（`writeUnit(..., "system")`）。資料庫那一端也一樣（下面「系統寫入不解決衝突」）：系統工作與 AI 的寫入由 `stampTransaction` 在標記上註明 `system`；**不在任何根寫入裡的寫入**（沒有 `mutate`、沒有 `stampTransaction`：它的標記由 `sync_allocate_stamp` 給，沒有作者）自 migration 221 起也註明 `system`，所以也不解決衝突；同一個交易之後的根寫入（`stampTransaction` 補上作者）照它自己說的算（`syncSystemWriteConflict.integration.test.ts`）。

### 一個包說什麼

- 每個數字都是**每個標籤、每個來源**一個（`spine/stampedBundle.ts` 的 `Have`：`{ 標籤: { 來源: 號碼 } }`，資料形狀 6 起；之前是每個來源一個、取所有標籤的最小值）。`base`：收的一方說它握有的（每個標籤、每個來源：連續握有到第幾號）；`holds`：送的一方在切點握有的（包裡的標記都不超過它）；`upTo`：收的一方收下這包之後握有的，等於 `holds`，除非有寫入被扣下（下面「讀者範圍外的寫入」：停在那個來源第一筆被扣下的寫入之前）。包裡有每個來源在 `(base, holds]` 之間、這個範圍的每一個寫入（被覆蓋的舊寫入不在：覆蓋它的寫入看過它），被扣下的除外。
- 一列只要有一個標記超過 `base` 就整列送（它所有的標記與 saw、meta、其他的頭，以及每個單位的值的文字），收的一方不必再問。刪掉的列是墓碑。
- **切點為什麼不會漏**：序號在工作區的事件鎖與 `sync_clock` 那一列之下取，鎖到交易結束才放，所以同一工作區的序號依序取、依序提交，較大的序號不會比較小的先提交。
  讀包時切點（`next_seq - 1`）與標記在**同一個唯讀快照**讀（`withActorReadSnapshot`）；不加鎖，讀不讓寫的人等。`stampedBundleCut.integration.test.ts` 在真的 Postgres 用兩條連線證明，並且在讀的中途提交一筆寫入，確認它不在這個包裡也不超過切點。
- 收的一方拒收整包（沒有任何東西留下）：資料形狀版本不同（`bundle_data_shape`）、送的人不是它收過的來源（`bundle_unknown_sender`；快照的來源，或 `admitSyncNode` 收進來的節點，或由已收的送的人帶來的來源）、起點超過它握有的（`bundle_gap`：改拿快照）、同一個（來源、序號）內容不同（`bundle_stamp_clash`：還原備份或複製設定檔）、送的人說它握有這個節點自己從沒寫過的序號（`bundle_own_origin_ahead`：這個節點被還原了）、時鐘超前（`stamp_clock_ahead`：稍後再送）、工作區正在加入（`merge_not_open`）。
  同樣的包再套一次什麼都不改。
- **`bundle_stamp_clash` 抓得到與抓不到**：抓得到——接收方的單位還握著那個標記：A 寫了標題（A, s），B 收下；A 被還原後又寫出（A, s）但內容不同，並多寫一筆讓這一列被送出 → 同一個（來源, 序號）內容不同，整包拒收（`stampedBundle.integration`「the same (origin, seq) with other content」）。
  抓不到——接收方的單位已經被後續寫入蓋掉：A 寫了（A, s）又寫了（A, s+1），B 只握有後者；還原後的 A 再寫出（A, s）不同內容 → 後者的 `saw` 已涵蓋（A, s），沒有東西可比，整包照收（已釘成測試：預期不拒收，`what bundle_stamp_clash cannot see`）。
  解法是還原後換新的節點編號：伺服器（`scripts/restore.sh`，任何年代的備份；換不了就拒絕）與桌面版（`packages/desktop/src/nodeRenewal.mjs`）都做了，見 [deploy.md「還原」](../../../../../docs/agents/deploy.md)。

### 收不進去：三個原因、一個出口

一個節點的本機歷史「照原樣收不進去」有三種：**時鐘超前**（`stamp_clock_ahead`，回報對方的讀數、本機時間與差距；存下來的 `hlc_wall` 只會取大，把時鐘調回來也解不開，`stampedBundle.integration`「a clock that was 30 minutes ahead and is set right again」釘住）、
**被還原**（`bundle_sender_restored`：收的一方握有送的人沒寫過的序號）、**離線太久**（`bundle_gap`：起點超過收的一方握有的，改拿快照；`stampedBundle.integration`「a node that was offline for too long」釘住：送的一方沒有收的一方缺的那一段，整包被拒、什麼都不寫）。三個的出口是同一個：該裝置換一個新的節點編號，把還沒被任何人收下的寫入用現在的時間重新蓋章再送——**這一批不做**，不另外發明「等時間到」或「放寬上限」的路。
`readUnsendable`（`spine/stampedBundle.ts`）是同一個結構的讀取函式：每個原因一筆 `{reason, writes, aheadMs?}`；今天只有 `clock_ahead` 能從本機資料算出來，另兩個要等有人拒收時才知道，還沒有東西把那個答案存下來。

### 刪除之後再建立

永久刪除寫一個墓碑，它的 `meta.seen` 是刪的人當時看過的（每個來源最大的序號）。同一個 id 再建立時，新的 `*` 把這個 `seen` 帶在自己的 `meta`（migration 206 的觸發器與 `createRow`），
所以**刪的人看過**的欄位寫入不再是新值旁邊的頭（`droppedBySeen`，`store.ts`）；刪的人**沒看過**的寫入留下，成為衝突（它的作者看得到）。收到永久刪除時，沒看過刪除的寫入不再有列可存：回報在 `lateEdits`（`rules/trash.ts` 的 `recoverLateEdits`），由呼叫者還給作者。

### 4.9 在已刪除父層底下的筆記：定案是「檢視」，不是寫入

`storeMergedRows` 的回報有 `orphaned`（哪些活著的筆記的父層已被**永久刪除**：它們跟著父層的刪除走；把它放到那裡的寫入——建立或搬進來——刪的人沒看過時通知寫的人）與 `notices`（要通知誰，含刪除時沒看過的修改），由 `rules/trash.ts` 從每個節點都有的戳記算出，所以每個節點答案相同；**不寫入**。
資料庫這條路（`dbRows.ts` `orphansOf`）**只回報**，而且只看**永久刪除**的父層；**沒有人讀這兩個回報**。父層只是丟進垃圾桶（`deleted_at`，可以還原）時，晚到的子筆記「跟著最近的已刪除祖先進垃圾桶」這條檢視（`rules/trash.ts` `trashOrphanedChildren` 的 `placed`）只在模擬器（`mergeCrossFieldSim.test.ts` R4）裡算，資料庫沒有接上：那則筆記在這台是活的、在它已刪除的父層底下（見「接上傳輸前必須完成」）。
為什麼不是寫入：衍生的修正必須是已複製狀態的純函式；若每個節點各蓋一筆「放進垃圾桶」的寫入，各自的戳記不同，兩邊就不再相同，也無從決定誰的那筆勝出。
還沒做的是**讀取**：清單、樹、搜尋今天還不知道這個檢視，會把孤兒筆記當成普通的頂層筆記；`stampedBundle.integration`「rule 4.9, the READ」用 `it.fails` 釘住，擋在 2b-2／畫面那批。

### 系統寫入不解決衝突

系統／背景工作（`systemJobOf`，`stampTransaction` 把 `system: true` 放進標記設定）寫到有其他頭的單位，資料庫拒絕（`sync_unit_in_conflict`，409，可重試）；人的寫入看過所有頭，照舊取代。這一批不另設重試上限：從 outbox 跑的工作是一般的可重試失敗，沿用 outbox 的額度（`RETRY_DAY_ATTEMPTS`，約一天，之後進入看得到的死亡列）；不是 outbox 的工作直接以 409 失敗（`syncSystemWriteConflict.integration` 釘住）。

範圍從 `content_nodes` 擴大到 `dbUnits.ts` 的 `UNIT_SOURCES`（一份資料：每張表的列鍵、工作區、欄位，守門 `stampedBundleSources.integration.test.ts` 對照資料庫裡標記觸發器的參數）與 `JSON_SOURCES`（JSON 欄位的鍵，一鍵一個單位）。

- 看板的區段（`node_attributes._canvas_sections`）**跟著走**，一個單位：屬性的 `value`（照一般單位合併：較晚的寫入勝，另一邊留成頭，每台相同；不逐個區段合併）。一份資料只有一種單位：migration 209 之後觸發器與起始標記都不再逐區段蓋章；
  之前留下的逐區段標記不刪、不改寫，摘要、快照與修改包都不讀它（`snapshotTables.ts` 的 `RETIRED_STAMP_LABELS`，守門 `stampedBundleSources.integration.test.ts`）。沒有任何讀者用過逐區段的標記。`content_nodes.collection_views` 是凍結欄位（沒有寫入者），不需要。
- 集合（`workspaces.modules_off`／`modules_confirmed`）**跟著走**：一個元素一個單位（在／不在），和 JSON 鍵同一個機制；寫回時排序存放，本機寫入也由 migration 209 的觸發器排序存放，所以相同的單位就是相同的位元組。
- `block_node_tags`：2b-2a 時掛在還不跟著走的段落（`block_nodes`）上；migration 215 起段落列跟著走，它也跟著走（下面「錨點與段落列跟著內文那筆寫入走」），`NOT_CARRIED_YET` 現在是空的。

列層的新規則：

- **掛在被永久刪除的筆記上的列**（屬性、標籤、指標、卡片位置、功能引用；錨點、段落列、錨點單位另有自己的規則，見下面「跟著筆記走的列」）：資料庫拒絕（外鍵），不建列；它的標記照存，**而且照樣跟著包走**（沒有列的標記也送），所以每台握有相同的寫入。規則 4.9 的檢視 `hanging`（`rules/trash.ts` `rowsOnDeletedNotes`）列出它們並通知建立的人（刪的人沒看過的才算）。不寫入、不在各台各蓋一筆刪除。
- **同一個衍生 id 在兩台各建**（指標、Onden 自己建的功能引用）：一列，輸的建立值留成頭。**人加的功能引用** id 不是衍生的，兩台各加同一個功能會撞唯一索引：留建立較早的那一列（`mergeDuplicateRefs`，每台相同），另一列不在表裡、標記照存，config 逐鍵併入是檢視（`duplicateRefs`），不寫入。
- **沒有列的標記也送**（列不在表裡就送它的標記；在表裡但不在讀者範圍內的不送，而且**扣下**：包的 `upTo` 停在那個來源第一筆被扣下的寫入之前，見下面「讀者範圍外的寫入」）。這只對握有整個工作區的讀者成立；**分空間的包（#1769）不能照這條送**：不在讀者範圍內、而且已刪的列的標記會洩漏它存在過，那一批要自己決定。
- **JSON 的鍵**：一鍵一個單位，第一次寫入的 `saw` 是空的（不是「跟著建立」）。列不在時鍵的標記照存（刪除觸發器在刪的那台留下鍵的墓碑）。標籤 schema 的鍵也算筆記的 `updated_at`（migration 209 重新定義 `sync_touch_updated_at`）。

### 成本：每一筆都照現在的表規劃

一包在一個交易裡讓表從小長大，查詢規劃器的統計卻還是交易開始前的（交易中不會有 autovacuum，PGlite 根本沒有）：快取的計畫（外鍵檢查、觸發器的查找）一直是整表讀，按鍵找一列的寫入走工作區的索引——每多一列就多讀整張表。
所以合併的交易內 `plan_cache_mode = force_custom_plan`（`stampedImport.ts` `openMerge`），一包在一張表建了 100 列以上就在交易內 `ANALYZE` 那張表（`dbRows.ts`）；讀包時每張表的變動鍵只找一次、每塊 10,000 列。
`stampedBundleScale.integration.test.ts` 斷言資料庫讀的列數（`pg_stat_user_tables`），不斷言時間。讀包的一端（寄件那台）也需要新的統計：`readBundlePages` 在讀之前，對包會讀的每一張表（`sync_stamps`、`sync_stamp_heads` 與每一張帶走的表）照 autovacuum 的預設門檻判斷統計是否過時（從沒分析過、分析後改了超過 50＋10 % 的列，或表在磁碟上的頁數和上次分析看到的差了 8＋10 % 以上：改動數在累計統計裡，PGlite 每次重開都丟掉，PostgreSQL 不乾淨的關機也丟），過時就在讀的那個唯讀快照裡 `ANALYZE`（`spine/senderStatistics.ts`）。伺服器的 autovacuum 讓每張表都在門檻內，所以什麼都不做；桌面版與瀏覽器版（PGlite，沒有 autovacuum）在要讀的時候得到伺服器會有的統計（`stampedBundleScale`「a sender with no statistics at all」，之前同一個設定 5 次有 3 次讀 14.4 倍的列）。
套用端的 `ANALYZE` 不需要比套用更多的權限，也不會讓套用失敗（本機 Postgres 16.15 實測）：表的擁有者以外的角色執行時只有一個 WARNING（`permission denied to analyze "…", skipping it`），交易照常提交——那時只是統計沒更新、成本回到修之前；
`ANALYZE` 可以在交易區塊內執行（`VACUUM` 才不行），在唯讀交易裡也可以，之後同一條連線的語句照常。PGlite 以超級使用者執行，沒有權限的問題。

### 接上傳輸前必須完成

（PR「fix/merge-space-follows-parent」加的十三項在最前面；之前的照舊。）

- **誰可以成為寄件者還沒有撤銷，也有兩個邊角**（第 2 批審查第 1 輪 C；配對那一批，第 8 批，要定）：`admitSyncNode` 把 `vouched_by` 是某個節點編號的列升成寄件者——
  快照來源的**舊編號**（加入時以 `vouched_by` ＝ 來源記下）也是這種列，admit 它就會讓一個已經不用的編號變成寄件者；admit 一個 `self-restore` 的編號什麼都不做、不報錯，
  呼叫者之後才在收包時看到 `bundle_unknown_sender`；程式裡沒有撤銷，撤掉一台時「由那一台擔保的列」（它帶來的來源）怎麼辦也還沒定。
- **重建的列在收件那台多一個欄位標記，寫的那台沒有**（自己的裝置之間的交換第 2 批用新種子找到，還沒修，屬於合併核心 `dbRows.ts`）：A 握有一則筆記的 `deleted` 欄位標記，
  它的（來源、序號）和那一列重建時的 `*` 相同（B 的同一筆寫入）、`saw` 是空的；寫的那台 B 沒有這個欄位標記（欄位跟著 `*`）。兩台的值相同、標記集合不同；
  這個標記在 B 的 `have` 以下，所以之後只有在另一筆寫入讓那一列整列送時才到得了 B，從 B 加入的 C 永遠收不到（A 給 C 的包不送它），整份重送存 1。
  重現：`SNAPSHOT_BROUGHT_SEED=31054` 在真 Postgres 上跑 `snapshotBrought.integration.test.ts`，`--sequence.seed=1795315587520`（「P3」紅：A 與 C 的 `content_nodes` 標記差 1）。
  產生器的全域狀態（`stampedBundleWorld.ts` 的 `ROW_TURNS`）讓單跑 P3 時寫入不同，所以要整個檔、同一個順序（那個檔現在每個測試先 `resetRowTurns`，種子每次新的，這個順序已經不存在）。
  手寫的幾種「永久刪除再以同一 id 重建」順序裡，收件那台確實會寫出這個欄位標記（A 把 N 丟進垃圾桶、B 沒看到就永久刪除再以同一 id 重建；收到時 A 的 `deleted` 換成 `(B, 重建的序號)`、`saw` 空），
  但之後那一列都被整列送過去，兩台、三台都相同；永遠送不到的那一步還沒找到，所以沒有 `it.fails` 釘住。`snapshotBrought` 的隨機寫入先關掉 `recreate`，修好之後打開。

- **擴大範圍時，讀者握有的進度以下、範圍外的舊列不會補送**：I5 只管「包扣下的寫入」（下面「讀者範圍外的寫入」）。一個節點用快照加入時沒拿到的空間（快照就不帶），之後讀者成了那個空間的成員，那個空間裡在它 `have` 以下的列（空間本身、舊筆記）永遠不會送；只有之後的寫入會到，掛在不在的空間上的筆記建不起來。範圍變大時要整份重送那些列（或分空間的 `have`）。
- **`upTo` 被扣下時，每一包都再送同一段**：被扣下的寫入之後那個來源寫的，每一包都會再送一次（收下不改任何東西），直到讀者讀得到。一個讀者永遠讀不到的空間（別人的個人空間）會讓這段一直長。解法是「已知缺口」清單（`have` 帶著扣下的序號），傳輸那一批決定。
- **不在任何根寫入裡的寫入，碰到有衝突的單位會 409**（migration 221 之後；PR #1940 第 1 輪第 8 點）：`sync_clock.writes_without_mutate` 數到的那些產品路徑，若一個人的動作經過其中一條、又碰到有衝突的單位，拿到的是 ON001；在 `withEventTransaction` 之外的寫入不會被翻成 `sync_unit_in_conflict`（409），是原始錯誤。交換打開之前要清點這些路徑（每一條改成走根寫入，或接到第 7 批「衝突的最小畫面」）。
- **大子樹換空間的成本在 slug，不在推導**（PR #1907 第 1 輪第 13 點，量過，PostgreSQL 16）：1,000 則（深約 7 層）搬到別的空間，收到的那台 1.5 秒、3,052 個語句，其中推導 14 個（每層一個向下、一個載入），3,003 個是給 slug 的那一步每則三個（查、查撞名、寫；4a 批起是 `spine/noteSlugs.ts` `settleSlugs`，撞名時還多讀「佔」的標記）；同一棵樹改最深那則的內文 20 毫秒、35 個語句。300 層的一條鏈：每層兩個語句（向下一層、向上一層），收到 0.5 秒。要變快：`settleSlugs` 改成整批（照 id 順序在記憶體裡模擬撞名），祖先改成一個遞迴查詢。
- **跟著樹換空間的筆記沒有通知**：回報在 `followedSpaces`（誰的筆記因為上層搬走而換了空間、能讀到它的人跟著變），沒有人讀；給 2b-2b／畫面。被留下的空間刪除（`keptSpaces`）一樣。
- **寫下的空間這台沒有**：推導用預設空間（每台相同）；沒有產品路徑做得出來（空間的列從不刪），所以沒有測試。
- **4.9 在丟進垃圾桶的父層底下**：資料庫只回報永久刪除的父層（上面 4.9）；父層在垃圾桶裡、晚到的子筆記仍是活的，打開父層的人看不到它，讀取（清單、樹、搜尋）把它當普通筆記。模擬器裡的檢視（跟著最近的已刪除祖先）要接到 `orphansOf` 與讀取。
- **被扣下的不只別人的個人空間**（I5，下面「讀者範圍外的寫入」）：別人的個人列（`node_positions`、`actor_module_settings`、RSS、外部行事曆的列）與擁有者不是成員的已刪除空間，讀者永遠讀不到，`upTo` 會一直停在它們之前。裝置自己寫的列，之後離開了擁有者的範圍（搬進擁有者不是成員的空間），永遠送不到中心，現在還會讓中心給它的 `have` 停住。要「已知缺口」或分範圍的 `have`。
- **被留下的空間（kept）的檢視不是每次都重算**：`spaces_show_deleted` 只在合併之後、和活的筆記**離開**那個空間時（`content_nodes_left_kept_space`，只接 UPDATE）重算；筆記**進入**、還原、DELETE 時不算。本機重算把空間翻成已刪除時沒有推進 epoch、沒有事件，用戶端停在舊畫面直到下一次同步。
- **合併把丟進垃圾桶的筆記帶進「寫下已刪除」的空間**：空間顯示為已刪除（裡面沒有活的筆記），垃圾桶裡的那則打不開，也沒有清除或搬走的入口。
- **永久刪除底下有筆記的標籤**：標籤那一列已經不在，`content_nodes_at_top(OLD.parent_id)` 讀不到它是標籤，觸發器 4 把那些筆記當成「從不是頂層變成頂層」，多蓋一筆 `space`（值不變），走 `sync_stamp_put_over`，清掉 `space` 的其他頭。產品沒有路徑把筆記放在標籤底下（`services/parentKind.ts`），沒有修（PR #1907 第 2 輪第 5 點）。
- **碰到「很多筆記曾從它搬出去」的那一則，每包都多讀那些筆記**：`effectiveSubtree` 的候選查詢讀出獲勝的 `parent` 寫入 `meta.from` 指向邊界上任一則的每一則（加上它們的祖先），多半不是被切環放回來的，載入後丟掉。量過（PostgreSQL 16）：一則收件匣曾有 1,000 則筆記搬出去，改它的標題的一包在收到的那台 49 毫秒、32 個語句、讀回約 2,000 列。要省：候選只取在環上的（要先知道哪些在環上），或把「被切環放回」記成自己的索引（第 2 輪第 6 點）。
- **推導只寫受影響的筆記，不寫它們的祖先**：一則頂層筆記存下的 `space_id` 只有在「寫下的空間這台沒有、之後才有」時會舊掉（推導用了預設空間，空間那一列後來才到，沒有東西讓它重推），之後它底下的筆記的一包會在延遲檢查失敗。到不了：讀者能讀一則筆記，就是它是那則筆記所在空間的成員，空間那一列在同一個範圍、同一包裡先寫（`UNIT_SOURCES` 父表先）；快照也一樣；空間的列從不刪。本機寫入讓頂層筆記的 `space_id` 一直等於寫下的（觸發器 2）。所以沒有釘測試（第 2 輪第 7 點）。
- **4.9 的 `seen` 只能決定通知誰**：刪除帶的 `seen` 是刪的人握有「被刪那一列」的進度，網路不按順序到時會說得比實際多；通知可能因此少發，沒有修。

- **範圍同步的包不能沿用「筆記不在就是刪了」**（`rowsThatGo`、migration 215 第 2c 節）：收件那台沒有那則筆記可能只是不在範圍內；那一批要決定跟著筆記走的列怎麼辦（上面「跟著筆記走的列」）。
- **錨點單位有兩個頭時，那則筆記「不是人」的寫入被拒**：單位在寫錨點的語句結束時寫，系統或 AI 的寫入（`stampTransaction` `notAPerson`）對有其他頭的單位丟 `sync_unit_in_conflict`（409），是那個語句失敗（`anchorsReplicated`「round 3, 7」；第四輪前是 COMMIT 才失敗）。人看不到這個衝突（沒有畫面讀 `sync_stamp_heads`）；人的下一次存檔會把那些頭解決掉。給 2b-2b：衝突要有畫面。
- **一包在一個交易裡收**（第 5 項的後半）：收件檢查是每張表、每一段一個語句（`checkReceived` 的 `columnProblems` 與 `carriedValuesDiffer`；一段至多 4 MB 的 UTF-8 JSON，所以語句數隨包的位元組長，每個語句的大小不隨包長），但一包仍是一個交易，PGlite 上收大包時本機存檔要排隊；分段收（`sync_inbox`）是傳輸提案的第 6 批。
- **大量刪除仍比 main 慢**（後續，第五輪第 6 點與第六輪第 6 點）：跟著筆記消失的錨點、段落列、單位不寫墓碑，連同它們的標記一起清掉（下面「跟著筆記走的列」），每一列不再各呼叫一次觸發器（語句層級）。刪一個 2,000 則筆記、每則 20 個錨點與 20 個段落列的空間（`anchorBulkCost`），寫的列＝main 的＋那些列原本的標記（82,500，刪掉）＋每則筆記的單位一列（斷言），時間見 PR 說明「測試結果」（和 main 比的倍數在那裡，只有一個數）。產品的寫入有 15 s 的 `statement_timeout`（`PG_STATEMENT_TIMEOUT_MS`），`purgeSpaceDeleted` 是一個語句：大到碰得到的空間要分批刪，這是後續（沒做）。
- **一則筆記的錨點數沒有上限**：找不到的錨點永遠不刪，寫入端也沒有上限，所以收件端無從定一個（審查第 6 點；沒做）。
- **兩台同時替同一個新段落各鑄錨點**：兩個錨點、兩列、兩個任務；下一次存檔依錨點的建立時間（鑄造那台的牆上時鐘）留一個、藏另一列、把它的任務丟進垃圾桶（`anchorsReplicated`「9」釘住）。規則（提議）：兩個有效錨點落在同一段時合成一個，任務與卡跟著留下的那個。 **第 1 批沒做**：那條規則要先決定被合掉的那一個任務自己的修改（到期日、完成、複習卡的進度）怎麼辦，每一種選擇都是產品的行為，不是合併的機制；今天的結果每台相同（下一次存檔的寫入內容相同、標記不同，不算衝突），所以照舊釘住，等業主選。 **已決定 (a)，2026-11-22**（業主）：留下的那個任務吸收另一個的欄位，逐單位取較新的，複習卡的進度同一條規則；另一批做（需要 4c 的「任務為準」），在那之前照舊釘住。
- **外鍵清空的欄位，被指的那一列之後以同一個 id 再建**（第十輪第 4 點）：B 離線在筆記 P 下建 K；A 永久刪除 P，送到 B（K 的父層清空，標記留著 P 的 id）；A 以同一個 id 再建 P（日記的 id 由日期算出）；K 這時才到 A，A 把 K 建在 P 下。兩台標記相同，K 在 A 在 P 下、在 B 在最上層，永遠如此（`anchorsReplicated`「round 10, 4」，`it.fails`）。方向：欄位跟著這台握有的頭與列走，之後建出的列把標記留著 id 的欄位補上。`task`／`detached` 是同一類（方向相反）；`spaces.owner` 指的 `actors` 不跟著包走，「不在」可能只是「還沒到」，也是這一類。 **第 1 批沒做，照舊釘住**：會收斂的規則是「欄位＝勝出的值，那一列在這台時；不在時是 NULL」，所以那一列以同一個 id 出現的每一條路都要把留著它 id 的欄位補上：合併建列做得到（之後推導空間）；但這台**自己**再建（收過永久刪除的那台又打開同一天的日記）時，補 `parent` 等於在一次普通的存檔裡把那則子筆記連同整棵子樹搬進新父層的空間，只做合併那條路就是半條規則（再建的那台不補、收的那台補：又不同）。反方向「清空了就一直空」也不收斂：第四台握有舊的 P 底下的 K、從沒收到刪除，它把 K 送出時帶的是 P，收到的那台有新的 P 就建在 P 下，留著空的那台不動。 業主會碰到的樣子（PR #1940 第 1 輪 C）：一個人、伺服器加桌面版時很少見——離線的桌面版在日記底下建了筆記、伺服器上那天的日記被永久刪除、桌面版同步之前又重開同一天——結果是那則筆記在兩台的位置不同（一台在日記底下、一台在最上層），不丟資料，手動搬一次就一致。
- **永久刪除後以同一個 id 再建，對上另一台已被結掉的 `deleted` 頭，兩台的頭不同**（PR #1940 第 1 輪 CI 補充，#1937 的 CI 以種子 416864270 找到，main 上就有）：A、B 各自把丟進垃圾桶的 X 取消丟進垃圾桶（交換後兩台都握兩個 `deleted` 的頭）；A 再丟進垃圾桶（人的寫入，結掉兩個頭）、永久刪除、以同一個 id 建回（建立的 `meta.seen` 只有 A 自己的寫入）；兩邊交換兩輪都收下，B 仍握著自己那個取消的頭（值 false），A 沒有，再交換也不變。手寫的決定性情境：`stampedBundlePlanted`「a note purged and made again under its id on A, after A and B each undid its trash」（一則 `it` 斷言前置條件與 B 多出的頭，一則 `it.fails` 斷言兩台相同；PR #1940 第 2 輪第 1 點）。推論、沒追進程式：永久刪除把 X 的標記一起拿掉，建立的 `seen` 沒帶 A 已經看過的 B 的寫入，所以 B 那邊沒有東西丟掉那個頭；A 的 `have` 已經涵蓋它，B 也不會再送。
- **筆記以外的帶標記的表，`updated_at` 不是標記的函式**（PR #1940 CI 補充，種子 142069）：`content_nodes` 的 `updated_at` 是它算數的標記裡最新的牆上時間（migration 206／209 `sync_touch_updated_at`），別的表（`node_attributes` 等）是寫那一列的時間——寫的那台是自己的時鐘，收的那台把包寫回已有的列時是收的時候。所以握有相同寫入的兩台，`updated_at` 不同（`snapshotBrought`「updated_at of an attribute」，`it.fails`；P2 的比對把這一欄當已知的差異另外比，`stampedBundleWorld.ts` `UPDATED_AT_OF_ATTRIBUTES`）。修法同筆記：每張帶 `updated_at` 的帶標記的表，值＝它算數的標記裡最新的牆上時間，本機寫與收包寫回同一個函式；那會改變單一伺服器上這一欄的寫法，所以不在這一批。
- **起始（genesis）標記的列，任務跟著建立走，筆記與任務都永久刪除**（第十輪第 5 點）：資料庫先清空任務再刪列的那一台，`sync_keep_emptied_id` 加一列任務的標記（起始建立的複本，留著任務 id）；先刪列的那一台沒有。起始標記不會在任何 `have` 之上，交換不送；整份重送才送，收的一方存下來，兩台不同（`anchorsReplicated`「round 10, 5」，`it.fails`）。今天正式伺服器上每一列都是起始標記；傳輸那一批要定：起始的列不加這一列，或整份重送不帶起始標記。
- **別的表：收件那台的連鎖清掉欄位標記，刪除的那台留著**（第十輪第 7 點）：B 設了筆記 N 的屬性又改，A 永久刪除 N，B 的寫入之後才到 A。A 不握有那一列，留著那些標記（沒有值，上面「別的表不留值」）；B 收到 A 的刪除時列被連鎖刪掉，刪除觸發器清掉那一列的欄位標記（合併不寫自己的墓碑，`sync_stamp_put_over`），建立的標記留著。所以 A 有 B 的值的標記、B 沒有；交換不再送（在 B 的 `have` 之下），整份重送才送，B 存下（沒有值）。沒有拒收、沒有留下字，兩台的標記不同（`anchorsReplicated`「round 10, 7」，`it.fails`）。第五到十輪的測試裡，整份重送會再存的別張表單位只有這一個（對所有表的標記在 `resendAll` 前後比對）。
- **215 之前各台各自衍生的錨點與段落列**：起始標記假設每台握有相同的列；今天只有快照加入（兩台的列來自同一份），沒有影響。已經各自衍生過的兩台要對齊，傳輸那一批要先定做法。
- **包的大小**：一次內文寫入帶一則筆記的一個錨點單位：50 個錨點 16.0 KB（gzip 2.7 KB）、200 個 61.9 KB（gzip 9.1 KB），未壓縮時一個錨點約 0.3 KB；快照與包都不壓縮。壓縮或不重複帶文字，傳輸那一批決定。
- **三則以上同時被搬或還原進一個空間、要同一個 slug 時，兩台的後綴可能不同**（4a 批，PR #1941；`receivedDerivation.integration`「slugs, NOT SETTLED: three notes moved into one space at once」`it.fails`）：因位置讓位的那則拿「第一個空的」，看的是這台的狀態。被搬或還原的筆記的基底 slug 沒有任何單位握著，所以這一批做不到。**slug（或「這筆寫入要的 slug」）在第 5 批成為單位**時收斂（note-91 決定，2026-11-22）。
- **內文寫出的值撞上另一台的 `derived` 預設列：`bundle_unique_clash`**（PR #1941 最後審查）：一台握有某個（筆記、鍵）的 `derived` 列（欄位預設、`_block_autotag`、`_import_*`：不是單位），另一台的內文把同一個鍵寫成 `markdown`（migration 223 起是單位）；帶過來的列撞 `(node_id, key)` 唯一鍵，整包被拒。`ui` 的值在 main 上已有同一類；223 把它擴大到內文寫出的值。要定的是「單位的列進來時，同一鍵不是單位的列怎麼辦」（讓位、合併或保留）。
- **`bundle_derivation_failed` 把程式錯誤也變成永久拒收**（4a 批，PR #1941）：收尾的每一步把「每次重送都一樣」的失敗包成有代碼的拒絕（`spine/receivedDerivation.ts` `deriving`），一個衍生的程式錯誤因此讓同一包每次都被拒、兩台的交換卡住。打開交換之前要有「這包卡在哪一步、哪幾則筆記」看得到的出口，修好程式之後能重試（拒收碼與訊息已經指名步驟與筆記）。
- **還原時保留了舊編號的節點不能交換**：`scripts/restore.sh --keep-node-id`（或桌面版「直接開啟現有資料」）把換不了號的備份照樣放回去時，資料庫的 `sync_restore_kept_node_id`（migration 224）有一列。
  規則：**這張表有列 ⇔ 這台現在的編號是還原時保留下來的、還沒重新加入**；之後一次成功的換號會清空它（`scripts/lib/renewNodeId.sql`），重新加入（交換那一批做）也要清。
  那台可能編出別台已經握有、內容不同的號碼；交換要在這張表有列時拒絕（見 [deploy.md「還原」](../../../../../docs/agents/deploy.md)）。今天沒有交換，所以沒有東西要擋。

### 筆記的空間跟著它的樹（migration 218）

`content_nodes.parent` 與 `space` 是兩個單位，資料庫卻要它們一起成立（延遲觸發器 `content_nodes_check_space`：筆記在父層、子層的空間）。逐欄合併做得出沒有人寫過的組合，整包在 COMMIT 失敗（原始的 23514），之後每一包帶同樣的標記：兩台永遠卡住（`mergeSpaceParent.integration.test.ts` 的 (a)(b)(c)）。合成一個單位救不了 (b)(c)：兩邊寫的是不同列。

| 欄 | 是什麼 | 誰寫 |
| --- | --- | --- |
| `written_space_id` | 人寫下的空間＝`space` 單位的值（只對頂層筆記有意義；在父層底下照樣存、照樣送，不拿來決定空間） | 本機寫入（觸發器 `content_nodes_derive_space`：頂層筆記的空間改變、筆記變成頂層時跟著 `space_id`）；合併寫回 |
| `space_id` | 筆記所在的空間＝頂層祖先的 `written_space_id`（套上 4.10 的切環；寫下的空間這台沒有就是預設空間）。**不是單位、不蓋章，合併從不把它當成標記的值讀**（#1853 的 `same-stamp-different-content` 就是把推導的欄當成標記的值） | 本機寫入（產品照舊把整棵子樹一起搬）；合併最後推導（`dbRows.ts` `deriveNoteSpaces`） |

- **只有寫下的改變才蓋 `space`**：搬整棵子樹只蓋根，子孫沒有標記（`updated_at` 也不動：它是自己寫入的函式）。
- **變成頂層的寫入蓋 `space`**（拖到最上層、父層被永久刪除：觸發器 `sync_stamp_space_with_root`），值是當下所在的空間；否則別台用的是建立時留下的舊頭。
- **頂層筆記換空間也蓋 `parent` 與 `sort`**（值不變，觸發器 `sync_stamp_parent_with_space`；「頂層」＝沒有父層或父層是標籤，`content_nodes_at_top`）：頂層筆記的空間與父層是同一個位置，別台沒看過這次搬動就把它拖到別處，兩筆寫入在 `parent` 競爭，輸的是衝突頭。只蓋 `space` 時，這次搬動會沒留下任何頭就失效（PR 說明的反例）。
  這兩筆標記放在既有的頭**旁邊**（`sync_stamp_put_beside`）：`saw` 是勝出那一筆的（加上它看過的；跟著建立的欄位則加上建立的每一個頭，和 `sync_stamp_put_over` 一樣）。`saw` 按來源計數（上面「同一個來源對同一個單位的寫入」），所以它也蓋住**勝出那一筆的來源較早的頭**；收到的每一台會把這些頭丟掉（`unit.ts` `covers`），寫的那台也在寫的時候丟掉同樣的那些，所以寫的與收的握有同一組頭，再收一次或整份重送都不改任何東西（PR #1907 第 2 輪第 2 點；第 1 輪的版本只留著它們，第二次搬空間後寫的那台與收的那台就不同了）。**代價**：勝出那一筆的來源自己較早輸掉的位置，在這次搬空間時算被看過——勝出的是這台自己較早的搬動時，就是這台自己輸掉的拖動。勝出那一筆沒有算到的來源的頭留著；勝出那一筆是別台的寫入、而它的 `saw` 已經算到這台時，這台較早的頭也一起走（第 3 輪第 6 點的測試：A 搬過、B 再搬，A 較早的拖動兩台都丟）。
- **合併的最後**：對包裡的筆記、因包而失去父層列的筆記、它們之間任何環上的筆記、以及它們底下的每一則（不在包裡的也算）推導空間。「底下」是**切環之後**的子女（`dbRows.ts` `effectiveSubtree`：存下的子女，加上獲勝的 `parent` 寫入的 `meta.from` 指向它、被切環放回它底下的筆記）；搬到別的空間（`services/spaces.ts` `moveToSpace` 與預覽）用同一個定義（`notesMovedWith`），所以搬的那台與收到的每一台是同一組筆記。先載入所有祖先；有環時讀每一則載入的筆記的父層寫入（`meta.from`）交給 `resolveMoveCycles`，切出來的舊父層不在就載入它與它的祖先再切一次，直到沒有缺的（`rules/space.ts` `cutParents` 的 `missing`）：答案只取決於複製的列，不取決於先載入了哪些。
  搬到別的空間時，「底下」是**搬動之後**的樹（`notesMovedWith` 的 `parentAfter`：根被拿出來，它所在的環也就打開了；第 2 輪第 1 點）。一則筆記被永久刪除時，它的墓碑（`*` 的刪除標記）的 `meta.space` 記下它當時顯示的空間（migration 218 第 8 節）。因此失去父層的筆記——父層欄被外鍵清空（它的 `parent` 標記留著那個 id），或切環把它放回那一則底下——在最上層，**而且在那個空間**（`dbRows.ts` `orphanedInto`），不是當初替它寫下的空間：一則一直在父層底下的筆記，寫下的空間是舊的（祖先搬空間時不改它），用它會讓刪掉另一則筆記的副作用變成「這幾則換到它們沒待過的空間、誰讀得到變了」（第 3 輪第 1 點；第 2 輪的版本就是那樣）。收到的那台把被切環放回被刪那一則底下的筆記也當種子（`cutBackUnder`）；刪的那台什麼都不用重推：那些筆記本來就在被刪那一則的空間。別台離線時在被刪那一則底下建的筆記（晚到的子筆記）走同一條規則。墓碑沒有 `meta.space`（標籤、這台沒握有過的筆記）時，用筆記自己寫下的空間。換了空間的筆記先用暫時的 slug，再和包裡的筆記一起給 slug。推導造成的改變在本機記結構紀錄（標記是決定它的那筆寫入：頂層筆記的 `space`，或它的建立）、推進成員 epoch；都不複製。
- **切環只是檢視**：`parent_id` 照合併的結果存（環也照存）；環上的每一則都經由被切的那一則走到同一個頂層，所以延遲檢查（讀 `parent_id`）成立。合併從不把切環寫回去（寫回去就是沒有人做的寫入，各台會互相蓋）。讀取（樹、清單）還沒有接上切環。
- **一個定義**：本機寫入讓頂層筆記 `space_id = written_space_id`、子筆記跟父層同一個空間（`content_nodes_check_space` 在 COMMIT 檢查）；合併算出同時滿足兩者的那一個。模擬器（`mergeCrossFieldSim.test.ts`）用同一個函式（`cutParents`、`spacesOfTree`）。

### 空間的刪除：寫下的與顯示的（migration 218 第 6 節）

同一種拆法：`spaces.written_deleted_at` 是人寫下的刪除（`deleted` 單位），`deleted_at`（每個讀取用的）由檢視推導：寫下了刪除、而且裡面沒有活著的筆記才顯示為已刪除。
空間裡有活著的筆記，一定是刪的人沒看過的寫入帶進來的（本機刪不掉有筆記的空間，看過刪除的寫入也放不進去），所以空間照樣顯示、刪除留著（它的作者看得到），筆記離開之後刪除自己生效。
一個定義 `spaces_show_deleted`：合併最後對每個寫下了刪除或顯示為刪除的空間呼叫；本機有活著的筆記離開這種空間時由觸發器呼叫。顯示改變時推進成員 epoch（本機）。
**刪除要傳得過去**：修改包的讀取範圍（`services/readPolicy.ts` `bundleScopeFor`）也帶擁有者是成員的已刪除空間，連同成員與裡面的筆記；以前已刪除的空間不在範圍內（`spine/spaceAccess.ts` 只讀活著的空間），包什麼都不送。快照照舊不帶已刪除的空間。

### 讀者範圍外的寫入：`holds` 與 `upTo`（I5）

包的標頭有兩個數：`holds` 是寄件那台在切點握有的（包裡的標記都不超過它，`bundle_stamp_beyond_cut` 照它檢查），`upTo` 是收件那台收下之後握有的。
一列在表裡、整個工作區的讀者會拿到、這個讀者卻不會（不是成員的空間）：它被**扣下**，它的標記不送，`upTo` 停在那個來源第一筆被扣下的寫入之前。
所以收件那台的 `have` 不會越過它沒拿到的寫入；讀者之後成了成員，下一包就送到（`mergeSpaceParent.integration.test.ts`「I5」）。
不選「送沒有值的標記」：收件那台的 `have` 照樣越過，那筆寫入的內容永遠到不了；也會把讀者讀不到的列的存在告訴它。代價見「接上傳輸前必須完成」。
**轉送**：被扣下的寫入之後那個來源的寫入照樣送到（收件那台存下，`have` 停在扣下的之前），所以一台可能握有某個來源超過它 `have` 的寫入；它再送給第三台時，`holds` 是它送出的每個標記與頭的最大號碼（不只是 `have`），`upTo` 仍是沒有缺口的那一段。之前 `holds` 只看 `have`，第三台收到超過 `holds` 的標記就 `bundle_stamp_beyond_cut`，永遠拒收（`stampedSawThreeNodes.integration.test.ts` 的隨機三台找到的，種子 902）。

收一包的最後先把延後的檢查提前跑（`SET CONSTRAINTS ALL IMMEDIATE`，`dbRows.ts` `checkDeferredNow`）：不合就整包拒收，唯一鍵是 `bundle_unique_clash`，其他是 `bundle_malformed`（422），原因寫出是哪個檢查，什麼都不寫。用的是畫面已有一句話的代碼。

### 沒做到的（在測試裡釘住，見 `stampedBundle.integration.test.ts`）

- 衍生資料：由內文衍生的（連結、段落列的顯示欄位、`note_block_refs`）與內文以外的寫入衍生的（連進來的連結、跨空間的邊、型別、`_block_autotag`、網站重建、永久刪除的清理、成員 epoch），自 4a 批起在收包的收尾、同一個交易裡由 `spine/receivedDerivation.ts` 插槽重算，用本機寫入用的同一組函式（`services/receivedDerivation.ts`、`services/bodyDerivation.ts` `deriveFromBody`），不寫任何單位。領域事件仍不寫（4b）。搜尋文字就是內文欄，本來就相同。錨點、段落列的 id 與任務行的連結、段落標籤自 migration 215 起是複製的，跟著寫入走（見下面那一節）。2b-1 釘的「永久刪除一列時收的一方的連鎖刪除不留墓碑」在 2b-2a 翻轉了：屬性的墓碑跟著包走。
- slug：由標題在寫的那一端算出，不是單位。包把 slug 跟著勝出的標題走；還原要的是它的標題給的 slug，換空間要的是它原本的。同一個空間兩則活著的筆記要同一個 slug 時，照一條規則（`spine/noteSlugs.ts` `settleSlugs`，本機搬動與收包都用它）：**比較晚「佔」這個名字的那則讓位**。讓位的那則若「佔」的是建立或標題（它的 slug 跟著那筆寫入走），改成 `slug-<id 前八碼>`（與 4a 之前的合併相同：名字不看這台的狀態，所以兩台同時新建、改名多少則都收斂）；若「佔」的是位置（搬動、跟著樹、還原：沒有寫入帶著它的 slug），拿從它開始第一個空的（`freeSlug`，`-2`…，與寫的那台的寫入路徑相同）。「佔」的時間是它的建立、標題、還原、它與它上面每一則的 `parent`、最上面那則寫下的空間這些標記裡最新的一個（`claimOf`）；標記是複製的，所以每一台選的是同一則。本機的搬動、還原、改名是這台最新的寫入，所以讓位的永遠是被搬的那些（含底下跟著的），原本就在目標空間的筆記 slug 不變（已發布的網址只因自己的寫入而變；PR #1941 審查第 1 輪第 1 點），與 main 相同。兩台各自把同 slug 的筆記搬進同一個空間（或一台搬、一台新建）：兩種送達順序都由較早的那則保留（`receivedDerivation.integration` 的三則 slug 測試）。**沒解決的**：因位置讓位的那則拿的「第一個空的」看的是這台的狀態；三則以上同時被搬或還原到一個 slug，或同時有人新建了剛好是那個 `-2` 的筆記，兩台的後綴可能不同。釘成 `it.fails`（`receivedDerivation.integration`「slugs, NOT SETTLED: three notes moved into one space at once」）。讓後綴成為複製狀態的純函數（PR #1941 第 2 輪的第三條路）在這一批做不到：被搬或還原的筆記的基底 slug 沒有任何單位握著（slug 不是單位，搬過之後只有標題跟著走）；拿標題的 slug 當基底，單機上一則 `x-2` 單獨搬進 `x` 空著的空間會變成 `x`（main 保留 `x-2`），而且同一組的另一則改名離開或被刪時，這一則的 slug（已發布的網址）也會變。兩條路（讓位的一律 `-<id 前八碼>`；slug 成為單位，第 5 批）由業主決定。只帶 slug 跟著還原或換空間那筆寫入走不行：兩台各贏一個單位時 slug 會對調（`stampedBundle.integration`「either order of delivery」抓到）。
- 從內文寫出的屬性（4a 批的 (b)）加上「`source` 不是單位」：A 的 `due` 是 `ui` 寫的，B 的同一個鍵是 `markdown` 寫的，B 存一份帶 `due:: x` 的內文，那筆寫入照一般規則在 B 贏、傳過去、蓋掉 A 的值。不會來回（收包從不重新衍生這些屬性）。兩台的內文被合成一份時，合成文字與它的屬性可能要到有人在本機存檔才一致。這是**接受的限制**，留給第 5 批（§2.12.4，每一個有寫入者的欄位：`source` 成為單位）與 4c（核取方塊↔任務）；PR #1941 審查第 1 輪第 6 點。
- 收包的衍生的成本（真 Postgres，一包 N 則新筆記、每則兩個 `[[連結]]`，PR #1941 第 2 輪）：1,000 則整包 11.1 s（衍生 7.6 s），5,000 則 94.9 s（衍生 76.8 s）。整段在包的交易裡、拿著事件鎖，收 5,000 則時本機寫入要等這麼久；衍生每則的成本隨筆記數變大（`deriveFromBody` 每則一次），第 6 批（分段收包）要用這些數字。
- 收到一份改了的內文，收的一方照本機存檔排一筆備份意圖（`enqueueBackup`：`git_commit`，空間允許時 `github_backup`）與內容掛鉤；語意搜尋模組開著時多一列 `embed`（每台自己的嵌入，用本機模型，不送外部）。模組沒匯入時掛鉤不跑（`modules/index.ts` `hooksWhenImported`），什麼都不排。PR #1941 審查第 1 輪第 7 點。
- 同一個 id 在兩個節點各自建立（算出來的 id）：輸的創建值以頭的形式留下，列的建立欄位（slug、建立時間）跟著勝出的建立。

## 握有別台修改的節點也能被快照（自己的裝置之間的交換第 2 批，migration 222）

提案：「自己的裝置之間怎麼交換」（own-node-transport-2026-11-22，還在 PR #1936 的分支上）§2.2、§3.4、第 6 節第 2 批；信任界線：[sync-trust-line.md](../../../../../docs/decisions/sync-trust-line.md)。
以前收過別台修改包的節點（例如中心收過一台裝置的包）就不能再被快照（`snapshot_foreign_origin`）：第二台裝置、換主機都卡住。現在：

- **快照帶「來源握有的其他來源」**（`brought`，快照第一行與每一頁相同）：來源的 `sync_origins` 裡除了舊編號（`self-restore`，照舊走 `former`）以外的每一列，
  每個標籤、每個來源握有到第幾號（就是它的 `sync_origins.have`）。加入的一方在 `markJoinDone` 各記一列（`vouched_by` ＝ 來源：帶來的來源，不是寄件者），
  數字照抄：**加入的那台知道的，正好是來源在切點知道的**，所以之後誰送包來都只送新的。
- **加入的一方怎麼檢查**（`checkPage`、`beginJoin` 的 `checkedBrought`；拒收就整份不寫）：`brought` 是「搬得動的標籤 → 節點編號 → 整數」的物件、最多 32 個來源
  （`MAX_BROUGHT_ORIGINS`，和 `former` 同一個上限）、節點編號只收小寫（資料庫寫的形式；大寫的同一個編號不算另一台）、不含來源自己、舊編號、genesis（`join_bad_brought`；舊的「每個來源一個數字」也是這一碼，不會被讀成標籤）；
  含這台自己的編號是 `join_origin_is_this_node`（這台以前用同一個編號送過包、清空後沒換號又來加入：要換新編號，提案 §3.5）；
  每一頁要和第一行相同（`join_wrong_brought`）；一個帶來的來源的標記不得超過它那個標籤報的號碼（`join_stamp_beyond_brought`；只有快照帶、包不帶的標籤
  `content_nodes.collection_views` 沒有自己的號碼，取它所有標籤的最小值：這種標記只會經快照來，加入時不超過那時的最小值，之後只會變大——`broughtBound`）；
  來源自己的標記不得超過切點（`join_stamp_beyond_cut`）；誰都沒擔保的來源照舊 `join_stamp_origin`。
- **快照帶來源握有的每一個標記**，包括沒有列的活標記（4.9 掛著的列、刪除留下的鍵）：和修改包的 `tombstone` 項同一組，摘要也算它們（`readTombstoneChunk`、`computeSnapshotDigest`；
  第 1 輪審查 A1：以前只帶 `deleted` 的，加入的那台少了掛著的標記、`brought` 卻說它握有，之後沒有包會送）。
- **舊編號那一列的號碼**取那一列寫了的標籤的最小值（`heldOfFormer`）：migration 213 只寫了當時的 19 個標籤，之後才搬得動的標籤舊編號沒寫過（第 1 輪審查 A2）。
- **來源那一端先檢查自己**（`services/stampedSnapshot.ts` `snapshotSourceNode`，讀之前，也在花掉新鮮確認之前）：自己正在加入（`snapshot_source_joining`）；
  握有某個來源的標記，卻沒有那個來源的列（`snapshot_foreign_origin`）；握有某個來源某個標籤的標記超過自己記的號碼（`snapshot_source_unsettled`：合併寫了標記卻沒記進度、
  或 206 之前只記了 `content_nodes` 的舊進度列——跟那個來源交換一次就好）；其他來源超過 32 個（`snapshot_too_many_origins`）。
  合併進行到一半不是一種會被讀到的狀態：一包一個交易，快照在一個 REPEATABLE READ 唯讀快照裡讀，要嘛全看到、要嘛全沒看到；讀之前的起始標記補寫（`sync_genesis_pass`，是寫入）碰到同一個標記鍵時會**等**開著的合併交易結束，所以合併中開始的匯出可能等它做完（最多到 statement timeout）（`snapshotBrought`「P4 … while a bundle is being taken」，真 Postgres 兩條連線，`pg_locks` 看過）。
- **`have` 改成每個標籤一個**（`Have`，請求的 `have` 與包頭的 `base`／`upTo`／`holds` 一起），資料形狀升到 6。已存的進度本來就是每個標籤一個（migration 206），照原樣讀，不必改寫；
  舊形狀（每個來源一個數字）以 `bundle_have_per_origin` 拒收，不被當成標籤讀。被扣下的寫入（I5）只讓它自己那個標籤停住。
- **`admitSyncNode` 把「帶來的來源」升成寄件者**，保留握有的號碼：C 從 B 加入、B 從 A 加入之後，C 收進 A 就從 B 知道的地方接著收（A→B、B→C 快照，之後 C↔A 修改包）。
  `self-restore`（這台自己以前的編號）不會變成寄件者。

## 錨點與段落列跟著內文那筆寫入走（錨點提案第 2、3 步，migration 215）

業主 2026-11-17 選設計甲：錨點的位置與狀態是**複製的**（[錨點提案 §3.1](../../../../../docs/architecture/proposals/anchors-deterministic-2026-11-16.md)）。一次內文寫入鑄的 id 由動手的那台鑄一次、跟著寫入走，收的一方原樣採用、不為收到的文字再鑄自己的。

| 一次內文寫入鑄的 id | 今天在哪裡鑄 | 放在哪裡跟著走 | 為什麼放那裡 |

- **一則筆記所有錨點的位置是一個單位**（`note_anchor_places`，鍵＝筆記 id，審查第二輪第 2 點）：`places` ＝ 量的那份內文的雜湊 `h`，加每個錨點的位置、狀態、備選、quote 與前後文、待補找；
  錨點自己的 `at_body_hash` 不是 `h` 時（215 之前留下、之後沒被讀過的列）帶第十個元素。有錨點的筆記，每一次內文寫入都寫它（至少 `h` 換新），所以這個單位的標記就是那筆內文寫入的標記，兩個單位同贏同輸（PR #1759 note-cf 第 2 題）；一次存檔寫一列、一個標記，與錨點數無關。沒有錨點的筆記沒有單位，它的內文寫入也不寫。
  寫的一台：寫錨點的每個語句結束時（語句層級的觸發器，帶轉換表），替那個語句碰到的每一則筆記寫一次單位（`note_anchor_places_follow`；第四輪第 2 點：延後的列觸發器在幾則筆記的列交錯時每一列都重寫一次）。一次存檔的錨點只有一個語句（`store.ts` `moveAnchorsForBodyChange`），所以只寫一次；一次存檔**新建**的錨點、段落列、段落標籤也各一個語句（`insertAnchors`、`syncBlockNodes`；之前每個一個語句，第一次存下 n 個錨點的筆記把最多 n 個條目的單位重寫 n 次：200 個在 PGlite 上 1.9 秒、讀 110 萬列，現在 0.7 秒、4.5 萬列，`anchorFirstSaveCost.integration.test.ts`）。
  大小：單位的文字（UTF-8 位元組，兩邊都量同一個東西）不超過 16,000,000（`anchor_unit_bytes_max()` ＝ `anchorUnit.ts` `ANCHOR_UNIT_BYTES_MAX`，測試比對兩者）。寫入端不會寫出更大的：每個錨點的前後文最多 400 個 UTF-16 單位（`similarity.ts` `quoteAt` 用 `cutToUnits` 取開頭，比對時也照這樣截），還是超過時依序放棄最舊的 `lost`、`maybe`、`valid` 錨點的字（列也一起改，單位仍等於列）；放棄了字的 `lost` 錨點再也找不回來（段落列一直藏著、任務留在垃圾桶、連結說那段不見了）。
  舊的列：215 之前的程式可能留下量在現在內文上、卻不是寫入端現在會寫的樣子的列（`valid` 帶備選或待補找；非 `valid` 卻有位置；正式站有個位數）。寫單位的那一刻把它們正規化（`note_anchor_places_write`），所以不論是存內文、還是只寫某一個錨點的位置，寫出的單位收的一方都收得下（`anchorUnitIsRows`「an old row …」六則）。
  文字是資料庫自己的 jsonb 寫法（鍵依長度再依位元組、`, ` 與 `: `）；收到的單位文字不是這樣寫的就拒收（`anchorUnit.ts` `parseAnchorUnit`，審查第三輪第 3 點）。
  錨點列（`block_anchors`）留著，由 `services/blockAnchors` 讀寫，只有 `*` 與 `note`（在哪一則筆記）兩個單位；位置欄位是單位的展開。`moved_how`／`moved_at` 是這台自己的紀錄（沒有讀者），不跟著走。
- **單位與列，兩個方向各一條路**：寫的一台，單位跟著列（語句層級的觸發器 `note_anchor_places_follow`，每個語句每則筆記一次，`note_anchor_places_of`）；收的一台，列跟著單位。
  **一包裡內文、錨點單位或錨點列（`note`）有變的每一則筆記都展開**（`RowSource.bearsOn`：筆記的內文、錨點所在的筆記指向那則筆記的單位；第三輪第 1 點），整包一個語句（`dbUnits.ts` `expandAnchorUnits`，`note_anchor_places_expand_all`）。
  選頭（`anchorUnit.ts` `chooseAnchorHead`，只看複製的狀態）：`h` 等於存下來的內文雜湊、而且位置都在那份內文之內的頭（多個時取標記大的）。
  單位有、這台沒有列的錨點（這台已永久刪除）：略過，不建列。有列、選出的頭沒有的錨點（輸的那筆寫入新鑄的）：`lost`，位置 0..0，量在選出的頭的內文上；它的 quote 與前後文取**指名它的頭裡最新的那個**，不是這台那一列的（第三輪第 2 點）；沒有一個頭指名它就沒有字（這台那一列原本的字是歷史：上一次展開寫的、或寄件那一台當時的列，不是複製的狀態；第四輪第 6 點），它就是再也找不回來的錨點。
  沒有一個頭量在存下來的內文上：每一列都 `lost`，雜湊是最新的可用頭的內文（不是存下來的那份，所以下一次存檔會重新找）。測試：`anchorsReplicated`「8a」「8b」「round 3, 1」（只帶內文的包，三台相同；只帶內文的包換了對得上的頭）「round 3, 2」（三台不同到達順序，字相同）。
  展開時資料庫不收的值（或兩個方向的檢查不合）→ 整包 `bundle_malformed`。
- **跟著筆記走的列**（第五、六輪；`dbUnits.ts` `goesWithNote`，守門 `stampedBundleSources`：欄是 NOT NULL、對 `content_nodes` 是連帶刪除的外鍵）：錨點、段落列、錨點單位的標記觸發器把列歸在它的筆記之下（`via:note_id`，和其他掛在筆記上的表同一條規則），所以連鎖途中對它的修改（任務連結設成空）不寫標記。
  **一條規則，兩邊同一條**：筆記不在這台的列跟著那則筆記走了。寫的一台是 migration 215 第 2c 節的語句層級觸發器（`sync_rows_go_with_note`），收的一台是 `dbRows.ts` `rowsThatGo`（包裡的筆記先寫，所以到這一步還不在就是沒有：包帶著收件這台 `have` 以上的每一筆寫入，寄件那台有、這台沒有的筆記一定跟著來；寄件那台也沒有，就是刪了）。
  - 在那則筆記裡**建的**列（它的 `note` 沒有自己的標記）：什麼都不留，標記與頭一起清掉。每一台握有它的都握在那則筆記裡，所以筆記自己的墓碑就說了它走了；錨點單位以筆記為鍵，永遠是這一種，所以永久刪除的筆記的文字不會留在任何一台的頭裡。
  - **搬進**那則筆記的列（`note` 有自己的標記）：標記留著，**每個標記帶著它寫的值**（`sync_stamps.kept_value`，觸發器從要刪的那一列取；頭本來就帶值；第八輪），因為它是「這一列走了」的唯一紀錄：還把它握在原處的那台收到時移除它。值只有 id 與 `detached`（子筆記 id 與標籤名），沒有筆記的文字。全部清掉的話，「搬走、再刪掉目的地、然後才同步」時，另一台會永遠留著那一列（第六輪的回覆有例子）。
  - 收的一台，贏的 `note` 指向這台沒有的筆記：移除本機的那一列，絕不寫 NULL；這台原本握有的那一列的標記與頭先清掉，再照上面兩種分（搬進來的寫回合併後的單位、每個值都留在標記上：`storeUnit` 的 `kept`；不是 `fresh`：第七輪第 1 點，`fresh` 會把這台已有的頭再插一次，那一包與之後的每一包都被拒）。
  - **一筆寫入在每一台說的都一樣**（第八輪 P1–P3）：沒有列可以放贏家的值時，值留在它的標記上（`kept_value`），包裡以標記的 `kept` 送（寄件那台不握有那一列：墓碑項目）；所以這三張表沒有「沒有值的格子」，合併就是平常的合併，只有「贏的 `note` 指向這台沒有的筆記 → 列走了」這一條規則。一筆寫入在列走了之後才同步，它的值照樣跟著走（第七輪那條「它跟著列走了、等於沒發生」不再成立）。跟著建立的欄位（沒有自己的標記）沒有留：建立的值在列裡，不在任何標記上；握有那一列的一台帶著它來，沒握有的兩台之間沒有人顯示它。
  - **留值只在這三張表**（第九輪第 2 點）：別的表的列，因為它的筆記或空間在這台被永久刪除而不在（4.9 那種掛著的列、合併時連鎖刪掉的列、已刪列的 JSON 鍵），只留標記、**不留值**，別台送來的值也不收（`dbRows.ts` `storeTable` 的 `withoutValues`；送來的 `kept` 對別的表不算數）。永久刪除就是刪掉：屬性值、JSON 鍵的值都不留在刪除的那一台（筆記的標題與內文也一樣，不過產品不會讓一則筆記失去它的空間：`deleteSpace` 只設 `deleted_at`）。資料庫擋：`sync_stamps` 的 CHECK（`sync_stamp_may_keep_value`：這三張表與下面那幾個欄位，守門比對宣告），測試另外搜那些字。
  - **沒有值的副本是副本的記號**（`unit.ts` `valueless`，存著也送著：頭的 `valueless`；標記的 `kept_value` 是 `{"none": true}`，或不握有的列的標記沒有 `kept`）：上一條那種列的標記，以及蓋在握有的列上、沒有值的贏家（第九輪第 4 點：之前下一次載入就把欄位現在的值當成它的值）。它不被當值檢查、不算一個可顯示的衝突、不寫進欄位、不出事件；同一筆寫入一邊有值一邊沒有不算衝突，留有值的那份（`maximalHeads`）。第七輪那個整個一側的旗標只在一次合併的當下成立，存下來就變成 NULL（第八輪第 1、2 點），已拿掉。
  - **外鍵會清空的欄位**（第九輪第 1 點；`dbUnits.ts` `clearedOnDelete`，守門從目錄讀出每一個 `ON DELETE SET NULL` 的單位欄位：筆記的 `parent`、空間的 `owner`、段落列的 `task` 與 `detached`、訂閱的 `auto_tag` 與 `default_parent`）：資料庫在被指的那一列刪掉時把欄位設成 NULL，這不是一次寫入、沒有自己的標記。所以**同一個標記下，一份是 id、一份是 NULL 不是衝突，留 id 的那一份**（`rows.ts` `mergeRow` 的 `cleared`，取代原本只給 `parent` 的特例）；一個說 NULL 的寫入（取消任務）有它自己的標記，照平常的規則。
    留下的 id 存在標記上（`kept_value`，握有那一列也一樣；欄位照舊是 NULL，因為它指的那一列不在了）：寫回時欄位指向不在的列就存（`storeUnit`），資料庫清空欄位而沒有寫標記時由觸發器存（`sync_keep_emptied_id`：合併時觸發器站在一旁；段落列的標記歸在筆記之下，同一個語句先刪了筆記也沒有標記——產品的永久刪除一個語句刪掉筆記與底下的任務，列被刪時是否還指著任務取決於順序）。載入時標記的值優先於欄位；本機下一次寫那個單位時清掉（`sync_stamps_kept_value_cleared`）。從帶來的值建列時，指向不在的列的欄位是 NULL（`clearMissingRefs`，資料庫在那一列刪掉時也是這樣留下的）：之前那一列根本建不起來（4.9 的 `missing-ref`，`it.fails`「10」）。查「那一列在不在」都是被指的鍵上的一次查找，用那個鍵自己的型別（觸發器的參數帶著被指的表與欄，`dbUnits.ts` `namedRowHere` 讀外鍵的型別；第十輪第 1 點，之前是 `::text` 比對，讀整張表）；觸發器在沒有匯入、筆記也還在時一開始就返回。`anchorSaveCost`「keeping an emptied id costs a look-up」量一般存檔與一包有父層的筆記的讀取量。
