## 一個單位怎麼合（`mergeUnit`）

單位的狀態是它的**頭**（heads）：沒有人在「看過它之後」寫新值的那些寫入。通常一個；兩台互不知情改同一處時兩個以上。
值＝標記最大的頭（`hlc.ts` `compareOps`），其餘內容不同的頭＝一筆衝突，留著（帶它的值）直到有人看過它們再寫。
這是多值暫存器（multi-value register）：狀態只取決於「寫入的集合」，所以交換、結合、冪等，衝突紀錄在每個節點也相同。

規則（逐條對應提案）：

- 較大的標記贏；創世（origin `genesis`、seq 0）輸給任何真實寫入，不算衝突；墓碑是一種值。
- **內容相同不算衝突也不算修改，不管標記是否相同**：兩個頭都留，值與顯示的標記取較大的那個（兩邊一致）。
- 創世對創世而值不同（兩台資料不同源）：不靜靜選一邊，兩個都留成衝突（add-device-snapshot §5 的「未知」）。真實寫入贏過創世值（值照提案），但沒看過的創世值仍留成衝突。
- 同一個 `(origin, seq)` 內容不同、格式不合：**拒絕**，不是衝突，不改變任何東西。標記的時鐘超過本機時鐘 10 分鐘（`DEFAULT_MAX_SKEW_MS`，參數）：**延後**，見下。

### 介面設計比較

| | 甲：只比兩個標記 | 乙（採用）：寫入帶 `saw` |
| --- | --- | --- |
| 輸入 | 本機 `(值, 標記)`、收到 `(值, 標記)` | 同左，每個寫入多一個 `saw`（寫的人當時看過該單位各來源的最大序號） |
| 值與標記收斂 | 是 | 是 |
| 衝突紀錄收斂 | **否**（見下） | 是 |
| 知道「是後續修改」還是「互不知情」 | 不知道 | 知道 |
| 代價 | 無 | 標記多一欄；單位狀態是頭的集合（通常一個） |

甲的反例（`stampedMerge.test.ts`「pinned」那一項，標成預期失敗）：X、Y（看過 X）、Z（看過 Y）。節點 1 依序收到 X、Y、Z 沒有衝突；
節點 2 只有 X、收到 Z：只比標記時分不出 Z 其實接在 X 後面，記一筆衝突，且之後 Y 到達也撤不回。兩個節點的衝突紀錄因到達順序而不同。
`saw` 是**每個單位自己的**：把整列各欄位的 `saw` 合起來宣稱「看過」，會讓別人的修改被誤判成已被取代而丟掉（所以 `*` 只在建立與永久刪除時寫，見下）。
`meta` 放寫入的人才知道的事（搬動前的父層、刪除當時看過的內容），隨寫入走，不參與「內容是否相同」。

呼叫範例：

```ts
const r = mergeUnit(local, incoming, { nowWall: Date.now(), maxSkewMs: DEFAULT_MAX_SKEW_MS });
// r.outcome: "same" | "took" | "kept" | "conflict" | "rejected" | "deferred"（時鐘超前：稍後再送）
// r.write: 這一列顯示的值或標記要改；r.losers: 這次新留下的衝突（輸的值）；r.unit: 合併後的整個單位（要存）
```

## 整列 `*` 與欄位

- `*` 存「這一列怎麼建立的」（欄位名→值）或「永久刪除」（墓碑）。
- 欄位沒有自己的標記時**跟著 `*`**：值與標記就是 `*` 的。欄位自己被寫過就有自己的單位。欄位現在的樣子＝兩者合併（`effectiveUnit`）。
  所以兩邊一個改標題、一個改內文，兩個都留；建立之後寫的欄位贏過它看過的建立值，不贏它沒看過的寫入。
- 本機修改**不重寫 `*`**（只建立與永久刪除）：整列寫入說不出「每個欄位各看過什麼」，說錯就會讓別人的修改被當成已被取代。
- 儲存形式正規化：與「跟著 `*`」相同的欄位單位不存，所以握有相同寫入的兩個節點，存的內容逐位元相同。
- JSON 欄位＝一組叫 `key:<名字>` 的欄位；移除一個鍵＝該欄位的墓碑。

## 這個設計成立的前提（模擬與審查找到的）

- `saw` 只談**自己這個單位**：「來源 o 的序號 ≤ s 的、對這個單位的寫入，我都看過」。所以不同單位的寫入之間不能用 `saw` 比先後
  （兩列的 `config` 同一個鍵是兩個單位：`rules/functionRefs.ts` 把它們都當成互相同時；模擬抓過我自己寫錯的版本）。
- 跟著 `*` 的欄位，標記是 `*` 的、`saw` 是**空的**：建立值只說「我沒看過任何東西」，因為 `*` 自己的 `saw` 談的是 `*` 那個單位。
  這樣一列不必整列一起送，欄位先到、建立後到都成立（審查指出的「重建者看過較晚的 `*`，卻涵蓋掉別人較早的欄位寫入」因此不會發生）。
- 同一個來源對同一個單位的寫入，後一筆一定看過前一筆；所以「每個來源的最大序號」才能代表「看過到這裡為止」。
  這也是為什麼**系統寫入不寫到有衝突的單位**（`writeUnit(..., "system")` 原樣回傳）：只看過勝出的那個頭，`saw` 說不出來，
  之後任何看過這筆系統寫入的寫入都會被當成也看過同來源較早的頭。只有人的寫入（看過所有頭）能結束衝突。
- 重新建立一列（`createRow` 遇到已在的列，例如永久刪除後在別台重建、算出來的 id 在第二台又建一次）：新的 `*` 涵蓋舊的 `*`，
  每個本機已有值的欄位另外帶同一個標記寫一筆，涵蓋該欄位的頭；沒看過的寫入留成衝突。
- 創世值也有「看過」：真實寫入的 `saw` 記它看過的創世值（以內容命名）。在 x 上寫 x2 取代 x，不取代另一台的創世值 y；y 留成衝突。
- 標記的時鐘超前超過上限是**延後**（`deferred`），不是拒絕：收件端的時鐘會追上，被延後的寫入要再送一次，而且不可把「我已有某來源到第幾號」記過它。
  一個單位裡只有超前的那一筆延後，其他的照收。拒絕只留給格式錯與同編號不同內容。
- S5 補的創世標記沒有 `saw`：到目前為止沒有任何交換，每個單位只有一個頭，而且是本節點寫的，補成 `saw = {}`（只涵蓋創世）是安全的，不需要重建。

## 跨列規則是「視圖」，不是寫入

`rules/` 的函式輸入是合併後的列，輸出是「要顯示成什麼」與「要通知誰」。不改資料，所以每個節點算出同一個答案、
之後使用者自己改名只是一般寫入。若呼叫者想把結果存成寫入，必須用由輸入算出的固定標記（內文提案 §5 第 5 項），否則兩台各存一筆，合併本身又成了下一個衝突。

## 接上資料庫（只到單位層；第 2a 批，migration 205）

`sync_stamps` 每個單位一列，現在多兩欄：`saw`（寫的人當時在這個單位上看過各來源的最大序號；寫在創世值之上的寫入，用 `genesis:<內容 sha-256>` 指名那個值，
內容文字的算法與 `unit.ts` `genesisContent` 相同：字串＝`s:`＋原文，其他＝`j:`＋canonical JSON）與 `meta`（目前只有筆記的搬動：`{"from": 原父層}`）。
舊的標記（含創世）`saw = {}`，不回填：至今沒有任何交換，每個單位只有一個頭，而且是本節點寫的。

### 兩種儲存設計與取捨

| | 甲（採用）：`sync_stamps` 加欄位，多出來的頭放 `sync_stamp_heads` | 乙：`sync_stamps` 的主鍵加 `(origin, seq)`，一個單位可有多列 |
| --- | --- | --- |
| 既有的讀取（快照、摘要、觸發器的 `ON CONFLICT`、202 的補標記、各測試） | 不變：一個單位仍是一列；「目前值」仍是這一列＋資料表的欄位 | 全部要改成「取較大標記那一列」，每個 `ON CONFLICT` 與 `DO NOTHING` 的意思跟著變 |
| 輸的值放哪裡 | `sync_stamp_heads.value`（欄位本身只放贏的） | 同表，但欄位值與標記的對應要靠另外的規則 |
| 讀「目前值」的成本 | 與以前相同（沒有多的 join） | 每次讀都要挑一列 |
| 代價 | 兩個地方有標記；觸發器寫入時要順手清掉 heads | 主鍵變大，既有的 upsert 全部重寫 |

畫面讀的「目前值」＝資料表的欄位＝標記最大的那個頭的值（`mergeUnit` 的 `unit[0]`）。其他內容不同的頭＝衝突，留在 `sync_stamp_heads`，直到有人的寫入看過它們。
觸發器（本機寫入）在蓋標記時從該單位目前的頭算出 `saw`，並清掉其他的頭（本機寫入看過這個節點握有的一切）。

### 單位的讀與寫

- `readUnit(workspace, address)`：資料庫裡某個單位 → 核心的輸入（`Unit`）。值一律是文字（欄位的文字形式）或 null；`*` 是 `{}` 或墓碑（建立值不存，所以兩個節點對「建立標記說了什麼」不會不同意）；沒有自己標記的欄位帶著所屬列的建立標記、`saw` 為空。
- `mergeUnitsIntoWorkspace(workspace, units, gate?)`（`spine/stampedImport.ts`，唯一讓觸發器讓開的入口，和快照匯入用同一個開關，`reason: "merge"`，計入 `sync_clock.merge_batches`）→ `storeMergedUnits`：逐單位 `mergeUnit`，有變的寫回（贏的值寫進欄位、標記與 `saw` 寫進 `sync_stamps`、其他頭寫進 `sync_stamp_heads`）；回報 `events`、`rejected`、`deferred`。**時鐘超前（`deferred`）不寫、不推進任何進度**，呼叫端晚點再送。
- 沒做：新增或移除整列、JSON 單位（`key:…`）、搬動以外的 `meta`、領域副作用（搜尋索引、連結、區塊錨點）、誰可以寫（來源的檢查在呼叫端）。
- 系統與背景工作的寫入：核心遇到有衝突的單位不寫（`writeUnit(..., "system")`）。**資料庫的觸發器不知道誰在寫**，一個普通寫入（背景工作經 `mutate`）碰到有衝突的單位，目前仍會把它「解決」。在還沒有任何傳輸之前，資料庫裡不會出現多個頭，所以沒有實際影響；接上傳輸之前要在寫入路徑上擋（見 PR 說明「需要決定」）。

### 一個包說什麼

- `base`：收的一方說它握有的（每個來源：連續握有到第幾號）；`upTo`：送的一方在切點握有的。包裡有每個來源在 `(base, upTo]` 之間、這個範圍的每一個寫入（被覆蓋的舊寫入不在：覆蓋它的寫入看過它）。
- 一列只要有一個標記超過 `base` 就整列送（它所有的標記與 saw、meta、其他的頭，以及每個單位的值的文字），收的一方不必再問。刪掉的列是墓碑。
- **切點為什麼不會漏**：序號在工作區的事件鎖與 `sync_clock` 那一列之下取，鎖到交易結束才放，所以同一工作區的序號依序取、依序提交，較大的序號不會比較小的先提交。
  讀包時切點（`next_seq - 1`）與標記在**同一個唯讀快照**讀（`withActorReadSnapshot`）；不加鎖，讀不讓寫的人等。`stampedBundleCut.integration.test.ts` 在真的 Postgres 用兩條連線證明，並且在讀的中途提交一筆寫入，確認它不在這個包裡也不超過切點。
- 收的一方拒收整包（沒有任何東西留下）：資料形狀版本不同（`bundle_data_shape`）、送的人不是它收過的來源（`bundle_unknown_sender`；快照的來源，或 `admitSyncNode` 收進來的節點，或由已收的送的人帶來的來源）、起點超過它握有的（`bundle_gap`：改拿快照）、同一個（來源、序號）內容不同（`bundle_stamp_clash`：還原備份或複製設定檔）、送的人說它握有這個節點自己從沒寫過的序號（`bundle_own_origin_ahead`：這個節點被還原了）、時鐘超前（`stamp_clock_ahead`：稍後再送）、工作區正在加入（`merge_not_open`）。
  同樣的包再套一次什麼都不改。
- **`bundle_stamp_clash` 抓得到與抓不到**：抓得到——接收方的單位還握著那個標記：A 寫了標題（A, s），B 收下；A 被還原後又寫出（A, s）但內容不同，並多寫一筆讓這一列被送出 → 同一個（來源, 序號）內容不同，整包拒收（`stampedBundle.integration`「the same (origin, seq) with other content」）。
  抓不到——接收方的單位已經被後續寫入蓋掉：A 寫了（A, s）又寫了（A, s+1），B 只握有後者；還原後的 A 再寫出（A, s）不同內容 → 後者的 `saw` 已涵蓋（A, s），沒有東西可比，整包照收（已釘成測試：預期不拒收，`what bundle_stamp_clash cannot see`）。
  真正的解法是還原後換新的節點編號（不在這批）。

### 收不進去：三個原因、一個出口

一個節點的本機歷史「照原樣收不進去」有三種：**時鐘超前**（`stamp_clock_ahead`，回報對方的讀數、本機時間與差距；存下來的 `hlc_wall` 只會取大，把時鐘調回來也解不開，`stampedBundle.integration`「a clock that was 30 minutes ahead and is set right again」釘住）、
**被還原**（`bundle_sender_restored`：收的一方握有送的人沒寫過的序號）、**離線太久**（`bundle_gap`：起點超過收的一方握有的，改拿快照；`stampedBundle.integration`「a node that was offline for too long」釘住：送的一方沒有收的一方缺的那一段，整包被拒、什麼都不寫）。三個的出口是同一個：該裝置換一個新的節點編號，把還沒被任何人收下的寫入用現在的時間重新蓋章再送——**這一批不做**，不另外發明「等時間到」或「放寬上限」的路。
`readUnsendable`（`spine/stampedBundle.ts`）是同一個結構的讀取函式：每個原因一筆 `{reason, writes, aheadMs?}`；今天只有 `clock_ahead` 能從本機資料算出來，另兩個要等有人拒收時才知道，還沒有東西把那個答案存下來。

### 刪除之後再建立

永久刪除寫一個墓碑，它的 `meta.seen` 是刪的人當時看過的（每個來源最大的序號）。同一個 id 再建立時，新的 `*` 把這個 `seen` 帶在自己的 `meta`（migration 206 的觸發器與 `createRow`），
所以**刪的人看過**的欄位寫入不再是新值旁邊的頭（`droppedBySeen`，`store.ts`）；刪的人**沒看過**的寫入留下，成為衝突（它的作者看得到）。收到永久刪除時，沒看過刪除的寫入不再有列可存：回報在 `lateEdits`（`rules/trash.ts` 的 `recoverLateEdits`），由呼叫者還給作者。

### 4.9 在已刪除父層底下的筆記：定案是「檢視」，不是寫入

`storeMergedRows` 的回報有 `orphaned`（哪些筆記在刪的人沒看過它們時，底下的父層就被永久刪除）與 `notices`（要通知誰，含刪除時沒看過的修改），由 `rules/trash.ts` 從每個節點都有的戳記算出，所以每個節點答案相同；**不寫入**。
為什麼不是寫入：衍生的修正必須是已複製狀態的純函式；若每個節點各蓋一筆「放進垃圾桶」的寫入，各自的戳記不同，兩邊就不再相同，也無從決定誰的那筆勝出。
還沒做的是**讀取**：清單、樹、搜尋今天還不知道這個檢視，會把孤兒筆記當成普通的頂層筆記；`stampedBundle.integration`「rule 4.9, the READ」用 `it.fails` 釘住，擋在 2b-2／畫面那批。

### 系統寫入不解決衝突

系統／背景工作（`systemJobOf`，`stampTransaction` 把 `system: true` 放進標記設定）寫到有其他頭的單位，資料庫拒絕（`sync_unit_in_conflict`，409，可重試）；人的寫入看過所有頭，照舊取代。這一批不另設重試上限：從 outbox 跑的工作是一般的可重試失敗，沿用 outbox 的額度（`RETRY_DAY_ATTEMPTS`，約一天，之後進入看得到的死亡列）；不是 outbox 的工作直接以 409 失敗（`syncSystemWriteConflict.integration` 釘住）。

## 每一張帶標記的表都跟著修改包走（第 2b-2a 批，migration 209）

範圍從 `content_nodes` 擴大到 `dbUnits.ts` 的 `UNIT_SOURCES`（一份資料：每張表的列鍵、工作區、欄位，守門 `stampedBundleSources.integration.test.ts` 對照資料庫裡標記觸發器的參數）與 `JSON_SOURCES`（JSON 欄位的鍵，一鍵一個單位）。
同一個核心（`rows.ts` `mergeRow`）、同一個列層寫回（`dbRows.ts`，依 `UNIT_SOURCES` 的順序：父表先），沒有第二套合併。`sync_origins.have` 每個標籤一個數字，一包在一個切點讀全部標籤，所以收下之後各標籤相同；
只收過 `content_nodes` 的舊節點，其他標籤從 0 起算（筆記會整份再送一次，收兩次不改任何東西）。`NOT_CARRIED_YET` 列出接了觸發器但還沒跟著走的，各附原因：

- 看板的區段（`node_attributes._canvas_sections`）**跟著走**，一個單位：屬性的 `value`（照一般單位合併：較晚的寫入勝，另一邊留成頭，每台相同；不逐個區段合併）。一份資料只有一種單位：migration 209 之後觸發器與起始標記都不再逐區段蓋章；
  之前留下的逐區段標記不刪、不改寫，摘要、快照與修改包都不讀它（`snapshotTables.ts` 的 `RETIRED_STAMP_LABELS`，守門 `stampedBundleSources.integration.test.ts`）。沒有任何讀者用過逐區段的標記。`content_nodes.collection_views` 是凍結欄位（沒有寫入者），不需要。
- 集合（`workspaces.modules_off`／`modules_confirmed`）**跟著走**：一個元素一個單位（在／不在），和 JSON 鍵同一個機制；寫回時排序存放，本機寫入也由 migration 209 的觸發器排序存放，所以相同的單位就是相同的位元組。
- `block_node_tags`：掛在段落（`block_nodes`）上，段落由內文衍生，合併進來的內文還不會重建段落（2b-2b）。

列層的新規則：

- **掛在被永久刪除的筆記上的列**（屬性、標籤、指標、卡片位置、功能引用）：資料庫拒絕（外鍵），不建列；它的標記照存，**而且照樣跟著包走**（沒有列的標記也送），所以每台握有相同的寫入。規則 4.9 的檢視 `hanging`（`rules/trash.ts` `rowsOnDeletedNotes`）列出它們並通知建立的人（刪的人沒看過的才算）。不寫入、不在各台各蓋一筆刪除。
- **同一個衍生 id 在兩台各建**（指標、Onden 自己建的功能引用）：一列，輸的建立值留成頭。**人加的功能引用** id 不是衍生的，兩台各加同一個功能會撞唯一索引：留建立較早的那一列（`mergeDuplicateRefs`，每台相同），另一列不在表裡、標記照存，config 逐鍵併入是檢視（`duplicateRefs`），不寫入。
- **沒有列的標記也送**（列不在表裡就送它的標記；在表裡但不在讀者範圍內的不送）。這只對握有整個工作區的讀者成立；**分空間的包（#1769）不能照這條送**：不在讀者範圍內、而且已刪的列的標記會洩漏它存在過，那一批要自己決定。
- **JSON 的鍵**：一鍵一個單位，第一次寫入的 `saw` 是空的（不是「跟著建立」）。列不在時鍵的標記照存（刪除觸發器在刪的那台留下鍵的墓碑）。標籤 schema 的鍵也算筆記的 `updated_at`（migration 209 重新定義 `sync_touch_updated_at`）。

### 成本：每一筆都照現在的表規劃

一包在一個交易裡讓表從小長大，查詢規劃器的統計卻還是交易開始前的（交易中不會有 autovacuum，PGlite 根本沒有）：快取的計畫（外鍵檢查、觸發器的查找）一直是整表讀，按鍵找一列的寫入走工作區的索引——每多一列就多讀整張表。
所以合併的交易內 `plan_cache_mode = force_custom_plan`（`stampedImport.ts` `openMerge`），一包在一張表建了 100 列以上就在交易內 `ANALYZE` 那張表（`dbRows.ts`）；讀包時每張表的變動鍵只找一次、每塊 10,000 列。
`stampedBundleScale.integration.test.ts` 斷言資料庫讀的列數（`pg_stat_user_tables`），不斷言時間。讀的那一端需要統計是新的：見下一節。
套用端的 `ANALYZE` 不需要比套用更多的權限，也不會讓套用失敗（本機 Postgres 16.15 實測）：表的擁有者以外的角色執行時只有一個 WARNING（`permission denied to analyze "…", skipping it`），交易照常提交——那時只是統計沒更新、成本回到修之前；
`ANALYZE` 可以在交易區塊內執行（`VACUUM` 才不行），在唯讀交易裡也可以，之後同一條連線的語句照常。PGlite 以超級使用者執行，沒有權限的問題。

### 接上傳輸前必須完成

- **送的一方的統計要是新的。** 呼叫 `readChangeBundle` 的一方要保證它的資料庫有新的統計：伺服器由 autovacuum 做；瀏覽器版（PGlite，沒有 autovacuum）由它自己的維護工作定期 `ANALYZE`。這是只屬於這一台的維護，不是複製的狀態（統計不跟著包走、也不進摘要）。
  統計在節點還小時取過一次就夠（`stampedBundleScale.integration.test.ts`「a sender whose statistics were taken once…」，3.7 倍）。**完全沒有統計**時計畫看運氣：同一個設定跑 5 次，3 次組合鍵的查詢走錯索引（`node_tags` 每個鍵讀同一個標籤的所有列，4 倍的標記讀 14.4 倍的列）、2 次是 0.5 倍；時過時不過的結果不能釘成 `it.fails`，所以沒有釘。傳輸那一批要讓節點在讀包之前至少有過一次統計。
- **同一個任務行在兩台是兩個任務**（錨點提案第 3 步：id 由寫入者鑄一次、跟著帶）。2b-2a 起任務筆記連同它的任務引用與 `_task_status` 跟著包走，所以收的一方的任務清單會列出兩個（對方的、和自己由同一行再做出的一個）；2b-2a 之前重複也在，只是收的一方看不到。`anchorIdsTwoNodes.integration.test.ts` 釘住現在的樣子，`it.fails`「the same ONE task on both nodes」等第 3 步翻過來。沒解掉之前接上傳輸，人會看到重複的任務。
- **觸發器不知道誰在寫**：一個普通寫入碰到有衝突的單位會把它解決（上面「系統與背景工作的寫入」）；要在寫入路徑上擋。

### （父層、排序鍵）是一個位置

| | 甲：觸發器把兩欄合成一個單位 `place` | 乙（採用）：兩個標記，核心當成一個合 |
| --- | --- | --- |
| 既有標記 | 要讀成一對，`parent`／`sort` 兩個名字在快照、結構紀錄、`updated_at`（搬動算、排序不算）、搬動成環規則（`meta.from`）、4.9 檢視、十幾個測試裡都要改 | 不變 |
| 「搬動算修改、排序不算」 | 一個單位分不出來，要另加記號 | 照舊（`NOT_AN_EDIT_FIELDS`） |
| 資料形狀 | 單位名稱改變 | 不變（另一項改變才升版，見下） |
| 要的條件 | 無 | 每一次改父層的寫入也蓋排序鍵（migration 209 的觸發器：鍵沒變也用同一個標記蓋一次） |

規則（`rules/place.ts` `placedSort`）：顯示的排序鍵＝`sort` 的頭裡，**就是**勝出的父層那筆寫入、或**看過**它的那一個（取較大者）；沒看過它的排序（在舊父層底下的重排）留成頭（衝突，作者看得到），不會顯示在新父層底下。
它是兩個單位的頭的函式，所以每台相同；`order_stamp` 跟著顯示的那個頭（`storeUnit`，以及 209 的 `order_stamp_follow_parent`）。209 之前「搬動但鍵沒變」的寫入沒有蓋 `sort`：找不到相連的頭時顯示 `sort` 最大的頭，跟以前一樣（那時沒有交換過）。
`note_pointers` 不需要：指標的父層是 id 的一部分（migration 194），換父層就是另一列。

**兩列最後拿到同一個鍵**：每台都以（鍵、設定這個鍵那筆寫入的標記 `order_stamp`、id）排序，相同；之後要插在它們中間，由下一個重排這一組的人在他那一台用 `planSiblingOrder` 把其中一列換新鍵（一筆有標記的寫入，只在動手的那一台寫一次）。
`respaceSiblings` 只在寫入了過長的鍵之後、作為那筆寫入的連帶，在寫的那一台做；合併從不重新編號（守門：`stampedBundle.guard.test.ts`「the merge never renumbers siblings」）。各台各自重新編號會是沒人寫過的寫入。

### 沒做到的（在測試裡釘住，見 `stampedBundle.integration.test.ts`）

- 衍生資料：由內文衍生的（連結、搜尋文字、錨點、任務行、複習卡、標籤記號、段落）與領域事件，合併進來時都不會更新（2b-2b，一個機制）。2b-1 釘的「永久刪除一列時收的一方的連鎖刪除不留墓碑」在 2b-2a 翻轉了：屬性的墓碑跟著包走。
- slug：由標題在寫的那一端算出，不是單位。包把 slug 跟著勝出的標題走；兩個活著的筆記在同一空間要同一個 slug 時，id 較大的加上 `-<id 前八碼>`。這只保證資料庫的唯一索引不破，不保證所有歷史下各節點相同（需要決定）。
- 同一個 id 在兩個節點各自建立（算出來的 id）：輸的創建值以頭的形式留下，列的建立欄位（slug、建立時間）跟著勝出的建立。
